### 1.3 量子化

| 用語 | 一言でいうと | この検証での具体 | 章 |
|---|---|---|---|
| 量子化 | 実数を「何段階かの整数」に丸めて表すこと | 丸めた分だけ誤差が出る。どこで丸めるかの設計が QDQ | 2.1 |
| `QuantizeLinear` / `DequantizeLinear`（Q / DQ） | 実数→整数（Q）、整数→実数（DQ）の op | `q = round(x/scale) + zp` / `x' = (q − zp) × scale` | 2.1 |
| **scale**★ | **1段階の幅**。これが粗いと小さい値が消える | `x²` のレンジ280万を uint16 で割ると **1段階 42.7** になり、通常値 0.04 が 0 に潰れた | 2.1 |
| zero point（zp）/ offset | 整数のどこを実数の 0 に当てるか | ONNX は `(q − zp)×scale`、**QNN は `(q + offset)×scale`**（符号が逆。検査式を間違えやすい） | 9.6 |
| step（1段階） | scale と同じ意味の言い方 | ログに `step=42.7` と出る。**この記録の出発点** | 2.1 |
| **Dynamic Range**★ | 最小値〜最大値の幅 | **bit 数ではなくこれを見る。**16bit でも 280万の幅なら 1段階 42.7 | 2.3 |
| 分解能 | どれだけ細かく表せるか | 「その値が何段階に載るか」で見る | 2.3 |
| 段（何段に載るか） | ある値が量子化の何段階ぶんか | 65% がコード 0、93.5% が ±1段以内 ＝ **16bit と名乗って実質3値** | 11.3 |
| 較正（calibration） | 実データを流して最小・最大を観測すること | 較正データが的外れだと scale が的外れになる | 2.2 |
| 較正データ | 較正に使う入力の集合 | 実際の使い方（プロンプト・文脈長）に寄せる必要がある | 2.2 |
| **per-tensor**★ | テンソル全体で scale を1つ | 活性化は QNN ではこれしか使えない | 2.4 |
| **per-channel**★ | チャンネルごとに scale を1つ | 重みはこちらが使える。**これが1本も効いていなかったのが誤差の主因**（7章） | 2.4 |
| per-axis / axis（軸） | per-channel をどの軸で切るか | `MatMul(x[...,K], W[K,N])` の重みは **軸 1** | 7.4 |
| 粒度 | scale を共有する単位の細かさ | per-tensor ＜ per-channel。粒度が細かいほど誤差は小さい | 2.6 |
| symmetric（対称） | zero point を 0 に固定する置き方 | 重みとバイアスはこれ。**gamma もこれにする必要があった**（C-13） | 2.5 |
| asymmetric（非対称） | zero point を自由に置く置き方 | 活性化に使う。値域が片寄っていても無駄が少ない | 2.5 |
| signed / unsigned | 符号付き（int）か符号なし（uint）か | ONNX は uint16 のつもり、**DLC では符号付き `sFxp_16`** に化けていた（C-13） | 9.4 |
| bitwidth | 何 bit で表すか | 8 / 16。段数は 2^bit（8bit＝256段階） | 9.4 |
| `sFxp_16` | 符号付き16bit固定小数点（QAIRT の型表記） | 上限 32767。超える要素は**黙って頭打ち**になる | 9.4 |
| encoding | DLC が持つ量子化情報（bitwidth / min / max / scale / offset） | 型は符号付きなのに encoding は符号なし前提、という食い違いが C-13 の正体 | 9.4 |
| **A16W8**★ | 活性化 16bit・重み 8bit で計算する形 | この検証の基本形。mixed-precision 実行である | 2.6 |
| A8 / A16 | 活性化を 8bit / 16bit にすること | A8（256段階）では実データを表しきれない場面があった | 2.2 |
| **`u16 × u8`**★ | MatMul の左辺を uint16、右辺を uint8 にする組合せ | v68 で**唯一通る**組合せ（C-8）。スコアを16bitに保てるのが肝 | 2.7 |
| 外れ値 | 分布から大きく離れた値 | 活性化に出る。1つ混ざるだけで全体の分解能を食う | 2.6 |
| clip / 頭打ち / 飽和 | 表せる範囲を超えた値が端で止まること | エラーにならず**精度だけ静かに壊れる**のが厄介 | 9.4 |
| 再構成誤差 | 量子化して戻したときの、元との差 | per-tensor と per-channel の差を試算して主因を裏づけた | 7.3 |
| 整数コード | 量子化後の整数そのもの | ホストと実機で**コードを直接比べて**発生源を1点に絞った | 11.2 |
| 量子化済み初期化子 | あらかじめ整数で持っている重み | 誤差の切り分けで「重みだけ元に戻す」ために使う | 7.1 |
| `add_qtype_converts` | 型が揃わないとき変換ノードを挿す ORT の設定 | `True` なら 8bit へ落とされ、`False` なら指定が無視される。**だから QDQ を直接書き換えた** | 1.5 |
| `tensor_quant_overrides` | テンソル単位の上書き指定 | 形状 op に入る float 入力は**これでも強制できない**（1.5） | 1.5 |
| float セグメント | グラフに残った float のままの区間 | v68 では fp16 op になり **err 1002**。完全 QDQ にする（C-1） | 2.8 |
| SmoothQuant | 活性化の外れ値を重み側へ移す手法 | 採らなかった。理由は 4.3節 | 4.3 |
| AdaRound / GPTQ | 丸め方そのものを最適化する手法 | v68 では重みを16bitにできないため、次の一手として名前だけ挙げている | 7.8 |
| テンソル | 多次元に並んだ数の集まり。モデルが扱う値の単位 | 「どのテンソルをどの scale で量子化するか」が QDQ | 1.2 |
| バイアス（bias） | 行列積のあとに足す定数項 | **symmetric でないと扱えない**（`Param Quantizer should be set to symmetric`） | 2.5 |
| Param Quantizer | パラメータ（重み・bias）側の量子化の設定 | 対称にしておく必要がある | 2.5 |
| 逆量子化 | 整数を実数に戻すこと（DQ） | KV が float の I/O だと、境界で量子化と逆量子化を毎回往復する | 7.5 |
| 定数に畳む | 計算せずに済む部分を、あらかじめ定数にしてしまうこと | Oracle で「重みの量子化を外す」とき `(q − zp) × scale` を畳んだ | 8.5 |
| グラフ入力 | モデルの入口のテンソル | float のまま形状 op に入ると C-1 違反になる | 1.5 |
| 型変換ノード | 型を合わせるために挿入される op | C-11 の書き換え後は**これが減って速くもなった**（1.178ms） | 5.1 |
| `QDQOpTypePerChannelSupportToAxis` | op ごとの per-channel の既定軸を決める ORT の表 | `{'MatMul':1}` を渡して既定を差し替えた | 7.4 |
| `has_per_channel_overrides()` | 上書き指定に軸が入っているかを判定する ORT の関数 | `"axis" in overrides_list[0]` で見ている | 7.4 |
| `qdq_quantizer.py` | ORT の QDQ 量子化の本体（自作ではない） | 1.30.0 のこれを読んで、`per_channel=True` が無視されていた理由が分かった | 7.4 |
| `step.lm_head.weight` | 重みごとの scale を指す名前 | 生成物の中身を直接見るときの手がかり | 7.2 |
| `u16 × int8 per-channel` | 活性化16bit・重み8bit を per-channel で行う組合せ | **v68 でただで効く**（速度を落とさずに精度が上がる） | 7.5 |

### 1.4 モデルの中身（Transformer）

| 用語 | 一言でいうと | この検証での具体 | 章 |
|---|---|---|---|
| Transformer | いまの言語モデルの基本構造。層を積み重ねる | Qwen2.5-0.5B は 24層 | 3.1 |
| **residual stream**★ | 層をまたいで横に流れ続ける値の本流 | ここに `±1677` の巨大値が乗っていた | 3.1 |
| 残差加算 | 本流に、その層の計算結果を足すこと | `x + Attention(...) + FFN(...)` | 3.1 |
| hidden states | 各層の途中の値（本流の中身） | 実測で ±0.09〜±1677 と幅が大きい | 2.2 |
| チャンネル（次元） | 値のベクトルの1要素 | 巨大値は**特定のチャンネルに固定で出る**（Qwen3 では ch35） | 11.4 |
| トークン | 文を区切った単位。1個ずつ処理する | 位置0（先頭）だけ様子が違うことがある | 11.4 |
| **massive activation**★ | 少数の次元だけ桁違いに大きい値 | ±1677。これ自体は壊れていない。**壊れたのは二乗した後** | 3.2 |
| **RMSNorm**★ | 値の大きさを揃える正規化。`x / √mean(x²) × gamma` | ONNX に op は無く、`Mul`→`ReduceMean`→`Add(eps)`→`Sqrt`→`Div` の並びで書かれる | 3.3 |
| RMS | 二乗平均平方根 | 大きさの代表値 | 3.3 |
| gamma（γ） | RMSNorm が持つ、チャンネルごとの倍率 | これを uint16 で量子化すると頭打ち（C-13） | 9.3 |
| eps（ε） | ゼロ割りを防ぐ小さな値 | C-11 の変形で m² 倍されるので 1e-12 に置き換えた | 5.2 |
| スケール不変★ | 入力を定数倍しても答えが変わらない性質 | RMSNorm はこれを持つ。**C-11 の書き換えはここに乗っている** | 5.1 |
| Attention | どのトークンを見るかを決めて混ぜる仕組み | `QK^T` → softmax → `PV` | 3.8 |
| QK^T / PV | Attention の中の2つの行列積（`^T` は転置） | **どちらも活性化×活性化**なので C-8 の対象 | 2.7 |
| スコア | `QK^T` の出力。softmax に入る前の値 | 8bit に落とすと softmax が壊れる。16bit に保つのが C-8 の肝 | 2.7 |
| softmax | 値の組を確率に変える関数 | **小さい差を増幅する**ので、誤差の影響が後段で大きくなる | 4.6 |
| 1/√d | スコアを割って大きさを揃える定数 | Attention の定石 | 3.8 |

## §2 つまずきやすい語の詳しい解説

### 2.1 scale・zero point・step — 「1段階」がすべてを決める

量子化は、実数を整数に置き換える。

    q  = round(x / scale) + zp      （QuantizeLinear）
    x' = (q - zp) × scale           （DequantizeLinear）

`scale` は **1段階の幅**である。整数が表せる段数は bit 数で決まる（8bit＝256段階、16bit＝65536段階）が、
**その段数で「どれだけの幅」を表すか**は較正で決まる。したがって:

    scale ＝ Dynamic Range ÷ 段数

この検証の出発点は、RMSNorm の内部で `x²` を量子化したところだった。
residual stream に ±1677 の巨大値があるため `x²` のレンジは約280万になり、16bit でも **1段階 42.7**。
通常のチャンネルの `x²` は 0.04 程度なので、**丸ごと 0 に潰れた**。
「16bit だから大丈夫」ではなく、**Dynamic Range を見る**のはこのためである（2.3）。

> **QNN の式は符号が逆**: `実数 = (量子化値 + offset) × scale`。
> ONNX の `zero_point` をそのまま当てはめると検査式を間違える（9.6）。

### 2.2 per-tensor と per-channel — 主因はこちらだった

- **per-tensor**: テンソル全体で `scale` が1つ
- **per-channel**: チャンネル（出力の列）ごとに `scale` を1つ

重みの列ごとの値域は揃っていない。実測で**チャンネル間のレンジ比は中央値 10.3倍・最大 67.1倍**。
per-tensor だと、一番広い列に合わせた粗い `scale` が、狭い列にもそのまま当たる。

この検証では `get_qnn_qdq_config(..., per_channel=True)` を渡していたのに、
**生成物は1本も per-channel になっていなかった**（設定は受け取られるが、軸の既定値が無い型では無視されていた）。

まず Oracle で主因を確かめる。**投影群と FFN の 168本だけ量子化を外す**と、相対L2 18.57% → **8.36%**、top-1 73.7% → **100.0%**。
lm_head（136M と一番大きい）だけ外しても 18.57% のまま変わらない。**168本が単独で誤差を作っていた。**

そこで `TensorQuantOverrides` に `axis` を明示して per-channel にした結果:

| prefill 窓64 | top-1 | 相対L2 | KL | cos | fp32 の1位の順位 |
|---|---:|---:|---:|---:|---:|
| per-tensor（従来） | 73.7% | 18.57% | 0.128 | 0.9826 | 1.42 |
| **per-channel** | **100.0%** | **9.99%** | **0.041** | **0.9950** | **1.00** |

| decode 24層 | top-1 | 相対L2 | KL | cos | fp32 の1位の順位 |
|---|---:|---:|---:|---:|---:|
| per-tensor（従来） | 68.8% | 31.19% | 0.680 | 0.9505 | **1908.8** |
| **per-channel** | **83.3%** | **14.06%** | **0.073** | **0.9902** | **1.4** |

**活性化は per-tensor しか使えない**（QNN の制約）。per-channel にできるのは重みだけである。

### 2.3 QDQ と「完全 QDQ」、そして C-1

QDQ は量子化の**設計図**であって、それ自体が整数演算をするわけではない。

- **ホスト（CPU EP）**: `Q → DQ → float 演算` を素直に実行する（だから中間の値を取り出せる ＝ 誤差分解ができる）
- **実機（HTP）**: Q/DQ と演算を**融合**し、整数のまま計算する

ここで v68 の事情が効く。**グラフに float のままの区間（float セグメント）が残ると、そこは fp16 の op としてコンパイルされる。
v68 の skel は fp16 に対応していないので、ロード時に `err 1002` で落ちる**（C-1）。
したがって「全部の op を量子化した完全 QDQ」にする必要がある。
ORT 既定の `quantize_static` は batchnorm / sub / div を float のまま残すため、**CPU 評価用にしかならない**。

厄介なのは、**形状 op（`Slice` / `Unsqueeze` 等）に float のグラフ入力が直接入る形**である。
量子化器はここを量子化せず、`tensor_quant_overrides` でも強制できない。
**op の順序を入れ替えて、量子化される op（`Concat` / `MatMul`）に先に入れる**のが解になった（1.5）。

### 2.4 A16W8 と `u16 × u8`（C-8）

- **A16W8** = 活性化 16bit・重み 8bit。重みは per-channel が使えるので 8bit でも足りる、という役割分担である。
- **`u16 × u8`** は MatMul の**左辺 uint16・右辺 uint8**という指定。v68 の対応は組合せ依存かつ**非対称**である。

| 組合せ | v68 |
|---|:--:|
| `u16 × u16` | 不可 |
| **`u16 × u8`** | **可** |
| `u8 × u16` | 不可（表では可とされているが実機は非対称） |
| `u8 × u8` | 可 |

Attention の `QK^T` と `PV` は**両辺が活性化**なのでここに当たる。
両方 8bit にするとスコアが 8bit になり softmax が壊れるため、**片側だけ 8bit に落とす**。

さらに `A×B = (B^T×A^T)^T` の**等価変形で、どちらを右辺（8bit 側）に置くかを選べる**。
`QK^T` で K（±130、1段階 0.99）ではなく Q（[-10,6]、1段階 0.064）を右辺へ置くと分解能が 15倍になる。

実測: 層1枚の相対L2 **30.4% → 19.2%（入替なし）→ 9.3%（入替あり）**、end-to-end top-1 **50.0% → 66.5% → 80.7%**、実機 17.42ms → 14.29ms。

### 2.5 ONNX → DLC → context binary → EPContext（AOT と `embed_mode`）

    PyTorch/HF → fp32 ONNX → QDQ ONNX → [qairt-converter] → DLC
                                       → [qnn-context-binary-generator --htp_socs sm8350] → context binary（約54分）
                                       → EPContext ONNX でラップ → 実機の ORT が読む

⑥⑦ は**コンパイル**である。SoC を指定して、その世代の命令に落とす。だから:

- ホストで通っても**実機で落ちる**ことがある（`Expand` は生成器が素通しし、端末で `err 1002`。C-10）
- ONNX のノードは融合されて**消える**ので、ONNX だけ見ても実機の姿は分からない（9章）

**EPContext** は、出来上がった context binary を ONNX の形で包んだもの。属性 `ep_cache_context` に本体かファイル名を持つ。
`embed_mode=1`（既定）は本体を ONNX に埋め込むが、**ロード時に ONNX 側と QNN 側で二重に持つ**ため、
736MB の context で RSS 1.47GB に達して SIGKILL された。`embed_mode=0` にすると **ONNX は 772MB → 442バイト**になる（C-12）。

### 2.6 ORT / EP / QNN / HTP — 誰が何をするか

| 層 | 何者か | この検証での役割 |
|---|---|---|
| ONNX | フォーマット（データ） | モデルの受け渡し。QDQ もここに書く |
| ORT | ランタイム（ソフト） | 読み込み・振り分け。CPU EP なら自分で実行 |
| QNN EP | ORT のプラグイン | グラフを QNN へ渡す。`pass_strict` で「全部渡せたか」が分かる |
| QNN | Qualcomm の実行基盤 | context binary を読み、HTP に載せる |
| HTP（v68） | ハード＋ドライバ | 実際に計算する。**制約の出どころはほぼここ** |
| FastRPC | CPU↔DSP の通り道 | `libcdsprpc.so`。アプリからは宣言が要る（C-7） |

**どの層の制約なのかを見分ける**のが 1.5節の主題である。
「ツールができない」（ORT の量子化器の都合）と「ハードができない」（v68 の制約）を混同すると、直し方を間違える。

### 2.7 residual stream・massive activation・RMSNorm（C-11）

Transformer の1層は、本流（residual stream）に Attention と FFN の結果を足していく形をしている。
その本流には、**少数の次元だけ桁違いに大きい値**（massive activation、実測 ±1677）が乗る。これ自体は壊れていない。

RMSNorm は `x / √mean(x²) × gamma`。ここで `x²` を量子化すると、レンジ280万・1段階 42.7 になり、
**通常チャンネルの `x²` が 0 に潰れて、正規化の分母が狂う**。24層で top-1 4.5% まで破綻した。

直し方（C-11）は、**RMSNorm がスケール不変**であることを使う:

    x / √mean(x²) = (x/m) / √mean((x/m)²)      m = そのトークンの max|x|

`x/m` は [-1,1] に入るので `xs²` は [0,1]。**1段階が 42.7 → 1.5e-05（280万倍）**になった。
結果、6層 6.2% → 74.4%、24層 4.5% → **80.7%**（Oracle が示した上限 85.2% に到達）。

### 2.8 gamma と `sFxp_16`（C-13）— ONNX で止めると気付けない

ONNX(QDQ) では gamma を uint16（符号なし、encoding は [0, 1.99]）で持っていた。
ところが `qairt-converter` は RMSNorm を融合 op `RmsNorm` にし、**gamma を `sFxp_16`（符号付き16bit）として渡す**。
符号付きの上限は 32767 なので、**それを超える要素は黙って頭打ちになる**。警告もエラーも出ない。

24層で 49本中49本が該当し、RMSNorm 単体の相対L2 は 13.54%。
gamma を**符号付き対称**（zero_point 0、`|gamma|max / 32767` を scale）で入れ直すと、24層のホスト↔実機は **36.7% → 18.5%** になった。

この真因は **DLC を開かないと見えない**。`convert.log` には出ない（9.6）。

### 2.9 KVキャッシュ・prefill・decode・RoPE・attention sink

- **prefill（メモでは「キャッシュ充填」）**: 質問のトークンをまとめて24層に通し、各層の K・V をキャッシュに貯めて、答えの最初の1トークンを出す。この検証では1トークンずつ入れていたので `履歴の長さ × 約40ms` かかった
- **decode（KVキャッシュ）**: 直前の1トークンだけを通して次を作る。過去の K/V はキャッシュから読む。28.5ms
- **窓ずらし（10.1節の表の「prefill」）**: KV キャッシュを使わない別の生成方式。毎ステップ直近の窓を全部入れ直す。窓16で 36.7ms、窓64で 42.0ms（24層）
- **メモでは「prefill」が2つの意味で出てくる**: 10.1節の表では「窓ずらし」のこと、10.8節の「prefill のキャッシュ」では一般的な意味（＝キャッシュ充填）
- 時間は `26.9 + 0.0335×L` ms（L＝キャッシュ長）。**固定費＋スロットあたりの可変費**で説明できる

**RoPE** は位置を回転で埋め込む。効くのは **Q と K の回転角の差**だけなので、
「絶対位置で回す」「キャッシュ内の位置で回す」「回し直す（再回転）」のどれを採るかで、窓が埋まった後の挙動が変わる。

**attention sink**（先頭の少数トークンが注意の逃げ場になる現象）は有名だが、
**このモデルには無かった**ので効かなかった。fp32 で先に測ったから、実機へ持ち込まずに済んだ。
代わりに**固定 prefix**（先頭に置いて追い出さない部分）は効いた。ただしサイズは中身の長さに合わせる。

### 2.10 指標 — 何を見て、何を見落とすか

| 指標 | 見ているもの | 落とし穴 |
|---|---|---|
| top-1 一致率 | 1位が同じか | **飽和する**。もう変わらない所では差が出ない（4.5 罠3） |
| 相対L2 | 誤差の相対的な大きさ | **分母が動くと形が変わる**（4.5 罠1、8.4） |
| KL | 確率分布の違い | softmax 後なので、logits の小さい差が増幅される（4.6） |
| cos | 向きの一致 | 0.99 でも生成は崩れうる |
| fp32 の1位の順位 | どれだけ惜しいか | 1つの数で分かりやすい。併記向き |
| 1位保持 / margin | 順位の安定 | **生成品質を予測しない**（11.8 で3例） |

**パディング位置まで平均に入れると誤差が薄まる**（4.5 罠2）。生成で実際に使うのは最終位置である。
そして**合否は自由生成で決める**。teacher forcing の数字が良くても、自由生成が崩れる例が出た。

### 2.11 測り方の作法 — Oracle・teacher forcing・検算

- **Oracle 実験**: 一箇所だけ理想条件に戻す。実装より圧倒的に安く、推定を事実に変えられる（residual を外す→効果なし、RMSNorm を外す→6.2%→74.4%）
- **teacher forcing**: fp32 が選んだトークンを強制して軌道を揃える。揃えないと「1トークンの違い」で別の文を比べることになる
- **サンプル数の分解能**: 24サンプルなら 1件＝4.2%。**それより小さい差は語れない**
- **検算**: 差が 0 になるはずの条件を必ず用意する。KVキャッシュの持ち回しでは**バグを6件**踏んだが、目視では1つも見つからなかった
- **陽性対照**: 道具が「効く条件」を検出できることを先に確かめる
- **生成物を真実として扱う**: `per_channel=True` と書いたことは根拠にならない。出来たファイルを見る

## §4 紛らわしい対

| 対 | 違い |
|---|---|
| per-tensor ↔ per-channel | scale がテンソルに1つ ↔ チャンネルごとに1つ。**活性化は per-tensor しか使えない** |
| 活性化 ↔ 重み | 実行時に決まる値 ↔ 事前に決まっている値。外れ値が出るのは活性化、per-channel にできるのは重み |
| symmetric ↔ asymmetric | zero point 0 固定 ↔ 自由。重み・bias・gamma は symmetric |
| A16W8 ↔ `u16×u8` | **テンソルの型の方針**（活性16bit・重み8bit）↔ **1つの MatMul の入力の組合せ**。別の話 |
| ONNX ↔ DLC ↔ context binary ↔ EPContext | 標準の設計図 ↔ Qualcomm の中間形式 ↔ その SoC 用にコンパイル済み ↔ それを ONNX で包んだ殻 |
| ORT ↔ QNN EP ↔ QNN ↔ HTP | ランタイム ↔ その受け渡し口 ↔ Qualcomm の基盤 ↔ ハード。**制約の出どころを見分ける**（1.5） |
| ホスト ↔ 実機 | Q→DQ→float をそのまま実行 ↔ 融合して整数で実行。だから ONNX で止めると気付けない |
| prefill ↔ decode | 質問をまとめて読み、KV キャッシュを作って最初の1トークンを出す ↔ 直前の1トークンだけ通して次を作る。**メモの「キャッシュ充填」が prefill**。10.1節の表の「窓ずらし（prefill）」はキャッシュを使わない別の生成方式 |
| 絶対位置 ↔ cache内位置 | 会話全体での位置 ↔ キャッシュ内での位置。RoPE をどちらで回すかで挙動が変わる |
| teacher forcing ↔ 自由生成 | 軌道を揃えて誤差を測る ↔ 実際の使い方で合否を決める。**数字が逆を向くことがある** |
| ホスト↔fp32 の誤差 ↔ 実機↔ホストの誤差 | 量子化のせい ↔ 実行系（融合・kernel・型）のせい。**混ぜない**（11.6） |
| `err 1002` ↔ `3110` | ロードできない（C-1/2/3/10 など）↔ op の設定が通らない（C-5/C-8） |
| 症状 ↔ 真因 | エラー文が指す場所 ↔ 実際の原因。`could not create op` は「その op が非対応」とは限らない |
