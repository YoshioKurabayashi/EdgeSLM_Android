## 1.1 混同しやすい4つを分ける

| 名前 | 正体 | 一言で |
|---|---|---|
| **ONNX** | モデルの計算グラフと重みを表す**標準フォーマット** | **設計図** |
| **ONNX Runtime (ORT)** | ONNX を読んで実行する**ランタイム** | 設計図を読んで動かすエンジン |
| **QNN Execution Provider (QNN EP)** | ORT から Qualcomm 側へ処理を渡す**プラグイン** | 取次ぎ |
| **QNN / HTP** | Qualcomm の実行基盤と NPU backend | 実際に計算するハード＋ドライバ |

**ONNX はランタイムではない。** ここが最初に混同しやすい。

```
PyTorch モデル
   ↓ export
ONNX モデル               ← 設計図（ファイル）
   ↓
ONNX Runtime             ← エンジン
   ↓
QNN Execution Provider   ← 取次ぎ
   ↓
QNN
   ↓
HTP / NPU                ← ハード
```

### ONNX ファイルの中身

「何をどう計算するか」の計算グラフと、重みが入っている。

```
MatMul / Add / Mul / Softmax / Transpose / Reshape / Slice /
Pow / ReduceMean / Sqrt / Reciprocal / QuantizeLinear / DequantizeLinear ...
```

**今回やった Graph Rewrite は、ランタイムを書き換えているのではなく
この ONNX という設計図を NPU 向けに変形している。**

```
元の ONNX           Q × K^T
書き換え後の ONNX    K × Q^T → Transpose
```

```
元の ONNX           x → Square → ...
書き換え後の ONNX    x → max(abs(x)) → 正規化 → Square → ...
```

### ORT の振り分け

ORT は ONNX を読んで「この演算は CPU で、この部分は QNN EP へ」と**振り分ける**。

今回ログに出る `pass_strict` は、

> **ONNX の全演算を ORT が QNN EP へ渡し、Qualcomm NPU 側で実行できた**

という意味である。内部的には `session.disable_cpu_ep_fallback=1` を付けて
セッションを開き、**成功したかどうかで判定している**（推測ではなく、
制約を課して通ったという事実で言っている）。

## 1.2 QDQ は「量子化の設計図」

### QDQ とは

ONNX 標準の **QuantizeLinear / DequantizeLinear** を使って、
どのテンソルをどの scale / zero point で量子化するかを**明示する**表現形式。

```
FP32 tensor
   ↓
QuantizeLinear      ← q = clip(round(x/scale) + zero_point)
   ↓
uint8 / uint16
   ↓
DequantizeLinear    ← x̂ = (q - zero_point) × scale
   ↓
MatMul / Add / Softmax ...
```

**QDQ は Qualcomm 専用ではない。** ONNX 標準の op を使うので、
ORT を含む複数の backend が解釈できる。

（数式の詳細は [2. 量子化の基礎](02_量子化の基礎.md)）

### ★重要: 実機では Q→DQ→float を順番に実行しているわけではない

ここは押さえておく価値がある。

| 実行系 | QDQ をどう扱うか |
|---|---|
| **ホストの CPU EP** | **Q/DQ を本当に実行する**（float → 整数 → float） |
| **QNN / HTP** | QDQ を**解析して整数 MatMul や量子化 kernel へ融合**し、NPU 命令に落とす |

つまり、

```
QDQ          = 量子化の設計図
QNN / HTP    = その設計図を実際の NPU 命令に落とす側
```

### この違いが「誤差分解」を可能にした

ホスト CPU では Q/DQ が実際に走るので、**量子化による情報の損失だけ**を測れる。
実機では融合されるので、**そこにハードの実装差が乗る**。
中間にホストを挟めば分解できる:

```
fp32  ──[ 量子化誤差 ]──>  ホストQDQ  ──[ QNN-HTP 追加分 ]──>  実機
```

実測（Qwen 層1枚、分母はすべて `‖fp32‖`）:

| | 相対L2 |
|---|---:|
| 量子化だけ（fp32 → ホストQDQ） | 9.31% |
| **実行系の差（ホストQDQ → 実機）** | **13.25%** |
| 合計（fp32 → 実機） | 16.11% |

**「同じ QDQ モデルなのにホストと実機で違う」のは、この融合の工程があるから。**

なお「QNN-HTP 追加分」と呼んでいるのは、HTP の積和精度だけでなく
**QNN への lowering・op fusion・QDQ 境界の変更・requantization・
layout 変換・kernel 選択**がすべてここに含まれうるため。
「HTP の演算誤差」と呼ぶと狭すぎる。

## 1.3 ONNX に RMSNorm という op は無い

**融合が起きることを知っておく**ために書いておく。
（当初はこれが decode の行き止まりだと考えていたが、**それは誤診だった**。1.6節）

**ONNX の標準 op に RMSNorm は無い**（opset 23 で `RMSNormalization` が入ったが、
本プロジェクトは opset 21）。したがって export すると**分解された形**になる:

```
Pow(x,2) → ReduceMean → Add(eps) → Sqrt → Reciprocal → Mul(x,·) → Mul(w)
```

ところが **QNN はこのパターンを見つけて `rms_norm` という1つの op に融合する。**
ログに

```
<E> "rms_norm_node___959230" generated: could not create op
```

と出たのはこれで、**ONNX 側には存在しない op 名が出てくる**のは
QNN が融合した結果を指しているからである。

> **ONNX に書いてある形と、HTP が実行する形は同じではない。**
> 融合が入るので、「ONNX でこう書いたから HTP でもこう動く」とは言えない。

**ただしこの `rms_norm` のエラーは decode の真因ではなかった。**
真因は KVキャッシュ入力の C-1 違反で、それを直したら
**`rms_norm` のエラーは一度も出ずに context binary ができた**（1.6節）。

### ⑥⑦ が「コンパイル」である

ここが普通の ONNX 推論と大きく違う点。

| | いつコンパイルするか |
|---|---|
| 通常の ORT + CPU | 実行時（セッション作成時） |
| **QNN EP + EPContext** | **事前にホストで**（AOT = Ahead Of Time） |

`qnn-context-binary-generator` が **HTP 向けの機械語相当**まで落としてくれる。
だから端末では「コンパイル済みバイナリを読むだけ」になり、起動が速い
（24層 772MB で**ロード約4秒**）。

代わりに **SoC を指定してコンパイルする**必要がある（`--htp_socs sm8350`）。
これが C-2（`soc_id` を刻まない）などの制約の出どころでもある。

### ⑧ EPContext とは

**context binary を ONNX の皮で包んだもの。** ORT は ONNX しか読めないので、
「この ONNX の中身は QNN のコンパイル済みバイナリです」と伝えるための薄い入れ物。

```
EPContext ノード1個だけのグラフ
  属性 ep_cache_context  … バイナリ本体、またはファイル名
  属性 embed_mode        … 1 なら埋め込み、0 なら別ファイル参照
  入力/出力              … 元のモデルと同じ名前・形・型
```

#### `embed_mode` の落とし穴（C-12）

`embed_mode=1`（既定）だと binary が ONNX の中に入るため、
**ロード時に ONNX 本体と QNN 側のコピーで二重に持つ**。

```
ONNX 772MB（binary 736MB を内包） + QNN へ渡すコピー 736MB ≈ 1.5GB
```

実測で **RSS 1.47GB に達してアプリが SIGKILL された**。

`embed_mode=0` にして別ファイル参照にすると **ONNX が 442バイト**になり、
二重持ちが消えて動いた。

> **設計図（ONNX）と実行形式（context binary）を分けて置ける。**
> 大きいモデルでは分けないとメモリが倍要る。

## 1.5 どの層の制約なのかを見分ける

本プロジェクトで何度も問題になった切り分け。

| 例 | どの層の制約か |
|---|---|
| `u16 × u8` の MatMul を ORT が表現できない | **ORT（ツール）の制約** |
| `u16 × u16` の MatMul が v68 で動かない | **HTP（ハード）の制約**（C-8） |
| 2GB 超モデルの opset 変換で落ちる | **ORT の制約**（opset 21 で export すれば回避） |
| `Expand` を含む context binary がロードできない | **HTP の制約**（C-10） |
| `Slice` に入る float のグラフ入力が量子化されない | **ORT の制約** → 順序を変えて `Concat` に入れれば通る（1.6節） |

### ツールの制約をハードの制約と取り違えると、存在する解を見落とす

実例: ORT の量子化器は `u16 × u8` を作れなかった。
そこで「v68 では無理」と結論しかけたが、**QDQ を直接書き換えたら通った**。

| 設定 | 結果 |
|---|---|
| 既定（`add_qtype_converts=True`） | もう片方にも変換ノードを挿して 8bit へ落とす |
| `add_qtype_converts=False` | **指定ごと無視され**、全部 u16 に戻る |
| 出力だけ u16 に固定 | `Desired producer quant_type ... doesn't match existing type` で拒否 |
| **QDQ を直接書き換え** | **通った** |

> **「このツールでできない」と「このハードでできない」は別。**

## 1.6 ★その原則に自分が引っかかった例（decode）

「v68 では KVキャッシュ decode が作れない」と記録していた。理由は

```
<E> "rms_norm_node___959230" generated: could not create op
```

で、**QNN の融合ロジックの限界**だと考えた。**これは誤診だった。**

残っていたログを読み直すと、失敗の最初の `<E>` はいつも別のものだった:

```
<E> "QNN_DATATYPE_FLOAT_32_converted_past_k_0_QNN_DATATYPE_FLOAT_16"
      generated: could not create op
```

**KVキャッシュの入力（float）が量子化されずに残っていた**（C-1 違反が48箇所）。
`node_mul_9` / `node_add_3` / `node_matmul_1` が「作れない」と言われていたのも、
**float セグメントの近傍が fp16 op になった結果**である。

### なぜ量子化されなかったのか

最小モデルで確かめた。`x`（float のグラフ入力）が1つの op に直接入るだけのモデル:

| `x` の消費者 | 結果 |
|---|---|
| `MatMul` | 量子化された |
| `Concat` | 量子化された |
| **`Slice`** | **float のまま**（`tensor_quant_overrides` でも強制できない） |

KVキャッシュの左シフトを `cat(past[:, :, 1:, :], k)` と書いていたので、
`past_k` が **`Slice` に直接入っていた**。

### 直し方は順序の入れ替えだけ

```
cat(past[:, :, 1:, :], k)     →     cat(past, k)[:, :, 1:, :]
```

**結果は同じ。** 違うのは `past_k` が最初に入る op が `Slice` か `Concat` か。
これで C-1 が通り、**2層 decode が実機で動いた**（全ノード HTP / 11.90 ms）。

> **`could not create op` は「その op が非対応」とは限らない。**
> **float セグメントがあると近傍の op がまとめて作れなくなる。**
> 並んだエラーの**どれが原因でどれが結果か**を決めずに、
> 一番目を引いた名前を真因として記録してしまった。
>
> 詳細は [`results/P6_20260913_decode.md`](../../results/P6_20260913_decode.md)。
