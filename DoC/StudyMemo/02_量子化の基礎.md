## 2.1 QuantizeLinear / DequantizeLinear の数式

量子化は2つの op で表される。

**QuantizeLinear**（float → 整数）:

$$
q = \mathrm{clip}\left(\mathrm{round}\left(\frac{x}{s}\right) + z,\ q_{\min},\ q_{\max}\right)
$$

**DequantizeLinear**（整数 → float）:

$$
\hat{x} = (q - z) \times s
$$

| 記号 | 意味 | ログでの呼び名 |
|---|---|---|
| $s$ | **scale** = 1段階の幅 | **`step`** |
| $z$ | **zero point** = float の 0 が整数のどこに来るか | |
| $q_{\min}, q_{\max}$ | 整数型の範囲。uint16 なら 0 〜 65535 | |

### 手を動かす

$s = 0.1,\ z = 10$、uint8（0〜255）のとき:

| $x$ | $\mathrm{round}(x/s)$ | $+z$ | $q$ | $\hat{x} = (q-z)s$ | 誤差 |
|---:|---:|---:|---:|---:|---:|
| 0.0 | 0 | 10 | 10 | 0.00 | 0 |
| 0.55 | 6 | 16 | 16 | 0.60 | 0.05 |
| -0.3 | -3 | 7 | 7 | -0.30 | 0 |
| 30.0 | 300 | 310 | **255**（clip） | 24.50 | **5.5** |

**clip に当たると誤差が爆発する。** これが「レンジを外すと潰れる」の正体。

## 2.2 scale はどう決まるか

較正（calibration）で観測した最小値 $lo$ と最大値 $hi$ から決める。

$$
s = \frac{hi - lo}{q_{\max} - q_{\min}}, \qquad z = \mathrm{round}\left(-\frac{lo}{s}\right)
$$

### `step = 42.7` の正体

今回 RMSNorm の `x²` は $lo = 0,\ hi \approx 2{,}800{,}000$ だった。uint16 なので:

$$
s = \frac{2{,}800{,}000 - 0}{65535 - 0} \approx 42.7
$$

**ログに出ていた `pow_13  16bit range=2801222.2  1段階=42.74326` はこれである。**

（2026-10-17 補足: ログの 42.74326 は範囲を 65,536 で割った値。式どおり 65,535 で割ると 42.7439 で、意味は同じ。このログを出したスクリプトは残っていない。同じ計算は演習 ex01 の 2 で確かめられる＝2.3 節の枠）

表現できる値は `0, 42.7, 85.4, 128.1, ...` だけ。
だから `x² = 1` や `x² = 10` は **`0` に潰れる**。

### 較正データが的外れだとどうなるか

$lo, hi$ は**較正データから決まる**。実行時の値域と違えば、そのまま的外れになる。

実測した例: Qwen の hidden states の実際の値域は **±0.09（std 0.0156）**だったが、
当初の較正は**乱数 ±1.0** を使っていた。**約11倍広い。**

| | 実データ較正 | 乱数 ±1.0 較正 |
|---|---:|---:|
| 層1枚の相対L2 | **30.4%** | 38.9% |

A16（65,536段階）なら11倍広くても耐えるが、
**A8（256段階）では実データが ±6段階に潰れる。**

> **較正は「実行時の入力分布を模倣する」。** ここを手抜きすると、
> 後でいくら方式を工夫しても土台が崩れている。

## 2.3 bit 数より Dynamic Range

直感では「16bit なら 65,536段階もあるから十分」と思う。**レンジが適切なら正しい。**

| 表現したい範囲 | uint16 の1段階 |
|---|---:|
| 0 〜 1 | **0.000015** |
| 0 〜 1,000 | 0.015 |
| 0 〜 2,800,000 | **42.7** |

同じ 65,536段階でも、**何の範囲を表すか**で分解能が280万倍違う。

**Dynamic Range** = そのテンソルの最小値から最大値までの幅。

> **bit 数ではなく Dynamic Range を見る。**
> 「16bit だから高精度」ではなく「16bit で何の範囲を表現しているか」を見る。

## 2.4 per-tensor と per-channel ← 今回の根っこ

> **【重要な訂正 2026-09-13】** 本節はこのあと
> 「活性化は per-tensor しか使えないが、**重みは per-channel だから扱える**」と書いている。
> **その前提は成り立っていなかった。** 実際に生成されていた QDQ は
> **重みも全部 per-tensor** で、**それが誤差の主因**だった
> （prefill 窓64 で全体 18.57% のうち重み 16.98%）。
> per-channel にしたら top-1 が 73.7% → **100.0%** になった（2026-10-17 補足: ホスト QDQ と fp32 の一致。実機では 57.9% → 68.4%。`DoC/検証結果まとめ.md`）。
> → [7. 重みの量子化](07_重みの量子化.md)

| 方式 | scale の数 | 主な用途 |
|---|---|---|
| **per-tensor** | テンソル全体で **1個** | **活性化**（QNN の活性化はこれしか使えない） |
| **per-channel** | チャンネルごとに1個 | **重み**（出力チャンネル単位） |

### なぜこれが根っこなのか

```
per-channel なら:
  ch0: max 1677  → 専用 scale（1段階 0.026）
  ch1: max 0.2   → 専用 scale（1段階 0.000003）   ← 細かく表現できる

per-tensor だと:
  全体: max 1677 → 共通 scale（1段階 0.026）
  ch1 の 0.2 は 約8段階しか使えない               ← 潰れる
```

重みは per-channel に**できる**ので、チャンネルごとにレンジが違っても各々に適した
scale を持てる。**一方 活性化は per-tensor なので、1つの巨大な値が
テンソル全体の scale を決めてしまう。**

> **★ただし「できる」と「なっている」は別である。**
> 本プロジェクトでは `per_channel=True` を指定していたのに
> **生成物は全部 per-tensor** で、重みの相対L2 が中央値 3.79%（per-channel なら 0.95%）だった。
> **設定ではなく生成物を見る**（[8章](08_比較を成立させる.md) 8.6節）。

> **「最大値で割ってから二乗する」という書き換え
> （[5. Graph Rewrite](05_GraphRewrite.md)）は、
> per-tensor しか使えない制約の中で Dynamic Range を押し込む工夫**である。

## 2.5 symmetric と asymmetric

| 方式 | zero point | 表せる範囲 |
|---|---|---|
| **symmetric** | $z = 0$ に固定 | $[-a, +a]$ のように 0 対称 |
| **asymmetric** | $z$ を自由に置く | $[lo, hi]$ を隙間なく使える |

- 重み … symmetric（int8、$z=0$）が一般的
- 活性化 … asymmetric（uint8 / uint16）が多い

ログに

```
Param Quantizer should be set to symmetric for 32 bit biases
```

と出るのはこの話（バイアスは symmetric でないと扱えない）。

### なぜ重みは symmetric なのか

重みは 0 を中心にほぼ対称に分布するので、$z=0$ で無駄が少ない。
また $z=0$ だと整数演算が単純になる（$\hat{x} = q \times s$ で済む）。

## 2.6 A16W8 とは実際に何をしているか

**A**ctivation **16**bit / **W**eight **8**bit の略。

| | 型 | 粒度 | 対称性 |
|---|---|---|---|
| 活性化 | **uint16** | per-tensor | asymmetric |
| 重み | **int8** | per-channel（**にできる**。既定では per-tensor になっていた） | symmetric |

**A16W8 は「16bit 演算 + 8bit 重み」ではない。**
**活性化を16bit・重みを8bitで表現する mixed-precision 実行**である。
演算そのものの精度を指しているのではない点に注意する。

### 重みを 8bit にしてよい理由

| | 分布 | 量子化のしやすさ |
|---|---|---|
| 重み | 0 中心に素直 | **しやすい**（per-channel も使える） |
| 活性化 | 外れ値が出る | **しにくい**（per-tensor しか使えない） |

だから「重みは 8bit でよく、活性化は 16bit 欲しい」という非対称な選び方になる。

実測でもそれが見える（重み固定 MatMul の誤差）:

| | 量子化誤差 | 実機差 |
|---|---:|---:|
| 重み固定 MatMul 1個（A16W8） | 0.92% | **0.11%** |

**重み 8bit でも 1% 未満。** 問題は活性化側にある。

## 2.7 `u16 × u8` とは何を意味するか

MatMul の**2つの入力の量子化型の組合せ**である。

```
MatMul( Q(uint16), K(uint8) ) → スコア(uint16)
```

### v68 の対応（実機で1つずつ確かめた）

| 組合せ | v68 |
|---|:--:|
| `u16 × u16` | **不可** |
| **`u16 × u8`** | **可** |
| `u8 × u16` | **不可**（公開資料では可とされていた。**実機は非対称**） |
| `u8 × u8` | 可 |

**失敗するとこう出る:**

```
<E> [4294967295] has incorrect Value 68, expected >= 73.
<E> QnnBackend_validateOpConfig failed 3110
<E> Failed to validate op matmul with error 0xc26
```

「**68 なのに 73 以上が必要**」＝ HTP のアーキ版数が足りないという意味。

### なぜ `u16 × u8` に価値があるか

**MatMul の出力を 16bit に保てる。**

```
両側 8bit   → スコアも 8bit  → 1段階 6.38  → softmax が壊れる
u16 × u8    → スコアは 16bit → 1段階 0.0248 → 保たれる
```

Attention のスコアは softmax に入るので、ここの分解能が決定的に効く
（詳細は [4. 原因の特定と指標の読み方](04_原因の特定と指標の読み方.md) の softmax 増幅）。

### 8bit にするのは常に右辺

`u8 × u16` が通らないので、**8bit にできるのは右辺だけ**。
どちらを右辺に置くかは `A × B = (B^T × A^T)^T` の等価変形で選べる
（[5. Graph Rewrite](05_GraphRewrite.md)）。

## 2.8 QDQ 形式と C-1 の関係

ONNX の QDQ 形式では、グラフ上は float のまま Q/DQ のペアを挟む。
**実行系がこのペアを見て「ここは整数で計算してよい」と判断する。**

だから **C-1「float セグメントを残さない」**が必要になる。

```
正常:   ... → DQ → MatMul → Q → ...        ← 整数で計算できると分かる
違反:   ... → MatMul → Add → ...            ← float のままだと解釈される
```

Q/DQ に挟まれていない float の区間は、**実行系が「float でやれ」と解釈する**。
v68 では fp16 op になり、**skel が fp16 非対応なので err 1002** になる。

### 実際に踏んだ例

`gqa_repeat` という単体モデルで、**グラフ入力が `Unsqueeze`（形状 op）に
直接入っていた**ため量子化器がそこを素通しし、float が残った。

```
"QNN_DATATYPE_FLOAT_32_converted_k_QNN_DATATYPE_FLOAT_16" generated: could not create op
```

**`float32 → float16 への変換が生成された`** とログが言っているのが手がかり。
