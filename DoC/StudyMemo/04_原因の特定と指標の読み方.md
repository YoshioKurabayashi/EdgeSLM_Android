# 4. 原因の特定と指標の読み方 — Oracle 実験

[← 目次へ](../StudyMemo.md) | [← 前: 3. Transformer の中で何が起きたか](03_Transformerの中で何が起きたか.md)

---

## 4.1 Oracle 実験とは

**現実にはそのまま使えない理想条件を仮に与えて、原因を特定する実験。**

今回は「**ここだけ量子化を外す**」をやった。量子化を外すと float が残り、
v68 では動かない（C-1 違反）。**製品には使えないが、診断には使える。**

医学の検査に近い。モデルには residual / Attention / RMSNorm / FFN / MatMul /
Softmax と多数の部品がある。全部入りでは壊れる。そこで**一個だけ正常に戻す。**

---

## 4.2 結果

6層モデル、ホスト上。`top-1` は fp32 と同じトークンを1位に選んだ割合。

| 除外した箇所 | ノード数 | **top-1** | KL | 相対L2 |
|---|---:|---:|---:|---:|
| なし | 0 | 6.2% | 9.61 | 139.7% |
| **residual（Add）** | 43 | **6.2%** | 9.59 | 139.6% |
| **RMSNorm（Pow/ReduceMean/Sqrt/Reciprocal）** | 52 | **74.4%** | 0.130 | 15.3% |
| residual + RMSNorm | 95 | 80.1% | 0.087 | 12.6% |
| 活性化×活性化 MatMul | 12 | 6.2% | — | — |

### なぜこれで「RMSNorm が犯人」と言えるのか

- **residual だけ戻す → 6.2% のまま。1ポイントも動かない**
- **RMSNorm だけ戻す → 6.2% → 74.4%**

**residual の量子化は主要因ではなく、RMSNorm が壊れていることで
大部分の精度低下が起きていた**と考えるのが合理的である。

### residual + RMSNorm で 80.1% になる意味

```
RMSNorm の問題  ████████████████████
residual の問題 ██
```

**residual 単独ではモデルを救えない**（6.2%）が、ゼロでもない（74.4% → 80.1%）。
**まず大きい方を直すべきだった。**

### この実験がなぜ安かったか

**5パターンで 5分21秒。** 対策の実装（SmoothQuant 相当）より圧倒的に安い。

> **推定 → Oracle で確定 → 実装** の順を守る。
> 推定のまま実装に入っていたら、**まったく効かない residual 側を直していた。**

---

## 4.3 なぜ SmoothQuant を使わなかったのか

SmoothQuant も「活性化の Dynamic Range を量子化しやすくする」技術で、
発想は今回と近い。ただしもっと広範囲に

$$
Y = XW = (X/S)(SW)
$$

という等価変形で **活性化の外れ値を Weight 側へ移す**（Weight は per-channel
量子化できるので扱える）。

今回 Oracle によって

```
モデル全体の activation 問題  ではなく
RMSNorm 内部の square が主犯
```

と絞れた。だったら**モデル全体へ SmoothQuant** より
**RMSNorm だけ書き換える**方がシンプルで、効果も Oracle が保証している。

> **対策の規模は、原因の絞り込み具合で決まる。**
> 絞れていないと「全体に効く強い手法」に頼ることになり、実装も重くなる。

## 4.4 指標の読み方

### top-1 一致率

fp32 の logits が

```
東京 12.0 / 大阪 10.0 / 京都 9.5
```

で、量子化版が

```
東京 11.5 / 大阪 10.2 / 京都 9.2
```

なら **top-1 一致**（どちらも「東京」を1位に選ぶ）。逆に

```
大阪 11.7 / 東京 11.6
```

なら **不一致**。

**top-1 80.7%** = 評価した位置の約80.7%で fp32 と同じトークンを1位に選んだ。

**貪欲デコード（argmax）で生成するなら、これが直接効く指標**である。

### 「fp32 の1位が量子化側で何位か」

top-1 が外れたとき、**どれだけ外れたか**を見る指標。

| | top-1 | fp32 の1位が何位か |
|---|---:|---:|
| 両側 A8 | 50.0% | **20.64位** |
| `u16×u8` | 66.5% | 1.95位 |
| `u16×u8` + 左右入替 | 80.7% | **1.34位** |

**50% と 66.5% の差は 16.5pt だが、順位では 20.6位 → 1.95位で 10倍違う。**
「外れても2位あたりにいる」のと「20位まで落ちる」のは質が全く違う。

### 相対 L2

出力ベクトル全体が fp32 からどれだけズレたか。

$$
\frac{\|y_{\text{quant}} - y_{\text{fp32}}\|}{\|y_{\text{fp32}}\|}
$$

```
fp32  [10, 20, 30]
quant [10.1, 20.2, 29.8]   → 小さい
quant [-50, 100, 3]        → 非常に大きい
```

今回 **139.7% → 12.5%**（完全崩壊からほぼ正常へ）。

### KL divergence

logits を softmax すると確率分布になる。

```
fp32  東京 70% / 大阪 20% / 京都 10%
quant 東京 68% / 大阪 22% / 京都 10%      → かなり近い
```

**この確率分布同士がどれだけ違うか**を見る。小さいほどよい。

今回 **9.61 → 0.085**。

**LLM では L2 より KL の方が意味を持つ場面が多い**（最終的に確率として使うため）。
サンプリング生成なら特にそう。

## 4.5 ★指標の罠（実際に3回踏んだ）

> このあと**さらに6つ踏んだ**。「何を見るか」ではなく
> 「**比べられる形になっているか**」の話として [8章](08_比較を成立させる.md) にまとめた。

### 罠1: 分母を揃えていなかった

`fp32 → ホストQDQ → 実機` の3者を比べるとき、

- 量子化誤差 … `‖ホストQDQ - fp32‖ / ‖fp32‖`
- 実機差 … `‖実機 - ホストQDQ‖ / ‖ホストQDQ‖`   ← **分母が違う**

**比較できない数字を並べていた。** すべて `/‖fp32‖` に揃えるべきだった。

さらに **L2 は加算関係にない**。`9.31 + 13.25 ≠ 16.11` は当然で、
2つの誤差ベクトルが**直交していれば二乗和の平方根**が合計に一致する。

実測すると:

| モデル | 量子化 | 実機差 | 合計 | **二乗和の平方根** |
|---|---:|---:|---:|---:|
| Qwen 層1枚 | 9.31% | 13.25% | **16.11%** | **16.19%** |
| Qwen 2層 e2e | 9.90% | 20.21% | **22.11%** | **22.51%** |

**ほぼ一致 ＝ 2つの誤差はほぼ無相関。** つまり別々の要因である。
これは分解の妥当性を裏づける良い副産物だった。

### 罠2: パディング位置も含めて平均していた

マスク入力版のモデルを評価したとき:

| 測り方 | top-1 |
|---|---:|
| 全16位置 | **48.8%** ← pad 位置の出力は無意味なので薄まる |
| 有効位置のみ | 79.6% |
| **最終位置のみ（生成で実際に使う）** | **90.0%** |

**同じモデルが 48.8% とも 90.0% とも見える。**

> **何を測っているか常に確認する。** 生成で使うのは最終位置だけなので、
> 最終位置の一致率が一番直接的な指標である。

### 罠3: top-1 の低下幅で因果を読み違えた

ホスト→実機の低下が

```
両側A8     50.0% → 46.6%（-3.4pt）
入替版     80.7% → 63.1%（-17.6pt）
```

だったので「**量子化を詰めると実機側の下限が顔を出す**」と解釈した。

L2 で分解すると**逆**だった:

| | 実機差（相対L2） |
|---|---:|
| 両側A8 | **31.98%** |
| 入替版 | 20.21% |

**実機差自体は粗い方式の方が大きい。** top-1 の低下が小さく見えたのは
**元々精度が低く argmax がもう変わらない飽和**だった。

> **指標を変えると結論が反転しうる。**

## 4.6 「その先で何に使われるか」まで見る — softmax の増幅

これも「見る場所」の話で、今回いちばん鮮やかだった例。

Attention スコアを 8bit にしたとき:

| | 1段階 | **スコアの L2 誤差** | **softmax 後の L2 誤差** | argmax 一致 |
|---|---:|---:|---:|---:|
| **8bit** | 6.38 | **0.49%** | **62.82%** | **29.2%** |
| 16bit | 0.025 | 0.0019% | 0.41% | 99.0% |

**スコアの誤差は 0.49% しかないのに、softmax を通すと 62.8%。**
**128倍の差**がある。

### 理由

- スコアのレンジは `[-26.7, +1600]` で、**L2 ノルムは大きい値に支配される**
  → 小さい値の誤差はノルムに現れない
- 一方 softmax の入力として 6.38 の差は $e^{6.38} \approx 590$ 倍の確率差になる
  → **確率分布は小さい差に敏感**

```
スコア  [1600, 10.0, 3.0]   → softmax → [≈1, ≈0, ≈0]
8bit化  [1600,  6.4, 0.0]   → softmax → [≈1, ≈0, ≈0]   ← 一見同じ

でも 1600 のトークンが無い行では:
スコア  [10.0, 9.5, 3.0]    → softmax → [0.58, 0.35, 0.07]
8bit化  [ 6.4, 6.4, 0.0]    → softmax → [0.47, 0.47, 0.06]   ← 1位が入れ替わる
```

> **テンソル単体の誤差で判断しない。その値が何に使われるかまで見る。**

## 4.7 ヘッドごとに見ると原因が絞れる（追加の診断）

スコアをヘッド軸で別々の scale にしたらどうなるかを numpy で試算した:

| 量子化の粒度 | softmax後の L2誤差 | argmax 一致 |
|---|---:|---:|
| テンソル全体 8bit（実際の制約） | 62.82% | 29.2% |
| **ヘッドごと 8bit**（分割すれば可能） | **17.94%** | **79.6%** |
| ヘッド×行ごと 8bit（理想・実現手段なし） | 0.80% | 99.2% |
| テンソル全体 16bit（v68 では不可） | 0.41% | 99.0% |

**head 1 だけレンジが桁違い**（1332 vs 他は54〜272）なので、
ヘッドを分ければ他の13ヘッドは細かく表せる。

ただし**本当に効くのは行（トークン）ごとの量子化**で、
QNN の活性化はテンソル単位なので**構造的に到達できない**。

> **「どの粒度なら直るか」を試算すると、
> 実装可能な範囲でどこまで行けるかが分かる。**
