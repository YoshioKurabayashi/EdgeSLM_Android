## 6.1 実際のログを6例読む

ここは「読み物」ではなく**練習**。実際に出たログを、自分で読めるようになるのが目的。

---

### 例1: `step` が原因を直接教えていた

```
pow_13            16bit range=2801222.2     1段階=42.74326
pow_19            16bit range=2800737.0     1段階=42.73572
rsqrt_input_13    16bit range=2801222.2     1段階=42.74326
```

**読み方:**

| 手がかり | 意味 |
|---|---|
| `pow_*` | RMSNorm の `x²`（[3章](03_Transformerの中で何が起きたか.md)） |
| `range=2801222` | Dynamic Range が 280万 |
| `1段階=42.74` | $2801222 / 65535$（[2章](02_量子化の基礎.md)） |

**`1段階=42.7` は「42.7 未満の値は 0 に潰れる」ことを意味する。**
通常チャンネルの `x²` は 0.04〜400 程度なので、**大半が消える。**

> **量子化の scale（step）を一覧で出すだけで、壊れている op が見える。**
> これは推論を1回も回さずに得られる情報である。

このログ（op ごとの scale の一覧）を出したスクリプトは残っていない（記録だけ）。今のソースで scale を見る道具は、重みなら `weight_percg.py --qdq`（scale の個数）、DLC（融合後）なら `dlc_audit.py`（6.2 の⑧の枠）。

### 例2: Oracle が「どこを直せばいいか」を教えた

```
[oracle] pattern=residual       excluded=43 nodes  top1=6.2%
[oracle] pattern=rmsnorm        excluded=52 nodes  top1=74.4%
```

（2026-10-17 補足: ログの形は要約。今の `oracle_exclude.py` は `rmsnorm            除外   52 ノード  top-1  74.4%  KL …  相対L2 …` の形で出す。出す所は 4.2 節の枠）

**読み方:**

- residual を量子化から外しても **6.2% で1ポイントも動かない**
- RMSNorm を外すと **6.2% → 74.4%**

→ **residual ではなく RMSNorm が主犯**（[4章](04_原因の特定と指標の読み方.md)）。

> **「疑わしい箇所を1つずつ無効化して測る」だけで、
> 仮説の大小関係が数字で出る。**

---

### 例3: 対策が Oracle の上限を再現した

```
[rmsnorm-fix] 6層  top1=74.4%  KL=0.085  relL2=12.5%
```

**読み方:** Oracle（理想条件）の 74.4% と**完全に一致した**。

> **「理想条件での上限」と「対策後の実測」が一致したら、
> その原因はもう残っていない**と判断できる。
> 仮説 → 確定 → 実装 → 再現、の閉じた輪ができた。

### 例4: 数字が「ハードの世代」を指していた

```
<E> [4294967295] has incorrect Value 68, expected >= 73.
<E> QnnBackend_validateOpConfig failed 3110
<E> Failed to validate op matmul with error 0xc26
```

**読み方:**

| 手がかり | 意味 |
|---|---|
| `Value 68` | **HTP v68**（手元の SM8350） |
| `expected >= 73` | この op は **v73 以降が必要** |
| `op matmul` | 対象は MatMul |

→ **`u16 × u16` の MatMul は v68 には無い**（[2章](02_量子化の基礎.md) C-8）。

> **エラーメッセージの数字はバージョンを指していることがある。**
> 「68」「73」が何の数字かに気付けば、一撃で分かる。

さらに大事なのは、**これはハードの制約**であって設定の問題ではないこと。
「ツールの制約」と「ハードの制約」を混同すると、ある解を見落とすか、
無い解を探し続けることになる（[1章](01_レイヤ構造とツールチェーン.md) 1.5）。

### 例5: 誤差分解と直交チェック

```
fp32 → ホストQDQ   相対L2  9.31%
ホストQDQ → 実機   相対L2 13.25%   （分母はすべて ‖fp32‖）
fp32 → 実機        相対L2 16.11%
二乗和の平方根            16.19%
```

**読み方:**

- `9.31 + 13.25 = 22.56 ≠ 16.11` → **L2 は足し算にならない**（当然）
- $\sqrt{9.31^2 + 13.25^2} = 16.19 \approx 16.11$ → **2つの誤差はほぼ直交**

→ **量子化誤差と実行系の差は別の要因**である。分解が妥当だったことの裏づけ。

> **分解した数字を「合うはずの形」で検算する。**
> 合わなければ分解の前提が間違っている。

### 例6: 同じエラーでも原因が違う — まず成果物の同一性を見る

マスク入力版の24層モデルで、**過去に見たのと同じ** err 1002 が出た。

```
<E> Failed to create context from binary. Error code: 1002
```

前回この番号は **`Expand`（v68 非対応）** で出ていたので、同じ系統を4つ潰した
（C-1 のグラフ I/O 境界 / `Expand` の残存 / 動く版との op 差分 /
マスクをグラフ入力にすること自体を単体 op で実機確認）。**どれも無罪。**

最後に md5 を取ったら一発だった:

```
生成器の出力  ctx_qwenpm/qwenpm_ctx.SM8350.bin  772,338,648  b0bac94d…
自分が配った側 ctx/qwenpm_ctx.SM8350.bin        772,342,648  7253d994…   ← 4000 bytes 多い
端末                                            772,342,648  7253d994…   （転送は正しい）
```

**読み方:**

| 手がかり | 意味 |
|---|---|
| 端末とホストの配布元が一致 | **転送は無罪**（adb push は正しく動いた） |
| ホストの生成物だけ md5 が違う | **包む前のファイルが生成器の出力ではない** |
| サイズが 4000 bytes 多い | 書き換え途中の混在した状態 |

真因は **context 生成が2回走っていて、2回目が同じパスへ書き直している最中に読んだ**こと。
ログには「OK 736.56 MiB」とあったが、それは**1回目のログ**だった。

> **同じエラー番号でも原因は同じとは限らない。**
> **「ハードの非対応」を疑う前に、成果物が壊れていないかを確かめる。**
> md5 とサイズの確認は5秒で済み、今回は4段階の切り分けを不要にできた。

## 6.2 覚えておくべき8つの原則

### ① bit 数ではなく Dynamic Range を見る

```
16bit で 0〜1          → 1段階 0.000015
16bit で 0〜2,800,000  → 1段階 42.7
```

**同じ 16bit で 280万倍違う。** 「16bit だから大丈夫」は成立しない。

関連: [2章](02_量子化の基礎.md)、[3章](03_Transformerの中で何が起きたか.md)

---

### ② 最終出力だけ見ない。中間テンソルを見る / Oracle で切り分ける

最終 logits だけ見ていては「どこが悪いか」は分からない。

| 手 | 何が分かる |
|---|---|
| 層ごとの max / p50 / p90 / p99 | どの層で massive activation が出るか |
| 量子化 scale の一覧 | どの op の分解能が足りないか |
| **Oracle（一箇所だけ外す）** | **どこを直せば何%戻るか** |

**Oracle は 5パターンで 5分21秒。** 対策の実装より圧倒的に安い。

> **推定 → Oracle で確定 → 実装。** この順を崩すと効かない場所を直す。

関連: [4章](04_原因の特定と指標の読み方.md)

---

### ③ 数学的に等価な変形で NPU に合わせる

ハードに合わせてモデルを妥協させるのではなく、**同じ答えを出す別の計算方法**を選ぶ。

| 書き換え | 効果 |
|---|---|
| RMSNorm を max で正規化 | 1段階 42.7 → 0.000015（**280万倍**） |
| `QK^T = (K Q^T)^T` | 8bit にする側を選べる（top-1 66.5% → 80.7%） |
| `Expand` → `Concat` | v68 でロードできる形にする |
| マスク定数 → 有限値 | 分解能をマスクに食わせない |

関連: [5章](05_GraphRewrite.md)

---

### ④ 等価変形は必ず数値で確かめる

「等価のはず」で進めると、実装ミスに気付けない。**fp32 で前後比較してから先へ。**

| 書き換え | fp32 での差 |
|---|---|
| マスク定数 / Expand→Concat / 左右入替 / スケール移動 | **0** |
| RMSNorm 正規化 | **0.22%**（ε を近似したため） |

自前で書き直した配線（decode の attention）も **HF と1トークンずつ突き合わせ**、
最大絶対差 **3.3e-05** を確認してから使った。

**検証側のバグにも注意。** 最初は 2層 vs 24層を比べて「配線バグ」と誤判定した。

### ⑤「このツールでできない」と「このハードでできない」は別

| 例 | 実際の制約元 |
|---|---|
| ORT が `u16×u8` を作れない | **ツール** → QDQ を直接書き換えたら通った |
| `u16×u16` が v68 で動かない | **ハード**（`expected >= 73`） |
| 2GB 超の opset 変換で落ちる | **ツール** → opset 21 で export すれば回避 |
| `Slice` に入る float のグラフ入力が量子化されない | **ツール** → 順序を変えて `Concat` に入れれば通る |

**ツールの制約をハードの制約と取り違えると、存在する解を見落とす。**
逆に取り違えると、無い解を探し続ける。

**この原則に自分が引っかかった**。decode を「v68 では作れない」と記録していたが、
真因は ORT が `Slice` に入る float 入力を量子化しないことで、
**順序を入れ替えるだけで動いた**（[1章 1.6](01_レイヤ構造とツールチェーン.md)）。

関連: [1章 1.5 / 1.6](01_レイヤ構造とツールチェーン.md)

---

### ⑥ 疑う前に、成果物が本物か確かめる

「ログに OK と出た」「サマリ行が出た」は**成功の証拠ではない**。

| 確かめること | やり方 |
|---|---|
| ファイルが本当にそこにあるか | `ls -la`（`adb push` の成功表示は信用しない） |
| 中身が生成物と一致するか | **`md5sum`**（ホスト / 配布元 / 端末の3点） |
| 生成が終わっているか | プロセスの不在 ＋ サイズと mtime の安定 |
| 空でないか | サイズ（47バイトの空 ONNX を掴んだことがある） |

err 1002 のように**原因が複数ありうるエラー**では、ここを先に通すと
切り分けの大半が消える。逆にここを飛ばすと、**正しい実装をハードの制約と誤診する。**

関連: [`試行錯誤の記録.md`](../試行錯誤の記録.md) の型1（7件）

### ⑦ 設定値ではなく生成物を真実として扱う

```
パイプラインの設定  : get_qnn_qdq_config(..., per_channel=True)
できあがった QDQ    : 390本すべて per-tensor
```

**「そう指定した」は根拠にならない。** この取り違えで、誤差の主因
（重みの量子化）に気付くのが遅れた。

| 確かめること | やり方 |
|---|---|

### ⑧ ONNX で止めず、**HTP が実際に実行する DLC まで**確認する

⑦（設定ではなく生成物）を ONNX までで止めていたために、**もう一段やられた**。

```
ONNX(QDQ) の gamma : uint16、zero_point 0、scale で [0, 1.99] を表現   ← ここは確認していた
DLC の gamma       : sFxp_16（符号付き）、encoding は [0, 1.99] のまま  ← 見ていなかった
```

**型は符号付き、エンコーディングは符号なし前提。**
量子化値が 32767 を超える要素は**黙って頭打ちになる**。警告もエラーも出ない。
RMSNorm 単体で相対L2 **13.54%**、これが実機の誤差の主因だった（C-13）。

| 見る場所 | 道具 | 何を見るか |
|---|---|---|
| ONNX / QDQ | `weight_percg.py` / `fix_norm_gamma.py --audit` | 粒度・本数・axis・dtype・scale・zero_point |
| **DLC（融合後）** | **`dlc_audit.py`**（`qairt-dlc-info` を包んだもの） | **signed/unsigned・bitwidth・scale・offset・min/max** |

**特に融合 op の定数・重み**を見ること。融合されると ONNX 側のノードは消えるので、
**ONNX を見ているだけでは永久に気付けない。**

#### ★`convert.log` は当てにならない

「融合されているか」を convert.log で確かめようとして、**この行を数えてしまった**。

```
WARNING - Unable to register converter supported Operation [RMSNormalization:Version 23] ...
```

これは**起動時に「この op は登録できなかった」と言っているだけ**で、中身とは無関係。
`qairt-dlc-info` で DLC を開くのが唯一の確認方法である。

#### 検査式を間違えないために

QNN の約束は **`実数 = (量子化値 + offset) × scale`**。
必要な量子化値は `実数/scale - offset`。
符号を逆にすると**全テンソルが「不整合」に見える**（一度やった）。
