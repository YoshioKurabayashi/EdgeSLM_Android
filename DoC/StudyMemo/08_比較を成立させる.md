## 8.1 ①② サンプル数 — 分解能を先に計算する

24サンプルで top-1 を測ると、**1サンプル = 4.2%** の分解能しかない。
そこで「33.3%」と出た値は、48サンプルでは **60.4%** だった。

理由は内訳を見れば分かる。

| ステップ | top-1 一致 |
|---|---:|
| **0（キャッシュが空）** | **0.0%** |
| 前半6ステップ（＝24サンプル版） | 54.2% |
| 後半6ステップ | 83.3% |

**評価セットが「キャッシュが空に近い区間」に偏っていた。**

生成ループの**トークン一致数**はさらに危ない。一度分岐すると以降は別の文になるので、
**分岐点が1つ動くだけで一致数が大きく変わる**。

> **一致率を出す前に「1サンプルが何%か」を言う。**
> 動いた量がそれ以下なら、まだ何も分かっていない。

## 8.2 ③ 軌道を揃える（teacher forcing）

生成モデルでは1トークン違えばその後が別の文になる。

```
fp32 : Paris → France → Europe → ...
QDQ  : Paris → France → city   → ...
```

この状態で fp32 のキャッシュと QDQ のキャッシュを比べても、差が

- 量子化誤差なのか
- キャッシュ誤差なのか
- **単に入力トークン列が違うから**なのか

分けられない。

### 直し方

**fp32 が選んだトークンを QDQ にも強制的に入れる。** 入力列が揃うので、
残る差は量子化とキャッシュの誤差だけになる。

実際、軌道を揃えたら「効いた」と思っていた対策の差が**消えた**。

| | キャッシュ k | キャッシュ v | logits 相対L2 |
|---|---:|---:|---:|
| 対策前 | 11.00% | 24.98% | 29.93% |
| 対策後 | 10.90% | 25.10% | 30.47% |

揃えずに測ったときに見えた「キャッシュのずれ 77.6% → 46.9%」は、
**分岐した側が fp32 と違う文を書いていたから**でしかなかった。

## 8.3 ④ 影響の試算は実データの分布で

「入口と出口で量子化レンジが食い違うので clip される」という仮説を立て、
**出口の範囲を一様に散らした10万点**で試算した。

| | clip 率 |
|---|---:|
| 一様分布での試算 | **3〜15%** |
| **実データ** | **0.0094%** |

理由は分布である。

```
past_k_10   p50 0.0000   p99 2.58   p99.99 9.74   範囲の端 10.13
```

**値は0の近くに集中していて、はみ出しが起きる範囲の端はほとんど使われない。**
一様分布で見積もったことで、端の重みを**1000倍以上**に評価していた。

> これは較正で踏んだ誤り（乱数 ±1.0 で較正して 30.4% → 38.9% に悪化）と**同じ型**。
> [2章](02_量子化の基礎.md) 2.2節に「較正は実行時の入力分布を模倣する」と書いておきながら、
> **自分の試算で同じ間違いをした。**

## 8.4 ⑤ 相対指標は分母を確かめる

層ごとの `present_v` 相対L2 を並べると、層12（37%）と層22（32%）が突出して見えた。
**局所的な原因がある**と読みかけた。

絶対誤差も並べると別の姿になる。

| 層 | \|K\| fp32 | \|ΔK\| | 相対L2 |
|---:|---:|---:|---:|
| 0 | **1873** | 6.6 | **0.4%** |
| 8 | **1458** | 10.8 | **0.7%** |
| 12 | 119 | 12.7 | 10.7% |
| 22 | 105 | 16.5 | 15.7% |

**`|ΔK|` は 6.6 → 17.9 と滑らかに増えるだけ。**
凸凹は `|K|` が層ごとに**18倍**違うこと（層0・層8 の massive activation）が作っていた。

> **相対L2 は分母が動くと形が変わる。** 層ごと・ステップごとに並べるときは
> **絶対誤差も一緒に出す。**
> ([4章](04_原因の特定と指標の読み方.md) 罠1「分母を揃えていなかった」の再発である)

## 8.5 ⑥ 道具には検算を用意する

Oracle で「重みの量子化を外す」を **`(q - zp) × scale` を定数に畳む**と実装した。
**これは量子化された値そのもの**で、`DQ` を残すのと数値的に同じである。

結果として「重みを外しても変わらない（31.19% → 31.25%）」と出て、
危うく「**量子化では説明できない**」と結論するところだった。

> ★2026-10-17 補足: このときの実装は今も `oracle_qdq.py` の `@weights` として残っている（下の枠）。`results/P8_20260913_weight_quantization.md` 8 節は「コメントに明記」と書くが、今のソースのコメントは「重みは前段に Q が無いので `unwrap_after` では外れない」とだけ書いていて、「この畳み方でも外れない」とは書いていなかった（★2026-10-18: ソースのコメントに「重みの丸め誤差はそのまま残る」の注意を足した。下の枠）。直したあとの道具（量子化前の重みに差し替えるもの）はリポジトリに残っていない。

### 何が救ったか

**「全部外したら fp32 に一致するはず」という検算**である。

| | 全部外したときの相対L2 |
|---|---:|
| 道具にバグがあったとき | **29.83%**（おかしい） |
| 直したあと | **0.10〜0.14%**（正しい） |

（★2026-10-17 注: 29.83% は `results/P8_20260913_oracle_full.json` の「完全に外す」（op の出力の Q/DQ を全部外し、重みは量子化のまま）。`@weights` も付けた `P8_20260913_oracle_all.json` の「量子化を全部外す」は 30.11%。どちらも 0 に近づかないことで、道具が重みを外せていないと分かる。「直したあと」の 0.10〜0.14% は 7.1 節の表の最終行）

> **測定器には「正解が分かっている入力」を通す。**
> 差分を測る道具なら「差が0になるはずの条件」を必ず用意する。

## 8.7 指標は併記する

top-1 だけで判断しない。logits が僅差なら小さな誤差で1位が入れ替わり、
差が大きければ大きな誤差でも変わらない。

```
Paris  10.01 / London 10.00   → ごくわずかな誤差で入れ替わる
Paris  10.0  / London  2.0    → 大きな誤差でも変わらない
```

**常に並べる5つ:**

| 指標 | 何が分かる |
|---|---|
| 相対L2 | 出力ベクトル全体のずれ |
| KL | 確率分布としてのずれ（LLM では L2 より意味がある場面が多い） |
| cos | 向きのずれ |
| **fp32 の1位が何位か** | **外したときにどれだけ外すか**。今回 1908位 → 1.4位 で効いた |
| top-1 一致 | 貪欲デコードでの体感に直結 |

5つをそろえて返すのは `app/pipeline/ab_host_device.py` の `metrics()` である（★2026-10-17 訂正: 旧「`app/pipeline/accuracy_logits.py` の `metrics()` がこの5つを返す」。今の `accuracy_logits.metrics` は cos を返さず、代わりに top-5 の重なりと順位の p95 を返す。下に両方の枠を載せた）。
**トークン一致率は最後にユーザー体験を確かめるために使い、解析の主指標にはしない。**

## 8.8 ★新しい機構を作ったら、**無効化したときに既知の方式と一致するか**を先に確かめる

ここまでは「測り方」の話だった。この節は「**作ったものが正しいか**」の話である。

KVキャッシュを会話のあいだ持ち回す機構を作ったとき、**バグを6件踏んだ**。
**目視や推測では1つも見つからなかった。** すべて、次の形の検算で見つけた。

```
新しい機構を無効にした状態  ==  既知の正しい方式
```

この場合は「**差分＋キャッシュ再利用**」と「**毎回フル入力・再利用なし**」に
**完全に同じトークン列**を食べさせ、**生成が1トークンも違わないか**を見る。

```
A: 差分＋再利用        B: 毎回フル入力
[1] 充填  923ms        充填  924ms     一致
[2] 充填  770ms        充填 1993ms     一致
[3] 充填 1025ms        充填 3239ms     一致
```

**出力が同じで時間だけ縮む**——これが「速くしただけで壊していない」の証明になる。

### 踏んだ6件

| # | バグ | 症状 |
|---|---|---|
| 1 | ポインタをキーにした `static map` → **解放済みアドレスの再利用** | 4往復目だけ効く |
| 2 | 再利用した**最後のトークンを二重投入** | fp32 と食い違う |
| 3 | **キャッシュに入っていない**トークンを「入っている」と記録 | 等価性が一致しない |
| 4 | **2件の修正どうしが噛み合わない**（片方が他方の前提を壊した） | UI だけ食い違う |
| 5 | **検算した経路と本番の経路が違った** | ログに `reused=0` |
| 6 | 非同期の**最後の1回が確定表示を上書き** | 画面に特殊トークンが出る |

### 特に間違えやすかったところ

生成ループは「**トークンを選ぶ → 次の周回で食わせる**」形なので:

```
キャッシュにあるのは  入力 + 生成[0 .. n-2]
生成[n-1]（最後に選んだ1つ）は **食わせずに終わる**
```

2 は「入っているもの」をもう一度食わせ（**二重**）、
3 は「入っていないもの」を入っていることにした（**欠落**）。
**どちらも文脈が1トークンずれるだけで、症状は同じ**——
「会話が始まったばかりのような定型文を返す」。

### 検算そのものを2回間違えた

| | 誤り |
|---|---|
| 1回目 | 対照のつもりの設定が**文脈ゼロ**になっていた（比べる意味が無い） |
| 2回目 | A と B で**食べている系列が違った**（片方だけ特殊トークンが二重） |

> **「同じ入力を与えているか」を先に確かめる。**
> 検算は、検算自体が正しいことを確かめないと使えない。

### 型として

| やること | なぜ |
|---|---|
| 新機構を**無効化できる**ようにしておく | 既知の方式と突き合わせられる |
| 無効化したときに**ビット単位で一致**するか見る | 「速くなった」と「壊れた」を分ける |
| **本番が通る経路**で測る | 別経路で検算しても意味がない（5） |
| 修正を入れたら**それに依存する箇所を洗う** | 前提が壊れる（4） |

## 8.9 まとめ: 比較の前に確かめる8項目

1. **サンプル数は足りているか。** 1サンプルが何%か言えるか
2. **軌道は揃っているか。** 生成を比べるなら teacher forcing
3. **分布は実データか。** 試算に一様分布を使っていないか
4. **分母は揃っているか。** 相対指標なら絶対値も出す
5. **道具に検算はあるか。** 「差が0になるはずの条件」を通したか
6. **見ているのは生成物か。** 設定値を根拠にしていないか
7. **新機構は無効化したとき既知の方式と一致するか。**（8.8節）
8. **測っているのは本番が通る経路か。**（8.8節）
