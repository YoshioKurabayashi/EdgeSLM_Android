# 9. 実機に合わせる — ホストで正しくても実機で正しいとは限らない

[← 目次へ](../StudyMemo.md) | [← 前: 8. 比較を成立させる](08_比較を成立させる.md)

---

## 9.0 この章の問い

[7章](07_重みの量子化.md)で重みを per-channel にして、**ホストでは top-1 が 100% になった**。
ところが実機は 68.4% のままだった。

```
ホスト QDQ      9.99%
実機 HTP       37.09%   ← ここが縮まらない
```

**同じモデルを同じ量子化で走らせているのに、実機だけ 4倍ずれる。**
この章はその 37% を追いかけた記録である。

---

## 9.1 まず指標を変えた

それまでは「fp32 との差」で見ていた。だがそれだと

- 量子化による誤差
- 実機（HTP）の実装による誤差

が混ざる。**同じ量子化グラフをホストと実機で走らせて、直接引く**方に変えた。

| 24層 decode | 相対L2 |
|---|---:|
| fp32 ↔ ホストQDQ | 14.06% |
| fp32 ↔ 実機HTP | 34.85% |
| **★ホストQDQ ↔ 実機HTP** | **35.28%** |

**ホスト↔実機が fp32↔実機とほぼ同じ大きさ**だった。
つまり実機の出力は**量子化誤差とほとんど無関係にずれている**。

> **二乗差（quadrature）で「HTP 追加分」を推定するのはやめた。**
> 直交を仮定しているので、成り立たない場面で平気で嘘をつく。
> 実際 logits 段では `√(34.85² − 14.06²)` が条件によって 17.9% にも 32.0% にもなり、
> **「prefill では縮み decode では増えた」という現象があるように見えていた**。
> **あれは分解モデルが壊れていただけだった。**

---

## 9.2 二分探索で場所を絞る

### 使えなかった道具

単体 op のモデルは21個あったが、**使えなかった**。

```
形状      hidden 128 / 4ヘッド   ← 本物は hidden 896 / 14ヘッド
較正      なし（乱数）           ← レンジ起因の問題は乱数では出ない
```

これらは「v68 がこの op を受け付けるか」を見るために作ったもので、
**精度を見る道具ではなかった**。目的が違う道具を流用しない。

### やったこと

**本物の層を切って、本物の activation で較正する**（`app/pipeline/split_layer.py`）。

| 部分 | ノード | fp32↔ホスト | **★ホスト↔実機** |
|---|---:|---:|---:|
| FFN 側 全体 | 14 | 4.10% | **14.37%** |
| └ **RMSNorm だけ** | 7 | **0.18%** | **★13.53%** |
| └ MLP だけ（MatMul×3 + SiLU） | 6 | 4.08% | **0.21%** |

**896×4864 の行列積3本は、実機でもホストと 0.21% しか違わない。**
**RMSNorm だけが 13.5% ずれていた。**

> 疑っていたのは MatMul と KVキャッシュだった。**どちらも白だった。**

---

## 9.3 ★誤差の「形」を見る

13.5% が何なのかは、誤差を**列（チャンネル）ごとの倍率**で補正してみたら分かった。

```
列ごとに最適な倍率で補正 → 13.54% が 0.03% になった
```

つまり実機の出力は「**一部の列が定数倍されているだけ**」だった。

| ch | gamma | 倍率 | **倍率 × gamma** |
|---:|---:|---:|---:|
| 783 | 1.9922 | 0.5000 | **0.9962** |
| 674 | 1.8125 | 0.5496 | **0.9961** |
| 241 | 1.3906 | 0.7164 | **0.9962** |
| 56 | 1.2422 | 0.8019 | **0.9961** |

**`倍率 × gamma` が全列で一定。** これは「**ある値で頭打ちになっている**」ということ。

```
0.9961 = 32767 × 3.03988e-05 = （符号付き int16 の上限）×（gamma の scale）
```

> **誤差を「大きさ」だけで見ていたら分からなかった。**
> 相関・倍率・部分空間への射影など、**形で見ると原因が出る**ことがある。

---

## 9.4 真因 — C-13

`qairt-converter` は RMSNorm を**融合 op `RmsNorm`** にする。
そのとき gamma を **`sFxp_16`（符号付き16bit）** として渡すが、
ONNX 側の QDQ は **uint16**（zero_point 0、scale で [0, 1.99] を表現）だった。

```
DLC: data type: sFxp_16
     encoding : bitwidth 16, min 0.0, max 1.9921875, scale 3.0399e-05, offset 0
                ↑ 型は符号付き、エンコーディングは符号なし前提
```

**量子化値が 32767 を超える要素は黙って頭打ちになる。警告もエラーも出ない。**

24層の prefill / decode とも **49本中49本**が該当していた（要素数 10,936個）。
**局所的な偶然ではなく、モデル全体に系統的に入っていた不整合。**

### 直し方

gamma を**符号付き対称**（zero_point 0、`|gamma|max / 32767` を scale）で入れ直す。

```
32767 を超えていた列 33 本 / q最大 65535
新しい scale 6.07985931e-05   再量子化の誤差 0.0020%
```

`app/pipeline/fix_norm_gamma.py`。**同じ context 生成パイプラインを通しただけ**で:

| RmsNorm 本体（実機） | 相対L2 | cos |
|---|---:|---:|
| 直す前 | **13.17%** | 0.9908 |
| **直したあと** | **0.0342%** | **1.000000** |

## 9.5 24層での効果

| | C-13 前 | **C-13 後** |
|---|---:|---:|
| **prefill 窓64** ホスト↔実機 | 36.69% | **18.45%** |
| 同 fp32 の1位の順位 | **132.37** | **1.63** |
| 同 実機 top-1 | 68.4% | **78.9%** |
| **decode 24層** ホスト↔実機 | 35.28% | **16.48%** |
| 同 fp32 の1位の順位 | **104.25** | **1.33** |
| 同 実機 top-1 | 62.5% | **75.0%** |

**「外すときに大きく外す」（fp32 の1位が100位超）が消えた。**

2層モデルでは ホスト↔実機 が **26.97% → 2.43%**（cos 0.99977 / top-1 100%）まで落ちた。
24層で 16〜18% 残るのは**層数に伴って増える別の要因**で、これは未解明である。

## 9.6 覚えておくこと

### ① ONNX で止めず、DLC まで見る

[6章の原則⑦](06_ログの読み方と原則.md)（設定ではなく生成物）を **ONNX までで止めていた**
ために、もう一段やられた。

| 見る場所 | 道具 |
|---|---|
| ONNX / QDQ | `weight_percg.py` / `fix_norm_gamma.py --audit` |
| **DLC（融合後）** | **`dlc_audit.py`**（`qairt-dlc-info` を包んだもの） |

**融合されると ONNX 側のノードは消える。** ONNX を見ているだけでは永久に気付けない。

### ② `convert.log` は当てにならない

「融合されているか」を convert.log で確かめようとして、**この行を数えてしまった**。

```
WARNING - Unable to register converter supported Operation [RMSNormalization:Version 23] ...
```

**起動時に「この op は登録できなかった」と言っているだけ**で、中身とは無関係。
結論は合っていたが、**根拠が間違っていた**。

### ③ 検査式の符号を間違えないために

QNN の約束は **`実数 = (量子化値 + offset) × scale`**。
必要な量子化値は `実数/scale − offset`。
符号を逆にすると**全テンソルが「不整合」に見える**（一度やった）。

### ④ 二分探索は「同じ入力を与える」まで含めて設計する

層ごとの誤差を並べただけでは、**前段から伝わった誤差とその層が作った誤差が混ざる**。
本物の層を切り出し、**同じ入力を与えて**初めて分離できる。

## 9.7 自動化した

**人間が毎回探すのは危険**なので、パイプラインのゲートにした。

```
S4 量子化の直後
  ├─ per-channel の本数・axis を生成物で検査
  └─ ★C-13: RMSNorm gamma のはみ出しを検出して自動修正
S5 DLC 変換
S6 context 生成
  ↓
配備（deploy_pm64.py）
  ├─ 生成器の出力が安定しているか
  ├─ ★DLC 検査: 型 / signed-unsigned / bitwidth / scale / offset / min-max
  │    不整合があれば **push 前に止まる**
  ├─ md5 3点照合
  └─ probe（全ノード HTP / strict）
```

`dlc_audit` は**全テンソル**が対象（24層 prefill で 2,132本）。

> この自動化が一番の成果かもしれない。**モデルを変えても効く。**
> 実際、Qwen3-0.6B に移ったとき C-13 は自動で走った
> （ただし `q_norm` / `k_norm` がパターンから漏れていて、そこは直した。9.8節）。

## 9.8 別のモデルへ持っていくとき

Qwen3-0.6B へ移して分かったこと。

| | Qwen2.5-0.5B | Qwen3-0.6B |
|---|---:|---:|
| RMSNorm の数 | 49 | **113** |
| 内訳 | layernorm 48 + 最終 1 | 上記 + **`q_norm` 28 + `k_norm` 28** |

Qwen3 は projection の直後に**ヘッドごとの RMSNorm** を持つ。
C-13 のパターンを `input_layernorm` / `post_attention_layernorm` / `norm` と
**列挙で書いていたので、半分を取りこぼした**。

```
修正前: 2層で 5本しか拾えない（正しくは 9本）
修正後: `norm.weight` を含むものを全部拾う → 9本 / 28層で 113本
```

> **列挙は、モデルが変わると壊れる。** 「その性質を持つもの」で拾う。
