## 10.1 2つの方式

| | 窓ずらし（prefill） | KVキャッシュ（decode） |
|---|---|---|
| 1ステップで入れるトークン | 窓のぶん全部（16 / 64） | **1つだけ** |
| 過去の文脈 | 毎回入れ直して計算し直す | **キャッシュで持ち回す** |
| 実測（24層） | 36.7ms（窓16）/ 42.0ms（窓64） | **28.5ms** |
| 生成前の準備 | 不要 | **キャッシュ充填**が要る |

KVキャッシュの方が速い。**過去の分を計算し直さないから**である。

## 10.2 文脈長を伸ばす — どこまで伸ばせるか

Snapdragon 888 / HTP v68 で、KV 64 / 256 / 512 を**同一セッションで**測った。

| KV | OrtRun | tok/s | **★ホスト↔実機** | context binary | KVメモリ |
|---:|---:|---:|---:|---:|---:|
| 64 | 28.73 ms | **34.8** | **16.48%** | 772,065,064 B | 1.5 MB |
| 256 | 35.46 ms | **28.2** | **17.00%** | 772,101,928 B | 6.0 MB |
| 512 | 44.02 ms | **22.7** | **16.95%** | 772,351,784 B | 12.0 MB |

3点とも 全ノード HTP / VTCM spill 0。

### ★移植の質は文脈長に依存しない

```
ホスト↔実機   KV64 16.48%   KV256 17.00%   KV512 16.95%
```

**KV を8倍にしても実機側の誤差は動かない。** 増えるのは速度コストだけ。

### 速度は「固定費 + キャッシュ長に比例」

| KV | 実測 | `26.9 + 0.0335×L` |
|---:|---:|---:|
| 64 | 28.73 ms | 29.0 ms |
| 256 | 35.46 ms | 35.5 ms |
| 512 | 44.02 ms | 44.0 ms |

```
固定費 26.9 ms        … 重みとの行列積（キャッシュ長に無関係）
可変費 0.0335 ms/slot … attention（キャッシュ長に比例）
```

3点が 0.1ms 以内で乗る。**この式があれば測らなくても見当がつく**
（KV1024 ≈ 61 ms ≈ 16.3 tok/s）。

> **速度は発熱で動く。** 同じモデルが今日1日で 16〜58ms の幅で出た。
> **比較は必ず同一セッション内で行う。**

### モデルが変わると前提が変わる

| | Qwen2.5-0.5B | Qwen3-0.6B |
|---|---:|---:|
| KV heads | 2 | **8** |
| head_dim | 64 | **128** |
| 層数 | 24 | **28** |
| **KVメモリ（L=512）** | **12 MB** | **112 MB**（9.3倍） |

KVキャッシュは float32 のグラフ I/O なので、**毎ステップ往復する**。
Qwen3 の L=512 では 1ステップ 224MB の転送になる。**ここは要注意。**

## 10.3 RoPE の位置 — 容量とは別物

### 3つの方式があり、前提が違う

| | Q の位置 | K の位置 | |
|---|---|---|---|
| 旧実装 | cache内（L-1 で clamp） | 絶対 | **不整合** |
| **現在** | **絶対** | **絶対** | 整合。naive sliding window |
| StreamingLLM | cache内 | cache内（**再回転**） | sink 用 |

### なぜ絶対位置のままでよいか

RoPE は **Q と K の回転角の差**が相対位置を表す。
K はキャッシュに入る時点でその時の絶対位置で回転済みなので、
**Q の位置を増やし続ける限り相対位置は正しい**。
キャッシュのスロット番号が 0 側へずれても関係ない。

### 旧実装の何が悪かったか

```cpp
const int64_t pos = std::min<int64_t>(t, L - 1);   // 窓が一杯になると L-1 に張り付く
```

L=256 なら 256トークン目以降**すべてが位置 255**。
「何番目か」が区別できなくなる。

### テーブルの行数は容量とは別

```
容量 L        … 何トークンぶん覚えるか（モデルに焼かれている）
テーブル行数  … 位置を何番まで表せるか（アプリが選ぶ）
```

**混同しやすい。** KV256 だからテーブル256行でよい、ではない。
窓が埋まっても位置は増え続けるので、**生成したいトークン数ぶん**要る。

`make_rope_table.py` で生成。Qwen2.5 は `theta=1e6 / head_dim=64`。
**端末に入っていた既存のテーブルと最大差 2.1e-06 で一致することを確認してから使う。**

## 10.4 ★窓が埋まると崩れる。原因は移植ではない

### 観察

実機で 600 トークン生成すると、途中から `1, 1, 1, ...` に崩壊した。
だが **fp32 を窓なしで回すと 600 トークン最後まで破綻しない**。

### 軌道を揃えて測る

生成どうしを並べても、貪欲デコードは序盤の僅差で別の軌道に入るので比較にならない
（[8.2節](08_比較を成立させる.md)）。
**窓なし fp32 が書いた系列を、窓256 の fp32 に teacher forcing で流す。**
量子化も HTP も入っていない。

| 絶対位置 | top-1 率 | 順位 中央 |
|---|---:|---:|
| 128〜192 | 76.6% | 1.0 |
| 192〜240 | 79.2% | 1.0 |
| 240〜256 | 75.0% | 1.0 |
| **256〜272** | **43.8%** | **2.5** ← 窓が埋まる |
| 272〜320 | 35.4% | 4.0 |
| 400〜500 | 18.0% | 5.0 |

**位置 256 ちょうどで崖。** 実トークンの追い出しが始まる点と一致する。

> **fp32 だけで再現する。** Snapdragon への移植の問題ではなく、
> 「古い文脈を捨てれば予測は変わる」という当たり前の帰結でもある。

## 10.5 attention sink は効かなかった

### 何を期待していたか

StreamingLLM は「先頭の少数トークンが attention の逃げ場になっており、
それを捨てるとモデルが不安定になる」と報告している。
**内容が重要だから残すのではない。**

### 測り方（交絡を外す）

崖の原因には

① sink を捨てたことによる不安定化
② **単に必要な過去情報が消えたこと**

## 10.7 実装で2回間違えた — 検算の作り方

再回転の実装を2回間違えた。どちらも**位置256より前で劣化する**ことで気付いた。

| | 誤り |
|---|---|
| 1回目 | cache内位置なのに `pos = min(t, L-1)` を使い、実効位置が `2·entry_t − current_t` になっていた |
| 2回目 | 再回転を `[lo:L-1]` に掛け、**最新スロットを除外**していた（`present` は次ステップで全スロットが左へ動く） |

推測で直すのをやめ、**等価になるはずの条件**を2つ作った。

1. **回転の式そのもの**: 位置 p で入れた K に `R(-1)` を掛け、位置 p-1 で入れた K と比べる
   → **相対差 0.0000%**（式は正しい）
2. **sink なしなら cache内位置と絶対位置は数学的に一致するはず**
   → 直す前 NLL 1.034 vs 2.374（不一致＝バグ）、直したあと **差 0.000003**

> **1回目の実装のままなら「sink は逆効果」という間違った結論を出していた。**
> 新しい機構を作ったら、**それを無効化したときに既知の方式と一致するか**を先に確かめる。

| 1 | 37 t | 0 t | 924 ms | 952 ms |

**充填時間が履歴の長さに依存しなくなる。**

### 設計で押さえたこと

| | なぜ |
|---|---|
| 状態は **Session が持つ** | 最初 `static map<Session*, …>` にしたら、**解放済みアドレスの再利用**で別セッションの状態を拾った |
| **トークン列を保持して前方一致を確認** | 履歴を編集されたり別の会話を始められたときに、**黙って壊れた文脈で続けない** |
| 呼び出し側は **差分だけ渡す** | 全履歴を渡す形だと、**呼び出し側がモデルの実際の応答を正確に持っていないと前方一致しない** |
| **失敗したら保存しない** | 途中で落ちたキャッシュを引き継ぐと次のターンが静かに壊れる |

### ★キャッシュに「入っているもの」を正確に数える

生成ループは「**トークンを選ぶ → 次の周回で食わせる**」形なので:

```
キャッシュにあるのは  入力 + 生成[0 .. n-2]
生成[n-1]（最後に選んだ1つ）は **食わせずに終わる**
```

ここを1つ間違えると**文脈が1トークンずれる**。二重に入れても、抜け落ちても、
症状は同じ「**会話が始まったばかりのような定型文を返す**」になる。

この機構で**バグを6件踏み、すべて等価性の検算で見つけた**。
型は [8.8節](08_比較を成立させる.md)にまとめた。

## 10.10 ★会話の品質は、移植ではなくモデルの問題だった

「質問と答えが合っていない」ので切り分けた。

| | 質問 | **fp32（移植の影響ゼロ）** | 実機 |
|---|---|---|---|
| 1 | エアコンを22度にして | 22度に設定します。 | 22度に設定します。 ✅ |
| 2 | 音楽をかけて | **お手伝いできません。** | おやすみなさい。 |
| 3 | さっき何度にしたっけ？ | **リアルタイムで情報を提供する能力はありません…** | お疲れ様です。… |

**fp32 でも答えになっていない。**
3 では**自分が直前に「22度に設定します」と書いたのに参照しない**。
**移植を完璧にしても直らない。**

プロンプトの組み立ては HF の `apply_chat_template` と**58トークンすべて一致**を確認済みで、
そこも問題ではない。

```
質問と答えが合わない
  ├─ モデルの能力（主因） … fp32 でも合わない
  └─ 移植の誤差（副次）  … 同じく合わない答えの、別の変種になる
```

> **移植誤差は「悪い答えを別の悪い答えに変える」だけで、良い答えを壊してはいない。**
>
> ここを分けずに「移植が悪い」と読むと、直らないものを追い続けることになる。
> **上限（fp32）を測れば、追う価値があるかどうかが分かる。**
