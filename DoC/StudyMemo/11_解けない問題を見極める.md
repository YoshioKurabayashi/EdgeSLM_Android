## 11.1 症状と、最初に切るべき切り口

```
FP32（PyTorch）          → ○ 正しく答える
Export FP32（ONNX）      → ○
Host QDQ（量子化・CPU）  → ○ 「エアコンを22度に調節しました。」
実機 HTP                 → × 「Okay, the user wants to set the thermostat to...」
```

**4段に分けたのが効いた。** もし「FP32 と実機」しか比べていなかったら、
export のバグなのか量子化なのか HTP なのか、永久に切り分けられない。

> **原則**: 経路を段に分け、**1段ずつ**通す。壊れた段の手前までは「正しい」と言い切れる状態を作る。

この時点で分かるのは「**量子化そのものは無実。HTP で実行したときだけ壊れる**」ということ。

## 11.3 ★整数の一致率は、誤差の大きさを表さない

上の表で一番大事なのはここ。

```
linear_19 : 整数が最大 70段 違う  →  実数誤差  3.55%
mul_41    : 整数が最大  3段 違う  →  実数誤差 16.83%   ← 一致率 98.1%
linear_20 : 整数が最大  2段 違う  →  実数誤差 55.11%
```

**効くのは「差の段数 × scale ÷ 信号の大きさ」である。**

`mul_41` は scale が 0.105 で、値の RMS が 0.091。つまり**典型的な値が1段より小さい**。
実際、要素の 65% がコード 0、93.5% が ±1段以内に入る。**16bit と名乗っていて、実質3値。**

この状態では、Host と HTP の丸め方がほんの少し違うだけで、0 と ±1 の境目をまたぐ。
それが信号の数十%になる。

> **原則**: 量子化の良し悪しは、**「値が何段で表されているか」**で見る。
> bit 数でも、コードの一致率でもない。

## 11.4 なぜ scale がこんなに粗いのか — 位置0 の巨大活性

`mul_41` / `linear_20` の scale は、**先頭トークン（位置0）が作る極端な値**に合わせて決まっていた。

9通りのプロンプトで層2 MLP の出力を測ると:

| プロンプト | 位置0 のトークン | 位置0 の最大 | 位置1以降の最大 |
|---|---|---:|---:|
| 日本語チャット（system あり） | `<\|im_start\|>` | **8142.7**（ch35） | 4.79 |
| 英語チャット | `<\|im_start\|>` | **8142.7**（ch35） | 4.48 |
| system 無し | `<\|im_start\|>` | **8142.7**（ch35） | 4.07 |
| 2ターン分の履歴 | `<\|im_start\|>` | **8142.7**（ch35） | 4.63 |
| 生テキスト「日本の…」 | 日本の | 7259.2（ch35） | 4.41 |
| コード `def add(...)` | def | 5749.7（ch35） | 2.50 |

**トークンの種類ではなく、位置0 で必ず出る。** しかも常に同じチャンネル（35）。
2ターン目以降の `<|im_start|>`（位置0 でない）は 1.25〜1.75 にとどまる。

```
位置0 の 8142 を表せる範囲を取る
        ↓
1段 = 0.113
        ↓
位置1以降の値（±10 程度、RMS 0.1〜0.3）は数段でしか表せない
        ↓
Host と HTP の ±1〜2段の違いが、信号の数十%になる
        ↓
その誤った K/V がキャッシュに積まれ、自己回帰で分岐する
```

> **これは 3章の massive activation の続き**である。Qwen2.5 では RMSNorm 内部の `x²` で問題になり、
> Graph Rewrite（C-11）で回避できた。Qwen3 では **MLP の出力そのもの**に出るので、
> 「計算の順序を変える」では逃げられない。

## 11.5 直そうとして起きたこと

| 試したこと | 結果 |
|---|---|
| 層2 の2本だけ範囲を狭める | **実機は改善**（add_26 の誤差 21.95% → **8.61%**）。だが **Host の生成が壊れた** |
| 同じ調整を28層へ拡張 | **Host が完全崩壊**（1位保持 85.7% → **0.0%**、単語にならないトークン列） |
| 位置0 だけ元の範囲に戻す | 崩壊は消える（80.4%）。だが「音楽をかけて」だけ再現性高く壊れる |
| 範囲幅を 1x〜8x で掃引 | **単調ではない。** 2x 文字化け → 3x 重複 → 3.5x 文字化け → 3.75x 話題回避 → **4x だけ正常** → 8x 別指標が急落 |
| その 4x を実機で測る | 21.95% → **18.67%**。効果がほとんど無い |
| `linear_20` の量子化を完全に外す（oracle） | **Host はむしろ悪化**（85.7% → 76.8%） |

**狭めれば実機に効くが Host が壊れ、Host を保つ幅は実機に効かない。**
1x〜8x の範囲に、両方を満たす点は存在しなかった。

> **原則**: 「原因を1箇所に特定できた」ことと「その1箇所を直せば良くなる」ことは**別**である。
> 局所の数値改善が、別の場所（自己回帰の意思決定）を壊しうる。

## 11.6 ★2つの軸を混同しない

この調査で一番危なかったのがここ。**「ずれ」には2種類ある。**

```
FP32  ←─ ① 量子化の誤差 ─→  Host QDQ  ←─ ② 実行環境の誤差 ─→  実機 HTP
```

KV キャッシュを入れ替える実験（Host 内）で、「層11-17 の V が悪い」と分かった。
そこで層11-17 の V の量子化だけを変えたモデルを作り、実機で測った。

| タップ | Host↔HTP の誤差（baseline） | 一致率 |
|---|---:|---:|
| L11-17 の V（read 側・8bit） | 1.14 〜 3.04% | 99.6% 以上 |
| L11-17 の V（write 側・16bit） | 0.07 〜 1.74% | 99.6% 以上 |

**層11-17 の V は、②の軸では最初からほとんどずれていなかった。**
つまり、①の軸（Host が FP32 からずれる）で見つけた犯人を、②の軸（実機が Host からずれる）の
対策に使おうとしていた。**別の問題を解こうとしていた。**

> **原則**: 「どこが悪いか」を言う前に、**どの2つを比べているのか**を明示する。
> 同じ「V が悪い」でも、①なら量子化設計の話、②なら実行環境の話で、打ち手がまったく違う。

## 11.7 ハードの制約が解を閉じることがある

打ち手は2つ考えられた。どちらも v68 で閉じた。

**(a) V の read 側を 8bit → 16bit に上げる**

```
qnn-context-binary-generator
   ↓
<E> [4294967295] has incorrect Value 68, expected >= 73.
<E> Failed to validate op node_matmul_23 with error 0xc26
```

**C-8**（活性×活性の MatMul は `u16×u16` 不可）そのもの。**精度以前に、グラフが作れない。**
「Host で試したら良かった」構成が、実機では**存在できない**。

**(b) KV の量子化範囲を広げる（飽和を消す）**

対話のほぼ全位置で KV が範囲外に出ていた（日本語107/107位置、「22度」の「2」で `past_v_14` の8〜9倍）。
そこで範囲を広げたら——**悪化した**（1位保持 85.7% → 78.6%）。

原因は、C-8 のため attention 直前で **8bit（255段）**に落としている段があること。
範囲を広げるとその刻みが粗くなる。**元の狭い範囲は、飽和と分解能の妥協点だった。**

> **原則**: 制約（C-n）は「守るべき作法」であると同時に、**解の空間を狭める壁**でもある。
> 壁に当たったら、それは失敗ではなく**確定した事実**として記録する。

## 11.7b ★「実機に載せられる形か」を先に確かめる

クローズ後の追試（P16）で、もう1つの壁が見つかった。

Host で唯一きれいだった 4x は、記録上は「自由生成が正常」とだけ書かれていた。
だが実際には **位置0 は baseline モデル／位置1以降は 4x モデル**という**2モデル構成**に依存していた。
実機は context binary 1本・セッション1つで、**会話の途中でモデルを切り替えられない**。

1モデルにまとめる（＝位置0 も 4x を通す）と:

| 変種 | 位置0 の扱い | 実機で可能か | 1位保持 | KL | 自由生成 |
|---|---|---|---:|---:|---|
| baseline | — | ○ | 85.7% | 0.195 | ○ |
| **A1**（層2 のみ 4x） | **4x（1モデル）** | ○ | **0.0%** | **18.24** | × 文字化け |
| B1（全28層 4x） | 4x（1モデル） | ○ | **0.0%** | 16.25 | × 文字化け |
| A2（層2 のみ 4x） | baseline（2モデル） | **×** | 83.9% | 0.219 | ○ |

**A1 と A2 は同じ scale。違いは位置0 をどちらのモデルで通すかだけ。** それで正常と完全崩壊に分かれた。
位置0 の 8142 が 4x の範囲（−15.7〜+31.4）で飽和し、**KV の先頭スロットとして最後まで参照され続ける**ため。

検討の順序はこうあるべきだった。

```
① 実機に載せられる形か     ← 4x はここで落ちた
② 量子化設計として妥当か   ← Host 品質で測る
③ 実行環境の差が小さいか   ← Host↔HTP で測る
```

> **原則**: 記録には「何が良かったか」だけでなく、**それが何に依存していたか**を同じ強さで書く。
> 「Host で正常」とだけ残すと、後からその設定を再利用しようとしたときに前提が見えない。

## 11.8 測り方で踏んだ落とし穴（4つ）

### (1) 分母を間違えると誤差が消える

残差の Host↔実機 誤差を **uint16 のコード値**で相対L2 を取ったら 0.093% だった。
コードは zero_point（1496）を含む大きな数なので、±5段の違いが薄まっていた。
**逆量子化してから測ると 31.53%。**

### (2) 観測が対象を変える

観測用の出力を増やすと、HTP の**融合が変わって数値が変わる**（add_26 が最大2段変化）。
また、中間の float をグラフ出力にすると v68 では `q::QNN_Convert`（fp16→fp32）が作れず、
**ビルド自体が落ちる**（C-1 の再来）。**観測は量子化後の整数コードで取る。**

→ 対照（観測あり版と観測なし版）を必ず並べて、観測の副作用が結論を変えないことを確かめる。

### (3) teacher forcing と自由生成は別物

FP32 と同じ履歴を強制的に与える teacher forcing と、自分の出力で進む自由生成では、軌道が違う。
**teacher forcing で改善しても自由生成が壊れる**ことがある（逆もある）。

### (4) ★集計指標は生成の健全性を予測しない

これが一番重い。

| 変種 | 1位保持 | margin 保持 | 自由生成 |
|---|---:|---:|---|
| baseline | 85.7% | 41.7% | ○ |
| 層2 両方 narrow | **87.5%** | — | **×**（前ターンの繰り返し） |
| range 3.75x | **87.5%**（最高） | 53.5% | **×**（話題回避） |
| range 4x | 83.9% | 50.0% | **○**（唯一きれい） |

**集計指標が baseline を上回るのに自由生成は崩れる例が3つ出た。**

> **原則**: 合否は**自由生成そのもの**で決める。集計指標は診断用。
> 見るなら「各回答の**最初のトークン**の margin」が比較的よく対応した。

## 11.10 持ち帰り

1. **経路を段に分ける。** FP32 → export → Host QDQ → 実機。壊れた段の手前を確定させる
2. **「値が何段で表されているか」で量子化を見る。** bit 数でもコード一致率でもない
3. **massive activation は位置で出ることがある。** トークンの種類ではなく位置0。
   Graph Rewrite で逃げられる場合（Qwen2.5 の `x²`）と、逃げられない場合（Qwen3 の MLP 出力）がある
4. **「Host が FP32 からずれる」と「実機が Host からずれる」は別の軸。** 混ぜると別の問題を解いてしまう
5. **局所の改善が全体を壊しうる。** 原因の特定と、対策の妥当性は別に検証する
6. **合否は自由生成で決める。** 集計指標が良くなっても生成が壊れることがある
7. **「実機に載せられる形か」を、精度の議論より先に確かめる。** 2モデル切り替えのように、
   Host では自然でも実機では存在できない構成がある（[11.7b](#117b-実機に載せられる形かを先に確かめる)）
8. **ハードの制約は解の空間を閉じる。** 閉じたら、それを確定した事実として記録して止める
9. **棄却した仮説と、事前に決めた判定基準を残す。** それがクローズの中身
