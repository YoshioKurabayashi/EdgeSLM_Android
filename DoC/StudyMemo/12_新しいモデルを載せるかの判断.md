```

        ↓
AI Hub の一覧に載っているか？ ── それは可否の基準にならない
```

## 12.2 HTP の世代で決まること

### 世代で変わるもの

| こと | v68（今回） | v69 | v73 以降 | 根拠 |
|---|:--:|:--:|:--:|---|
| 活性×活性の `u16 × u16` MatMul | **×** | × | **○** | 実機のエラー `has incorrect Value 68, expected >= 73`（C-8） |
| LPBQ / 16a4w_block（ブロック量子化） | **×** | **○** | ○ | SDK 文書（中間まとめ 3.11） |
| 重み共有（prefill 用と decode 用で重みを1つに） | **×** | × | **○**（変換は x86 Linux のみ） | QAIRT 文書。v68 でまとめても 233MiB×2 のまま（後続検証の実測） |
| Genie の LLM 経路 | × | × | ○ | ai-hub-apps の `llm_on_genie`（要件定義書 #8） |
| float（fp16）の区間を残せるか | **×**（skel が fp16 非対応＝C-1） | 未確認 | 未確認（新しい世代は fp16 演算に対応している見込み） | 実機 |

### 世代を上げても変わらないもの

| こと | 帰結 |
|---|---|
| **活性化は per-tensor のみ**（per-channel にできるのは重みだけ） | 活性の分布が原因の破綻（Qwen3）は、世代を上げても直らない |
| **動的形状は扱えない** | 固定形のグラフと固定長の KV キャッシュが前提 |
| **`GroupQueryAttention` は HTP 非対応** | attention は素の op に分解して書く |
| **グラフは事前コンパイル（AOT）で、SoC と世代に紐づく** | `--htp_socs sm8350` で作った context binary は別世代に持っていけない。**対応端末を増やす＝生成物を増やす** |

検証結果まとめ 4.3節の注記がこの章の要点の1つである。

> **注意: v73 の端末に替えても解決するとは限らない。** v73 の利点は `u16×u16` の MatMul と
> weight sharing であって、**per-tensor 活性化量子化という制約は変わらない**。

### 世代の制約か、ツールの都合か

判断を間違えないために、制約の出どころを分ける（1.5節の考え方）。

| 種類 | 例 | 回避できるか |
|---|---|---|
| **ツール・ランタイムの都合** | Genie が v73 以上を要求／AI Hub の配布に無い／ORT の量子化器が `per_channel=True` を無視する | **できる**。経路を変える、生成物を直接書き換える |
| **ハードの実体** | skel が fp16 非対応／`u16×u16` 不可／LPBQ 不可／重み共有不可／活性は per-tensor のみ | **できない**。等価変形で迂回するか、諦める |

「Genie が v73 以上を要求 → NPU で LLM は不可」は、前者を後者と取り違えた例として記録されている（中間まとめ）。
ORT の QNN EP は SM8350 を正式にサポートしており、別経路で動かせた。

## 12.3 メモリ — 載るか

### 壁は3つある

| 壁 | 何の上限か | 超えるとどうなるか | 今回の実測 |
|---|---|---|---|
| **NPU の1プロセス上限** | 1プロセスが開ける context の合計（dma-buf） | 開けない（`err 1002`） | 約1,710MiB |
| **RAM（OS による kill）** | 端末全体のメモリ | lmkd に kill される（SIGKILL。ログは途切れる） | 1,467MiB を2つ常駐させると2つ目が kill された |
| **ロード中の山** | 読み込みの間の一時メモリ | 読み込みの途中で kill される | 1,467MiB → 山 1,573MiB。`embed_mode=1` だと二重に持ち、736MB で RSS 1.47GB（C-12） |

NPU の上限は**プロセス単位**なので、別プロセスにすればもう1つ開ける。ただしそのときは RAM の壁に当たる。
上の「2つ目が kill」はこれである。

### 見積もり方

```
NPU に載る量     ≒ 重みの量（パラメータ数 × bit ÷ 8）＋ 活性の置き場
必要な空き RAM  ≒ 定常（context ＋ KV ＋ アプリ）＋ ロード中の山 ＋ 余裕 1GB
```

実例（同じ端末）:

| モデル | 量子化 | context binary | 結果 |
|---|---|---:|---|
| Qwen2.5-0.5B（24層） | A16W8（`lm_head` は16bit） | 772MB | 1本で載る |
| Qwen3-0.6B（28層） | A16W8 | 872MB | 載る（精度で閉じた。11章） |
| Qwen2.5-1.5B | W8 | — | 埋め込み表を CPU 側に置いて載せた（後続検証） |
| Gemma 4 E2B | QAT 済み（重み 4/2/8bit 混在） | 1,467MiB | 1本で載る。**prefill 用と decode 用の2本は RAM 不足** |

### 2つのグラフを持つとき

入力をまとめて食べる prefill 用と、1トークンずつ作る decode 用は**重みが同じ**である。

| 世代 | 2本の持ち方 | 結果 |
|---|---|---|
| v68（今回） | 重み共有が無いので**重みが2倍** | 常駐できず、持ち替え（約2.5秒）が要る |
| v73 以降 | **重み共有**で1つの context binary に入れる | 重みは1つ。持ち替えも不要 |

後続検証の算出では、v68 のまま2本を常駐させるには**空き 5.5〜6GB（RAM 10〜12GB の端末）**が要る。

## 12.4 帯域 — 速さを見積もる

### 1トークンの生成は帯域で決まる

```
1トークンの時間 ≒ 毎トークン読む量（≒ context binary の大きさ）÷ 実効帯域
実効帯域       ≒ 理論帯域 × 効率
```

実測（同じ端末、Gemma 4 E2B の検証）:

| グラフ | 大きさ | 1回の時間 | 逆算した実効帯域 |
|---|---:|---:|---:|
| 9層の部分グラフ | 233MiB | 11.1ms | 約22GB/s |
| 35層の全体 | 1,467MiB | 77ms（うち推論 73ms） | 約20〜21GB/s |

**大きさが6倍違っても実効帯域がほぼ同じ**。計算ではなく、重みを読む時間で決まっている証拠である。
理論 51.2GB/s に対して効率は**約40%**。

### まとめて処理しても1回の時間はほとんど増えない

同じ9層を「1回に16トークン食べる」形にしても、1回の時間は **11.1ms → 12.0ms（1.08倍）**だった。
重みを読む回数が同じだからである。したがって:

```
最初の文字までの時間 ≒ ⌈入力の長さ ÷ T⌉ × プレフィル1回 ＋ 生成1回      （T は1回に食べるトークン数）
```

T=1 のグラフだけだと入力の長さぶん NPU を呼ぶことになり、30トークンで 2.8秒、152トークンで 12.6秒かかった。

### 文脈の長さでも変わる

Qwen2.5-0.5B の decode は **`26.9 + 0.0335×L` ms**（L＝キャッシュ長、10.2節）。
KV キャッシュが float32 の入出力だと毎ステップ往復するので、長い文脈では無視できない
（Qwen3・L=512 で1ステップ 224MB）。

### 実機が無いときの見積もり手順

1. 目標モデルの「毎トークン読む量」を出す（量子化後の重み ＋ KV）
2. 対象端末の理論帯域を調べる（LPDDR の世代・速度・バス幅）
3. 効率 **40〜70%** を当てて、1トークンの時間に幅を持たせる（40% は今回の実測。新しい世代で上がるかは未確認）
4. 同じ世代の実測値があれば、そこから効率を較正して幅を狭める
5. 最初の文字までの時間 ＝ プレフィル回数 × 1回の時間 で出す

例（推定）: 3B 級を4bit にして約1.9GB、理論 85GB/s の端末なら、実効 34〜60GB/s で **1トークン約32〜56ms（約18〜31 tok/s）**。

> **速さは計算で当たりがつく。精度は計算で当たりがつかない**（12.6）。

## 12.5 モデルで確認すること — 形と op

| # | 確認 | なぜ | 今回の知見 |
|---|---|---|---|
| 1 | **静的形状にできるか** | QNN EP は動的形状を扱えない | prefill の窓と decode の KV を固定長にした（10章） |
| 2 | **KV キャッシュをグラフの入出力に出せるか** | decode を NPU で回すため | attention を自前で書き直し、HF と1トークンずつ突き合わせた（5.7節） |
| 3 | **非対応の op が無いか** | 変換かロードで落ちる | `GroupQueryAttention` は HTP 非対応（手分解）。`RotaryEmbedding`（com.microsoft）は converter で落ちるが素の op に分解すれば通る。`SimplifiedLayerNormalization` はファイルとして持ち込めない。`Expand` は端末でだけ落ちる（C-10） |
| 4 | **量子化の形式** | NPU で整数実行できる形か | QDQ（標準の MatMul ＋ Q/DQ）で通した。ORT の4bit 独自 op `MatMulNBits` が v68 で成立するかは**版ごとに要確認**（中間まとめ・基本設計②） |

| 7 | **1モデル・1セッションで完結するか** | 実機は会話の途中でモデルを切り替えられない | Qwen3 の 4x 案は「位置0 だけ別モデル」に依存していて、実機に載せる形が無かった（11.7b節） |

## 12.6 モデルで確認すること — 量子化に耐えるか

### なぜここが本命か

形・op・メモリ・速さは、**やってみれば道具が答えを出す**。
量子化に耐えるかはモデル固有の性質で、**事前に見る手段は活性の分布しかない**。
しかも活性化は per-tensor しか使えず、これは世代を上げても変わらない（12.2）。

### 見るものと、危ない目安

fp32 で数層だけ動かして活性を記録し（`make_calib_data.py`）、次を計算する（★2026-10-17 補足: `make_calib_data.py` が作るのは較正用の入力（埋め込み後の hidden_states、または input_ids）で、分位（p50・p99 など）は出すが層の中の活性は記録しない。層の中の活性を記録したのは `massive_origin_check.py`（11.4 節。位置0 の巨大活性）と `layer2_probe.py`（11.2 節。整数コードの分布）である）。

| 見るもの | 危ない目安 | 今回の実例 |
|---|---|---|
| **per-tensor の1段階 ÷ 典型値（p50）** | 典型値が1段階を下回る | RMSNorm の `x²`: 典型値 0.04 に対し1段階 42.7 → 完全に潰れた（3章） |
| **整数コードの分布** | ±1段以内が9割を超える | 93.5% ＝ **16bit と名乗って実質3値**（11.3節） |
| **位置0 と位置1以降の最大値の比** | 2桁違う | 8142 対 1.25〜1.75（Qwen3、11.4節） |
| **チャンネル間のレンジ比（重み）** | 中央値で10倍以上 | 中央値 10.3倍・最大 67.1倍 → 重みは per-channel 必須（7.3節） |
| **fp32 ↔ ホストQDQ の top-1** | 90% を切る | 直した後の prefill 窓64 は 100.0% |
| **ホストQDQ ↔ 実機の相対L2** | 15% を超える | Qwen3 の 4x 案は 18.67% で打ち切り（**基準は事前に決めた**） |

### 逃げ道があるか

| 構造 | 逃げ道 | 例 |
|---|---|---|
| その計算に**性質**がある（スケール不変など） | その性質を使う**等価変形**で逃げられる | RMSNorm はスケール不変 → max で割ってから二乗（C-11） |
| 原因が1か所に絞れない | 全体の等価変形（SmoothQuant など）を検討する。ただし重い（4.3節「対策の規模は、原因の絞り込み具合で決まる」） | — |
| 位置やトークンに固定で出る巨大値で、性質も無い | **v68 では閉じる**ことがある | Qwen3 の位置0（11章） |

## 12.7 AI Hub で分かること・分からないこと

この検証では AI Hub を使っていない。以下は Qualcomm AI Hub Workbench の公式ドキュメント（2026-09-24 時点）で確認した内容である。

### 何をするサービスか

クラウド上の**実機**でモデルをコンパイルし、動作と速度を確かめられるサービスと、最適化済みモデルの一覧。
**Genie が前提なのは LLM のレシピ（`llm_on_genie`）だけ**で、サービス全体の前提ではない。

| ジョブ | 何をするか |
|---|---|
| **Compile** | 対象向けに変換・最適化する |
| **Profile** | 実機で走らせ、**層と演算ユニットの対応・推論時間・ピークメモリ**（とロード時間）を測る |
| **Inference** | **自分の入力データで走らせ、数値の正しさを確かめる** |
| Quantize | 量子化する |
| **Link** | **複数の DLC を1つの context binary にまとめ、名前と内容が一致する重みを自動で共有する** |

- 入力形式は PyTorch / TorchScript / **ONNX** / TensorFlow Lite。**ONNX はそのまま投げられる**（動的形状の ONNX も一部の経路で受け付ける）
- 出力先は Qualcomm AI Runtime（QNN）/ TensorFlow Lite / **ONNX Runtime**
- 端末はクラウドにある実機から選ぶ（例: Galaxy S24）。**手元の世代がそこに無ければ、その世代の数字は取れない**
- 大きさ・時間の上限は、確認したページには書かれていなかった（未確認）

### 読むときの注意（ドキュメントに明記されている）

> When running on those devices using the ONNX Runtime, Qualcomm® AI Hub Workbench will **not automatically enable
> the QNN Execution Provider**. This behavior allows **all models to succeed by running them on the CPU**.

**ONNX Runtime を指定すると、どんなモデルでも CPU で動いて「成功」する。** 数字が出ても CPU の数字かもしれない。
profile の「層と演算ユニットの対応」で NPU に載ったかを確かめるか、QNN（context binary / DLC）を出力先にする。
これは本検証で `pass_strict` を毎回見ていたのと同じ話である。

> ONNX models produced by AI Hub Workbench contain hardware-compatibility fixes that optimize for Qualcomm hardware.
> **ONNX models uploaded directly may not contain these fixes.**

**持ち込みの ONNX には、ハード互換の手当てが入っていない。** 本検証の Graph Rewrite（5章）に相当するものは自分で入れる必要がある。

**Link ジョブは重み共有そのもの**である。12.3 の「prefill 用と decode 用を1つに」をクラウドで作れる可能性がある
（手元の QAIRT では x86 Linux が必要）。ただしドキュメントの例は入力形状違いの画像モデルで、
**LLM の prefill / decode は明記されていない**。使えるかは要確認。

### 性能一覧（掲載値）から推測できること・できないこと

| 推測できる | 推測できない |
|---|---|
| その構成が **NPU に載る実績**があるか（形・変換・ロードの関門は通る見込み） | **LLM の tok/s**（掲載は1回の推論時間。生成ループ・KV の受け渡し・文脈長依存が入らない） |
| **世代間の相対比**（同じモデルの数字を世代で並べる） | **量子化に耐えるか**（精度は一覧に出ない。Qwen3 のような破綻は見えない） |
| 1トークンの時間の概算（12.4 の式の効率を較正できる） | **実行系の誤差**（C-13 のような converter 由来のずれ） |
| メモリに載るかの当たり | ロードできるか・ロード中の山（`embed_mode` の二重持ち・OS の kill） |
| — | 熱による持続性能の低下 |
| — | 古い世代の値（v68 は掲載自体が無い） |

**一覧に載っていない＝動かない、ではない。** 対応チップセット表は、実質「Qualcomm が検証した世代の表」である。
載っていなくても 12.1〜12.6 の関門を通れば動く（本検証がその実例）。
逆に、載っていても対象の世代に無ければそのまま使える保証は無い。

## 12.8 判断の手順 — 安い順に通し、落ちたら止める

| 順 | 問い | 確かめ方 | 落ちたときの手 |
|---|---|---|---|
| **0** | **そのモデルは fp32 でその仕事ができるか** | PC で普通に動かす。上限を測る（10.10節） | モデルを替える。移植の問題ではない |
| **1** | **端末は条件を満たすか** | 12.1 の 1〜4（世代・skel・unsigned PD・Android の版） | 端末を替える |
| **2** | **静的形状にでき、1モデル・1セッションで完結するか** | 自分で書き出す（12.5 の 1・2・7） | 書き出しを作り直す。無理なら不可 |
| **3** | **変換とロードが通るか** | AI Hub の Compile ／ 手元の `qairt-converter` と実機。C-1〜C-13 を自動検査 | 落ちた op を等価変形で置き換える |
| **4** | **メモリに載るか** | 12.3 の見積もり → AI Hub の Profile のピークメモリ ／ 実機で開く | 分割する、`embed_mode=0`、窓を縮める、埋め込み表を CPU 側へ |
| **5** | **全部 NPU に載ったか** | Profile の層と演算ユニットの対応 ／ `pass_strict` | CPU に落ちた op を潰す |
| **6** | **速さが足りるか** | 12.4 の見積もり → Profile の推論時間から組み立て | 量子化を強める、モデルを小さくする |
| **7** | **量子化に耐えるか** ← 本命 | 12.6 の分布 → 数層でホストQDQ と実機の2軸を測る → Inference で出力比較 | 等価変形で逃げられるか。駄目なら諦める |
| **8** | **自由生成が崩れないか** | 実機で普通に会話させる | **合否はここで決める**（11.8節） |

### 守ること

1. **順序を守る。** 「実機に載せられる形か」を「量子化設計として妥当か」より先に見る（11.7b節）。
   Qwen3 の 4x 案は、Host で良くても実機に載せる形が無かった
2. **基準を先に決める。** 「4x の実機誤差が 15% 以下なら前向き」と決めてあったので、18.67% で打ち切れた（11.9節）
3. **精度は小さい版で先に確かめる。** 速さは計算で当たりがつくが、精度は当たりがつかない。
   同じ系列の小さいモデル（0.5B など）を先に通すのが一番安い
4. **AI Hub の数字は「NPU で動いたか」を確かめてから読む**（12.7）

## 12.10 持ち帰り

1. **AI Hub に載っているかは「近道があるか」であって、可否の基準ではない。**
2. **端末は、世代・メモリ（3つの壁）・帯域の3つを先に調べる。**
3. **世代を上げると解けるのは、型の組合せ・重み共有・メモリ。活性の per-tensor は解けない。**
4. **速さは計算で当たりがつく**（読む量 ÷ 実効帯域。今回の効率は約40%）。
5. **精度は計算で当たりがつかない。** 活性の分布を見て、小さい版で実地に確かめる。
6. **AI Hub の数字は、NPU で動いたかを確かめてから読む**（ONNX Runtime 指定は CPU で成功してしまう）。
7. **基準を先に決め、安い順に通し、落ちたら止める。**
