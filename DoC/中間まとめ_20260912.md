## 1. いま、どこにいるか

```
✅ P0    足場（端末プロファイル・NDK・計測ハーネス設計）
✅ P1    配管Gate    — ZipDepth（第三者製）が SOG05 で NPU 動作
✅ v0.1  自作 runner — 同じモデルを自作コードで実行し同結果
✅ P2    パイプライン — 自作モデルを自作変換で作り NPU 実行
✅ P2b   Transformer 構成要素の重点検証   **実 export 形**を含む端末 22/22 合格
🔶 P3    本物の Qwen                実機で動作（440MB / 17.4ms）。**精度が不足**（原因は C-8）
⬜ P3    経路比較と熱
⬜ P4/P5 Decode / Prefill（Qwen2.5-0.5B）
```

### 1.1 なぜこの順序だったのか

**「変数を1つに絞る」原則**で進めている。3層それぞれの疑いを別々に消した。

| フェーズ | 持ち込んだもの | 消えた疑い |
|---|---|---|
| P1 | **端末だけ**（アプリ・モデル・ランタイムは全て第三者製） | 端末（au版 SOG05 固有の firmware / carrier 差） |
| v0.1 | **自分のコードだけ**（モデル・QNN・ORT は ZipDepth と同一物） | runner の実装 |
| P2 | **自分のモデルだけ**（器は検証済みの自作 runner） | 量子化・変換パイプライン |

→ **以降 Transformer で失敗したら、原因は「Transformer 固有の事情」に限定して調べられる。**

## 2. 実測値

### 2.1 性能

| 対象 | 条件 | OrtRun |
|---|---|---|
| ZipDepth（第三者アプリ） | A16W8 / 384×384 / 連続推論 | 36.0〜42.8 ms（**中央値 ≒39**）、初回 38.4 |
| 同モデルを自作 runner で | A16W8 / 384×384 / 隔離ループ | **median 35.77** / p90 37.19 / min 33.98 / max 38.18 / stddev 1.08 |
| 自作 testnet | A16W8 / 32×32 の小型CNN | **median 0.277** / p90 0.281 / min 0.272 |

前処理は 0.2〜0.5 ms で**推論の1%未満**。ボトルネックは完全に NPU 側。
推論頻度は約 22〜23 回/秒（ZipDepth のカメラ駆動時）。

**ウォームアップ効果はモデルが小さいほど顕著**:

| モデル | 1回目 → 3回目 | 比 |
|---|---|---|
| ZipDepth（384×384） | 38.0 → 37.6 ms | 1.01× |
| testnet（32×32） | **1.083 → 0.283 ms** | **3.9×** |

小さいモデルほど固定費（グラフ finalize 等）の比率が大きい。
**単発実行から結論を出さない**という方針の根拠になる。

### 2.2 熱

| 指標 | アイドル | 連続推論時 |
|---|---|---|
| **NPU（`nspss-0-usr`）** | 32.7 ℃ | **55〜59 ℃（+25℃）** |
| CPU（`cpuss-1-usr`） | — | 64〜68 ℃ |
| GPU（`gpuss-0-usr`） | — | 54〜57 ℃ |
| `DmaBufTotal` | 725,536 kB | 最大 770,804 kB（**+45 MB**） |

**重要な観察**: 開始 **8秒** で `thermal-cpufreq-7`（大コアの周波数制限）が 0→1 に発動した
一方、**`cdsp`（NPU）は 0 のまま**だった。

→ **エッジ推論の熱問題は必ずしも NPU から来ない。** NPU が 59℃ でも平気な一方、
先に CPU が音を上げた。P3 の設計に反映する。

| 項目 | 値 |

## 3. v68 固有の制約（確定事項）

### 3.1 モデル生成時（C-1〜C-5）

違反すると**端末でのロード時に `error 1002`** で落ちる。変換時には気付けない。

| # | 禁止事項 | 正しい形 |
|---|---|---|
| **C-1** | グラフ内に float セグメントを残す | **全op型を量子化した完全QDQ**。float op は fp16 HTP op になり、**v68 の skel は fp16 非対応** |
| **C-2** | `soc_id` を刻む（socModel=30） | **`--htp_socs sm8350` のみ**。unsigned PD は SoC id を照会できない。生成物は `socModel=0` + `dspArch=68` |
| **C-3** | backend_extensions の `devices`/`cores` を渡す | 渡さない。**unsigned PD は power config を適用できない** |
| **C-4** | float 混在グラフに `--preserve_io_datatype` | 完全QDQに対してのみ |
| **C-5** | `BatchNormalization` を残す | 量子化前に `Mul`+`Add` へ畳む（**error 3110**） |

### 3.2 アプリ側（C-6・C-7）

| # | 禁止事項 | 正しい形 |
|---|---|---|
| **C-6** | `useLegacyPackaging = false`（AGPの既定）のまま | `true` にして **`extractNativeLibs="true"`** を得る。FastRPC は skeleton に**実ファイルパス**を要求する。**APK内の圧縮方式で判定してはいけない**（ZipDepth は DEFLATED かつ正常動作） |
| **C-7** | `<uses-native-library>` を宣言しない | **`libcdsprpc.so` / `libadsprpc.so` を宣言する**（`required="false"`）。Android 12+ では宣言が無いと vendor ライブラリがリンカ名前空間に入らない |

### 3.3 実行形態（R-9）

**HTP は `untrusted_app` ドメインのプロセスからしか使えない。**

| 実行主体 | SELinux ドメイン | `/dev/adsprpc-smd` |
|---|---|---|
| `adb shell` | `u:r:shell:s0` | 拒否 |
| `run-as <pkg>` | `u:r:runas_app:s0` | 拒否 |
| **アプリ本体** | `u:r:untrusted_app:s0` | **open 成功** |

→ 成果物は「**UIなし最小 Service + JNI + C++ 推論コア**を adb から駆動する」形。
最終目標の「C++ 推論サービスを搭載」と矛盾しない。

### 3.4 電力プロファイルは制御できない

unsigned PD では `setPowerConfig`（HAP_Power DCVS）が許可されない。

| 経路 | 症状 |
|---|---|
| **生成時**に `perf_profile` を埋め込む | ロード時に err 1002（C-3） |
| **実行時**に `htp_performance_mode` を設定 | **Run 時**に失敗 |

→ 測定値は**常にデフォルト電力プロファイル**。全レコードに
`power_profile="default(unsigned_pd)"` を機械的に刻み、他者の burst 測定値や
公称値と混ぜられないようにしている。

### 3.5 ★C-8: 活性化 × 活性化の MatMul は 16bit で通らない（P2b で実測）

**v68 で Transformer が載らない理由は、いま判明している範囲では1点だけ**だった。

```
<E> [4294967295] has incorrect Value 68, expected >= 73.
<E> QnnBackend_validateOpConfig failed 3110
<E> Failed to validate op matmul with error 0xc26
```

| MatMul の形 | A16 で | 実例 |
|---|:--:|---|
| **重み固定**（片側が initializer） | **通る** | Q/K/V/O projection、FFN の gate/up/down |
| **両辺が活性化** | **通らない** | attention の **QK^T** と **PV** |

回避策も同時に確認した。同一モデルを3方式で作って比較している。

| 方式 | matmul_act | attention | kvcache | block |
|---|:--:|:--:|:--:|:--:|
| A16W8 | NG | NG | NG | NG |
| **A8W8** | OK | OK | OK | OK |
| **A16W8 + 該当 MatMul のみ A8** | **OK** | **OK** | **OK** | **OK** |

→ **本線の量子化方式を「素の A16W8」から「A16W8 + 該当 MatMul のみ A8」へ改めた。**
全体を A8 に落としても通るが、**重み固定の MatMul まで 8bit にすると精度を無駄に捨てる**。

他の C-n と違い、**ホストの context 生成時に落ちる**ので端末へ持ち込む前に気付ける。

### 3.6 ★C-9 / C-10: 本物の export でしか踏まない2つ（P2b 続で実測）

P2b の13モデルは**私の推測**で書いていた。本物の Qwen2.5-0.5B を export したら
**4箇所が違っており**、そのうち1つは **v68 で動かない op** だった。

| 部位 | 手書き（推測） | **本物** | 影響 |
|---|---|---|---|
| GQA複製 | `Concat` | **`Unsqueeze`→`Expand`→`Reshape`** | **C-10。端末で err 1002** |
| マスク | `Add`(-60.0) | `Add`(**-3.4e38**) | **C-9。精度が静かに壊れる** |
| RoPE | `Split` | `Slice` | 実機で OK |
| RMSNorm | `Div` | `Reciprocal` | 実機で OK |

**C-9**: マスクの `-3.4e38` が混ざると、量子化の全分解能がそこに食われる
（16bit で1段階 0.0006 → 5e33）。**エラーにならず精度だけが壊れる**。
有限値（-60.0）へ置換する。fp32 の logits がビット一致することを確認済み。

**C-10**: **v68 は `Expand` を含む context binary をロードできない**。
ホストの context 生成は素通しするため、端末で初めて分かる。
実機で `unsqueeze_only`=OK / **`expand_only`=err1002** / `gqa_concat`=OK と
1つずつ切り分けて **`Expand` 単独が原因**と特定した。`Concat` へ書き換えて解決。

### 3.7 ★C-8 の本当の代償（P3 で実測）

C-8 は「回避策がある制約」だと思っていたが、**回避策自体が精度の主犯**だった。

| 方式 | 相対L2誤差 | v68 で動くか |
|---|---:|---|
| A16W8 素 | **5.50%** | **動かない（C-8）** |
| A16W8 + attention のみ A8 | **30.39%** | 動く |
| A8W8 全部 | 52.39% | 動く |

**v68 で動かすために誤差が 5.5倍になる。**

原因の鎖:
```
C-8 → attention スコアを 8bit にせざるを得ない
    → スコアのレンジ 1627 に対し、必要な分解能は 7（行内の幅の中央値）
      → 1段階 6.38 → softmax の入力で 6.38 差は確率 590倍
        → argmax 一致 29.2%（attention が壊れる）
```

**テンソル単体の誤差を見ても気付けない**（スコアの L2 誤差は 0.49%。
大きい値がノルムを支配するため）。**softmax を通して初めて 62.8% と分かる**。
→ **量子化の良し悪しは「その先で何に使われるか」まで見る。**

試して効かなかった対策（詳細は `results/P3_20260912_accuracy_layer1.md`）:
- スケールを MatMul の前へ移す → **変化なし**（量子化されるのはスケール後なので当然だった）
- softmax の前で行最大を引く → **悪化**（スコアは MatMul 出力時点で既に 8bit。打つ位置が違った）
- MatMul の出力だけ 16bit → **量子化器が拒否**（出力型は入力型と一致させる制約）

試算では**ヘッドごとに MatMul を分割**すると 62.8%→17.9% に改善する（1ヘッドだけ
レンジが桁違いなため）。ただし本当に効くのは行ごとの量子化で、QNN の活性化は
テンソル単位なので**構造的に到達できない**。

### 3.8 ★end-to-end で確かめた（P3）

層の L2 誤差だけで結論するのは「見る場所を間違える」誤りなので、
**次トークン予測の一致率**で測り直した。結果は同じ向きだった。

| | top-1 一致 | fp32のtop1が何位か | KL |
|---|---:|---:|---:|
| A16W8 素（**v68 不可**） | **85.2%** | 1.20位 | 0.024 |
| A16W8 + attentionのみA8（**v68 可**） | **50.0%** | **20.64位** | 0.556 |

（Qwen2.5-0.5B の埋め込み + 先頭2層 + lm_head、較正と別の文 176トークン位置）

**容量は足りた**: 440MB の EPContext が**全ノード HTP** でロード（4.15秒）、
prefill 16トークンが **17.42ms**。151,936語彙の埋め込み Gather も lm_head も載る。
事前調査で気にしていた PD メモリは、**419.67 MiB の context で問題なし**という
自前の実測値が取れた。

**24層は測れていない**——onnxruntime の量子化器が 2GB 超モデルを保存できない
（`EncodeError: Failed to serialize proto`）。**v68 の制約ではなくホスト側の限界**。

### 3.9 ★C-8 の再特定（2026-09-13）: `u16 × u8` は通る

外部指摘を受けて検証したところ、**C-8 は当初の理解より狭い制約**だった。

| 組合せ | v68 |
|---|:--:|
| `u16 × u16` | 不可 |
| **`u16 × u8`** | **可** |
| `u8 × u16` | **不可**（表では可とされるが実機は**非対称**） |
| `u8 × u8` | 可 |

左辺 u16・右辺 u8 にすれば **MatMul の出力（attention スコア）を 16bit に保てる**
（1段階 6.38 → 0.0248）。

| | 層1枚の相対L2 | end-to-end top-1 | fp32top1の順位 |
|---|---:|---:|---:|
| A16W8 素（**v68 不可**／上限） | 5.5% | 85.2% | 1.20位 |
| **`u16×u8` + 左右入替** | **9.3%** | **80.7%** | **1.34位** |
| `u16×u8`（入替なし） | 19.2% | 66.5% | 1.95位 |
| 両側 A8（当初） | 30.4% | 50.0% | 20.64位 |

さらに **8bit にできるのは常に右辺**なので、`A×B = (B^T×A^T)^T` の等価変形で
**右辺に置くテンソルを選べる**。QK^T で K（±130、1段階 0.99）ではなく
Q（[-10,6]、1段階 0.064）を右辺へ持ってくると**分解能が 15倍**になり、
**到達不可能な上限 85.2% に対し 80.7% まで回復した**（当初 50.0%）。
実機も 17.42ms → **14.29ms** と速くなっている。

**ORT の量子化器では表現できない**（入力型を必ず揃える）ため、
`force_mixed_matmul.py` で QDQ を直接書き換えた。
**ツールの制約をハードウェアの制約と取り違えるところだった。**

**さらに、壊れているのは layer 0（と 1）だけ**と判明。層2〜23 は 8bit でも
argmax 一致 **95.7%**。先頭2層での測定は**24層中で最悪の2層**を使っていた。

### 3.10 ★実機で測ったら違った（2026-09-13 / runner v0.3）

ここまでの精度はすべて**ホスト CPU 上の QDQ シミュレーション**だった。
runner に `infer` task（実データを読んで出力を返す）を足して実機で測り直した。

| 方式 | ホスト top-1 | **実機 top-1** | ホスト相対L2 | **実機相対L2** |
|---|---:|---:|---:|---:|
| **`u16×u8` + 左右入替** | 80.7% | **63.1%** | 9.85% | **22.11%** |
| 両側 A8（当初） | 50.0% | **46.6%** | 32.59% | **38.27%** |

**ホストの数字は楽観的だった。** ただし**方式の順位は保たれた**ので、
ホスト上で選んだ方式は実機でも正しい選択だった。

**★劣化の仕方が方式によって違う**のが示唆的である:

| 方式 | ホスト→実機の低下 |
|---|---:|
| 両側 A8 | -3.4ポイント |
| `u16×u8` + 入替 | **-17.6ポイント** |

**量子化誤差を小さくした方が、実機での低下が大きい。**
HTP 側に量子化とは別の誤差要因（積和の中間精度・丸め・タイリング）があり、
量子化誤差が大きいうちはそれに埋もれ、小さくすると顔を出す、と解釈できる。
→ **ホスト上で量子化を詰めても実機では頭打ちになる。**

なお **A16W8 素は v68 で動かないので実機値が無い**。
ホストの 85.2% と実機の 63.1% を直接比べるのは誤りで、
**精度面での v68 / v73 の差はこの測定からは出せない**。

### 3.11 その他

- **QNN EP は動的形状を扱えない**。静的形状化と固定長KVキャッシュが必須
- **LPBQ / 16a4w_block は V69以上**で v68 不可。通常の 16a4w は別方式で使用可
- **weight sharing は v73以上**（+SA8295P）。v68 は prefill/decode で重み2重持ち
- **GroupQueryAttention は HTP 非対応**（GPUのみ）。attention は手分解が前提。
  なお**手分解した attention は v68 で通る**ことを P2b で確認済み（C-8 の精度指定は必要）
- **`RotaryEmbedding`（com.microsoft）は converter 段で落ちるが、素の op へ分解すれば通る**
- **`SimplifiedLayerNormalization` はファイルとして持ち込めない**（ORT が内部融合で作る op で、
  標準 opset に存在しない）。「非対応」ではなく「この経路では存在し得ない」。
  RMSNorm は素の op へ分解した形で通るので実害はない
- **ORT 自身の x86 EPContext 生成は v68 で失敗**（未修正）。QAIRT の
  `qnn-context-binary-generator` を使う

## 5. ★判断を誤ったパターン（最も再利用価値が高い）

技術的事実より、**誤りの型**のほうが後で効く。今回 8 件あり、**5つの型**に分類できた。

### 型1: 事例の一般化（3件）

| 誤り | 実際 |
|---|---|
| 「Genie が v73+ を要求する → NPU で LLM は不可」 | Genie 経路の話。**ORT QNN EP は SM8350 を正式サポート**しており別経路がある |
| 「PDメモリ 698MB が v68 の上限」 | **InternVL3-1B の vision encoder** 1件の事例。同じ報告者が後に 1B の推論に成功している。Issue は Closed |
| 「`num_sharding` 24 でも効かない → sharding は無意味」 | その 24 は**失敗した encoder ではなく LLM 側の設定**だった |

**対策**: 「1つの事例」を「一般則」に昇格させない。**出典の対象範囲を確認する。**

### 型2: 版依存の事実を固定化（1件）

| 誤り | 実際 |
|---|---|
| 「MatMulNBits は fp16 Conv2D 依存 → v68 では不可」 | **v2.3 時点の実装詳細**。v2.6.0 で整数QDQ活性化に対応し前提が変わった |

**対策**: 要件定義書 3.3節を【固定事実】と【**バージョン依存事実**】に分離した。
後者は使用版を変えたら再確認する。

### 型3: 実行主体の取り違え（2件）

| 誤り | 実際 |
|---|---|
| 「**シェルから** `dlopen("libcdsprpc.so")` が成功 → ライブラリは使える」 | シェルバイナリは**アプリの名前空間制限の対象外**。アプリには C-7 の宣言が必要 |
| 「`/dev/adsprpc-smd` は other に read がある → DAC の問題ではない…が run-as なら通るはず」 | `run-as` は `runas_app` ドメインで、`untrusted_app` とは権限が違う |

**対策**: **同じ操作でも実行主体が違えば結論は変わる。** 検証は本番と同じ主体で行う。

### 型4: 症状と真因の混同（1件）

| 誤り | 実際 |
|---|---|
| 「`EPContext node is not compatible with any execution provider` → EP の登録方法が悪い」 | 実態は「**DSP に繋がれていない**」。真因は C-7。provider option や soc_model をいくら変えても直らない |

**対策**: エラー文言を額面どおり読まない。**動いている参照実装との差分**を取る。
今回はマニフェストの全文比較で確定した（**もっと早くやるべきだった**）。

### 型5: 文書の読み違い（1件）

| 誤り | 実際 |
|---|---|
| 「`check-python-dependency` の required_packages に `onnx` が無い → QAIRT に onnx は不要」 | required_packages は**そのスクリプトの検査対象**であって全依存の網羅ではない。`qairt-converter` は `import onnx` する |

**対策**: 「リストに無い＝不要」と読まない。**リストが何の一覧なのか**を確認する。

### 番外: 観測手段そのものの誤り

`dd if=/dev/adsprpc-smd bs=1 count=0` の出力を `tail` で絞り、**エラー行を隠したまま
「成功した」と誤判定**した。`dd` は失敗してもサマリ行を出す。

**対策**: 確実な open テストは `exec 3</dev/...`（リダイレクト）か `open(2)` を直接呼ぶ
C プログラム。**サマリだけを見ない。**

### 7.2 次の一手

**本物の Qwen2.5-0.5B を通す。**

P2b で確定したのは「**op は載る**」ことだけである。使ったのは自作の乱数重み・
縮小形状（hidden 128 / 1ブロック / vocab 512）で、**精度は一切測っていない**。

| | P2b で使ったもの | 本物 |
|---|---|---|
| 重み | **乱数** | 学習済み |
| hidden / 層数 / vocab | 128 / **1** / 512 | 896 / 24 / 151,936 |
| キャリブレーション | **乱数と合成パターン** | トークン化した実テキスト |

最初にやるのは **ONNX export して op を数え、手で書いた13個と突き合わせる**こと。
GQA のヘッド複製を `Concat` で書いたが実際は `Expand`/`Tile` かもしれず、マスクも
`Add` ではなく `Where`/`Trilu` かもしれない。**違えば P2b の結果は転用できない。**
（C-8 だけは QK^T / PV がどんな実装でも活性化×活性化なので残る。）

その後 ①実テキストでキャリブレーションして**精度を測る** ②本物の規模で
**容量の壁**（PD / VTCM / SMMU）が出るかを見る。端末もビルドも要らず、
ホスト側だけで進む。モデルはローカルの HF キャッシュに既にある。
