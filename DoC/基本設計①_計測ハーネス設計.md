## 1. 本書の目的と位置づけ

本書は要件定義書 **FR-1（端末プロファイル取得）**と **FR-11（計測）**の実装設計である。

本プロジェクトの成果物は「コードではなく実測記録」であり（要件定義書1.3節）、**計測ハーネスは全フェーズの土台**になる。ここで記録項目を取りこぼすと、後のフェーズで「測り直し」が発生し、しかも端末の温度状態が変わっているため再現できない。したがって**最初に記録スキーマを確定させる**。

**本書は P0-a（端末素性調査）の結果を入力とする。** 4章のデータ源は端末・firmware によって存在するパスが異なるため、`scripts/p0a_collect.sh` の出力を見てから確定する。それ以外の章は端末に依存しないため先に確定させた。

## 2. 設計の前提となる3つの制約

### 2.1 単発実行から結論を出してはならない

EdgeSLM 側の検証で「**初回実行は常に遅く、実装の差ではなくウォームアップ起因のノイズが支配的**」と判明している（EdgeSLM `DoC/基本設計_高速化設計.md` 3.5節②）。EdgeSLM-cpp でも、コールドスタート1回の計測で C++ 版が Python 版より遅く見える現象が観測され、「この数値から速度の結論を出してはならない」と明記されている。

→ **ハーネスは単発測定をAPIとして提供しない。** 必ず「ウォームアップ + 反復 + 統計量」のセットで返す（5章）。

### 2.2 電力プロファイルを制御できない

要件定義書3.4節 C-3 の通り、**unsigned PD では `perf_profile`（burst）・`rpc_control_latency`・電力votes を適用できない**。これを binary に埋め込むとロード自体が失敗する。

→ 本プロジェクトの HTP 測定値は**すべてデフォルト電力プロファイル**での値である。ハーネスは全レコードに `power_profile = "default(unsigned_pd)"` を固定で刻み、**他者の burst 測定値や公称値と混ぜられないようにする**。

### 2.3 USB 接続中は充電による発熱が常に乗る

計測中は adb 接続が必要であり、充電電流による発熱を除去できない。サーマル試験（7章）では特に影響が大きい。

→ **除去できないものは条件として記録する。** 電池残量・充電状態・電池温度を全レコードに含める（6章）。加えてサーマル試験では開始時の電池温度を揃える手順を定める。

## 3. 計測メトリクスの定義

### 3.1 推論性能

| 列名 | 型 | 定義 | 備考 |
|---|---|---|---|
| `ttft_ms` | float | 入力投入から最初のトークン出力までの時間 | LLM のみ。CNN では `latency_ms` を使う |
| `latency_ms` | float | 1回の推論（`Run` 相当）の実時間 | CNN・単体op検証の主指標 |
| `decode_tok_per_s` | float | decode 段のトークン毎秒 | LLM のみ |
| `prefill_tok_per_s` | float | prefill 段のトークン毎秒 | LLM のみ |
| `stage_ms.*` | dict | 段階別の内訳（tokenize / prefill / decode_step / sampling / detokenize） | EdgeSLM の `StageTimer` と同じ粒度に揃え、PC側の値と直接比較できるようにする |

### 3.2 メモリ（要件定義書2.4節の4層を別々に記録する）

| 列名 | 型 | 定義 | 取得不能時の代替 |
|---|---|---|---|
| `rss_peak_mb` | float | プロセスのピーク RSS | — |
| `htp_pd_mb` | float | HTP PD メモリ使用量 | **直接取得できない場合**は `ctx_size_estimate_mb`（QNN/FastRPC ログに出る context size estimate）と `ctx_binary_mb`（context binary のファイルサイズ）を代替指標とする（FR-11） |
| `ctx_binary_mb` | float | context binary のファイルサイズ | — |
| `ctx_size_estimate_mb` | float | ログから抽出した context size estimate | — |
| `shared_weight_mb` | float | shared weight バッファのサイズ | FastRPC/SMMU マッピング失敗の切り分け用（#18862 の事例） |
| `num_sharding` | int | コンテキスト分割数 | — |
| **`dmabuf_total_kb_before` / `_after`** | int | `/proc/meminfo` の `DmaBufTotal`（推論前 / 後） | **PD メモリの代替主指標**（4.7節）。DSP へ渡したバッファ量を差分で観測する |
| **`dmabuf_delta_kb`** | int | 上記の差分 | 同上 |
| `proc_dmabuf_mb` | float | 推論プロセスの `/proc/<pid>/smaps` 上の dma-buf マッピング合計 | アプリ形態になった時点で取得する（4.7節） |

**4層（PD / FastRPC-SMMU / VTCM / システムRAM）を1つの数値に丸めない。** 丸めると「どの層で詰まったか」が失われ、対処（sharding / W4 / `htp_share_resource_optimization`）を選べなくなる。

### 3.3 精度

| 列名 | 型 | 定義 |
|---|---|---|
| `accuracy_metric` | str | 指標名（モデル種別により異なる） |
| `accuracy_value` | float | 値 |
| `reference` | str | 比較対象（例 `pc_fp32_onnxruntime`） |
| `token_match` | bool/int | LLM の場合、PC 参照実装とトークン列が一致した連続ステップ数（7.1節 Gate 判定に使う） |

LLM の正しさ判定は **PC 参照実装とのトークン列完全一致**を主指標とする。EdgeSLM-cpp で有効だった手法であり、KVキャッシュ管理に誤りがあれば数トークンで破綻するため、パイプライン全体の正しさの実質的証明になる。

### 3.4 配置（delegate 状況）

| 列名 | 型 | 定義 |
|---|---|---|
| `nodes_total` | int | ONNX ノード数 |
| `nodes_on_htp` | int | HTP に載ったノード数 |
| `nodes_on_cpu` | int | CPU に落ちたノード数 |
| `cpu_fallback_disabled` | bool | `disable_cpu_ep_fallback=1` で成功したか |
| `unsupported_nodes` | list | 非対応と報告されたノード（op type 単位で集計） |

取得元は実行経路で異なる（要件定義書 FR-5）。

- **QDQ 直接経路**: Framework Op Tracing の `qnn_op_trace.json`（`subgraph_traces` が ONNX→QNN の対応、`unsupported_nodes` がそのまま使える）
- **EPContext 経路**: `qairt-converter` / `qnn-context-binary-generator` の変換・finalize ログ、および `qnn-context-binary-utility` の `--json_file` 出力

### 3.5 熱・クロック

| 列名 | 型 | 定義 |
|---|---|---|
| `temp.<zone>` | float | thermal zone ごとの温度（ミリ℃ → ℃ に正規化） |
| `cpu_freq.<cpuN>` | int | コアごとの現在クロック |
| `cooling.<device>` | int | cooling device の cur_state（スロットリング発動の直接証拠） |
| `battery_temp_c` | float | 電池温度 |

対象ゾーン・デバイスの具体名は **P0-a の結果で確定（4章 TBD）**。

## 4. データ源（P0-a 実測により確定・2026-09-12）

`results/P0a_20260912_150041.txt` の実測に基づき確定した。**非rootで必要な情報はほぼ全て取得できる。**

### 4.1 thermal zone（全71ゾーンが読めた）

`-usr` 接尾のゾーンがセンサ読み出し、`-step` 接尾が段階的な温度緩和ゾーン。**両方とも読めた。**

| 役割 | ゾーン名（`type`） | 採用 |
|---|---|---|
| **NPU（Hexagon / NSP）** | **`nspss-0-usr` / `nspss-1-usr` / `nspss-2-usr`**（`-step` 版もあり） | **必須**。NPU温度を直接観測できる。本プロジェクトの中核指標 |
| CPU 小クラスタ（cpu0-3 / A55） | `cpu-0-0-usr` 〜 `cpu-0-3-usr` | 採用 |
| CPU 大クラスタ（cpu4-7 / A78+X1） | `cpu-1-0-usr` 〜 `cpu-1-7-usr` | 採用 |
| CPU サブシステム | `cpuss-0-usr` / `cpuss-1-usr` | 採用（クラスタ代表値） |
| GPU（Adreno 660） | `gpuss-0-usr` / `gpuss-1-usr` | 採用 |
| メモリ | `ddr-usr` / `pop-mem-step` | 採用 |
| SoC 全体 | `aoss-0-usr` / `aoss-1-usr` | 採用 |
| PMIC / 電池系 | `pm8350_tz` / `pm8350c_tz` / `pm8350b_tz` | 採用（電池温度は `dumpsys battery` を主とし、これは補助） |
| モデム系（多数） | `modem-*` / `mdmss-*` | **除外**（通信の発熱は本検証の対象外。ただし外乱要因として `mdmss-0-usr` のみ記録する） |
| カメラ / ビデオ | `camera-0/1-usr` / `video-usr` | 除外 |

**異常値のフィルタが必須。** 実測で次の値が返るゾーンがあった。サニティチェックを入れ、範囲外は `null` として記録する（「読めたが無効」と「読めない」を区別する）。

| ゾーン | 実測値 | 解釈 |
|---|---|---|
| `pm8350c-bcl-lvl0/1/2` | **-274000**（= -274℃） | 無効値（絶対零度以下）。閾値センサで温度ではない |
| `mx-pe-step` / `cx-pe-step` | **0** | 未初期化または非温度 |
| `modem-mmw2-mod-usr` | **2000**（= 2℃） | 実環境としてあり得ない。無効とみなす |
| `pm8350b-ibat-lvl0` | **-78** | 電流センサであり温度ではない |

採用ルール: **`-50000 〜 150000`（-50〜150℃）の範囲外は無効**として扱う。

|---|---|---|---|

| **NPU(CDSP) ハード緩和** | **`cdsp_hw`** | **1** | **必須** |
| CPU 小クラスタの周波数制限 | `thermal-cpufreq-0` | 15 | 採用 |
| CPU 大クラスタの周波数制限 | `thermal-cpufreq-4` / `thermal-cpufreq-7` | 15 / 18 | 採用 |
| 大クラスタ全体 | `thermal-cluster-4-7` | 18 | 採用 |

### 4.3 CPU クロック

**`scaling_cur_freq` は非rootで読めた**（実測 cpu0=1401600 / cpu4=1881600 / cpu7=960000）。

構成も確定した。**1 + 3 + 4 の典型的な SD888 構成**である。

| コア | 最大 | 最小 | 対応 |
|---|---|---|---|
| cpu0-3 | 1,804,800 | 300,000 | Cortex-A55（小） |
| cpu4-6 | 2,419,200 | 710,400 | Cortex-A78（中） |
| cpu7 | **2,841,600** | 844,800 | Cortex-X1（大） |

governor は全コア `schedutil`。CPU実行の比較時はスレッド数とコア親和性の設計に使う。

### 4.4 GPU

| 項目 | パス | 結果 |
|---|---|---|
| モデル | `/sys/class/kgsl/kgsl-3d0/gpu_model` | **`Adreno660v2`**（読めた） |
| 稼働率 | `/sys/class/kgsl/kgsl-3d0/gpubusy` | **読めた**。2値（busy, total）が返るので差分から利用率を算出する |
| クロック | `gpuclk` / `devfreq/cur_freq` / `clock_mhz` | **いずれも読めない**（非root不可） |

→ GPUクロックは諦め、`gpubusy` の差分を利用率として記録する。

### 4.5 メモリ

| 項目 | 取得元 | 実測値 |
|---|---|---|
| 物理メモリ | `/proc/meminfo` `MemTotal` | 7,370,900 kB ≒ **7.03 GiB**（公称8GB） |
| 利用可能 | `MemAvailable` | 3,021,052 kB ≒ **2.88 GiB**（測定時点） |
| **zram スワップ** | `SwapTotal` / `SwapFree` | **4,194,300 kB ≒ 4.0 GiB** / 3,234,456 kB |

**`MemAvailable` が約2.9GiBしかない点は重要。** 要件定義書 R-3 の「prefill/decode で重みを2重持ち（0.6B W8 で約1.2GB）」は収まるが、**3Bクラスは物理的に不可能**であることが実測で確定した。測定前に `MemAvailable` を記録し、**2.0GiB 未満なら測定を中止する**（スワップに落ちて値が無意味になるため）。

### 4.6 電池・環境条件

`dumpsys battery` から取得する。実測値の形式は次の通り。

| 項目 | 実測値 | 備考 |
|---|---|---|
| `level` | 50 | 残量% |

### 4.7 HTP PD メモリ：ゲージは無いが dma-buf 会計で代替観測できる

**PD メモリの総容量・残量を直接示すノードは存在しない。** `/sys/kernel/debug/ion/heaps` と `/sys/kernel/debug/dma_buf/bufinfo` はいずれも非rootで読めず（debugfs）、`/dev/adsprpc-smd` 経由の取得も SELinux で阻まれる（4.8節）。

**ただし、DSP へ渡すバッファは dma-buf(ION) として確保されるため、その量は観測できる。**

| 取得元 | 実測 | 用途 |
|---|---|---|
| **`/proc/meminfo` の `DmaBufTotal`** | **800,840 kB（≒782 MiB）** | **システム全体の dma-buf 確保量。context ロード前後の差分が、DSP に渡したバッファ量の実質的な測定値になる**（主指標） |
| `/proc/<pid>/smaps` の dma-buf マッピング | 読める（shell 自プロセスで37件一致） | **自プロセス単位**の dma-buf マッピング量。アプリ形態になれば推論プロセスの内訳が取れる |
| `/sys/kernel/boot_cdsp` | 存在する | CDSP の起動状態 |
| `/sys/class/devlink/...msm_fastrpc_compute_cb*` | `cb1` 〜 `cb14` を確認 | **FastRPC の SMMU コンテキストバンク**。#18862 の「shared weight の SMMU マッピング失敗」を切り分ける際の前提情報（同時に確保できる FastRPC コンテキスト数の上限に関わる） |

**`DmaBufTotal` の差分測定における注意**: システム全体の値なので、他プロセス（主にグラフィクス）の増減がノイズになる。画面消灯・アイドル状態で測り、複数回の差分の中央値を取る。ベースライン（推論前）を必ず同一セッション内で記録する。

→ 結論として、3.2節のメトリクスに **`dmabuf_total_kb`（推論前/後）と `dmabuf_delta_kb`** を追加する。これに context binary サイズ・RSS・（失敗時の）ログ上の `context size estimate` を合わせれば、**「どの層で詰まったか」の切り分けに必要な情報は揃う**。

**留保**: 本節の結論は「adb shell から sysfs / procfs を探索した範囲」での判断である。**R-9 により QNN バックエンド自体をまだ一度も初期化できていない**ため、QNN のログや API（`QnnBackend_getBuildId` 系、プロファイリング出力など）がメモリ情報を出すかは未評価である。未決事項#14 が解決してアプリ文脈で QNN を動かせるようになった時点で、**本節は再評価の対象とする**。

### 4.8 ★FastRPC は `adb shell` からアクセスできない（P0-c 実測）

`results/P0c_*.txt` の実測結果。

```
uid=2000 gid=2000
OPEN FAIL  /dev/adsprpc-smd  (O_RDONLY) errno=13 Permission denied
OPEN FAIL  /dev/adsprpc-smd  (O_RDWR)   errno=13 Permission denied
DLOPEN OK  libcdsprpc.so  (remote_handle64_open / remote_handle_open / remote_session_control いずれも found)
DLOPEN FAIL /vendor/lib64/libSNPE.so  -> library not found
```

- デバイスノードの権限は `crw-rw-r-- system:system` であり、**DAC 上は other に read がある**。にもかかわらず `O_RDONLY` すら EACCES になる → **拒否は SELinux による**（`shell` ドメインに当該デバイスタイプへのアクセス権がない。`avc: denied` は dontaudit されておりログに出ない）
- `libcdsprpc.so` は `/vendor/etc/public.libraries.txt` に登録されているため dlopen でき、FastRPC の API シンボルも見える。**ライブラリは使えるがデバイスが開けない**という状態
- `libSNPE.so` は同リストに無いため dlopen できない（端末に preinstall されているが、アプリ/シェルからは使えない）

**計測ハーネスへの影響**: ハーネスの端末側アクセス（`device.py`）は **sysfs の読み出しと `dumpsys` に限定される**ため、この制約の影響を受けない。影響を受けるのは**推論そのものの実行形態**であり、要件定義書側の課題として扱う（成果物の形＝CLI かアプリか）。

## 5. 測定プロトコル

2.1節の制約から、**単発測定を禁止**し次の手順を標準とする。

```
1. 冷却待機   : 電池温度が基準値（既定 32℃）以下になるまで待つ。超過なら待機し、
                待機時間も記録する。サーマル試験前は必須
2. ウォームアップ : N_warmup 回（既定 3）実行し、結果を破棄する
3. 本計測     : N_iter 回（既定 10）実行し、全サンプルを保持する
4. 統計量     : median / p90 / min / max / stddev を算出する。**平均は主指標にしない**
                （初回の外れ値に引きずられるため）
5. 順序入替   : 複数経路（CPU fp32 / CPU int8 / HTP）を比較する場合、実行順を
                入れ替えた2周目を必ず行う。順序効果（先に走った方が冷えている）を検出する
```

**生サンプルを必ず残す。** 統計量だけ残すと、後から「外れ値1個に引きずられていた」ことを検証できない。

## 6. 全レコードに付与する測定条件（NFR-6 / NFR-7）

以下は**例外なく全レコードに付ける**。1つでも欠けると後から比較可能性を判断できない。

| 列名 | 内容 |
|---|---|
| `timestamp` | 取得時刻（ISO 8601） |
| `phase` | どのフェーズの測定か（P1 / P2 / P2b / P3 / P4 / P5 / P6） |
| `baseline` | 使用した版の組（例 `qairt=2.48.0.260626, ort=1.27.0`）。要件定義書3.2節の4本のどれか |
| `power_profile` | **`default(unsigned_pd)` 固定**（2.2節） |
| `battery_level` / `battery_status` / `battery_temp_c` | 電池残量・充電状態・電池温度（2.3節） |
| `warmup_n` / `iter_n` | ウォームアップ回数・本計測回数 |
| `device_uptime_s` | 直前に再起動したかの判別用 |
| `ambient_note` | 室温など手入力のメモ（任意だが推奨） |

`power_profile` を固定値として機械的に刻むのは、**将来この数値を他者の burst 測定値と比較しそうになったときのブレーキ**である。

## 7. サーマル試験の手順（FR-11・2回実施）

| 実施時期 | 対象 | 内容 |
|---|---|---|
| **P3** | CNN（A16W8） | CPU fp32 / CPU int8 / HTP の3経路で5分連続推論 |
| **P5完了後** | 実SLM | Qwen2.5-0.5B の連続 decode で再実施。**P3 の結果を流用しない**（単一opやCNNの発熱とLLMの連続decodeは挙動が異なる） |

手順:

1. 開始条件を揃える（5章の冷却待機。開始時の電池温度を記録）
2. 連続推論を 5 分間実行
3. **1秒間隔**で全 thermal zone・cooling device・CPUクロック・推論レイテンシを記録
4. 出力は「経過秒数 × 各指標」の時系列。**スロットリング発動点**（cooling device の `cur_state` が 0 から変化した時刻、またはレイテンシが定常値から逸脱した時刻）を特定して記録する

## 8. ハーネスの構成

責務を分け、**端末に触る層を1箇所に閉じ込める**。

```
scripts/p0a_collect.sh        端末素性の一括取得（P0-a。実装済み）
  ↓ 出力を本書4章の確定に使う

app/harness/device.py         adb 越しの端末アクセスを集約（getprop / sysfs 読み / dumpsys）
app/harness/sampler.py        指定間隔で 3.5節の指標をサンプリングする
app/harness/protocol.py       5章のプロトコル（冷却待機・ウォームアップ・反復・統計量）
app/harness/record.py         6章の条件を自動付与し JSONL へ追記
app/harness/report.py         JSONL → 集計表 / 時系列グラフ
```

出力形式:

- **生データ**: `results/<phase>/<timestamp>.jsonl`（1行1サンプル。全サンプル保持）
- **集計**: `results/<phase>/<timestamp>_summary.csv`
- **記録文書**: `DoC/フェーズ記録_Pn.md`（人が読む考察。数値は上記から引用）

`device.py` 以外は端末に直接触らない。これにより、後で計測対象が CNN から LLM に変わっても、また取得パスが端末更新で変わっても、変更箇所が `device.py` と4章の設定に限定される。
