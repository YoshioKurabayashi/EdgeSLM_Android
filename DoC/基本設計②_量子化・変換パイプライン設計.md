## 1. 本書の目的と位置づけ

本書は **ホストPC側で「fp32 ONNX を SM8350/v68 で動く context binary に変換する」工程**の実装設計である。要件定義書の FR-4（パイプライン確立）・FR-6（Transformer 構成要素の重点検証）・FR-7（MatMulNBits 単体試験）・FR-13（量子化方式の段階的評価）に対応する。

**本書の範囲は端末に触らない。** 端末側の実行形態（CLI かアプリか。要件定義書 R-9 / 未決事項#14）は本書の対象外であり、P1 の結果を見て基本設計③として別途設計する。この分離により、#14 の結論がどちらに転んでも本書の内容は影響を受けない。

### 1.1 設計の出発点

本書は推測ではなく**2つの実証済み情報**から出発している。

1. **ZipDepth の変換スクリプト一式**（`tools/variants/`）— SM8350/v68 向けに A16W8 の CNN を変換し、**出荷済みの動作する context binary をバイト同一に再生成できる**ことが検証されているパイプライン。その README には「violating any of these produces binaries that fail `QnnContext_createFromBinary` with error 1002 on device」として禁止事項が明記されている（要件定義書3.4節 C-1〜C-5 に転記済み）
2. **QAIRT 2.48.0.260626 の実機確認**（2026-09-12）— `qairt-converter` / `qnn-context-binary-generator` / `qnn-context-binary-utility` がホストで起動することを確認済み。`get_qnn_qdq_config` の実パラメータも実環境で確認済み

## 2. 設計の前提となる3つの制約

### 2.1 C-1〜C-6 は「守るべき指針」ではなく「守らないと動かない絶対条件」

要件定義書3.4節の禁止事項は、違反すると**端末でのロード時に `error 1002` で落ちる**。しかもエラーは変換時ではなく**端末に持っていった後**に出るため、違反に気付くのが遅い。

→ **本パイプラインは各工程の出口で C-1〜C-6 を機械的に検証する**（5章）。人間のレビューに委ねない。

### 2.2 Python 環境が2つに分かれている

要件定義書3.2節の通り、**量子化は本体環境（onnxruntime）、変換は QAIRT 専用環境（Python 3.10）**で行う。両者は numpy / opencv のバージョンが共存不可能である。

→ **パイプラインは1本のスクリプトで完結させず、環境境界で明確に分割する**（3章・4章）。境界をまたぐのは**ファイル（ONNX / DLC / bin）だけ**とし、Python オブジェクトを受け渡さない。

### 2.3 LLM は CNN と同じ形では扱えない

ZipDepth は「1入力1出力の固定形状 CNN」であり、`session.run()` 1回で完結する。LLM は prefill / decode の2グラフに分かれ、KVキャッシュの入出力を持ち、動的形状が許されない（要件定義書3.3.2節#11）。

→ **CNN で確立した工程をそのまま LLM に流用しない。** 6章で Transformer 構成要素を個別に通してから、7章で prefill / decode のグラフ設計に進む。

## 4. 工程ごとの詳細設計

### S1: fp32 ONNX の用意

| 対象 | 入手方法 | 形状 |
|---|---|---|
| **小型CNN / BERT系**（P2の足場） | 既存資産（XiaozhiServer の BERT 意図分類器）または torchvision の小型モデル | 固定形状 |
| **Qwen2.5-0.5B**（P4以降） | HF から取得し、**prefill / decode を別グラフとして export** | 固定形状（バッチ1固定・固定長KVキャッシュ） |

**LLM の export 方針**（詳細は基本設計④で扱うが、本書の前提として記す）

- **fused GQA を生成させない**（要件定義書 R-4）。`GroupQueryAttention` は HTP 非対応のため、export 時に素の `MatMul` / `Softmax` / `MatMul` 列として出させる。生成されてしまった場合は分解する
- KVキャッシュは**固定長**。EdgeSLM Phase A の `app/pipeline/kv_cache.py` を仕様の参照元とする
- 動的次元は一切残さない（バッチ・シーケンス長・KV長のすべてを固定値に）

### S2: 前処理

```python
# app/pipeline/preprocess.py
fold_batchnorm(src_fp32, folded)          # C-5 対策。BatchNormalization を Mul+Add へ
quant_pre_process(folded, prepped,        # shape inference + optimization
                  skip_optimization=False,
                  skip_symbolic_shape=False)
```

`fold_batchnorm` は ZipDepth の実装を踏襲する。各 `BatchNormalization` ノードについて

```
scale = gamma / sqrt(var + eps)
shift = beta - mean * scale
```

を計算し、`(1, C, 1, 1)` 形状の initializer として `Mul` → `Add` に置換する。

**出口検証**: モデル内に `BatchNormalization` が1つも残っていないこと（C-5）。

#### 補足1: BN 畳み込みの数学的根拠

推論時の BatchNorm は `gamma` / `beta` / `mean` / `var` すべてが定数であり、**チャネルごとの一次式に還元できる**。

```
y = gamma * (x - mean) / sqrt(var + eps) + beta
  = scale * x + shift      where  scale = gamma / sqrt(var + eps)
                                  shift = beta - mean * scale
```

したがって `Mul(scale)` → `Add(shift)` の2ノードで等価に置換できる。`scale` / `shift` は `(1, C, 1, 1)` 形状の initializer として持たせる（NCHW のチャネル方向ブロードキャスト）。`eps` はノード属性から読む（既定 1e-5）。

**これは最適化ではなく「通すために必須」の措置である。** QNN HTP は signed per-channel の Conv QDQ と BatchNorm の併存を拒否し **error 3110** になる（C-5）。

**適用範囲の注意**: BatchNorm は Conv 系 CNN 固有である。**Transformer（LLM）は LayerNorm / RMSNorm を使うため C-5 は該当しない見込み**で、S2 の BN 畳み込みが効くのは主に P1 / P2 の CNN 段階である。

#### 補足2: `quant_pre_process` が行う3つの処理

| 処理 | 内容 | 本パイプラインでの意味 |
|---|---|---|
| symbolic shape inference | 全テンソルの形状を推論して埋める | **量子化器は形状を知らないと Q/DQ を正しく置けない**。特に per-channel 量子化はチャネル軸を形状から決めるため、形状欠落は失敗または不適切な配置を招く |
| グラフ最適化（定数畳み込み等） | 定数で決まる部分を事前計算し冗長ノードを削除 | **計算されずに残った float の小島が C-1 違反の原因になる**。ここで畳んで残存 float を減らす |
| ONNX shape inference + checker | 整合性の確認 | 壊れたモデルを量子化工程へ入れない |

**順序は「BN 畳み込み → `quant_pre_process`」とする。** 畳み込みで生まれた `Mul`/`Add` を定数畳み込みがさらに簡約できるため、また形状推論は最終トポロジに対して走らせるべきため。

#### ★補足3: 最適化でノード名・テンソル名が変わる（S4 への影響）

`quant_pre_process` のグラフ最適化は**ノード名・テンソル名を変更・統合する**。S4 の `init_overrides` は**テンソル名を指定して精度を上書きする**仕組みなので、

> **`init_overrides` に渡す名前は、必ず `quant_pre_process` の「後」のモデルから取得する。**

元の fp32 モデルから名前を拾うと一致せず、**上書きが黙って無効になる**（エラーにならないため気付きにくい）。実装では `quant_pre_process` 後のモデルを走査して対象ノード（RMSNorm / LayerNorm / MatMul 等）を特定し、その出力テンソル名を `init_overrides` のキーにする。この手順は未決事項#2 の回答の一部である。

### S3: キャリブレーションデータ生成

`CalibrationDataReader` を実装する。**キャリブレーションは実行時の入力分布を模倣する**のが原則。

| 対象 | 設計 |
|---|---|
| CNN（ZipDepth 再現時） | ZipDepth の方式を踏襲: 実画像 + augment（crop / flip / brightness / gamma / noise）+ **合成パターン**（単色0.0〜1.0・勾配・市松模様） |
| BERT系 | 実際の発話データから抽出したトークン列 |
| **LLM** | 代表的なプロンプトの埋め込み/活性化を通す。**range-pinning 用の合成入力も混ぜる**（活性化の最大値を取りこぼすと精度が崩れるため） |

**合成パターンを必ず混ぜる。** 実データだけでは活性化の値域の端が現れず、MinMax キャリブレーションが過小な範囲を学習してしまう。ZipDepth が合成パターンを入れているのはこの理由と解釈する。

### S4: QDQ 量子化（本工程の中核）

```python
# app/pipeline/quantize_qdq.py
from onnxruntime.quantization import quantize, QuantType, CalibrationMethod
from onnxruntime.quantization.execution_providers.qnn import get_qnn_qdq_config

cfg = get_qnn_qdq_config(
    prepped_model,
    calibration_data_reader,
    calibrate_method=CalibrationMethod.MinMax,
    activation_type=QuantType.QUInt16,   # A16（A8 にするときは QUInt8）
    weight_type=QuantType.QInt8,         # W8（per-channel signed）
    per_channel=True,
    init_overrides=overrides,            # op単位の精度指定（下記）
)
quantize(prepped_model, out_qdq, cfg)
```

**`quantize_static` に op リストを手で渡す形は使わない。** `get_qnn_qdq_config` は QNN EP 向けの制約を織り込んだ設定を生成するため、これを通さないと既定の op 集合で float セグメントが残り C-1 に違反する。

#### op 単位の精度指定（`init_overrides`）

要件定義書3.3.2節#17c / #17d の混合精度機構を使う。**v68 で危険な箇所を個別に落とす**のが目的。

| 対象 | 指定 | 根拠 |
|---|---|---|
| **LayerNorm / RMSNorm** | **16a16w にしない**（A16W8 または 16a4w 相当へ） | 16bit活性化×16bit重みの matmul は **V73以上**。ExecuTorch の v68 recipe も LayerNorm を 16a16w から落とすことで解決している（要件定義書3.3.1節#5・#6） |
| MatMul | A16W8 を基本。精度が出ない層のみ個別に調整 | HTP の `MatMul` 対応型は (uint8,uint8) / (uint8,uint16) / (uint16,uint8)（#17b） |
| KVキャッシュの入出力 | 個別指定（8bit を検討） | ExecuTorch の v68 recipe が custom key-value アノテーションを入れている |
| **LPBQ / block quantization** | **使わない** | V69以上（#9）。conv2d block quantization を無効化するのが v68 の正解 |

**出口検証（C-1）**: 最重要。5.1節で定義する。

### S5: qairt-converter

QAIRT 環境で実行する。

```
qairt-converter --input_network <qdq.onnx> \
                --preserve_io_datatype \
                --output_path <x.dlc>
```

`--preserve_io_datatype` はグラフ I/O を float32 に保ち、内部を完全な固定小数点にする。**完全QDQに対してのみ付ける**（C-4）。float 混在グラフに付けると「変換不可能な fp32 op」が出力され finalize が 1002 で落ちる。

### S6: qnn-context-binary-generator

```
qnn-context-binary-generator --dlc_path <x.dlc> \
    --backend <QAIRT>\lib\x86_64-windows-msvc\QnnHtp.dll \
    --binary_file <tag>_ctx \
    --output_dir <dir> \
    --htp_socs sm8350
```

**`--htp_socs sm8350` 以外のターゲット指定をしない**（C-2）。また **backend_extensions の config を渡さない**（C-3）。

- `soc_id: 30` を刻むと、**unsigned PD は DSP の SoC id を照会できない**ためロードが拒否される
- `devices`/`cores` セクション（`perf_profile: burst`、`rpc_control_latency`）を埋め込むと、**unsigned PD は power config を適用できない**ためロードが拒否される

**この制約の副作用として、本プロジェクトでは電力プロファイルを burst にできない。** 性能測定値はすべてデフォルトプロファイルでの値になる（基本設計① 2.2節・6章）。

### S7: メタデータ抽出と検証

```
qnn-context-binary-utility --context_binary <bin> --json_file <meta.json>
```

`meta.json` から `socModel` と graph I/O の型を読み、C-2 を機械的に確認する。

### S8: EPContext ONNX ラッパー

**第一候補は ORT 公式スクリプト**（要件定義書3.3.2節#23）。

```
python <ORT>/tools/qnn/gen_qnn_ctx_onnx_model.py -b <ctx.bin> -q <meta.json>
```

QNN 生成の context binary は **channel-last レイアウト・8/16bit I/O** のため、このスクリプトが Cast / Transpose / Q/DQ を**必要な分だけ自動挿入**する。

公式スクリプトで期待する形にならない場合は、**既知正解スキーマの自前ラッパーに切り替える**（ZipDepth の `wrap_epctx.py` が採っている形）。

| 属性 | 値 |
|---|---|
| ノード | `EPContext`（domain `com.microsoft`） |
| `embed_mode` | 1 |
| `ep_cache_context` | context binary のバイト列 |
| `ep_sdk_version` | `"2.48.0"`（使用する QAIRT に合わせる） |
| `main_context` | 1 |
| `partition_name` | `"QNNExecutionProvider_QNN_0"` |
| `source` | `"QNNExecutionProvider"` |
| I/O | float32、**batch は 1 に固定** |
| `ir_version` | 9 |
| opset | `("", 17)` + `("com.microsoft", 1)` |

## 5. C-1〜C-6 の機械的検証（本設計の要）

`app/pipeline/verify_artifacts.py` に実装する。**各工程の直後に実行し、失敗したら次工程へ進ませない。**

### 5.1 C-1: float セグメントの残存ゼロ（最重要）

**判定方法**: QDQ ONNX を読み、次を確認する。

1. グラフ I/O を除く**すべての中間テンソルが整数型**であること（`QuantizeLinear` の出力から `DequantizeLinear` の入力までが整数で繋がっている）
2. `QuantizeLinear` / `DequantizeLinear` / 入出力境界の `Cast` **以外のノード**が、float 型のテンソルを入力または出力に持たないこと
3. 例外として許す float は **scale（Q/DQ の第2入力）と bias** のみ

違反ノードがあれば**そのノード名と op type を列挙して失敗させる**。「どこが float のままか」が分からないと直せないため、件数だけ返すのは不可とする。

### 5.2 C-2: socModel == 0

`qnn-context-binary-utility` の `--json_file` 出力を読み、`socModel` が **0** であることを確認する。30 等が入っていたら失敗。あわせて graph I/O が float32 であることも確認する。

### 5.3 C-3: backend_extensions config を渡していない

生成コマンドラインを記録し、`--config` / `--backend_extensions` 系の引数が**含まれていない**ことを確認する。マニフェスト（S9）の `commands` に対する検証として実装する。

### 5.4 C-4: `--preserve_io_datatype` の前提充足

`--preserve_io_datatype` を付けた変換について、その入力 QDQ モデルの **C-1 が pass していること**を確認する。C-1 未検証のモデルに付けた場合は失敗とする。

### 5.5 C-5: BatchNormalization の残存ゼロ

S2 の出口および QDQ モデルの両方で `BatchNormalization` が0件であることを確認する。

### 5.6 C-6: `extractNativeLibs == true`（アプリ化する場合のみ）

本書の範囲外（端末側）だが、チェックの一覧性のため記す。

**判定方法**: ビルドした APK のマニフェストを `aapt2 dump xmltree --file AndroidManifest.xml <apk>` で読み、**`android:extractNativeLibs="true"`** であることを確認する。これは `packaging { jniLibs { useLegacyPackaging = true } }` の設定結果である。

**APK 内の `.so` の圧縮方式（STORED / DEFLATED）で判定してはならない。** ZipDepth の実 APK を検証した結果（2026-09-12）、`.so` は **DEFLATED（圧縮）** で格納されているが `extractNativeLibs=true` のため**インストール時に実ファイルとして展開され**、正常に動作している。見るべきはマニフェストであって圧縮方式ではない。

## 6. Transformer 構成要素の重点検証（FR-6 / P2b の設計）

> **【2026-09-12 実施結果】** 本節の計画で 13種の単体 op を S1〜S8 に通した。
> 結論: **v68 の壁は「活性化 × 活性化の MatMul を 16bit で受け付けない」1点だけ**。
> attention の QK^T と PV に直撃するが、**その2箇所のみ A8 に落とせば通る**。
> 実装は `app/pipeline/make_op_models.py` / `p2b_ops.py` / `scripts/p2b_build_ops.sh`、
> 結果は [results/P2b_20260912_op_matrix_host.md](../results/P2b_20260912_op_matrix_host.md)。
> 6.1節の表は**当初の計画**として残す（着目点の設定が妥当だったかを後から検証できるように）。

Transformer を丸ごと変換して失敗すると、数百〜数千ノードから原因を探すことになる。**構成要素を個別に通してから組み上げる。**

### 6.1 検証単位と順序

各要素について「**単体の最小 ONNX を作り、S2〜S7 を通し、端末で実行できるか**」を確認する。判定は「①そのまま通る ②分解すれば通る ③通らない」の3値。

| # | 要素 | 優先 | 着目点 |
|---|---|---|---|
| 1 | **MatMul** | 最高 | 精度組合せ (uint8,uint8) / (uint8,uint16) / (uint16,uint8) ごとの可否。本線 A16W8 の成立確認 |
| 2 | **RMSNorm**（`SimplifiedLayerNormalization`） | 最高 | **16a16w にならないこと**を `init_overrides` で保証できるか。ORT の RMSNorm fusion（#18）が v68 で通るか |
| 3 | **LayerNorm** | 高 | 同上。rank 不整合時の `LN → Mul + Add` 分解（#11 v2.4.0）の挙動 |
| 4 | **RoPE**（`RotaryEmbedding`） | 高 | `QNN_OP_ROPE`（#18）が v68 で通るか |
| 5 | **Softmax** | 中 | 出力 encoding の扱い（#18 v2.5.0 の修正） |
| 6 | **Attention 全体** | 高 | **fused GQA は使えない**（#19）ため MatMul/Softmax/MatMul への手分解で成立するか |
| 7 | **KVキャッシュ I/O** | 高 | 固定長での入出力構成。concat / slice が整数型で通るか |
| 8 | **Gather / Transpose / Reshape** | 中 | 形状操作が整数テンソルで通るか |
| 9 | **Transformer 1ブロック** | — | **P2b Gate**。上記を組み合わせて1ブロックを HTP に完全 delegate できること |

### 6.2 MatMulNBits 単体試験（FR-7）

**複数バージョンで試す。** 要件定義書3.3.2節#16・#17 の通り、v2.3 の HTP 実装は fp16 Conv2D を経由するが **v2.6.0 で整数 QDQ 活性化に対応**した。

| baseline | 期待 |
|---|---|
| QAIRT 2.48.0.260626 + 旧 QNN EP | fp16 経路のため **失敗する可能性が高い** |
| **QAIRT 2.50.40 + onnxruntime-qnn v2.6.0** | **uint16/int16 QDQ 活性化が使えるため成立する可能性がある** |

2bit / 4bit、block size 32 / 64 の組合せで試す（8bit は公開仕様として前提にしない）。**結果は版ごとに記録する。** 本線は A16W8 なので、失敗しても計画は止まらない。

## 7. 量子化方式の段階的評価（FR-13）

**精度と実現性の両方を、1方式ずつ動かしてから次へ進む。**

```
① A16W8（QUInt16 活性化 / QInt8 重み per-channel）  ← 本線。公式ドキュメントの標準例と一致
      ↓ 精度・速度・メモリを記録
② A8W8（QUInt8 / QInt8）
      ↓ 精度低下と速度改善を測る
③ 混合 A8/A16（init_overrides + convert で領域分割）
      ↓
④ W4  ← 別枝。必須マイルストーンではない
```

### W4 の位置づけ

要件定義書 FR-13 の通り、W4 は **①Context/PD/FastRPC 制約が顕在化した場合の回避候補 ②decode の重み帯域律速に対する性能最適化**である。v68 で取りうる経路は限られる。

| 経路 | v68 での見込み |
|---|---|
| ORT `MatMulNBits` | 従来の「fp16依存ゆえ不可寄り」は撤回。**2.50系で再評価**（6.2節） |
| ORT LPBQ | **不可**（V69以上） |
| ExecuTorch 16a4w（per-channel） | 可能性あり（v68 での使用実例がある） |
