## 1. 本書の目的

**端末上で推論を実行する器**を設計する。基本設計②がホスト側（モデルを作る）、基本設計①が計測（測る）を扱うのに対し、本書は**実行**を扱う。

### 1.1 なぜアプリが必要になったか

2026-09-12 の実測により、**HTP(NPU) は `untrusted_app` ドメインのプロセスからしか使えない**ことが確定した。

| 実行主体 | SELinux ドメイン | `/dev/adsprpc-smd` |
|---|---|---|
| `adb shell` | `u:r:shell:s0` | 拒否 |
| `run-as <pkg>` | `u:r:runas_app:s0` | 拒否 |
| **アプリ本体プロセス** | **`u:r:untrusted_app:s0`** | **open 成功** |

したがって `adb shell` から直接起動するネイティブ CLI では NPU に届かない。**推論コードをアプリプロセスの中で動かす**必要がある。

### 1.2 当初目標との関係

本プロジェクトの最終目標は「**C++ で作成した推論サービスを搭載**して軽量 SLM をローカル完結で動かす」ことであり、**JNI 経由で C++ 推論コアをアプリプロセス内で動かす構成はその目標形そのもの**である。変わるのは起動の外形だけで、中身（C++ 推論サービス）は変わらない。

**UI は作らない。** 画面を持たない Service だけの「殻」を1枚被せ、adb から駆動する。

## 2. 設計の主軸：再ビルドを要する変更を最小化する

### 2.1 なぜこれが主軸なのか

Claude Code の実行環境では **JVM プロセスが外部通信できない**ため、**Gradle ビルドだけは代行できない**（環境構築記録4.2節）。つまり **APK を作り直すたびにユーザーの手を止める**。

一方、本プロジェクトは性質上 **何十回と試行を繰り返す**（量子化方式を変える、モデルを変える、反復回数を変える、op を1つずつ試す…）。**毎回ビルドが要るなら検証が回らない。**

→ **「何を変えたら再ビルドが必要か」を設計時に決め打ち、変更頻度の高いものを全て APK の外に出す。**

### 2.2 再ビルドの要否（設計の到達目標）

| 変更内容 | 再ビルド | 手段 |
|---|---|---|
| **モデルの差し替え**（variant / 量子化方式 / サイズ / CNN↔LLM） | **不要** | `adb push` で外部ファイルディレクトリへ置く（4.3節） |
| **実行パラメータ**（反復回数・ウォームアップ数・スレッド数・EP オプション・プロンプト） | **不要** | ジョブ仕様 JSON を push、または Intent の extras（5章） |
| **計測項目・集計・グラフ** | **不要** | ホスト側（基本設計① のハーネス）で行う |
| 実行するシナリオの追加（単発推論 / 反復ベンチ / op単体検証 / 生成） | **不要** | ジョブ仕様の `task` で切り替える（5.2節） |
| C++ 推論コアのロジック変更 | **必要** | — |
| JNI 境界（関数シグネチャ）の変更 | **必要** | — |
| QNN ランタイムや ORT の版上げ | **必要** | — |

**→ したがって JNI 境界とジョブ仕様は、最初に「広めに」決めておく。** ここを狭く作ると後で必ず再ビルドが要る。

### 3.1 プロセス構成

**ZipDepth のようなカメラ分離は不要**なので、**単一プロセスとする**。ZipDepth が2プロセスに分けているのは Camera2 のバッファ所有権を QNN プロセスから切り離すためで、カメラを使わない本プロジェクトには当てはまらない。

ただし **Foreground Service にする**。バックグラウンド実行制限と、長時間の連続推論（サーマル試験は5分）中に OS に殺されないようにするため。

## 4. 端末上のファイル配置

### 4.1 3種類のパスを使い分ける

| 用途 | パス | 誰が書けるか | 理由 |
|---|---|---|---|
| **モデル・ジョブ仕様・結果** | `/sdcard/Android/data/org.edgeslm.runner/files/` | **adb shell とアプリの両方** | shell は `ext_data_rw`(gid 1078) を持つため書け、アプリは `getExternalFilesDir()` で読める。**再ビルドなしでモデルを差し替えられる唯一の現実的な経路** |
| **QNN ランタイム(.so)** | `<nativeLibraryDir>`（APK から展開） | インストーラのみ | **FastRPC が V68 skeleton に実ファイルパスを要求する**（C-6）。`backend_path` にこのディレクトリの `libQnnHtp.so` を渡す |
| アプリ内部データ | `getFilesDir()` | アプリのみ | 一時ファイル等 |

### 4.2 なぜ `/data/local/tmp` を使わないか

`/data/local/tmp` は `shell` ユーザーのもので、**アプリ（uid 10xxx）からは読めない**。`run-as` 経由でコピーする手もあるが、`run-as` は `runas_app` ドメインで制約が多く、大きなモデルのコピーも非効率である。**外部ファイルディレクトリを使うのが正解。**

### 4.3 ディレクトリ構成（端末側）

```
/sdcard/Android/data/org.edgeslm.runner/files/
├── models/
│   ├── <tag>_epctx.onnx        基本設計② S8 の成果物
│   └── <tag>_manifest.json     同 S9（使用版・量子化設定・C-1〜C-5 の検証結果）
├── jobs/
│   └── job.json                ジョブ仕様（5.2節）
├── inputs/
│   └── <任意の入力データ>        テンソル・プロンプト・トークン列
└── out/
    ├── results.jsonl           1行1サンプルの生データ（基本設計① 8章）
    └── run_<timestamp>.log     実行ログの写し
```

## 5. 制御インターフェース

### 5.1 方式の選択

| 方式 | 評価 |
|---|---|
| **Foreground Service + ジョブ仕様ファイル**（採用） | ジョブ内容が複雑でも Intent の extras 制限を受けない。ホストは push → 起動 → pull の3手で済む。**長い反復測定をアプリ側で完結させられる**（基本設計① 5章のプロトコルをアプリ内で回す） |
| Intent extras のみ | 簡単だが、`init_overrides` のような構造化パラメータを渡しづらい。**短いパラメータの上書き用として併用**する |
| ローカルソケット + `adb forward` | ホストから同期的に駆動でき、トークンのストリーミングにも向く。**ただし初期段階では過剰**。P4/P5 で生成の逐次観測が必要になった時点で追加する（未決事項#3） |
| BroadcastReceiver | 長時間処理に不向き |

### 5.2 ジョブ仕様（`job.json`）

**ここを広めに設計することが、再ビルド回数を減らす鍵である。**

```json
{
  "job_id": "p2b_matmul_a16w8_001",
  "task": "bench",
  "model": "models/matmul_a16w8_epctx.onnx",
  "ep": {
    "provider": "QNN",
    "backend": "libQnnHtp.so",
    "options": {
      "offload_graph_io_quantization": "0",
      "qnn_context_priority": "high"
    },
    "session": {
      "disable_cpu_ep_fallback": "1",
      "intra_op_num_threads": 1,
      "graph_optimization_level": "all",
      "log_severity_level": 2
    }
  },
  "protocol": {
    "warmup": 3,
    "iterations": 10,
    "cooldown_battery_temp_c": 32.0,
    "duration_s": null
  },
  "input": { "kind": "random", "shape": [1, 3, 384, 384], "dtype": "float32", "seed": 0 },
  "output": { "results": "out/results.jsonl", "keep_raw_samples": true }
}
```

`task` の値で振る舞いを切り替える。**新しい検証を追加するたびにアプリを作り直さないための仕掛け**である。

| `task` | 用途 | 対応フェーズ |
|---|---|---|
| `probe` | セッションを開いてバックエンド名とグラフ配置だけ報告し即終了 | 全般（最初の疎通確認） |
| `bench` | 基本設計① 5章のプロトコル（冷却待機→ウォームアップ→反復→統計）を実行 | P2 / P3 |
| `op_check` | 単体 op モデルを読み、finalize と実行の可否・配置を返す | **P2b（FR-6/FR-7）** |
| `soak` | 指定秒数の連続実行（サーマル試験用） | P3 / P5後 |
| `generate` | prefill + decode の生成ループ（トークン列を出力） | P4 / P5 |

### 5.3 起動と回収

```bash
# ① モデルとジョブ仕様を置く（再ビルド不要）
adb push <tag>_epctx.onnx /sdcard/Android/data/org.edgeslm.runner/files/models/
adb push job.json          /sdcard/Android/data/org.edgeslm.runner/files/jobs/

# ② 起動（extras でジョブ仕様の一部を上書きできる）
adb shell am start-foreground-service \
  -n org.edgeslm.runner/.RunnerService \
  -a org.edgeslm.runner.RUN \
  --es job jobs/job.json

# ③ 結果回収
adb pull /sdcard/Android/data/org.edgeslm.runner/files/out/results.jsonl
adb logcat -d -s EdgeSLMRunner
```

**実行中の温度・クロック・dma-buf のサンプリングは、ホスト側のハーネスが adb 経由で並行して行う**（基本設計① 8章 `device.py`）。アプリ側は推論に専念し、端末の状態監視は持たない。**責務を分けることで、アプリの再ビルドなしに計測項目を増やせる。**

## 6. コンポーネント設計

### 6.1 Kotlin 側（最小限に留める）

| ファイル | 行数目安 | 責務 |
|---|---|---|
| `RunnerService.kt` | 150〜200 | Foreground Service。ジョブ仕様の読み込み、JNI 呼び出し、結果ファイルの書き出し、通知（Foreground 要件のため最小の通知を出す） |
| `NativeBridge.kt` | 50〜80 | JNI の宣言のみ。`System.loadLibrary("edgeslm_runner")` |
| `RunnerReceiver.kt`（任意） | 30 | `am broadcast` での停止指示受付 |

**Kotlin にロジックを持たせない。** 推論も計測も C++ 側に置く。理由は ①最終目標が「C++ 推論サービス」であること ②Kotlin を触ると再ビルドが必要になること。

### 6.2 JNI 境界（広めに固定する）

ZipDepth の8関数構成を参考に、**引数を JSON 文字列にして拡張耐性を持たせる**。

```cpp
// edgeslm_jni.cpp
jlong   nativeCreate(JNIEnv*, jobject, jstring configJson);   // セッション生成。EP設定は JSON で渡す
jstring nativeDescribe(JNIEnv*, jobject, jlong handle);       // バックエンド名・グラフ配置・I/O 情報を JSON で返す
jstring nativeRunJob(JNIEnv*, jobject, jlong handle, jstring jobJson);  // ジョブ実行。結果を JSON で返す
jboolean nativeCancel(JNIEnv*, jobject, jlong handle);        // soak/generate の中断
void    nativeDestroy(JNIEnv*, jobject, jlong handle);
jstring nativeVersions(JNIEnv*, jobject);                     // ORT/QNN の版を返す（FR-12 の記録用）
```

**引数・戻り値を JSON 文字列に統一する理由**: パラメータを1つ増やすたびに JNI シグネチャが変わると、そのたびに再ビルドが必要になる。**JSON なら C++ 側の解釈を変えるだけで済む**……ただし C++ を変えれば結局再ビルドである。それでも**Kotlin 側は一切触らずに済む**ため、変更範囲が C++ だけに閉じる利点は大きい。

### 6.3 C++ 推論コア

```
android_runner/app/src/main/cpp/
├── CMakeLists.txt
├── edgeslm_jni.cpp          JNI の薄いシム（JSON ⇄ C++ 呼び出しの変換のみ）
├── runner/
│   ├── session.{h,cpp}      ORT セッション生成・EP設定・グラフ配置の取得
│   ├── job.{h,cpp}          ジョブ仕様のパースと task 分岐
│   ├── protocol.{h,cpp}     基本設計① 5章のプロトコル（冷却待機以外）
│   ├── stage_timer.{h,cpp}  段階別計測（EdgeSLM の StageTimer と同じ粒度）
│   └── result_writer.{h,cpp} results.jsonl 出力
└── pipeline/                ★EdgeSLM-cpp からの移植（P4以降で使用）
    ├── tokenizer_adapter.{h,cpp}
    ├── kv_cache.{h,cpp}
    ├── sampler.{h,cpp}
    └── generation_loop.{h,cpp}
```

**`pipeline/` は EdgeSLM-cpp（`D:\AI\source\n_chap5\EdgeSLM-cpp`）からの移植である。** 同プロジェクトは既に Python 版とトークン列完全一致まで検証済みであり、これを Android 向けにクロスビルドする。

**NFR-4（既存プロジェクトを変更しない）を守るため、EdgeSLM-cpp を参照せず本プロジェクト配下に複製する。** 複製元の commit / 日付を `pipeline/ORIGIN.md` に記録し、追跡可能にする。

## 7. ビルド構成

### 7.1 Gradle 設定の要点

| 項目 | 値 | 理由 |
|---|---|---|
| `compileSdk` / `targetSdk` / `minSdk` | 34 / 34 / 26 | ZipDepth と揃える（実績のある組合せ） |
| `abiFilters` | **`arm64-v8a` のみ** | 他 ABI は不要。APK サイズと ビルド時間を削る |
| **`packaging { jniLibs { useLegacyPackaging = true } }`** | **必須** | **C-6**。FastRPC が V68 skeleton に実ファイルパスを要求する |
| NDK | **21.4.7075529** | ZipDepth と同一。既に導入済みで実績がある |
| CMake | 3.22.1 | 同上 |
| JDK | 17 | AGP の要求 |
| **`<uses-native-library>`** | **`libcdsprpc.so` / `libadsprpc.so` を必ず宣言する（`required="false"`）** | **C-7**。Android 12+ では宣言が無いと vendor ライブラリがリンカ名前空間に入らず、FastRPC に到達できない。症状は `QNN_DEVICE_ERROR_INVALID_CONFIG` という**真因を示さないエラー**になる |
| `debuggable` | true（当面） | `run-as` でのファイル確認等の診断に使える（推論には使えないが） |

### 7.2 同梱するバイナリ

| 物 | 入手元 | 注意 |
|---|---|---|
| QNN ランタイム（`libQnnHtp.so` / `libQnnHtpPrepare.so` / `libQnnHtpV68Skel.so` / `libQnnHtpV68Stub.so` / `libQnnSystem.so`） | **`D:\QAIRT\v2.48.0.260626\...\lib\aarch64-android\` と `lib\hexagon-v68\unsigned\`** | **版をセットで揃える**（FR-12）。1つだけ差し替えると初期化エラー・誤った配置・ネイティブクラッシュになる |
| ONNX Runtime（QNN EP 入り） | Maven の `com.microsoft.onnxruntime:onnxruntime-android-qnn`、または ZipDepth 同梱の 1.27.0 AAR | **QNN ランタイムの版と整合させる**。ZipDepth は AAR が引き連れる QNN 2.42 をあえて排除し jniLibs の 2.48 で統一していた |

**ライセンス**: QAIRT バイナリは proprietary だが、**アプリに組み込んだ形での配布は許可されている**（単体再配布は禁止）。本用途は問題ない（要件定義書3.2節）。

## 8. 段階的な作り方

**最初から LLM 対応を作り込まない。** P2 で必要な最小構成を先に動かし、段階的に広げる。

| 段階 | 作るもの | 対応 |
|---|---|---|
| **v0.1** | `probe` + `bench` のみ。固定形状の単一入出力モデルを実行できればよい | **P2 の前段**（下記 8.1） |
| v0.2 | `op_check` を追加。finalize 失敗時のエラー文字列をそのまま返す | **P2b**（FR-6 / FR-7） |
| v0.3 | `soak` を追加 | P3 |
| v0.4 | `generate` と `pipeline/` の移植 | P4 / P5 |
| v0.5 | 必要ならローカルソケットでのストリーミング | P5（未決事項#3） |

### 8.1 ★v0.1 は自作モデルを待たずに着手する（実装順序の決定）

**v0.1 の検証に、基本設計②の成果物（自作モデル）は不要である。** ZipDepth が同梱する EPContext モデルが、**この端末で動くことを P1 で実証済み**だからである。

```
third_party/Edge_ZipDepth-SM8350/app/src/main/assets/zipdepth.onnx   6.62 MiB（SHA-256照合済み）
```

**したがって実装順序は「基本設計③ v0.1 →（検証）→ 基本設計②」とする。** 逆順にしてはならない。理由は P1 と同じ**「変数を1つに絞る」原則**である。

| 順序 | v0.1 が失敗したときの切り分け |
|---|---|
| ②を先 → 自作モデルで v0.1 を試す | **原因がパイプライン側か runner 側か分からない**（両方とも新品） |
| **v0.1 を先 → 既知良好モデルで試す** | **原因は runner 側に限定される**（モデルは動くと分かっている） |

v0.1 が通れば「**我々のアプリの器は正しい**」ことが確定する。その後 ② で自作モデルを作り、**同じ器**に入れて失敗したなら、原因はパイプライン側と断定できる。P1 で端末の疑いを先に消したのとまったく同じ構造である。

### 8.2 初回テストは ZipDepth と同じ材料で組む

**我々が持ち込むのは自分のコードだけ**にする。

| 要素 | v0.1 初回 | v0.1 通過後 |
|---|---|---|
| モデル | **ZipDepth の `zipdepth.onnx`** | 基本設計②の成果物（自作） |
| QNN ライブラリ | **ZipDepth 同梱の jniLibs**（SHA-256 照合済み） | QAIRT SDK から取り出したものへ差し替えて再確認 |
| ORT | **ZipDepth 同梱の 1.27.0 AAR** | Maven 版を検討（未決事項#2） |

### 8.3 v0.1 の合格条件

1. `task=probe` で **`QNN HTP - EPContext - all nodes` 相当**のバックエンド名とグラフ配置が返ること
2. `disable_cpu_ep_fallback=1` を有効にしてもセッション生成が成功すること
3. `task=bench` で `OrtRun` が完走し、**P1 で ZipDepth が示した中央値 ≒ 39ms と同オーダー**であること
4. `nativeVersions()` が ORT / QNN の版を返し、manifest と突き合わせられること

これは **P1 で ZipDepth が示した状態を、我々のコードで再現する**ことを意味する。

### 8.4 時間の使い方

v0.1 はビルドがユーザー実行になるため待ち時間が発生する。**その待ち時間に基本設計②を実装して並行させる。**

```
v0.1 のコードを書く ──→ ビルド依頼 ─────────→ 実機で probe/bench 検証
                              │
                              └─ 待機中に②（量子化・変換パイプライン）を実装
```

②を先にやると、②の完成を待ってから v0.1 を書き、さらにビルドを待つことになり**直列になる**。

## 9. リスクと対処

| # | リスク | 対処 |
|---|---|---|
| 1 | **ビルドがユーザー実行のため反復が遅い** | 2章の設計で再ビルド頻度を下げる。加えて **JNI 境界とジョブ仕様を最初に広く決める**。C++ 変更が必要な修正はまとめて依頼する |
| 2 | QNN ライブラリと ORT の版不整合 | 7.2節。`nativeVersions()` で実行時の版を記録し、manifest と突き合わせる（FR-12） |
| 3 | Foreground Service の通知要件 | Android 13 は通知権限が必要。最小の通知チャンネルを作る。取得できない場合でも Service は動く設計にする |
| 4 | 長時間実行中の OS による停止 | Foreground Service + `soak` 中は wake lock を取る。ただし**画面は消灯させたい**（発熱要因を減らすため）ので `PARTIAL_WAKE_LOCK` を使う |
| 5 | 外部ファイルディレクトリのパスが端末で変わる | `getExternalFilesDir()` の実パスを `probe` 時にログへ出し、ホスト側はそれを使う |
