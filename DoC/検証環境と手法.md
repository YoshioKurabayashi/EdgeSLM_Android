# 検証環境と手法 — SLM を Qualcomm NPU に載せて精度を確かめるのに何が要るか

2026-09-18 作成 / 対象読者: これから同じことをやる人

「どのソフトを入れ、どの順で変換し、精度をどう測るか」を1枚にまとめたもの。
背景や結論は別のドキュメント（末尾の[参照](#9-参照)）にある。ここは**手を動かすための情報**に絞る。

---

## 1. 何をするための環境か

```
PyTorch のモデル（Hugging Face）
        ↓ ① export            ONNX（静的形状・KVキャッシュを I/O に出す）
        ↓ ② 量子化            QDQ 付き ONNX（A16W8）
        ↓ ③ DLC 変換          Qualcomm の中間表現
        ↓ ④ context 生成      端末の NPU 向けバイナリ（.bin）
        ↓ ⑤ 配備・実行        Android 端末の HTP（NPU）で走る
        ↓ ⑥ 精度確認          FP32 / Host / 実機 の3段で比べる
```

**①②⑥は PC（Python）**、**③④は Qualcomm の SDK**、**⑤は Android 端末**で行う。

### 2.1b Qualcomm SDK（QAIRT）とは何か

**QAIRT = Qualcomm AI Runtime。** Qualcomm のチップ（Snapdragon）で推論を動かすための開発キットで、
**PC 側の変換ツール**と**端末側で動くランタイム**の両方が1つの配布物に入っている。約 2.2 GB。

歴史的には SNPE → QNN SDK → **QAIRT** と呼び名が変わってきた経緯があり、**同じ SDK の中に
`qairt-*` と `qnn-*` の両方のコマンドが混在している**（今回使ったものも両方ある）。

#### 押さえる用語

| 用語 | 意味 |
|---|---|
| **QNN** | Qualcomm Neural Network。ランタイムの API とバックエンドの総称 |
| **HTP** | Hexagon Tensor Processor。いわゆる NPU。**バックエンドの1つ**（他に CPU / GPU / DSP がある） |
| **v68 / v73** | HTP の**世代**。SM8350（Snapdragon 888）は **v68**。世代ごとに対応 op・型が違う（今回の壁の大半はこれ） |
| **DLC** | Deep Learning Container。Qualcomm の中間表現（`.dlc`）。ONNX を変換した結果 |
| **context binary** | DLC を**特定チップ向けにコンパイル**した実行用バイナリ（`.bin`）。今回 772〜914 MB |
| **EPContext** | ONNX Runtime が context binary を包んで読む形式。ORT からは「ただの ONNX」に見える |
| **skel / stub** | DSP 側で動く実体（skel）と、CPU 側からそれを呼ぶ代理（stub）。**FastRPC** で繋がる |
| **unsigned PD** | 署名なしで DSP に載せられる実行領域。これが使えないと自作モデルを動かせない |

#### 実際に使ったもの（PC 側）

| 実行ファイル | 何をするか | 今回の使いどころ |
|---|---|---|
| **`qairt-converter`** | QDQ 付き ONNX → **DLC** | S5。28層で136分かかる最大のボトルネック |
| **`qnn-context-binary-generator`** | DLC → **context binary**（`--htp_socs sm8350`） | S6。ここが実際の NPU 向けコード生成 |
| `qnn-context-binary-utility` | context binary のメタ情報を読む | 生成物の I/O 名・形状の確認（S7） |
| **`qairt-dlc-info`** | **DLC の中身を数える唯一の手段** | dtype / signed / bitwidth / scale / offset / axis / min-max の監査。**C-13 はこれでしか見つけられなかった** |
| `QnnHtp.dll`（ホスト側 lib） | context 生成時に**バックエンドとして読ませる** | `--backend` に渡す。パスが違うと「Unable to load backend」 |

> SDK にはこの他にも `qairt-quantizer`（Qualcomm 側の量子化器）、`qairt-net-run`、
> `qnn-accuracy-debugger`、`genie-*`（LLM 向けの上位ランタイム）等が入っている。
> **今回は量子化を ONNX Runtime 側で行ったため `qairt-quantizer` は使っていない**
> （QDQ 付き ONNX を持ち込む経路を選んだ）。

#### 実際に使ったもの（端末側）

| ライブラリ | 役割 | 置き場所 |
|---|---|---|
| `libQnnHtp.so` | HTP バックエンド本体。**ORT の QNN EP がこれを `dlopen` する** | APK 同梱 |
| `libQnnHtpPrepare.so` | グラフ準備。context binary 利用時は実質待機 | APK 同梱 |
| `libQnnHtpV68Stub.so` | CPU 側の代理。呼び出しを FastRPC へ流す | APK 同梱 |
| **`libQnnHtpV68Skel.so`** | **DSP 側の実体。** CDSP に読み込まれて実際に計算する | APK 同梱 |
| `libQnnSystem.so` | context binary の読み込み・デシリアライズ | APK 同梱 |
| `libcdsprpc.so` | FastRPC。skel を unsigned PD に載せる | **端末の OS 側**（`/vendor/lib64/`） |

> **V68 の部分は端末世代に合わせる。** SDK には v69/v73/v75 等も入っているので、
> 取り違えると動かない。SDK 内では `lib/hexagon-v68/unsigned/` 以下に skel がある。

#### どの工程で SDK が要るか（逆に、要らない工程）

```
PyTorch → ONNX          : SDK 不要（torch / onnx）
ONNX → QDQ 付き ONNX    : SDK 不要（onnxruntime.quantization）
QDQ → DLC               : ★qairt-converter
DLC → context binary    : ★qnn-context-binary-generator（+ QnnHtp.dll）
生成物の監査             : ★qairt-dlc-info
端末で実行               : ★libQnn*.so 5本（+ OS 側の libcdsprpc.so）
精度の比較・可視化       : SDK 不要（numpy / onnxruntime）
```

**PC 側で SDK が要るのは③④と監査だけ**で、モデル作りと精度評価は ONNX Runtime 側で完結する。
この切り分けが、Host で先に確かめてから実機へ進む進め方を可能にしている。

#### SDK 起因でつまずいた点（実績）

| 症状 | 原因 | 対処 |
|---|---|---|
| `qairt-converter` が動かない | **Python 3.12 では不可** | SDK 付属の **Python 3.10 環境**を別に用意 |
| `Unable to load backend` | `--backend` のパスが誤り（変数展開の失敗など） | 絶対パスで `QnnHtp.dll` を渡す |
| ロード時に落ちる | `embed_mode=1`（C-12） | `embed_mode=0` で binary を別ファイルに |
| `has incorrect Value 68, expected >= 73` | **v68 に無い機能を要求**（C-8: 活性×活性の16bit） | 片側を 8bit に落とす |
| `could not create op: q::QNN_Convert` | float の中間タップ（C-1。v68 の skel は fp16↔fp32 の変換 op を作れない） | 観測は量子化後の整数コードで取る |
| `Squash not possible for op ...` | グラフ入口・出口に隣接する Q を出力にした | その位置の Q は観測しない |
| **失敗しても "Cache binary ... copied to" と出る** | 成功時と同じ文言が出る | **ログの ERROR 行と生成物のサイズで判定する** |

## 3. 変換パイプライン（③④）

`scripts/build_context.sh <qdq.onnx> <出力先> <tag>` に集約してある。中身は2段。

```bash
# S5: ONNX(QDQ) → DLC
qairt-converter --input_network model_qdq.onnx --preserve_io_datatype --output_path model.dlc

# S6: DLC → context binary（端末の NPU 向け）
qnn-context-binary-generator --dlc_path model.dlc \
  --backend <QAIRT>/lib/x86_64-windows-msvc/QnnHtp.dll \
  --binary_file model_ctx --output_dir ctx_dir --htp_socs sm8350
```

| 段 | 所要時間の実績 | 備考 |
|---|---|---|
| S5 | 28層 872MB で **136分**、7層 111MB で **12分** | **1コアしか使わない**。クロック速度が効く |
| S6 | 1〜4分 | ここが実際の NPU 向けコード生成 |

生成物は `wrap_epctx.py` で **EPContext 形式の ONNX** に包み、ORT の QNN EP から読ませる。

> **禁止事項**（踏むと動かない）
> - `--htp_socs sm8350` 以外に soc_id を刻まない（C-2）
> - `backend_extensions` の config を渡さない（C-3）
> - 大きなモデルを `embed_mode=1` で埋め込まない（C-12。RSS 二重で SIGKILL）

## 4. 量子化の方式（②）

| 対象 | 方式 |
|---|---|
| 活性 | **uint16・per-tensor・asymmetric**（per-channel は使えない） |
| 重み | **int8・per-channel・symmetric**（`TensorQuantOverrides` の `axis` で指定。`per_channel=True` だけでは効かない） |
| 活性×活性の MatMul | **右辺を uint8 に落とす**（C-8。`u16×u16` は v68 で不可） |
| RMSNorm の gamma | **符号付き対称**（C-13。uint16 のままだと DLC で `sFxp_16` になり 32767 超が黙って飽和） |

QNN の規約は **`実数 =（量子化値 + offset）× scale`**。ONNX の `zero_point` とは符号が逆なので注意。

## 5. 精度をどう確かめるか（⑥）

### 5.0 「ホスト検証」とは何をしているのか

**使うのは ONNX Runtime の CPU 実行だけ**（QAIRT SDK は不要）。実機と**同じモデルファイル**を読む。

```python
import onnxruntime as ort
so = ort.SessionOptions()
so.intra_op_num_threads = 4
so.log_severity_level = 3
s = ort.InferenceSession("model_qdq.onnx", so, providers=["CPUExecutionProvider"])
out = s.run(None, {"input_ids": ids, "cos": cos, "sin": sin, "attn_mask": mask, **cache})
```

#### ★ Host QDQ は「整数演算」ではない

QDQ 形式の ONNX は、グラフ上は float のまま Q/DQ のペアを挟んでいる。

```
float値 → QuantizeLinear → 整数コード → DequantizeLinear → float値 → 次の演算（float）
          round(x/scale)+zp             (q - zp) * scale
```

つまり **「量子化で失われる情報だけを再現した float 計算」**（fake quantization）である。

| | Host QDQ（ORT CPU） | 実機 HTP |
|---|---|---|
| scale / zero point | **同じ** | 同じ |
| 重みの値 | **同じ** | 同じ |
| 丸めによる情報落ち | **再現される** | 起きる |
| **演算そのもの** | **float32** | **固定小数点の整数演算** |
| op の融合 | ほぼ無し | **あり**（RMSNorm が `RmsNorm` 1つになる等） |
| 積和の順序・中間精度 | ORT の実装 | HTP の実装（内部で fp16 も使う） |

**「量子化の影響」までは同じで、「計算のやり方」が違う。** これが Host↔HTP 差（②の軸）の正体。

#### なぜ Host でやるのか

| | Host | 実機 |
|---|---|---|
| 準備 | **即座**（モデルを読むだけ） | **136分**（S5）＋配備 |
| 中間テンソルの取得 | **任意の場所をグラフ出力に足せる** | 部分グラフを作り直して再ビルド |
| 量子化パラメタの変更 | **メモリ上で書き換えて即実行** | 再ビルドが必要 |
| 変種の比較 | 約10分／変種 | 約140分／変種 |

範囲の掃引（1x〜8x の7点）や層ブロックごとの A/B（7ブロック）ができたのは、**すべて Host 上で
メモリ上の scale/zero point を書き換えるだけ**で済んだため。実機でやれば数日かかる。

#### Host 検証の限界（3つとも実際に踏んだ）

1. **Host で崩れる設定は実機でも良くならない。** 実機は Host に忠実になるだけ
2. **Host で良くても実機で良いとは限らない。** 実行環境の差（②）が別にある
3. **Host で作れても実機で作れない構成がある。** 2モデル切り替え（P16）、16bit の act×act（C-8）

> 参考: 「実機と同じランタイムをホストで動かす」案（QNN の CPU バックエンド）も試したが、
> **QNN CPU backend は `Gather` も `RmsNorm` も持っておらず**このモデルでは組めなかった。
> 記録として `app/pipeline/qnn_cpu_compare.py` を残してある。

### 5.1 まず3段に分けて測る

```
FP32（PyTorch）→ Export FP32（ONNX）→ Host QDQ（ORT CPU）→ 実機 HTP
```

**この4点を用意してから比べる。** いきなり FP32 と実機を比べると、export のバグ・量子化・実行環境の
どれが原因か切り分けられない。

比べる軸は2つあり、**混同しない**こと。

| 軸 | 何の話か | 打ち手 |
|---|---|---|
| ① FP32 ↔ Host QDQ | **量子化の設計**が妥当か | scale/レンジ・粒度・bit 配分 |
| ② Host QDQ ↔ 実機 HTP | **実行環境の差** | 融合・エンコーディング・op 対応 |

### 5.2 指標（場所ごとに違う）

| 測る場所 | 指標 | 見どころ |
|---|---|---|
| 層ごとの活性（残差・KV・MLP 中間など） | **整数コードの一致率 / ±1段率 / 最大差**、相対L2、clip 率 | **「差の段数 × scale ÷ 信号の大きさ」**が効く。一致率だけでは誤差の大きさは分からない |
| ロジット | top-1 一致率、**基準の1位の順位**、**margin**、KL、相対L2 | margin ＝ `logit[基準の1位] − そのモデルでの最強の対抗`。負なら1位を失っている |
| 生成 | **自由生成そのもの** | 最終的な合否はここで決める |

> **★ 合否は自由生成で決める。** 1位保持率・margin 保持率・KL が baseline を上回るのに
> 自由生成が崩れる例が3回出た。集計指標は診断用と割り切る。
> 比較的よく対応したのは「**各回答の最初のトークンの margin**」。

### 5.3 端末での測り方

| 目的 | 方法 |
|---|---|
| 1ステップの数値比較 | runner の `infer` タスク。全入力を `.bin` で与え、出力を `.bin` で受け取る |
| 生成・対話 | デモアプリの `generate_kv`（KV キャッシュを持ち回す） |
| 層の内部を見る | **部分グラフを切り出して**別モデルにし、同じ入力を Host と端末に与える |

**部分グラフの切り出しには作法がある。**

- 観測タップは**量子化後の整数コード**で取る。DQ 後の float を出力にすると、v68 は
  fp16→fp32 の Convert を作れず**ビルドが落ちる**（C-1）
- **グラフの入口・出口に隣接する Q は出力にしない**（`Squash not possible` で変換が落ちる）
- 出力を増やすと HTP の**融合が変わって数値が変わる**ことがある。→ **観測なし版と並べて対照**を取る
- 変換器が観測出力を**消すことがある**（EPContext の宣言と QNN の実体が食い違い `Inconsistent output sizes`）。
  → メタ情報で実際に残った出力を確認してから包む

### 5.4 必ず通す「差が0になるはずの条件」

新しい測定器や部分モデルを作ったら、**壊れていないことを先に証明する**。

| 確認 | 期待値 | 実績 |
|---|---|---|
| 部分グラフ ↔ 本体（同じ入力・Host） | 完全一致 | 最大差 0.000 |
| 観測あり版 ↔ 観測なし版 | 一致（または影響が無視できる） | 実機で最大2段・結論不変 |
| 公式 HF ↔ ONNX export | ほぼ一致 | KL 0.0000 |
| 配布物の md5（PC ↔ 端末） | 一致 | 3点照合 |

## 6. 落とし穴（実際に踏んだもの）

| 症状 | 原因 | 対処 |
|---|---|---|
| 誤差が小さく見える | **uint16 のコード値**で相対誤差を取った（zero_point を含む大きな数で薄まる） | **逆量子化してから**測る（0.09% → 31.53%） |
| 「per-channel にしたのに効かない」 | 生成物は全部 per-tensor だった | **設定値ではなく生成物を数える**（`qairt-dlc-info`） |
| ONNX では正常なのに実機だけ壊れる | 変換器が RMSNorm を融合し、gamma を `sFxp_16` として渡していた（C-13） | DLC まで見る。dtype/signed/scale/offset/min-max を確認 |
| context binary を作ったのにロードで落ちる | `embed_mode=1` で埋め込み（C-12） | `embed_mode=0` で別ファイル |
| 端末では走るのにホストで読めない QDQ | scale/zero_point の初期化子を**他ノードと共有**していて壊した | **配布前にホストで必ず読み込む** |
| 「成功」と出たのに古い結果を見ていた | 出力ファイル名が前回のジョブのもの | **job_id を確認**してから読む |

## 7. 最小の再現手順

```bash
# 0) 端末を確認
adb devices && adb shell getprop ro.board.platform      # lahaina なら SM8350

# 1) モデルを export（静的形状・KVキャッシュを I/O へ）
.venv/Scripts/python.exe app/pipeline/export_qwen_decode.py --layers 28 --cache-len 256

# 2) 量子化（A16W8 + C-8 + C-13 を自動適用）
.venv/Scripts/python.exe app/pipeline/p2b_ops.py --spec work/ops/<name>/<name>.spec.json

# 3) ★ホストで読み込めるか確かめる（ここを飛ばさない）
.venv/Scripts/python.exe -c "import onnxruntime as ort; ort.InferenceSession('<qdq.onnx>')"

# 4) DLC → context binary（時間がかかる。放置可）
bash scripts/build_context.sh <qdq.onnx> work/<name>/ctx <tag>

# 5) EPContext に包んで端末へ
.venv/Scripts/python.exe app/pipeline/wrap_epctx.py --ctx <ctx.bin> --qdq <qdq.onnx> --out <epctx.onnx> --tag <tag>
adb push <epctx.onnx> <ctx.bin> /sdcard/Android/data/org.edgeslm.runner/files/models/ops/

# 6) 実機で1ステップ比較（入力は .bin、出力も .bin）
.venv/Scripts/python.exe app/pipeline/device_accuracy.py --model models/ops/<epctx.onnx> --eval-npz <eval.npz> --fp32 <fp32.onnx>
```

## 8. 工数の目安（実績）

| 作業 | 時間 |
|---|---|
| 環境構築（SDK・NDK・QAIRT・venv 2つ） | 1日 |
| export＋量子化（28層） | 30〜60分 |
| DLC 変換（S5、28層） | **136分**（7層なら12分） |
| context 生成（S6） | 1〜4分 |
| 端末配備（914MB） | 30秒（端末内コピーなら3秒） |
| 1ステップの Host↔実機 比較 | 5〜10分 |
| 対話3ターンの自由生成（Host・28層） | 10分／変種 |

**「Host で先に確かめてから実機へ」**が鉄則。実機ビルドに 136分かかるので、
Host で15分の確認を挟むだけで大幅に節約できる（実際、それで無駄な実機ビルドを2回避けた）。
