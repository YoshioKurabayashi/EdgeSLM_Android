## 0.5 Qwen3-0.6B（2026-09-15〜09-17・**クローズ済み**）

Qwen2.5 で確立した手順を Qwen3-0.6B（28層・KV256）へ適用した。詳細は
[results/P14_20260917_qwen3_closing.md](../results/P14_20260917_qwen3_closing.md)。

**動いたこと**: 28層 872MB が**全ノード NPU** で動作（OrtRun 95.78ms、fp32↔実機 top-1 **75.0%**、
Host↔実機 relL2 17.33%）。fp32 では **System Prompt を守り、会話履歴も参照できる**（Qwen2.5 は両方できない）。

**動かなかったこと**: 実機の自由対話が崩れる。原因は HTP の計算間違いではなく、
**位置0 の巨大活性**（層2 MLP の出力・channel 35 が 8142。トークンによらず位置0 で必ず出る）に
per-tensor の scale を合わせた結果、**後続トークンが実質3〜4段でしか表現できなくなる**こと。
Host と HTP の **±1〜2段**の丸め差が、その粗い格子の上で信号の数十%になり、KV に蓄積して自己回帰で分岐する。

| 層2 の実測（Host） | scale | 値の RMS | 使われたコード | Host↔HTP 整数差 | 実数誤差 |
|---|---:|---:|---:|---:|---:|
| `mul_41`（SiLU×up） | 0.105 | 0.091 | **14 種** | max 3 | **16.8%** |
| `linear_20`（down_proj） | 0.113 | 0.121 | **8 種** | max 2 | **55.1%** |

**v68 の制約との関係**:
- **C-8** が効いてくる。V の read 側（GQA 複製後の act-act MatMul 右辺）は 8bit 固定で、
  16bit へ上げる構成は**グラフ検証で落ちる**（`node_matmul_23`）。KV 範囲を広げる方向も 8bit の分解能で相殺される
- **C-1** は観測時にも出る。中間の float をグラフ出力にすると `q::QNN_Convert`（fp16→fp32）が作れず
  graph finalize が失敗する。**観測タップは量子化後の整数コードで取る**

**結論**: per-tensor A16 ＋ C-8 の組み合わせでは解けなかった。**Reference Model は Qwen2.5-0.5B のまま**。
未解決として残すのは ①位置0 の巨大活性への対処（outlier channel 分離 / SmoothQuant 系 / 回転系。v68 での
実装可否は未確認）②V read の 16bit 化（v73 以降の候補）③速度（10.4 tok/s。KV I/O が 9.3倍）④課題精度の定量。

### 2.4 ★生成結果（これが一番分かりやすい）

```
プロンプト : The capital city of Japan is Tokyo. The capital city of France is
端末(NPU)  : " Paris. The capital city of"
fp32(PC)   : " Paris. The capital city of"
トークン一致: 6/6
```

**top-1 一致率 73.3% という数字から想像するより、実際の生成は素直だった。**
曖昧さの少ないプロンプトでは量子化後も同じトークンを選ぶ。

一方、プロンプトが短いと品質が落ちるが、**fp32 も同じように崩れる**:

| プロンプト長 | pad 数 | 端末 | fp32 |
|---:|---:|---|---|
| 14 | 2 | ` Paris. ...` | ` Paris. ...`（一致） |
| 11 | 5 | `、東京の南` | `？ - お笑` |
| 3 | 13 | `、その名の「日本語言` | `、2018年10` |

原因は**窓のパディング**である。prefill モデルは因果マスクを定数で焼き込んでおり、
**パディング用のマスク入力を持たない**ため pad トークンも attention される。
**現状のボトルネックは量子化より窓とマスクの扱い。**

→ **「読んだ方が早い」は正しかった。** 数字だけ見て量子化を詰めていたら、
**実際には効かない方向に工数を使っていた。**

**精度面での v68 / v73 の差は、この測定からは出せない。**

### 2.6 誤差の内訳

```
fp32  ──[ 量子化誤差 ]──>  ホストQDQ  ──[ QNN-HTP 追加分 ]──>  実機
```

**分母はすべて `‖fp32‖` に揃えてある。L2 なので3つは加算関係にない**
（直交していれば二乗和の平方根が合計に一致する）。

| モデル | 量子化 | **QNN-HTP 追加分** | 合計 | 二乗和の平方根 |
|---|---:|---:|---:|---:|
| 重み固定 MatMul 1個（A16W8） | 0.92% | **0.11%** | 0.92% | 0.92% |
| 活性化×活性化 MatMul | 2.44% | **1.98%** | 2.50% | 3.14% |
| Qwen 層1枚 | 9.31% | **13.25%** | 16.11% | 16.19% |
| Qwen 2層 e2e | 9.90% | **20.21%** | 22.11% | 22.51% |

- **HTP は本質的に不正確ではない**（重み固定 MatMul で 0.11%）
- **活性化×活性化 MatMul の実機差は 18倍**（0.11% → 1.98%）。
  **ただし単体 1.98% では Qwen の 13.25% を説明できない**——softmax による増幅を疑っている
- **層を重ねると積み上がる**（1層 13.3% → 2層 20.2%）
- **量子化誤差と実機差はほぼ直交**（二乗和の平方根が合計に一致）＝別々の要因
- **実機は完全に決定的**（同じ入力を2回でビット一致）＝ノイズではなく系統的なズレ

**「QNN-HTP 追加分」と呼んでいるのは、HTP の演算精度だけではないため。**
QNN への lowering・op fusion・QDQ 境界の変更・requantization・layout 変換・
kernel 選択がすべてここに含まれうる。

→ **ホスト上で量子化を詰めても、実機で確かめない限り意味が付かない。**
ホストで 9.9% まで詰めても実機は 22.1% で、差の大半は実行系にある。

## 3. v68 で守るべきこと（C-1〜C-13）

違反すると**端末でのロード時**に落ちる。変換時には気付けないものが多い。

### 3.1 モデル生成時

| # | 禁止 | 正しい形 |
|---|---|---|
| **C-1** | float セグメントを残す | 完全 QDQ。float op は fp16 HTP op になり **v68 の skel は fp16 非対応** |
| **C-2** | `soc_id` を刻む | **`--htp_socs sm8350` のみ**。unsigned PD は SoC id を照会できない |
| **C-3** | backend_extensions の config を渡す | 渡さない。unsigned PD は power config を適用できない |
| **C-4** | float 混在に `--preserve_io_datatype` | 完全 QDQ に対してのみ |
| **C-5** | `BatchNormalization` を残す | `Mul`+`Add` へ畳む（**error 3110**） |

### 3.2 アプリ側

| # | 禁止 | 正しい形 |
|---|---|---|
| **C-6** | `useLegacyPackaging=false` | `true`（`extractNativeLibs=true`）。FastRPC は**実ファイルパス**を要求 |
| **C-7** | `<uses-native-library>` 未宣言 | `libcdsprpc.so` / `libadsprpc.so` を宣言。Android 12+ の必須事項 |

### 3.3 LLM 固有（P2b / P3 で発見）

| # | 禁止 | 正しい形 |
|---|---|---|
| **C-8** | 活性化×活性化 MatMul を `u16×u16` / `u8×u16` で | **`u16×u8` にする**（下記） |
| **C-9** | 因果マスクの `-3.4e38` をそのまま量子化 | **有限値（-60.0）へ置換**。エラーにならず**精度だけ静かに壊れる** |
| **C-10** | `Expand` を含んだまま context binary を作る | **`Concat` の繰り返しへ書き換える**。ホストは素通しし端末で err 1002 |
| **C-11** | RMSNorm の `x²` をそのまま量子化する | **トークンごとの max\|x\| で割ってから二乗する**。`x²` のレンジが 280万→1 になる。これが無いと **24層は top-1 4.5% で破綻**（下記 4.3節） |
| **C-12** | 大きなモデルを `embed_mode=1` の EPContext にする | **`embed_mode=0`** にして binary を別ファイルに。埋め込むと**ロード時に二重に持ち**、736MB で RSS 1.47GB → **SIGKILL**（下記 4.5節） |
| **C-13** | RMSNorm の gamma を **uint16** で量子化する | **符号付き対称**（zero_point 0、`\|gamma\|max/32767` を scale）にする。converter は RMSNorm を融合 op `RmsNorm` にし、gamma を **`sFxp_16`（符号付き）** として渡すため、**量子化値が 32767 を超える要素が黙って頭打ちになる**。警告も出ない。24層で **49本中49本**が該当。RMSNorm 単体で相対L2 **13.54%**、24層でホスト↔実機 36.7%→**18.5%**（下記 4.6節） |

### 3.4 ★C-8 の詳細（最重要）

**v68 の MatMul 対応は組合せ依存かつ非対称:**

| 組合せ | v68 |
|---|:--:|
| `u16 × u16` | **不可** |
| **`u16 × u8`** | **可** |
| `u8 × u16` | **不可**（公開資料では可とされるが**実機は非対称**） |
| `u8 × u8` | 可 |

**8bit にできるのは常に右辺**である。したがって
`A × B = (B^T × A^T)^T` の等価変形で**右辺に置くテンソルを選ぶ**:

```
変更前: MatMul(Q, K^T)            → 右辺 = K   （±130、1段階 0.99）
変更後: Transpose(MatMul(K, Q^T)) → 右辺 = Q^T （[-10,6]、1段階 0.064）  ← 15倍細かい
```

これで **MatMul の出力（attention スコア）を 16bit に保てる**（1段階 6.38 → 0.0248）。

**ORT の量子化器では表現できない**（入力型を必ず揃える）ため、
`app/pipeline/force_mixed_matmul.py` で **QDQ を直接書き換える**。

### 3.5 その他の制約

- **QNN EP は動的形状を扱えない** → 静的形状化と固定長 KV キャッシュが必須
- **LPBQ / 16a4w_block は V69以上**で v68 不可
- **weight sharing は v73以上** → v68 は prefill/decode で重み2重持ち
- **GroupQueryAttention は HTP 非対応** → attention は手分解が前提（**手分解版は動く**）
- **ORT 自身の x86 EPContext 生成は v68 で失敗** → QAIRT の生成器を使う
- **電力プロファイルは制御できない**（unsigned PD）→ 全測定が `default(unsigned_pd)`
- **HTP は `untrusted_app` ドメインからしか使えない** → `adb shell` / `run-as` では不可

#### 制約ではないと確認したもの

- **attention マスクを float32 のグラフ入力にするのは v68 で可**
  （単体 op `attn_mask_input` と24層モデルの両方で `pass_strict`。2026-09-13）
- **float32 のグラフ入力そのものも可**（`--preserve_io_datatype` + 入力が `QuantizeLinear` へ入る形なら）

## 4. Qwen2.5-0.5B について分かったこと

### 4.1 実際の export に出てくる op

手書きで推測していた形と **4箇所違っていた**。

| 部位 | 推測していた形 | **実際** |
|---|---|---|
| GQA のヘッド複製 | `Concat` ×rep | **`Unsqueeze`→`Expand`→`Reshape`** |
| RoPE の rotate_half | `Split` | **`Slice` ×2** |
| RMSNorm の除算 | `Sqrt`→`Div` | **`Sqrt`→`Reciprocal`→`Mul`** |
| 因果マスク | `Add`（-60.0） | `Add`（**-3.4028235e+38**） |

`LayerNormalization` / `RotaryEmbedding` / `SimplifiedLayerNormalization` は
**実際の export には出てこない**（融合形はファイルとして持ち込めない）。

### 4.2 病的なのは layer 0 だけ

| 層 | scaled スコア幅 | 8bit の1段階 | argmax 一致 |
|---|---:|---:|---:|
| **0** | **1677** | 6.58 | **35.8%** |
| 1 | 429 | 1.68 | 63.5% |
| 3 | 132 | 0.52 | 96.7% |
| 23 | 101 | 0.40 | 90.9% |
| **層2〜23 平均** | — | — | **95.7%** |

**end-to-end 測定に使った先頭2層は、24層中で最悪の2層である。**
24層全体では数字が上振れするはずだが、まだ測れていない
（ORT の量子化器が 2GB 超モデルを保存できない）。

### 4.3 ★24層が壊れる理由: massive activations

**2層は動くのに 6層・24層はホストの時点で壊れる**（top-1 80.7% → 6.2% / 1.7%、
fp32 との相関 0.9977 → 0.125）。**v68 で動かない A16W8 素でも壊れる**ので C-8 とは無関係。

| 層 | 残差の最大 \|x\| |
|---|---:|
| 0 | 6.2 |
| 1 | 7.4 |
| **5〜20** | **約 1677** |
| 23 | 110 |

per-tensor の uint16 量子化はテンソル全体で1スケールなので、レンジ ±1677 なら
**1段階 0.051**。ところが**各層が残差に加える寄与は ±10〜20** で、
「大きな数の上の小さな数」が粗さに埋もれる。

層ごとの相関がそれをそのまま示す:

| テンソル | 最大\|x\| | 相関 |
|---|---:|---:|
| 残差（add_42） | 1604.9 | 0.9903 |
| **層の寄与（add_39）** | **20.3** | **0.7224** |
| **層の寄与（add_40）** | **9.3** | **0.6466** |

**残差は保たれるのに層の寄与が崩れ、最後の RMSNorm が大きい成分を消すと
ノイズだけが残る。**

**Percentile 較正（p99.999）は効かなかった**（top-1 6.2% のまま）。
massive activation は少数の次元に常時存在するため、切っても残る。

**これは量子化の既知の難問**で、標準的な対処は per-channel 活性化量子化（**QNN では不可**）
か **SmoothQuant**（活性化の外れ値を重み側へ移す等価変形。**オフラインなので適用可能**）。

**注意: v73 の端末に替えても解決するとは限らない。** v73 の利点は `u16×u16` の MatMul と
weight sharing であって、**per-tensor 活性化量子化という制約は変わらない**。

### 4.4 ★24層を動かすのに必要だった3つ

| 壁 | 症状 | 解決 |
|---|---|---|
| ORT が 2GB 超を量子化できない | `EncodeError: Failed to serialize proto` | **opset 21 で export**（16bit 量子化の opset 自動変換が fp32 2.52GB をシリアライズしていた。**出力の QDQ は 0.63GB でサイズの問題ではなかった**） |
| 24層が数値的に破綻 | ホストで top-1 **4.5%**、fp32 との相関 0.125 | **C-11: RMSNorm 正規化**（`x²` のレンジ 280万→1）。oracle 実験で「残差を外しても 0 効果、RMSNorm を外すと 6.2%→74.4%」と確定してから実装した |
| アプリが SIGKILL される | ロード6秒後にプロセス消滅。RSS 1.47GB | **C-12: `embed_mode=0`**（ONNX 772MB → **442バイト**） |

### 4.5 較正データ

| 較正 | ホスト top-1 |
|---|---:|
| 実テキストから作った hidden_states | 30.4%（層1枚の相対L2） |
| 乱数 ±1.0 | 38.9%（同上） |

本物の hidden_states は **±0.09（std 0.0156）**。乱数較正の ±1.0 は**約11倍広い**。
A16 なら耐えるが **A8 では実データが ±6段階に潰れる**。

## 5. ★踏んだ誤りの型（最も再利用価値が高い）

技術的事実より、**誤りの型**のほうが後で効く。
**各項目の詳細（何をして何が起きたか）は [試行錯誤の記録.md](試行錯誤の記録.md) にある。**
本章はその要約である。

### 型1: 「ファイルができた＝成功」と読む（5件）

| 事象 | 実際 |
|---|---|
| `dd \| tail` のサマリ行 | 失敗してもサマリは出る。`Permission denied` を隠していた |
| `Cache binary ... copied to` | **失敗時も出る**。ファイルは作られていない |
| `quant_pre_process` | 2GB 超で **47バイトの空モデル**を無言で出力 |
| `adb push` の「1 file pushed」 | **パスが化けて別の場所**に置かれていた（MSYS） |
| 自作スクリプトの `bash` 呼び出し | Python から解決できず**無言で何もしない** |

**対策**: 成果物の中身（ノード数・opset・ファイルの実在）を門にする。
パイプラインに `_assert_sane()` を入れた。

### 型2: 症状が真因を示さない（3件）

| 表示 | 真因 |
|---|---|
| `EPContext node is not compatible with any execution provider` | マニフェストの宣言漏れ（C-7） |
| `ORT Tensor data size does not match` | ラッパーの I/O 型が float32 決め打ち |
| `Failed to create context from binary. Error code: 1002` | **`Expand` が1個入っていた**（C-10） |

**対策**: エラー文言を額面どおり読まない。**動いている参照実装との差分**を取る。
単体モデルを1つずつ試して切り分ける（`op_check` task がこれを支える）。

### 型3: 見る場所を間違える（6件）

| 誤り | 実際 |
|---|---|
| スコアテンソルの L2 誤差 0.49% を「小さい」と判断 | **softmax を通すと 62.8%**。argmax 一致 29% |
| 層の L2 誤差だけで「使えない」と結論しかけた | end-to-end で測り直すべき（今回は同じ向きだった） |
| 実機の低下幅（top-1）で「HTP に下限がある」と解釈 | **L2 で分解すると逆**。飽和していただけ |
| 誤差分解で**分母を揃えていなかった** | 量子化は `/‖fp32‖`、実機差は `/‖ホストQDQ‖`。**比較できない数字を並べていた**。L2 は加算もしない |
| 24層破綻の原因を**残差**と推定 | **oracle 実験で外れと判明**（残差除外は 0 効果）。真因は **RMSNorm の `x²`** |
| 「層の寄与 ±10〜20 が step 0.051 に埋もれる」 | **割り算すれば 196段階ある**。見るべきは最大値でなく**分布**（p50 は 7〜29段階しか無かった） |

**対策**: **その先で何に使われるか**まで見る。指標を変えると結論が反転しうる。

### 型4: 事例の一般化（3件）

| 誤り | 実際 |
|---|---|
| 「Genie が v73+ を要求 → NPU で LLM 不可」 | ORT QNN EP は別経路 |
| 「PD メモリ 698MB が v68 の上限」 | **1件の事例**。実測では 420MB 問題なし |
| **「C-8 は両側 A8 にするしかない」** | **`u16×u8` が通る。回避策を1つしか試していなかった** |

**対策**: 「1つの事例」を「一般則」に昇格させない。**出典の対象範囲を確認する。**

### 型5: ツールの制約をハードウェアの制約と取り違える（1件）

ORT の量子化器が `u16×u8` を表現できないことを、**v68 ができないこと**と
取り違えかけた。QDQ を直接書き換えて試したら**通った**。
**「このツールでできない」と「このハードでできない」は別。**

### 型6: 実行主体の取り違え（2件）

| 誤り | 実際 |
|---|---|
| 「シェルから `dlopen` 成功 → アプリでも使える」 | シェルは名前空間制限の**対象外** |
| 「`run-as` なら通るはず」 | `runas_app` は `untrusted_app` と別ドメイン |

### 型7: 道具を目的外に使う（1件）

P2b の自作 op モデル（重み = 小さな乱数）を**精度測定に流用**した。
`block_real` の誤差が 0.01% と出たが、**出力が残差の `x` に支配されて薄まっただけ**。
**「op が載るか」を見る道具であって、精度を測る設計になっていない。**

### 型8: 版依存の事実を固定化（1件）

「MatMulNBits は fp16 依存 → v68 不可」は **v2.3 時点の実装詳細**。
→ 要件定義書 3.3節を【固定事実】と【バージョン依存事実】に分離した。

### 24層の 2GB 問題は解決済み

`quantize_static` → `update_opset_version` → `convert_version` → `SerializeToString()` で
**fp32 の全重み 2.52GB を1つの protobuf にしようとして**落ちていた
（16bit 量子化が opset ≥ 21 を要求するための自動変換）。
→ **最初から opset 21 で export すれば変換自体が起きない。**
出力の QDQ は 0.63GB で、そもそもサイズの問題ではなかった。

opset 21 の export は **PyTorch と 1e-4 で一致**し（top-1 100%）、
C-9 / C-10 / 左右入替の Graph Rewrite も **48件すべて正しく適用**された。

### 作業分担

**JVM プロセスだけが外部通信できない**ため、**Gradle ビルドは代行できない**。
モデル・ジョブ仕様は APK の外に置く設計にしてあるので、
**ビルドが必要なのは runner 自体を変えるときだけ**（これまで v0.1 / v0.2 / v0.3 の3回）。

### 手で adb を叩くときの注意

**MSYS のパス変換で宛先が化ける。** 必ず付けること:

```bash
export MSYS2_ARG_CONV_EXCL='/data/local/tmp;/sys;/vendor;/dev;/system;/proc;/sdcard;/storage'
```
