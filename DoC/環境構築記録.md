## 1. 本書の目的

後から**同じ環境を再構築できる**こと、および**同じ罠を二度踏まない**ことを目的とする。

特に4章「つまずいた点と解決」は本書の中心である。今回の構築では**ドキュメントの記述と実体が食い違う箇所**（QAIRT の対応Python版）や、**エラーメッセージが真因を示さない箇所**（DLL load failed の真因がPythonバージョン）に複数遭遇した。これらは記録がないと再調査に数時間かかる。

## 3. 実施手順（再現用）

### 3.1 adb（Android Platform-Tools）

```powershell
winget install Google.PlatformTools
```

- PATH はユーザー環境変数に自動登録される。**反映には新しいターミナルを開く必要がある**
- `fastboot` も同時に入る
- 確認: `adb version` → `Version 37.0.1-15733141`

### 3.2 Android cmdline-tools

Android Studio（GUI）は入れず、**コマンドライン版のみ**を使う。非対話環境でも扱えるため。

```
https://dl.google.com/android/repository/commandlinetools-win-15859902_latest.zip
```

- サイズ 148.4 MB、SHA-256 `90ae805d20434428bffcb699c290860f19bb5f66a67e6b330067e3de801fb04a`（**一致を確認済み**）
- 展開後、`cmdline-tools` ディレクトリを **`D:\Android\sdk\cmdline-tools\latest`** に配置する（この `latest` というディレクトリ名が sdkmanager の要求するレイアウト）

### 3.3 JDK 17

AGP 8.7.3 が Java 17 を要求するため（ZipDepth の `compileOptions` / `jvmTarget` も 17）。**既定の Oracle JDK 22 とは別に、プロジェクト専用として用意する。**

- 取得元: `https://api.adoptium.net/v3/binary/latest/17/ga/windows/x64/jdk/hotspot/normal/eclipse`（ZIP、182 MB）
- 展開して `jdk-17.0.20.1+1` を **`D:\Android\jdk17`** にリネーム配置
- **システムの `JAVA_HOME` は設定していない。** 使うときだけ明示的に指定する（他の作業への影響を避けるため）

### 3.4 Android SDK パッケージ（※ユーザー実行）

PowerShell の場合:

```powershell
$env:JAVA_HOME="D:\Android\jdk17"; & "D:\Android\sdk\cmdline-tools\latest\bin\sdkmanager.bat" --sdk_root=D:\Android\sdk "platform-tools" "platforms;android-34" "build-tools;34.0.0" "cmake;3.22.1" "ndk;21.4.7075529"
```

Git Bash の場合:


- ライセンス同意のプロンプトで `y`
- **この工程は Claude Code 側から代行できない**（4.2節）
- `sdkmanager` は非推奨警告（新 `android` CLI への移行を促す）を出すが、動作する

## 4. つまずいた点と解決（★本書の中心）

### 4.1 JDK の MSI インストーラが管理者昇格を求めて失敗した

`winget install EclipseAdoptium.Temurin.17.JDK` が **exit code 1602（ユーザーがインストールを取り消しました）** で失敗。非対話環境では UAC プロンプトに応答できないため。

→ **ZIP 版に切り替えて解決。** 結果的にこちらの方が望ましかった。管理者権限が不要で、**システムの `JAVA_HOME` や PATH を一切変更しない**ため、既存の Oracle JDK 22 に依存した他の作業に影響を与えない。

### 4.2 Claude Code の実行環境では JVM だけ外部通信ができない

`sdkmanager` が `Failed to download any source lists!` / `IO exception while downloading manifest` で失敗した。切り分け結果:

| 実行主体 | 結果 |
|---|---|
| Java（Oracle 22 / Temurin 17 の**両方**） | `142.251.24.136:443`・`:80`・`1.1.1.1:443` すべて `SocketTimeoutException`（8秒） |
| **同一シェルの curl（同じIPに対して）** | **HTTP 200** |
| Python 3.11（socket / urllib） | 正常（4〜38ms、pypi へ 200） |
| PowerShell の .NET | 正常 |

プロキシは一切なし（env / `netsh winhttp` / WinINET すべて Direct）、DNS 正常、IPv4 強制でも失敗、サンドボックス無効化でも失敗。**設定ミスではなく実行環境の特性。**

→ **JVM を使う工程はユーザー自身のターミナルで実行する。** 該当するのは `sdkmanager`（3.4節）と、今後の **Gradle 依存解決（P1 の APK ビルド）**。Python・curl・ネイティブ exe・adb を使う工程は代行可能。

**なお、同じコマンドをユーザーのターミナルで実行したら正常に完了した。** つまりマシン全体の問題ではなく、Claude Code の実行環境に限った制約である。

### 4.3 PowerShell には `VAR=value cmd` の構文がない

Git Bash 向けに書いた `JAVA_HOME="..." sdkmanager.bat ...` を PowerShell で実行すると `用語 'JAVA_HOME=D:/Android/jdk17' は...認識されません` になる。

→ PowerShell では `$env:JAVA_HOME="..."; & "..."` の形にする（3.4節に両方の書式を記載）。

### 4.4 ★QAIRT 2.48 は Windows では Python 3.10 必須（ドキュメントの記述と実体が食い違う）

SDK 同梱の `bin/check-python-dependency` には

> Currently supported: Python **3.10 and 3.12**

と書かれているが、**Windows x86_64 の拡張モジュールは実際には Python 3.10 にしかリンクされていない。**

Python 3.12 環境で `qairt-converter` を実行したときの症状:

```
ImportError: DLL load failed while importing libDlModelToolsPy312: 指定されたモジュールが見つかりません。
```

`os.add_dll_directory()` で SDK の `lib\x86_64-windows-msvc` と `bin\x86_64-windows-msvc` を追加すると**一段進んで**別のモジュールで同じ失敗になる:

```
ImportError: DLL load failed while importing libPyIrGraph312
```

**DLL 検索パスの問題に見えるが、真因は違った。** PE のインポートテーブルを全件調べた結果（`pefile` を使用）、

- `lib/python/qti/aisw/converters/common/windows-x86_64/` の 22個
- `lib/python/qti/aisw/dlc_utils/windows-x86_64/` の 4個

**計26個の `.pyd` すべてが `python310.dll` を要求**していた。**`libPyIrGraph312.pyd` や `libDlModelToolsPy312.pyd` のように "312" と名付けられたファイルも `python310.dll`** を参照している（この版のパッケージング不整合）。

→ **QAIRT 専用環境を Python 3.10 で作り直して解決。** `qairt-converter --help` が正常に起動した。

**同種の症状が出たときの診断手順**（再利用可能）:

```bash
uv run --with pefile python -c "
import pefile, os
pe = pefile.PE(r'<問題の .pyd>', fast_load=True)
pe.parse_data_directories(directories=[pefile.DIRECTORY_ENTRY['IMAGE_DIRECTORY_ENTRY_IMPORT']])
print(sorted({e.dll.decode() for e in pe.DIRECTORY_ENTRY_IMPORT}))
"
```

`api-ms-win-*` は OS の API セットなので「見つからない」と出ても問題ない。**`pythonXXX.dll` の XXX を見る**のが要点。

### 4.5 `check-python-dependency` が pip を要求する

必須パッケージの検査はすべて通るのに、最後に次で落ちた。

```
subprocess.CalledProcessError: Command '[...python.exe, -m, pip, list]' returned non-zero exit status 1
```

同スクリプトは内部で `python -m pip list` を呼ぶが、**`uv venv` は既定で pip を入れない**ため。

→ QAIRT 専用環境に `pip` を明示的に入れて解決。なお同スクリプトは**仮想環境の中でしか実行できない**（`VIRTUAL_ENV` / `CONDA_DEFAULT_ENV` を検査して、無ければ終了する）。

### 4.6 QAIRT とプロジェクト本体の Python 依存は共存できない

要件定義書 NFR-5 の「環境を分ける」は当初は予防的な方針だったが、**実測で必要性が確定した。**

| パッケージ | QAIRT 2.48 の要求 | 本体 `.venv` の実際 | 判定 |
|---|---|---|---|
| **numpy** | **1.26.4** | **2.5.3** | **共存不可** |
| **opencv-python** | **4.8.1.78** | **5.0.0.93** | **共存不可** |
| matplotlib | 3.10.8 | 3.11.2 | 衝突 |
| pillow | 10.2.0 | 12.3.0 | 衝突 |
| psutil / packaging / pytest / rich | 6.1.1 / 24.0 / 8.1.1 / 13.9.4 | 7.2.2 / 26.3 / 9.1.1 / 15.0.0 | 衝突 |

さらに **QAIRT の依存リストに `onnx` / `onnxruntime` は含まれない**。つまり「**量子化は本体環境（ORT）、変換は QAIRT 環境**」という分担が SDK 側の設計と一致している。ZipDepth のビルドスクリプトも QAIRT 専用 Python とシステム Python を使い分けていた。

### 4.6b QAIRT 専用環境には `onnx` も必要だった（4.6 の補足・訂正）

4.6節で「QAIRT の依存リストに `onnx` / `onnxruntime` は含まれない」と書いたが、
**`qairt-converter` は ONNX フロントエンドで `import onnx` する**ため、QAIRT 専用環境にも
`onnx` が必要である。入れないと変換が次で落ちる。

```
ERROR - Encountered Error: Error loading onnx, Message: No module named 'onnx'
  File ".../qti/aisw/converters/onnx/onnx_to_ir.py", line 26, in <module>
```

→ 追加インストール。**`numpy==1.26.4` を明示して固定する**こと（onnx が numpy 2.x を
引き込むと QAIRT の要求を壊す）。

```bash
uv pip install --python D:/QAIRT/qairtenv/Scripts/python.exe "onnx>=1.16,<1.18" "numpy==1.26.4"
```

**教訓**: `check-python-dependency` の `required_packages` は**そのスクリプトが検査する対象の
一覧**であって、SDK の全依存の網羅ではない。「リストに無い＝不要」と読んではいけない。

### 4.6c 本体環境には `sympy` が必要

`quant_pre_process` の symbolic shape inference が `sympy` を要求する。
形状が埋まらないと per-channel 量子化が成立しないため、`skip_symbolic_shape=True` で
逃げるのではなく入れる。

### 4.7 QAIRT のダウンロードURLは HEAD では 403 を返す

`curl -I`（HEAD）だと **403 Forbidden**、GET なら 200/206 で実体が取れる。

→ **403 を見て「認証が必要」と判断しない。** 認証は不要である（Community 版）。

### 4.8 ダウンロード速度はホストによって大きく違う

- Android cmdline-tools（`dl.google.com`）: 約 **250KB/s**（148MB に約10分）
- QAIRT（`softwarecenter.qualcomm.com` → AWS）: 約 **10MB/s**（2.1GB に約3.5分）

→ 前者が遅いのは回線ではなく配信側の事情。**回線速度をボトルネックと誤認しない。**

## 6. 作業分担（Claude Code 側の代行可否）

4.2節の制約に由来する。

| 代行できる | 代行できない |
|---|---|
| curl による任意のダウンロード、**Python 全般**（uv/pip・ONNX量子化・**QAIRT の Python ツール**）、**QAIRT のネイティブ exe**（`qnn-context-binary-generator` 等）、adb、git（LFS含む）、ファイル配置、文書作成 | **`sdkmanager`**、**Gradle の依存解決** → **Android APK のビルド** |

P2 以降の本線（量子化 → QAIRT 変換 → context binary 生成 → ORT 実行）は Python とネイティブ exe で完結するため代行可能。JVM が必要なのは実質 **P1 の APK ビルドだけ**である。
