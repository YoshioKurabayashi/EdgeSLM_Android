## 1. 背景・目的

### 1.1 背景

既存プロジェクト EdgeSLM（`D:\AI\source\n_chap5\EdgeSLM`）は Phase A（PC上でのPython実装によるアルゴリズム検証）をほぼ完了し、EdgeSLM-cpp では自作推論パイプラインのC++移植がPython版とトークン列完全一致まで到達している。しかし両者はいずれもPC上の検証であり、**Qualcomm SoC 実機・NPU(HTP) への搭載は未着手**である（EdgeSLM 要件定義書4.2節 Phase B）。

一方、エッジ環境へSLMを搭載するうえで中核となる要素技術——NPUへの割り当て、量子化、静的形状化、KVキャッシュのNPU向け設計——は、実機なしでは習得できない。

### 1.2 目的

本プロジェクトの目的は **製品の構築ではなく、Qualcomm NPU へのSLMポーティング要素技術の習得**である。具体的には以下を実測をもって理解する。

1. **NPUの利用と割り当て**: どの演算がHTPに載り、どれがCPUに落ちるか。その切り分けをどう観測するか
2. **量子化の勘所**: v68で選択可能な量子化方式と、精度・速度・メモリのトレードオフ
3. **LLM固有の難所**: 静的形状化、prefill/decode分離、KVキャッシュのNPU向け構成
4. **エッジ固有の制約**: メモリ制約の階層（PD / FastRPC-SMMU / VTCM / システムRAM）、サーマルスロットリング、電力

最終的な到達目標は **SOG05 上でローカル完結して軽量SLM（Qwen2.5-0.5B）が動作すること**。ただし3.3節の通り「SM8350 × LLM」の組合せは現時点で公開実証がなく、**到達できないこと自体も成果として記録する**方針とする。

### 1.3 位置づけ

- 本プロジェクトは **EdgeSLM / EdgeSLM-cpp / EdgeSLM_Offload とは独立した別プロジェクト**である。既存3プロジェクトのソースコード・ドキュメントには一切変更を加えない
- EdgeSLM の Phase B への正式なインプットとしては位置づけない。得られた知見が固まった段階で、改めて Phase B へ反映するかを判断する
- Git管理の対象外とする（EdgeSLM本体のみGit対象という既存方針を踏襲）
- 成果物の主体は**コードではなく実測記録**である。各フェーズごとに `DoC/フェーズ記録_Pn.md` を残す

## 2. 検証の考え方

### 2.1 段階構成の理由

本検証は「Qwen2.5-0.5B を ONNX 化して QNN EP を指定する」という一発勝負を**意図的に避ける**。Transformer は数百〜数千の演算から構成され、丸ごと変換して失敗した場合に原因の切り分けが発散するためである。

したがって次の順で、**失敗時に原因が一意に特定できる粒度**に分解して進める。

```
P0   足場（端末・ビルド・計測）
  ↓
P1   配管Gate       : 既知の成功例（ZipDepth）をSOG05で再現
  ↓                   → SM8350/v68/FastRPC/QAIRT の配管を一括確認
P1.5 実現性スパイク : ExecuTorch の v68 recipe で Qwen2.5-0.5B を移植
  ↓                   → 「SM8350 × LLM」が成立するかを最短で確認
P2   ORT本線        : 小型A16W8 QDQモデルを自前パイプラインでHTPへ
  ↓
P2b  重点op検証     : Transformer構成要素を個別にHTPへ通す（最重要Gate）
  ↓
P3   経路比較と熱
  ↓
P4   Decode（AR-1）
  ↓
P5   Prefill（AR-N）+ Hybrid
  ↓
P6   最適化（A8W8 / 混合 / W4）
```

### 2.2 ORT を第一ルートとし、ExecuTorch をオラクル兼フォールバックとする

現時点の実証状況は2つの軸に分かれて互いを補完している。

| | SoC軸（SM8350での実証） | LLM軸（v68でのLLM実証） |
|---|---|---|
| **ORT + QNN EP** | ○ ZipDepth が実機動作 | × 実例なし |
| **ExecuTorch + QNN** | △ QcomChipset に定義のみ | ○ SA8295/v68 で Qwen2.5-0.5B 動作 |

**未実証なのは「SM8350 × LLM」の交点のみ**である。

- **第一ルートは ORT + QNN EP**。理由は ①SOG05 と同一SoC・同一メーカー端末での公開実証がORT経路である ②EdgeSLM / EdgeSLM-cpp の既存資産がORTベースである ③最終目標のC++推論サービスと親和性が高い
- **ExecuTorch は「弱いフォールバック」ではなく、実現性判定のオラクル兼有力な代替**として位置づける。P1.5 の目的は製品化ではなく、①ハードウェア側に根本的な壁がないことを先に確定させる ②基準値（tok/s・TTFT・RAM）を得る ③後にORTが詰まったとき「端末の限界」ではなく「ORT側の問題」と切り分け可能にする、の3点である
- **ただし P1.5 の成功は ORT での成功を保証しない**。ExecuTorch と ORT では lowering 後のQNNグラフが同一とは限らない。この点を明示的な前提とする
- ORT / ExecuTorch の最終決定は **P3〜P4 まで保留**する

### 2.3 ExecuTorch の v68 recipe の扱い

ExecuTorch Issue #18280 で Qualcomm collaborator が提示した v68 向け recipe 修正は、**「どの演算・どの精度が v68 で危険か」を示す仕様書として利用する**。ただし ExecuTorch（ATen graph → QNN Quantizer）と ORT（ONNX graph → QDQ → QNN EP）ではグラフ表現が異なるため、**そのままの精度設定を移植はしない**。危険箇所を特定し、ORT側で同等のQNN制約を個別に検証する（FR-6）。

### 2.4 メモリ制約は階層で扱う（断定しない）

v68 環境では複数のメモリ制約が別レイヤで存在する。**これらを一括して「PDメモリが律速」と単一化しない**。

| 層 | 内容 | 既知の事例 |
|---|---|---|
| **HTP PD メモリ** | QNN context をロードする処理ドメインの容量 | InternVL3-1B の vision encoder（605MB の `.pte`、context size estimate 697,858,304バイト）が SA8295(v68) でロード失敗（#18410） |
| **FastRPC / SMMU マッピング** | shared weight バッファの DSP へのマップ | InternVL-2B の約467MB の shared weight が mmap 失敗（err 1002、#18862・Open） |
| **VTCM** | HTP 内の高速スクラッチ領域。tiling・spill/fill・性能に影響 | SM8350 は 4MB、SA8295 は 8MB、QCM6490 は 2MB |
| **システムRAM** | 8GB。プロセス全体 | — |

**重要**: 上記の数値を SOG05 の上限値として扱ってはならない。#18410 は **Closed（completed）** であり、同じ報告者は後続の #18862 で「InternVL-1B の推論には成功した」と明記している。また #18410 で `num_sharding` を 1→24 にしたのは **LLM側の設定**であり、失敗していた vision encoder に対する分割ではない。したがって「v68では約670MB以上は載らない」「shardingはPD対策として効かない」はいずれも成立しない。**SOG05 での実効上限は未確定であり、FR-8 で実測する。**

### 2.5 事前に把握しているリスク

| # | リスク | 影響 | 対処 |
|---|---|---|---|
| R-1 | **大きな QNN context のロード失敗**（PD メモリ / FastRPC-SMMU マッピング） | 大。v68 で 4〜7百MB級の context / shared weight がロード失敗した事例が複数ある（2.4節）。ただし閾値は不明で、1Bクラスが動いた報告もある | FR-8 で SOG05 の実効上限を実測。sharding / 複数コンテキスト分割を初期から**設計可能な状態にしておく**。顕在化した場合の回避候補として W4 と `htp_share_resource_optimization` を保持 |
| R-2 | **SOG05 は VTCM 4MB**（LLM成功例の SA8295 は 8MB） | 中。tiling・spill/fill・性能面の制約。**PD容量とは別レイヤ**であり、VTCMが半分だからcontext上限も半分になるという根拠はない | P1.5 / P3 で性能面の影響を観測。SA8295 の性能・配置条件をそのまま転用しない |

| R-5 | **MatMulNBits の v68 での実効可否が未確定** | 中。v2.3 の HTP 実装は fp16 Conv2D を経由するが、**v2.6.0 で uint16/int16 QDQ 活性化に対応**した。採用版により結論が変わる | FR-7 で**複数バージョン（2.48系 / 2.50.40系）で単体試験**する。本線は A16W8 なので結果に依存しない |

| R-7 | **SOG05 固有の firmware / carrier 差** | 中。ZipDepth の実機は Xperia 1 III (SO-51B)。同じSM8350でも CDSP/FastRPC の公開状態は同一とは限らない | P1 を最初のGateに置く |
| R-8 | **キャリア版のため bootloader unlock 不可** | 小 | root非前提で設計。adb shell + アプリの範囲に限定 |
| **R-9** | **`adb shell` からも `run-as` からも FastRPC を開けない（実測・確定）** | **成果物の形が変わる。HTP 経路は「アプリプロセス内で推論を動かす」形が必須** | 2026-09-12 実測確定。`/dev/adsprpc-smd` は `shell`（`u:r:shell:s0`）からも `run-as`（`u:r:runas_app:s0`）からも `O_RDONLY` で `errno=13`。DAC は other に read を許可しているため**拒否は SELinux**で、`adsprpc_device` へのアクセス権は **`untrusted_app` ドメインにのみ**ある（アプリ本体プロセスでは fd 90/91 が実際に open されていることを確認）。`libcdsprpc.so` 自体は dlopen でき API シンボルも見えるため「ライブラリは使えるがデバイスが開けない」状態。→ **対処は案②（アプリプロセス内で推論）に確定**（未決事項#14、`results/P0c2_20260912_selinux_domain.md`） |

#### ★Windows では QAIRT 2.48 は Python 3.10 が必須（ドキュメントの記述と実体が食い違う）

`bin/check-python-dependency` は「Currently supported: Python **3.10 and 3.12**」と明記しているが、**Windows x86_64 の拡張モジュールは実際には Python 3.10 にしかリンクされていない**。

PE のインポートテーブルを全件調べた結果（2026-09-12）、`lib/python/qti/aisw/converters/common/windows-x86_64/` と `lib/python/qti/aisw/dlc_utils/windows-x86_64/` の **26個の `.pyd` すべてが `python310.dll` を要求**していた。**`libPyIrGraph312.pyd` や `libDlModelToolsPy312.pyd` のように "312" と名付けられたファイルも `python310.dll`** を参照している（この版のパッケージング不整合）。

症状: Python 3.12 環境で `qairt-converter` を実行すると
`ImportError: DLL load failed while importing libDlModelToolsPy312` → `os.add_dll_directory` で SDK の `lib`/`bin` を追加すると一段進んで `ImportError: DLL load failed while importing libPyIrGraph312` になる。**DLL 検索パスの問題に見えるが、真因は Python のバージョン不一致である**（`python310.dll` が無い）。

- ライセンス: QAIRT バイナリは proprietary。**アプリに組み込んだ形でのオブジェクトコード配布は許可されるが、QAIRT 単体での再配布は禁止**（ZipDepth `DEPENDENCIES.md` の記述）。成果物の受け渡し時に関係する（未決事項#12）

→ **当初「社内手続きを要するクリティカルパス」と想定していたが、その前提は解消された。** P0 → P1 → P2 を待ち時間なしで連続実行できる見込み。

### 3.4 SM8350/v68 で context binary のロードが失敗する禁止事項（実証済み一次情報）

ZipDepth の `tools/variants/README.md` および `compile_variants.sh` のコメントに、**同一SoC（SM8350/v68）で `QnnContext_createFromBinary` が `error 1002` になる条件が実証付きで文書化されている**。同スクリプトは「出荷済みの動作するcontext binaryをバイト同一に再生成できる」ことが検証されており、信頼度は高い。**本プロジェクトはこれを設計制約として最初から守る。**

| # | 禁止事項 | 理由 | 正しい形 |
|---|---|---|---|
| **C-1** | **グラフ内に float セグメントを残す** | float op は **fp16 HTP op** としてコンパイルされ、**Hexagon v68 の skel は fp16 非対応**。結果 `createFromBinary` が err 1002 | **全op型を量子化した完全QDQ**にする。既定の `quantize_static`（既定op集合）は batchnorm / sub / div を float のまま残すため**CPU評価用にしかならない** |
| **C-2** | **`soc_id` を刻む（socModel=30）** | **unsigned PD は DSP の SoC id を照会できず**一致を証明できないため、ランタイムが binary を拒否（err 1002） | 生成は **`--htp_socs sm8350` のみ**。生成物は **`socModel = 0` + dsp_arch v68** になる（これが出荷済み動作版の形） |
| **C-3** | **backend_extensions の `devices`/`cores` を生成時に渡す**（`perf_profile: burst`、`rpc_control_latency` 等） | perf_profile が binary に埋め込まれるが、**unsigned PD は power config を適用できない**ためロード失敗（err 1002） | backend_ext config を**渡さない**。→ **副作用として burst 等の電力プロファイルは本プロジェクトで使えない**（FR-11 の測定条件に反映） |
| **C-4** | **float 混在グラフに `--preserve_io_datatype` を付ける** | 変換器が **unpreparable な fp32 op** を出力し finalize が err 1002 | **完全QDQに対してのみ**付ける。これでグラフI/Oはfloat32、内部は全て固定小数点になる |
| **C-5** | **`BatchNormalization` を残す** | HTP は **signed per-channel Conv QDQ と BatchNorm の併存を拒否**（**error 3110**） | 量子化前に **`Mul`+`Add` へ畳む** |
| **C-7** | **`<uses-native-library>` を宣言しない**（アプリ化する場合） | **Android 12+（API 31以降）では、vendor のネイティブライブラリを使うアプリはマニフェストで明示宣言しないとリンカ名前空間に含まれない**。宣言が無いと **FastRPC クライアント `libcdsprpc.so` に到達できず**、`QnnDevice_create` が失敗する。**症状が真因を示さない**のが最大の罠で、`QNN_DEVICE_ERROR_INVALID_CONFIG: Invalid config values` → `EPContext node is not compatible with any execution provider` と表示される（「config が不正」「EP が無い」と言われるが実態は「DSP に繋がれない」） | マニフェストの `<application>` 直下に次を置く。`required="false"` は DSP を持たない端末でもアプリが起動できるようにするため（ZipDepth も同じ）<br>`<uses-native-library android:name="libcdsprpc.so" android:required="false" />`<br>`<uses-native-library android:name="libadsprpc.so" android:required="false" />`<br>**2026-09-12 に実機で確認**（`results/v01_20260912_runner_acceptance.md`）。**シェルから `dlopen` できることは根拠にならない** — シェルバイナリはアプリの名前空間制限の対象外である |
| **C-8** | **活性化 × 活性化の MatMul を `uint16 × uint16` で量子化する** | **2026-09-13 に制約を狭く特定し直した。**当初「両辺が活性化なら 16bit 不可」と理解していたが、実際は**組合せ依存かつ非対称**である:<br>`u16 × u16` → **不可**（`has incorrect Value 68, expected >= 73` / `validateOpConfig failed 3110`）<br>**`u16 × u8` → 可**（context 生成も実機実行も成功）<br>**`u8 × u16` → 不可**（同上のエラー。**表では可とされているが実機は非対称**）<br>`u8 × u8` → 可<br>attention の **QK^T** と **PV** がこれに該当する | **左辺を uint16、右辺を uint8 にする**。attention なら Q と 確率 P が 16bit、**K と V が 8bit**。これで**スコア（MatMul の出力）を 16bit に保てる**のが肝で、両側 A8 にするとスコアが 8bit になり softmax が壊れる。<br>**ORT の量子化器では表現できない**（入力型を必ず揃える。`add_qtype_converts=True` なら変換ノードを挿して 8bit へ落とし、`False` なら指定ごと無視して 16bit に戻す）。`app/pipeline/force_mixed_matmul.py` で **QDQ を直接書き換える**。<br>**さらに `A×B = (B^T×A^T)^T` の等価変形で、右辺に置くテンソルを選べる**（`preprocess.swap_actact_matmul_operands()`）。QK^T で K（±130、1段階 0.99）ではなく Q（[-10,6]、1段階 0.064）を右辺へ持てば**分解能が 15倍**。<br>効果（実測）: 層1枚の相対L2 **30.4% → 19.2%（入替なし）→ 9.3%（入替あり）**／end-to-end top-1 **50.0% → 66.5% → 80.7%**（到達不可能な上限は 85.2%）／fp32 top1 の順位 **20.6位 → 1.95位 → 1.34位**／実機 **17.42ms → 14.29ms**（`results/P3_20260913_mixed_matmul.md`） |
| **C-9** | **因果マスクの定数を `-3.4e38` / `-inf` のまま量子化する** | HuggingFace の因果マスクは **`-3.4028235e+38`（float32 の最小値）**を使う。量子化は「最小値〜最大値を N 段階に割る」処理なので、この値が1つ混ざると**全分解能がそこに食われ、実際のスコアが丸ごと潰れる**（16bit で 1段階 0.0006 → 5e33）。エラーにはならず**精度だけが静かに壊れる**のが最も危険な点 | **有限値（既定 -60.0）へ置き換える**。`exp(-60) ≒ 8.8e-27` なので遮断としては十分で、分解能も食わない。小さすぎると遮断が甘くなり、大きすぎる（-1e4 等）と分解能を失うため両方を見て決める。`app/pipeline/preprocess.py` の `clamp_extreme_constants()`。**2026-09-12 に本物の Qwen2.5-0.5B で検証**: 置換前後の logits は fp32 で**完全にビット一致**（`results/P2b_20260912_real_form.md`） |
| **C-10** | **`Expand` を含んだまま context binary を作る** | **HTP v68 は `Expand` を含む context binary をロードできない**（`Failed to create context from binary. Error code: 1002`）。**ホストの `qnn-context-binary-generator` は素通しする**ため、端末に持って行くまで分からない。HuggingFace の GQA ヘッド複製が `Unsqueeze`→**`Expand`**→`Reshape` で出るため、**実モデルでは必ず踏む** | **`Concat` の繰り返しへ書き換える**。「サイズ1の軸を n 倍」なら同じテンソルを n 個 `Concat` するのと結果は同一。`app/pipeline/preprocess.py` の `rewrite_expand_to_concat()`（fp32 で最大絶対差 0 を確認済み）。**実機で単体切り分け済み**: `unsqueeze_only`=OK / **`expand_only`=err1002** / `gqa_concat`=OK。`Unsqueeze` は無罪で **`Expand` 単独が原因** |
| **C-11** | **RMSNorm の `x²` をそのまま量子化する** | 残差に少数の巨大チャンネル（±1677）があるため **`x²` のレンジが約280万**になり、uint16 で **1段階 42.7**。**通常チャンネルの `x²`（0.04 程度）が丸ごと 0 に潰れ**、巨大値を持たないトークンでは `mean(x²)` が壊れて正規化の分母が狂う。これが無いと **24層は top-1 4.5%（fp32 との相関 0.125）で破綻**する | **RMSNorm のスケール不変性**（`x/√mean(x²) = (x/m)/√mean((x/m)²)`）を使い、**m = トークンごとの max|x|** で割ってから二乗する。`xs²` が [0,1] に収まり **1段階 1.5e-05**（280万倍の改善）。`mean(xs²) ≥ 1/C` なので分母がゼロに潰れる心配も無い。eps は m² 倍されるので 1e-12 へ置換（fp32 での差は相対L2 0.22% / top-1 100%）。`app/pipeline/preprocess.py` の `normalize_rmsnorm_input()`。**効果: 6層 6.2%→74.4% / 24層 4.5%→80.7%** |
| **C-12** | **大きなモデルを `embed_mode=1` の EPContext にする** | binary が ONNX に埋め込まれるため、**ロード時に ONNX 本体と QNN 側のコピーで二重に持つ**。736MB の context では **RSS が 1.47GB に達して SIGKILL**（ログは途切れ、`lowmemorykiller` は「Not killing」と言う）。420MB では `embed_mode=1` のままでも動いたので、**境界はその間のどこか** | **`embed_mode=0`** にして binary を別ファイルにし、`ep_cache_context` にファイル名を入れて ONNX と同じディレクトリに置く。**ONNX が 772MB → 442バイト**になる。`wrap_epctx.run(..., embed=False)`。**2026-09-13 にこれでフル24層（772MB）が実機動作**（`results/P3_20260913_full24_device.md`） |
| **C-6** | **`useLegacyPackaging = false`（AGP の現代の既定）のままにする**（アプリ化する場合） | 既定では `.so` が APK 内に**無圧縮(STORED)で格納され、APK から直接 mmap でロードされる**ため、**ファイルシステム上に `.so` の実体パスが存在しない**。**FastRPC は V68 skeleton に通常のファイルシステムパスを要求する**ため開けない | `packaging { jniLibs { useLegacyPackaging = true } }` を設定する。これによりマニフェストに **`android:extractNativeLibs="true"`** が入り、**インストール時に `.so` が実ファイルとして展開される**。**検証はマニフェストの `extractNativeLibs` で行う**（`aapt2 dump xmltree --file AndroidManifest.xml <apk>`）。**APK 内の圧縮方式（STORED / DEFLATED）を見るのは誤り** — ZipDepth の実物は DEFLATED かつ `extractNativeLibs=true` で正常に動作している（2026-09-12 に APK を実検証） |

## 4. スコープ

### 4.1 対象

- SOG05 実機上での HTP(NPU) 推論の実現と計測
- 軽量MLモデル（CNN / BERT系）および軽量SLM（Qwen2.5-0.5B）
- ORT + QNN EP を第一ルートとした推論パイプライン
- ExecuTorch + QNN を実現性オラクル兼フォールバックとして使用
- **成果物の形（2026-09-12 の実測により確定）**
  - **CPU 経路**: adb 経由で動作する arm64 ネイティブ CLI（当初想定どおり）
  - **HTP(NPU) 経路**: **最小の推論サービス APK（UIなし Service + JNI + C++ 推論コア）を adb から駆動する形**。R-9 により `adb shell` / `run-as` からは FastRPC を開けず、`untrusted_app` ドメイン＝アプリプロセス内で動かす以外に手段がないため（未決事項#14 で決着）
  - **これは当初目標と矛盾しない。** 本プロジェクトの最終目標は「**C++ で作成した推論サービスを搭載**して軽量 SLM をローカル完結で動かす」ことであり、JNI 経由で C++ 推論コアをアプリプロセス内で動かす構成はその目標形そのものである。変わるのは**起動の外形**（`adb shell <bin>` → `adb shell am ...`）だけで、C++ 推論サービスという中身は変わらない
- 各フェーズの実測記録の文書化

### 4.2 対象外

- **UI を持つ Android アプリ**（画面設計・操作性・プロダクト品質のアプリ化）。**ただし HTP 推論に必要な「UIなし最小 Service + JNI」は 4.1節の通りスコープ内に変更した**（v1.9）。作るのは adb から駆動する殻だけで、画面は作らない
- root / bootloader unlock を前提とする手法
- 1.5B以上のモデル（3.3.1節#9・2.4節の制約により本端末では非現実的）
- Genie / GenieX 経路（3.3.1節#8によりv68は対象外）
- 8 Gen 2以降の端末での検証（未決事項#6）
- 製品品質の実装（エラーハンドリング・運用機能など）

## 5. 機能要件

### FR-1: 端末プロファイルの実測取得

`adb` 経由で `ro.board.platform` / `ro.product.cpu.abi` / Android版数 / RAM / CPUコア構成 を取得し、温度・クロック・メモリ使用量を継続取得する計測ハーネスを構築する。NDKクロスビルドした arm64 バイナリを `/data/local/tmp` から実行できることを確認する。

### FR-2: 既知成功例の再現（配管Gate）

ZipDepth（SM8350/v68 向け A16W8 CNN）を SOG05 上で動作させる。これにより SM8350 / HTP v68 / FastRPC / `libcdsprpc.so` / HTP skeleton / QAIRT 2.48 の配管を一括確認する。**本項目の成否が以降全フェーズの前提となる。**

### FR-3: 実現性スパイク（ExecuTorch）

ExecuTorch の v68 向け recipe（3.3.1節#6）を **SA8295 から SM8350 へ移植**し、Qwen2.5-0.5B を SOG05 で動作させる。SA8295 は VTCM 8MB・weight sharing特例ありという差があるため、**単純移植が成立する前提を置かない**。取得するもの: 動作可否、tok/s、TTFT、ピークRSS、メモリ関連のログ（2.4節の3層それぞれ）。

### FR-4: ORT 推論パイプラインの確立

小型の A16W8 QDQ モデルに対し、以下のホスト側パイプラインを確立する。**ORT自身の x86 EPContext 生成経路は使用しない**（3.3.2節#22）。

```
ONNX(fp32) → QDQ量子化(A16W8) → qairt-converter
  → qnn-context-binary-generator --htp_socs sm8350
  → gen_qnn_ctx_onnx_model.py → EPContext ONNX
  → ORT + QNN EP
```

**生成時のオプションは `--htp_socs sm8350` のみとする。** 3.3.2節#12b に「`soc_model` が推奨識別子」とあるが、**これは実行時の provider option の話であり、生成時に SoC id を刻むのは v68 では禁止**である（3.4節参照。unsigned PD が DSP の SoC id を照会できないため `QnnContext_createFromBinary` が err 1002 で拒否する）。実行時 provider option で `soc_model` を強制するかは P2 で検証する（生成物が `socModel = 0` である以上、強制しない方針を既定とする）。

量子化の具体手順は ZipDepth の実証レシピに従う（3.4節）。

1. 独立した `BatchNormalization` を **`Mul`+`Add` に畳む**
2. `onnxruntime.quantization.shape_inference.quant_pre_process`（shape inference + optimization）
3. **`onnxruntime.quantization.execution_providers.qnn.get_qnn_qdq_config`** を使う。`calibrate_method=CalibrationMethod.MinMax`、`activation_type=QuantType.QUInt16`（A16。A8 は `QUInt8`）、`weight_type=QuantType.QInt8`、`per_channel=True`
4. `quantize(prep, out, cfg)` — **`quantize_static` に op リストを手で渡す形は使わない**

ホスト側の環境変数は `PATH` に `bin/x86_64-windows-msvc` と `lib/x86_64-windows-msvc` の両方、`PYTHONPATH=<QAIRT>\lib\python`、`PYTHONUTF8=1`。

EPContext ラッパーは ORT 公式の `gen_qnn_ctx_onnx_model.py`（3.3.2節#23）を第一候補とするが、**既知正解の最小スキーマも判明している**ため、合わない場合は自前ラッパーに切り替える。既知正解の属性: `EPContext` ノード（domain `com.microsoft`）、`embed_mode=1`、`ep_cache_context=<binary>`、`ep_sdk_version="2.48.0"`、`main_context=1`、`partition_name="QNNExecutionProvider_QNN_0"`、`source="QNNExecutionProvider"`、float32 I/O、`ir_version=9`、opset `("",17)` + `(com.microsoft,1)`、**batch は 1 に固定**。

### FR-5: HTP delegate の検証（2経路を分けて定義する）

検証手段は実行経路によって異なるため、以下を分けて実施する。

**A. QDQ ONNX を ORT に直接渡す場合**（比較・調査用）

- `disable_cpu_ep_fallback=1` を設定し、CPUへ暗黙に落ちていないことを強制確認する
- **Framework Op Tracing**（`qnn_op_trace.json`）により ONNX op と QNN op の対応を取得し、どのノードがdelegateされたかを一覧化する

**B. QAIRT native → EPContext 経路の場合**（本線 / FR-4）

- EPContext 化した後は、ORT から見て元の Transformer ノード群は既に QNN context 内部にあるため、A の partition log では中身が見えない
- したがって `qairt-converter` / `qnn-context-binary-generator` の変換・finalize ログ、および QNN グラフダンプ・`optrace` profiling（`profiling_level=optrace`、`qnn-profile-viewer`）により、**QNN 内部の演算構成とHTP実行状況を確認する**
- さらに **`qnn-context-binary-utility.exe --context_binary <bin> --json_file <out.json>`** で生成物のメタデータを取り出し、**`socModel = 0` であること**と **graph I/O が float32 であること**を検証する（3.4節の禁止事項に違反していないことの機械的チェック。ZipDepth の `check_meta.py` がこの検証を行っている）

### FR-6: Transformer 構成要素の重点検証（最重要Gate）

Transformer を丸ごと変換する前に、構成要素を個別に SM8350/v68 へ通す。3.3.1節#6 が示した危険箇所を優先する。

| 対象 | 検証内容 |
|---|---|
| RMSNorm / LayerNorm | **16a16w にならないこと**を保証できるか（#5・#6）。ORT の RMSNorm fusion（3.3.2節#18）が v68 で通るか |
| MatMul | 精度組合せごとの可否 |
| RoPE | `QNN_OP_ROPE`（3.3.2節#18）が v68 で通るか |
| Softmax | 出力encoding の扱い |
| Attention | **まず ONNX export 時に fused GQA を生成させない**方針を取る。生成された場合は MatMul/Softmax/MatMul へ分解して成立させる（3.3.2節#19） |
| KVキャッシュ I/O | 固定長での入出力構成 |

### FR-7: MatMulNBits の v68 単体試験（複数バージョンで実施）

小さな MatMulNBits 単体モデルを `htp_arch=68, soc_model=30` で finalize できるか確認する。**QAIRT 2.48系だけで判定してはならない。** v2.6.0 / QAIRT 2.50.40 では HTP が uint16/int16 QDQ 活性化を受け付けるようになっており（3.3.2節#17）、fp16 経路に依存しない可能性がある。両 baseline で試験し、結果を版ごとに記録する。本線（A16W8）は結果に依存しないため、失敗しても計画は継続する。

### FR-8: メモリ制約の切り分けと実効上限の実測

2.4節の3層（HTP PD メモリ / FastRPC-SMMU マッピング / VTCM）とシステムRAMを**別々に記録し、SOG05 における実効上限を実測する**。既知事例の数値（697,858,304バイト、467MB）は**他SoCでの事例であり、SOG05の閾値として扱わない**。

併せて `num_sharding` / 複数コンテキスト分割を**設計可能な状態**にしておく（後付けでは間に合わないため）。ロード失敗が顕在化した場合の回避候補として `htp_share_resource_optimization`（3.3.2節#20）も試す。

### FR-9: Decode グラフ（AR-1相当）

Qwen2.5-0.5B の decode 1ステップを固定形状グラフとして構成し、KVキャッシュ入出力を設計する。EdgeSLM Phase A の固定長KVキャッシュ実装（`app/pipeline/kv_cache.py`）および EdgeSLM-cpp の C++ 版を仕様の参照元とする。

### FR-10: Prefill グラフ（AR-N相当）と Hybrid 生成

固定長 prefill グラフを構成し、decode と組み合わせて生成を完結させる。メモリは **weight sharing なしを worst case として2グラフ分を実測**し、併せて **ORT/QNN toolchain の weight sharing 機構（3.3.2節#21）が SM8350 で実効的に使えるかを確認する**（3.3.1節#9の公式対応デバイスには含まれないが、機構自体は存在するため）。

### FR-11: 計測

全フェーズで共通に以下を取得する。TTFT、tokens/sec、ピークRSS、コンテキストバイナリサイズ、温度推移、クロック推移、量子化前後の精度。

**PDメモリ使用量は直接取得できない可能性がある。** 取得できない場合は、**QNN/FastRPC ログに出る context size estimate、context binary のファイルサイズ、プロセスRSS を代替指標**として記録する。

**重要な測定条件**: 3.4節の通り、**unsigned PD では `perf_profile`（burst）・`rpc_control_latency`・電力votes を適用できない**。したがって本プロジェクトで測る HTP 性能は**すべてデフォルト電力プロファイルでの値**であり、Qualcomm の公称値や burst 設定での他者の測定値と直接比較してはならない。この前提を全計測結果に併記する。

サーマル試験は2回実施する。

- **P3**: CPU fp32 / CPU int8 / HTP A16W8 を同条件比較し、5分連続推論のスロットリング曲線を取得
- **P5完了後**: 実SLMの連続decodeで再実施する。CNNや単一opの発熱とLLMの連続decodeでは挙動が異なるため、P3の結果を流用しない

### FR-12: バージョン行列の管理

3.2節の3本の baseline を明示管理し、各フェーズがどの baseline で実施されたかを記録する。版を上げる際は既存の実証構成（特にP1のZipDepth再現）を壊さないことを確認する。3.3.2節の【バージョン依存事実】は使用版を変更した時点で再確認する。

### FR-13: 量子化方式の段階的評価

**A16W8 → A8W8 → 混合A8/A16** を本線とする。一律適用ではなく**op単位で精度を指定**することを前提とする（3.3.1節#6）。

W4 の位置づけは **「必須ではなく、①Context/PD/FastRPC 制約が顕在化した場合の回避候補 ②decode の重み帯域律速に対する性能最適化」** である。v68 で取りうる W4 経路は以下の通りで、ORT 経路の可否は採用版に依存する。

| 経路 | v68での見込み |
|---|---|
| ORT MatMulNBits | **「fp16依存なので不可寄り」という従来の評価は撤回**。v2.6.0 で整数QDQ活性化に対応したため、**2.50系で再評価する**（FR-7）。ただし v68 で fp16 経路を完全回避できる証明はまだない |
| ORT LPBQ | 不可（V69以上） |
| ExecuTorch 16a4w（per-channel） | 可能性あり（v68での使用実例がある） |

### 7.1 Gate の合格条件

各 Gate は「動いた」という主観ではなく、以下の判定基準で通過を決める。

| Gate | 合格条件 |
|---|---|
| **P1** | ①深度マップが表示され推論が完了する ②**アプリ内蔵のオンデバイス精度テスト**（同梱の fp32 CPU 参照深度マップに対する採点）が通る ③**起動ログが `QNN HTP - EPContext - all nodes`**（または `QNN HTP - EPContext - CPU I/O boundary`）**と報告する** ④テレメトリの `HTP`（= `OrtApi::Run` 時間）が参考値 **40〜60ms**（384×384・ウォームアップ後）と同じオーダーに入る ⑤**推論中に `nspss-*-usr`（NPU温度）の上昇を観測できる**（ログに依存しない物理的裏取り。基本設計① 4.1/4.2節） |

**P1 の性質について**: 配布モデルは EPContext ノードを持つ ONNX であり、**EPContext ノードは CPU EP では実行できない**。したがって「NPU が使えず静かに CPU にフォールバックして結果だけ出る」という最も厄介な失敗モードは原理的に起きない。加えてアプリは SoC / QNN runtime / model / camera / inference のいずれかが非対応・失敗した場合に明示的にエラーを出す設計である。

**副産物**: 7つの variant（A16W8 / A8W8 × 384 / 320 / 288 / 256 px）が再インストールなしで画面上で切替可能なため、P1 の時点で「量子化方式と入力解像度に対する速度・精度・発熱」の比較データが取れる。**P3（経路比較と熱）の予習として活用する。**
| **P2** | ①session 作成成功 ②`disable_cpu_ep_fallback=1` を有効にしても成功する（＝全ノードがHTPに載っている） ③出力が PC 上の fp32 参照実装と許容誤差内（指標と閾値はP2で定義し記録する） |
| **P2b** | FR-6 の全対象について「そのままHTPで動く / 分解すれば動く / 動かない」のいずれかに判定が付く。かつ **Transformer 1ブロック相当を構成して HTP で完全 delegate できる** |
| **P3** | Gate ではない（ORT/ExecuTorch の判断材料が揃えば完了） |
| **P4** | ①decode 1ステップが HTP で完全 delegate される ②**20ステップ連続で PC 参照実装とトークン列が完全一致する**（EdgeSLM-cpp で有効だった検証手法を踏襲。KVキャッシュ管理に誤りがあれば数トークンで破綻するため、パイプライン全体の正しさの実質的証明になる） |
| **P5** | ①prefill + decode で文章生成が完結する ②生成トークン列が PC 参照実装と一致する ③2.4節の各メモリ層の使用量が記録されている |
