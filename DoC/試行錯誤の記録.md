| | |
|---|---|
| 最終更新 | 2026-09-13 |

| なぜ残すか | このプロジェクトで最も高価だったのは**誤った仮説で費やした時間**である。同じ壁に当たったとき最短で抜けるため |

## 読み方

失敗には**型**がある。型ごとにまとめた方が再利用しやすいので、そうしてある。
各項目は「**何をした → 何が起きた → 真因 → どう直したか → 学んだこと**」の順。

時系列で追いたい場合は [要件定義書.md](要件定義書.md) の改版履歴（v1.0〜v3.2）を見る。

## 型1: 「成果物ができた」を「成功した」と読んだ（7件）

**これが最多。** ツールは失敗してもサマリ行を出すことがある。

### 1-1. `dd` のサマリ行に騙された

FastRPC デバイスが開けるかを調べるのに `dd if=/dev/adsprpc-smd bs=1 count=0 | tail` を使い、
**`dd` が出すサマリ行を見て「開けた」と判断した。**

実際は `Permission denied` が出ていたが、`tail` で隠れていた。
`dd` は**失敗してもサマリを出す**。

→ 確実な open テストは `exec 3</dev/...`（リダイレクト）か `open(2)` を直接呼ぶ C プログラム。
**サマリだけを見ない。**

### 1-2. `Cache binary ... copied to` は失敗時も出る

`qnn-context-binary-generator` は**失敗しても**最終行に
`Cache binary for SM8350 copied to ...` を出す。**ファイルは作られていない。**

→ `build_context.sh` は最初から `ls *.bin` の実在確認で成否を見ていたため誤判定は免れた。
**ログの最終行を成否の根拠にしない。**

### 1-3. `quant_pre_process` が 47バイトの空モデルを無言で出した

24層（fp32 2.52GB）で、**例外も警告も出さずに 47バイトのファイル**を残した。
気付いたのは後段の `get_qnn_qdq_config` が `StopIteration`（`opset_import` が空）で
落ちたときで、**原因から遠く離れた場所**だった。

→ `preprocess._assert_sane()` を追加（ノード数と opset が空なら即座に落とす）。S4 にも同種の門を入れた。

### 1-4. `adb push` の「1 file pushed」

440MB を push して「1 file pushed, 0 skipped. 42.7 MB/s」と出たのに、端末にファイルが無い。
真因は **Git Bash のパス変換**で、宛先が `C:/Program Files/Git/sdcard/...` に化けていた。

→ `scripts/run_runner.sh` は `MSYS2_ARG_CONV_EXCL` を設定済みだが、
**手で adb を叩いたときに忘れた**。環境構築記録に書いてあった罠を再度踏んだ。

```bash
export MSYS2_ARG_CONV_EXCL='/data/local/tmp;/sys;/vendor;/dev;/system;/proc;/sdcard;/storage'
```

### 1-5. 自作スクリプトの `bash` 呼び出しが無言で何もしなかった

`subprocess.run(["bash", "scripts/run_runner.sh", ...])` が Python（Windows exe）から
解決できず、**エラーも出さずに何もしなかった**。「結果が見つからない」とだけ表示され、
**最初の2回は私が手で実行したジョブの結果を拾っていただけ**だった。

→ adb を直接叩く形に変更。**外部コマンドの成否を確認する。**

### 1-6. 完了判定を標準出力の文言で行った

`"done at" not in stdout` で失敗と判定していたが、**端末側は成功していた**。

→ 成果物（結果 JSON の `job_id`）で判定するよう変更。
**「何が起きたか」は出力の文言ではなく成果物で確かめる。**

### 1-7. 生成途中の context binary を掴んだ（2026-09-13 / err 1002）

マスク入力版 prefill（24層）を端末でロードしたら **err 1002**。
過去に err 1002 は `Expand`（C-10）と float 残存（C-1）で出していたので同じ系統を疑い、

| 調べたこと | 結果 |
|---|---|
| C-1（グラフ I/O 境界） | 問題なし |
| `Expand` の残存 | 0個 |
| 動く24層版との op 差分 | 新しい op 種別なし |
| **マスクをグラフ入力にすること自体**（単体 op を新規作成して実機確認） | **無罪**（`pass_strict`） |

…と4つ潰してから、**md5 を取って一撃で分かった**:

```
生成器の出力  ctx_qwenpm/qwenpm_ctx.SM8350.bin  772,338,648  b0bac94d…
自分が配った側 ctx/qwenpm_ctx.SM8350.bin        772,342,648  7253d994…   ← 4000 bytes 多い
端末                                            772,342,648  7253d994…   （転送自体は正しい）
```

真因は **context 生成が2回走っており、2回目が同じパスへ書き直している最中に読んだ**こと。
ログには「OK 736.56 MiB」と出ていたが、それは**1回目のログ**だった。

→ 生成完了（プロセス不在＋サイズと mtime の安定）を確認してからやり直したら一発で `pass_strict`。

**学んだこと:**

> **err 1002 は「v68 が非対応」とは限らない。バイナリが壊れていても同じエラーになる。**
> **サイズと md5 を先に確かめる。** 5秒で済み、切り分けの大半が消える。
> 1-4（adb push の嘘）と同じ型だが、今回は**転送ではなく生成側**だった。

## 型2: 症状が真因を示さない（4件）

| 表示 | 真因 |
|---|---|
| `EPContext node is not compatible with any execution provider` | **マニフェストの `<uses-native-library>` 宣言漏れ**（C-7） |
| `ORT Tensor data size does not match QNN tensor data size` | **EPContext ラッパーの I/O 型が float32 決め打ち**（int64 の索引を float32 と宣言していた） |
| `Failed to create context from binary. Error code: 1002` | **`Expand` が1個入っていた**（C-10） |
| `EncodeError: Failed to serialize proto` | **opset 18→21 の自動変換**が fp32 2.52GB をシリアライズしていた |

### 2-1. C-7 を突き止めるまで

症状は `QNN_DEVICE_ERROR_INVALID_CONFIG: Invalid config values` →
`EPContext node is not compatible with any execution provider`。
「config が不正」「EP が無い」と言われるが、**実態は「DSP に繋がれていない」**。

試して外したもの（7つ）: provider option の個別切り替え、`soc_model`、`htp_arch`、
`ADSP_LIBRARY_PATH` の自前設定、ライブラリの MD5 照合、APK の圧縮方式、SELinux ドメイン。

**決め手は「動いている参照実装（ZipDepth）とのマニフェスト全文比較」だった。**
もっと早くやるべきだった。

### 2-2. err 1002 の切り分け

`Expand` が原因と分かったのは、単体モデルを1つずつ実機で試したから:

| モデル | 結果 |
|---|---|
| `unsqueeze_only` | OK |
| **`expand_only`** | **err 1002** |
| `gqa_concat` | OK |

→ **`Expand` 単独が原因。`Unsqueeze` は無罪。`Concat` は代替として使える。**
`op_check` task（再ビルドなしで複数モデルを1回の実行で判定）がここで効いた。

## 型3: 見る場所を間違えた（9件）

### 3-1. スコアの L2 誤差だけ見て「問題ない」と判断しかけた

attention スコアを 8bit にしたとき、**テンソルの L2 誤差は 0.49%** しかなかった。
ところが **softmax を通すと 62.8%**、attention の argmax 一致は **29.2%**。

レンジが `[-26.7, +1600]` と広く、L2 ノルムは大きい値に支配されるため
誤差が小さく見えていた。1段階 6.38 の差は softmax の入力として約 590倍の確率差になる。

→ **量子化の良し悪しは「その先で何に使われるか」まで見て判定する。**

### 3-2. 最大値だけ見て分布を見なかった

「層の寄与 ±10〜20 が 1段階 0.051 に埋もれる」と説明したが、
**割り算すれば 196段階ある**。成立しない説明だった。

実測すべきだったのは分布で、測ると層2以降は **p50 が 7〜29段階**しか使えていなかった
（実質3〜5ビット）。

→ **max だけでなく p50/p90/p99 を見る。**

### 3-3. 誤差分解で分母を揃えていなかった

`fp32 → ホストQDQ → 実機` の3者を比べるとき、量子化誤差は `/‖fp32‖`、
実機差は `/‖ホストQDQ‖` としていた。**比較できない数字を並べていた。**

また **L2 は加算関係にない**（`9.31 + 13.25 ≠ 16.11` は当然）。
直交なら二乗和の平方根が合計に一致し、実測ではほぼ一致した（16.19 vs 16.11）。

→ **分母を揃える。絶対値も併記する。加算できると思わない。**

### 3-4. top-1 の低下幅で「HTP に下限がある」と解釈した

ホスト→実機の low下が「両側A8 は -3.4pt、入替版は -17.6pt」だったので
「量子化を詰めると実機側の下限が顔を出す」と解釈した。

**L2 で分解すると逆**で、実機差自体は粗い方式の方が大きい（31.98% > 20.21%）。
top-1 の低下が小さく見えたのは**元々精度が低く argmax がもう変わらない飽和**だった。

→ **指標を変えると結論が反転する。**

### 3-5. 24層破綻の原因を残差と推定した（→ oracle 実験で覆った）

「残差の massive activations（±1677）が各層の寄与を潰している」と説明した。
**oracle 実験（量子化を部分的に外して精度を測る診断）で覆った:**

| 除外した箇所 | top-1 |
|---|---:|
| なし | 6.2% |
| **残差（Add 43個）** | **6.2%** ← **1ポイントも戻らない** |
| **RMSNorm（52個）** | **74.4%** |

**真因は RMSNorm 内部の `x²`**（レンジ約280万 → 1段階 42.7）だった。

→ **推定で対策を決めていたら、まったく効かない残差側（SmoothQuant）を実装していた。**
**推定 → oracle で確定 → 実装**の順を守る。oracle 実験は5パターンで5分21秒。

### 3-6. top-1 73.3% から「精度が足りない」と判断しかけた

指標では 73.3%。しかし**実際に生成させると** well-formed なプロンプトで
**fp32 とトークン 6/6 一致**し、`The capital city of France is` → ` Paris.` と正答した。

そのとき「**現状の最大の品質要因は量子化ではなく窓のパディング**だ」とも考えたが、
これは後に **3-7 で撤回した**（実機で測ると答えはほとんど変わらなかった）。

→ **「読んだ方が早い」。数字だけ見て量子化を詰めていたら、効かない方向に工数を使っていた。**
→ ただし**同じ回で立てた2つ目の仮説（パディング）は外れていた。**
  「生成を読む」で得た確かな知見と、そこから推測した仮説は区別すべきだった。

### 3-7. 対策を実装してから「その問題が実際に出ていたか」を測った

「短いプロンプトだとパディングが混ざるので精度が落ちる」と考え、
**マスクをグラフ入力に出した prefill** を作った（約80分の context 生成を含む）。

実機で測ると:

| | 正解(パディング無し fp32)との一致 |
|---|---:|
| マスク入力版 | **6/8** |
| マスク無し版（従来） | **6/8** |

**8プロンプト中7つで同じトークンを出した。** 外れた2件は量子化誤差であって
パディングのせいではない（マスクを正しく与えた fp32 でも同じ所で外れる）。

→ 量子化モデル同士では差が見えなかった。**しかしこの比べ方が粗かった。**
後に fp32 だけで測り直すと、パディングは確かに答えを変えていた:

| 窓 | 正しいマスク | 全部見える |
|---|---:|---:|
| W=16 | 10/10 | **6/10** |
| W=64 | 10/10 | **3/10** |

**量子化モデル同士で比べたため「パディングの差」が「量子化の差」に埋もれていた。**
2つの誤差要因を比べるときは**片方を固定する**（ここでは fp32 で測る）。

なお当初そう見えた別の理由として、**全16位置で top-1 を平均していた**こともある（3-3 と同じ型）。

| 測る位置 | top-1 |
|---|---:|
| 全16位置 | 24.2% |
| 有効位置のみ | 63.3% |
| **最終位置のみ（生成で使う）** | **75.0%** |

**学んだこと:**

> **対策を作る前に、その問題が実際に出力を変えているかを測る。**
> 理屈の上で問題があることと、出力が変わることは別である。
> ただしマスク入力版は**パディング長が変わっても数学的に正しい**ので、
> 窓を 16→64 に広げるときの本線としては無駄にならなかった。

### 3-8. 並んだエラーの因果を決めずに真因を記録した（decode / `rms_norm`）

decode（seq=1 + KVキャッシュ）の context 生成が失敗し、ログにこう出ていた:

```
<E> "rms_norm_node___959230" generated: could not create op
```

「**QNN が RMSNorm を融合した op が seq=1 で作れない**」＝ QNN の融合ロジックの限界、
と記録した。最小モデル（`[1,1,896]` の RMSNorm）は通るので「融合の掛かり方依存」で止めた。

**誤診だった。** 残っていたログを読み直すと、失敗の最初の `<E>` は常に別のものだった:

```
<E> "QNN_DATATYPE_FLOAT_32_converted_past_k_0_QNN_DATATYPE_FLOAT_16"
      generated: could not create op
```

**KVキャッシュの float 入力が量子化されずに残っていた**（C-1 違反 48箇所）。
`node_mul_9` / `node_add_3` / `node_matmul_1` / `rms_norm_*` が「作れない」のは、
**float セグメントの近傍が fp16 op になった下流症状**である（v68 の skel は fp16 非対応）。

C-1 を直したら **`rms_norm` のエラーは一度も出ずに context binary ができ、
2層 decode が実機で動いた**（全ノード HTP / OrtRun 11.90 ms）。

**学んだこと:**

> **`could not create op` が複数並んでいるとき、どれが原因でどれが結果かを決める。**
> **float セグメントは近傍の op をまとめて壊す**ので、先に C-1 を潰してから残りを読む。
> 一番目を引いた名前（`rms_norm`）を真因として記録したのが誤りだった。
> 1-2（良性の ERROR 行）と同じ型で、**ログの読み順**の問題である。

さらに真因の真因は**ツールの制約**だった（型5と同じ）:

| float のグラフ入力の消費者 | ORT は量子化するか |
|---|---|
| `MatMul` | する |
| `Concat` | する |
| **`Slice`** | **しない**（`tensor_quant_overrides` でも強制できない） |

KVキャッシュの左シフトを `cat(past[:, :, 1:, :], k)` と書いていたので `past_k` が
`Slice` に直接入っていた。**`cat(past, k)[:, :, 1:, :]` に変えるだけで通った**（結果は同一）。

### 3-9. 指標が動かないのを「効かない」と読みかけた（キャッシュ I/O）

decode の精度不足は「キャッシュ I/O の再量子化が本命」と考えた。
**実装する前に Oracle で測った**のは正しく、結果は**寄与ゼロ**だった
（68.8% → 66.7%、相対L2 31.19% → 31.16%）。Concat/Slice・Softmax・RMSNorm 内部・
MatMul 全部を外しても横ばい。ここで「キャッシュ I/O は関係ない」と結論しかけた。

**しかし半分しか正しくなかった。** 単発の推論では**キャッシュを往復させない**ので、
往復で起きる問題は原理的に測れていなかった。

ホストで24トークンの decode ループを回すと**差が出たように見えた**（9/24 → 19/24）。
**しかしこれは1プロンプトの偶然だった。** 3プロンプトで測り直すと:

| | ホスト（72中） | 実機（72中） |
|---|---:|---:|
| そのまま | 28 | 17 |
| 量子化パラメータを揃える | **30** | **19** |

さらに**fp32 と同じトークン列を強制して軌道を揃える**と、キャッシュのずれも logits も変わらない
（k 11.00%→10.90% / v 24.98%→25.10% / logits 29.93%→30.47%）。
最初に見えた「キャッシュのずれ 77.6% → 46.9%」は、**分岐して別の文を書いていたから**だった。

clip の試算も過大だった。**出口範囲を一様に散らした**点で 3〜15% と見積もったが、
**実データの clip 率は 0.0094%**。値は0の近くに集中していて、はみ出す範囲の端がほぼ使われない。

機構も思っていたのと違った。「float32 で往復するから誤差が乗る」ではない——
**scale と zero point が同じなら往復は量子化格子の上の恒等写像で無損失**である。
真因は **ORT が `past_X` と `present_X` を別テンソルとして較正するため範囲が食い違い、
はみ出した分が clip される**ことだった（48本中42本、最大 15.5%）。

**学んだこと:**

> **指標が動かないとき、「効かない」と「その測り方では見えない」を区別する。**
> 単発の top-1 と相対L2 では、ループでの崩れ方が**まったく見えなかった**。

> **しかし「見えない差」を探しに行った結果、今度は無い差を見たと誤認した。**
> **少数サンプル**（1プロンプト）・**非現実的な分布**（一様分布で clip 率を試算）・
> **揃っていない軌道**（分岐した実行同士を比較）——3つとも同じ調査の中で踏んだ。
> **比較の条件を揃えてから差を読む。**

## 型4: 1つの事例を一般則に昇格させた（4件）

| 誤り | 実際 |
|---|---|
| 「Genie が v73+ を要求 → NPU で LLM 不可」 | Genie 経路の話。**ORT QNN EP は別経路**で SM8350 を正式サポート |
| 「PD メモリ 698MB が v68 の上限」 | **1件の事例**（しかも vision encoder）。実測では **736MB の context がロードできた** |
| 「`num_sharding` 24 でも効かない」 | その 24 は**失敗した encoder ではなく LLM 側の設定**だった |
| **「C-8 は両側 A8 にするしかない」** | **`u16×u8` が通る。回避策を1つしか試していなかった** |

### 4-1. C-8 の再特定が最大の転換点

当初「活性化×活性化の MatMul は 16bit 不可 → 両側 A8 にするしかない」と理解し、
**それを前提に「v68 は精度の壁」という結論まで出していた。**

外部からの「`uint16×uint8` は可では」という指摘を受けて実測すると:

| 組合せ | v68 |
|---|:--:|
| `u16 × u16` | 不可 |
| **`u16 × u8`** | **可** |
| `u8 × u16` | **不可**（引用された表では可。**実機は非対称**） |
| `u8 × u8` | 可 |

さらに `A×B = (B^T×A^T)^T` の等価変形で**右辺に置くテンソルを選べる**ので、
レンジの狭い Q を 8bit 側へ持ってくると**分解能が 15倍**になった。

結果: end-to-end top-1 **50.0% → 66.5% → 80.7%**（到達不可能な上限は 85.2%）。

→ **「回避策を1つ試して駄目だった」で結論を出さない。表も鵜呑みにしない。**

## 型5: ツールの制約をハードウェアの制約と取り違えた（1件）

ORT の量子化器は MatMul の入力型を必ず揃える:

| 設定 | 結果 |
|---|---|
| 既定（`add_qtype_converts=True`） | **もう片方にも変換ノードを挿して 8bit へ落とす** |
| `add_qtype_converts=False` | **指定ごと無視され**、全部 u16 に戻る |
| 出力だけ u16 に固定 | `Desired producer quant_type ... doesn't match existing type` で拒否 |

ここで「v68 では `u16×u8` は作れない」と結論しかけた。
**QDQ を直接書き換える**（`force_mixed_matmul.py`）と**通った**。

→ **「このツールでできない」と「このハードでできない」は別。**

## 型6: 実行主体を取り違えた（2件）

| 誤り | 実際 |
|---|---|
| 「シェルから `dlopen("libcdsprpc.so")` 成功 → アプリでも使える」 | **シェルバイナリはアプリの名前空間制限の対象外** |
| 「`run-as` なら通るはず」 | `run-as` は `runas_app` ドメイン。`untrusted_app` とは権限が違う |

HTP は **`untrusted_app` ドメインのプロセスからしか使えない**:

| 実行主体 | SELinux ドメイン | `/dev/adsprpc-smd` |
|---|---|---|
| `adb shell` | `u:r:shell:s0` | 拒否 |
| `run-as <pkg>` | `u:r:runas_app:s0` | 拒否 |
| **アプリ本体** | `u:r:untrusted_app:s0` | **open 成功** |

→ **同じ操作でも実行主体が違えば結論が変わる。検証は本番と同じ主体で行う。**

## 型7: 道具を目的外に使った（1件）

P2b で作った自作 op モデル（重み = `N(0, 0.05)` の乱数）を**精度測定に流用した。**

`block_real`（自作の Transformer 1ブロック）の誤差が **0.01%** と出たが無意味だった。
出力 `x + attention(x) + FFN(x)` が**残差の `x` に支配され、誤差が薄まって見えた**だけ。

→ あれは「op が載るか」を見る道具で、精度を測る設計になっていない。
**道具を目的外に使うと静かに間違った数字が出る。**
**残差の前後を必ず両方測る**（branch が 20% でも残差後は 2% に見える）。

## 型8: 版依存の事実を固定化した（1件）

「MatMulNBits は fp16 依存 → v68 では不可」は **v2.3 時点の実装詳細**で、
v2.6.0 で整数 QDQ 活性化に対応して前提が変わった。

→ 要件定義書 3.3節を【固定事実】と【**バージョン依存事実**】に分離した。
後者は使用版を変えたら再確認する。

## 型9: 文書の読み違い（1件）

`check-python-dependency` の `required_packages` に `onnx` が無いので
「QAIRT に onnx は不要」と結論した。**`qairt-converter` は `import onnx` する。**

`required_packages` は**そのスクリプトが検査する対象の一覧**であって、全依存の網羅ではない。

→ **「リストに無い＝不要」と読まない。リストが何の一覧なのかを確認する。**

## 型10: 自分の検証コードのバグ（3件）

**検証側が壊れていると、正しい実装を「バグ」と誤判定する。**

### 10-1. 層数を揃えずに比較した

decode の自前配線を HF と突き合わせたとき、**自前は2層・HF は24層**で比べ、
最大絶対差 20.5 を見て「配線バグ」と判定した。HF 側も2層にしたら **4.3e-05** だった。

### 10-2. logits の判定条件が雑だった

`shape[-1] > 100` を logits とみなしたため、層出力 `[1,16,896]` の hidden 次元に対する
argmax を「top-1 一致 95.3%」として出した。**無意味な数字。**
→ 語彙サイズ級（`>= 10000`）に限定した。

### 10-3. C-1 検証器に穴があった

グラフ I/O を丸ごと検査対象外にしていたため、
「float の入力が `QuantizeLinear` を経ずに計算ノードへ入る」を見逃した。
`gqa_repeat` で **PASS を返したのに context 生成が落ちた**。

P2 のモデルは先頭が Conv（必ず量子化される）だったので穴が露出していなかった。
→ 修正後は 24件中、実際に落ちた1件だけを検出（誤検知ゼロ）。

### 10-4. 重み判定が甘かった（2回）

「入力名が initializer か」で活性化×活性化の MatMul を判定したが、
**QDQ では重みも `DequantizeLinear` 経由**、**fp32 では `Transpose` 経由**で入ってくる。

- `force_mixed_matmul` で**重み側の MatMul まで書き換えた**
- `swap_actact_matmul_operands` で **lm_head（896×151936）を左右入替**し
  `Invalid attribute perm {0,2,1}` で落ちた

→ どちらも **DQ / Transpose / Reshape などを辿って大元が initializer かを見る**よう修正。

## 効かなかった対策（再試行を防ぐために残す）

| 試したこと | 目的 | 結果 |
|---|---|---|
| **スケールを MatMul の前へ移す**（`Mul(MatMul(q,k),s)` → `MatMul(Mul(q,s),k)`） | attention スコアの分解能を上げる | **変化なし**（30.3819% → 30.3904%）。量子化されるのはスケール後の値なので当然だった |
| **softmax の前で行最大を引く** | 同上。numpy 単独試算では 62.8% → 3.2% と劇的 | **悪化**（30.4% → 41.6%）。**スコアは MatMul 出力時点で既に 8bit** なので打つ位置が違った |
| **MatMul の出力だけ 16bit に固定** | スコアを 16bit に残す | ORT が拒否（出力型は入力型と一致させる制約） |
| **Percentile 較正（p99.999）** | massive activations を切る | **効果なし**（top-1 6.2% のまま）。外れ値は少数次元に常時あるので切っても残る |
| **層分割（チャンク化）** | 24層の破綻を回避 | **この問題には無効**（チャンク入口で同じスケールで量子化される）。2GB 問題には有効 |
| **`seq=1` にして 2GB 問題を回避** | フルモデルの量子化 | **成立しない**（**重みは seq に依存しない**）。真因は opset 変換だった |
| **`init_overrides` でキャッシュ入力を量子化** | decode の C-1 違反を解消 | **効かない**（量子化器が `Slice` を素通し扱いにする） |
