# P10. 文脈長を 64 → 256 に伸ばす

- 日付: 2026-09-14
- 端末: Xperia 5 III SOG05 / SM8350 / HTP v68

---

## 1. KV キャッシュ 256 は v68 で動く

| 24層 decode（C-13 + per-channel） | KV 64 | **KV 256** |
|---|---:|---:|
| 全ノード NPU / strict | ✓ | **✓** |
| DLC 検査（型とエンコーディング） | 2,132本 整合 | **2,107本 整合** |
| VTCM spill / fill | 0 / 0 | **0 / 0** |
| context binary | 772,065,064 B | **772,101,928 B**（+37KB） |
| **OrtRun** | 29.26 ms | **35.80 ms** |
| **スループット** | **34.2 tok/s** | **27.9 tok/s**（−18.4%） |
| **★ホストQDQ ↔ 実機HTP** | **16.48%** | **17.00%** |

**KV を4倍にしても HTP 側の誤差は増えていない**（16.48% → 17.00%）。
代償はレイテンシ +22.4% / スループット −18.4% だけ。

キャッシュのメモリ（24層・float32 で持ち回り）:

| 長さ | 64 | 256 | 512 | 1024 |
|---|---:|---:|---:|---:|
| | 1.5 MB | **6.0 MB** | 12.0 MB | 24.0 MB |

### 途中で足りなかった道具

**`downgrade_actact_rhs.py`（新規）** — C-8 は「act × act の MatMul は `u16×u8` のみ」なので、
左右入替（swap）だけでは足りず**右辺を 8bit に落とす**必要がある。
`p2b_ops` では `a16w8_rms_swap` と `a16w8_rhs8` が**排他の分岐**になっていて組み合わせられず、
新しいモデルはすべて `expected >= 73` で context 生成に失敗していた。
実機で動いている 24層の `final_qdq` は右辺が uint8 になっていたが、
**その手順はスクリプトとして残っていなかった**ので書き起こした。

> ★**自分の道具にバグを入れて、実機の数字だけ見て誤結論しかけた。**
> 最初の版は scale / zero_point の初期化子を**その場で書き換えて**いたが、
> それらは**他のノードと共有されていた**。結果 `lm_head` の DQ が uint16/uint8 混在になり、
> ホストではロードできず、**実機では動いて相対L2 700% / top-1 0% を出した**。
> 「ホストでロードできるか」の検算で捕まえた。実機だけ見ていたら
> 「KV 256 は v68 で壊れる」と書いていた。

## 2. RoPE の位置の clamp を外した

### それまでの実装

```cpp
const int64_t pos = std::min<int64_t>(t, L - 1);   // 窓が一杯になると L-1 に張り付く
```

L=256 なら 256トークン目以降**すべてが位置 255** になる。「何番目か」が区別できない。

### 直した考え方

**RoPE テーブルの行数は KVキャッシュの容量とは別物である。**

```
容量 L        … 何トークンぶん覚えるか（モデルに焼かれている）
テーブル行数  … 位置を何番まで表せるか（アプリが選ぶ）
```

K はキャッシュに入る時点でその時の絶対位置で回転済みなので、
**Q の位置を増やし続ける限り相対位置は正しい**。スロット番号が 0 側へずれても関係ない。

- `make_rope_table.py`（新規）で 2048行のテーブルを生成（端末の64行版と最大差 2.1e-06）
- `job.cpp` の clamp を **テーブル行数基準**に変更。結果に `rope_rows` / `rope_exhausted_at` を出す
- 2048行は**暫定**。本来は `max_position_embeddings`（32768）まで作るか、アプリで随時計算する

実機で 626 トークン生成して `rope_exhausted_at: -1`（位置は最後まで正しく進んだ）を確認。

## 3. ★窓が埋まると崩れる。原因は移植ではなく窓そのもの

### まず観察

実機で 600 トークン生成すると、途中から `1, 1, 1, ...` に崩壊した。
だが **fp32 を窓なしで回すと 600 トークン最後まで破綻しない**。

### 軌道を揃えて測る

生成どうしを並べても、貪欲デコードは序盤の僅差で別の軌道に入るので比較にならない
（[StudyMemo 8.2](../DoC/StudyMemo/08_比較を成立させる.md)）。
そこで **窓なし fp32 が書いた 626 トークンを、窓256 の fp32 に teacher forcing で流し**、
位置ごとに「次トークンを何位に置くか」を測った。**量子化も HTP も入っていない。**

| 絶対位置 | top-1 率 | 順位 中央 | 順位 平均 |
|---|---:|---:|---:|
| 64〜128 | 76.6% | 1.0 | 1.3 |
| 128〜192 | 76.6% | 1.0 | 1.3 |
| 192〜240 | 79.2% | 1.0 | 1.3 |
| 240〜256 | 75.0% | 1.0 | 1.2 |
| **256〜272** | **43.8%** | **2.5** | **13.2** ← 窓が埋まる |
| 272〜320 | 35.4% | 4.0 | 39.7 |
| 320〜400 | 33.8% | 4.0 | 41.6 |
| 400〜500 | 18.0% | 5.0 | 45.1 |

**位置 256 ちょうどで崖になる。** 窓が埋まって**実トークンの追い出しが始まる点**と一致する。

> **崩れるのは量子化でも HTP でもなく、窓が先頭を捨てることそのもの。**
> fp32 だけで再現する。StreamingLLM が報告している現象が、
> Qwen2.5-0.5B / 窓256 で実測されたことになる。

## 4. ここから

attention sink（先頭 N トークンを固定して残す）を試す根拠ができた。
ただし**「present の先頭スロットを上書きするだけ」では足りない**。

sink K を絶対位置 0〜3 のまま置くと、現在 Q（位置1255）との RoPE 距離が 1255 になり、
**長距離減衰で sink の効果が打ち消される**。StreamingLLM が cache 内の位置を使うのはそのため。
**キャッシュ済み K の再回転（rebase）が要る。**

RoPE は回転なので合成でき、毎ステップ全キャッシュに `R(-1)` を掛ければアプリ側でも可能だが、
24層×2×256×64 = 786k 要素への毎ステップ演算が増え、繰り返し回転で浮動小数誤差も溜まる。

| | |
|---|---|
| 次 | sink 4 + recent 252、K の rebase 込みで実装し、**同じ teacher forcing で崖が消えるか**測る |
| 判定 | 位置256 以降の top-1 率が 75% 付近を保てば成功 |

## 6. attention sink は Qwen2.5-0.5B では効かなかった

### 交絡があったので測り直した

3節の「窓256 で位置256 から top-1 が落ちる」には

  ① attention sink を捨てたことによる不安定化
  ② **単に必要な過去情報が消えたこと**

が混ざっている。②だけでも一致率は落ちるので、**崖＝sink が原因とは言えない**。
そこで **sink の有無だけを変えて** fp32 で比べた（NPU の再生成は不要）。

### 3つの方式は前提が違う

| | Q の位置 | K の位置 | |
|---|---|---|---|
| 旧実装 | cache内（L-1 で clamp） | 絶対 | **不整合**（今日まで気付いていなかった） |
| naive | 絶対 | 絶対 | 整合。現在の実装 |
| sink | cache内 | cache内（**再回転**） | StreamingLLM |

再回転は `R(-1): K' = K·cos(θ) − rot_half(K)·sin(θ)`。

### ★実装を2回間違えた。検算で捕まえた

| | 誤り | どう気付いたか |
|---|---|---|
| 1回目 | cache内位置なのに `pos = min(t, L-1)` を使い、実効位置が `2·entry_t − current_t` になっていた | 位置256 **より前**で劣化した |
| 2回目 | 再回転を `[lo:L-1]` に掛け、**最新スロットを除外**していた。`present` は次ステップで**全スロットが左へ動く**ので全部に掛ける必要がある | 同上 |

原因の切り分けに使った検算が2つ:

1. **回転の式そのもの**: 位置 p で入れた K に `R(-1)` を掛け、位置 p-1 で入れた K と比べる
   → **相対差 0.0000%**（式は正しい）
2. **sink なしなら cache内位置と絶対位置は数学的に一致するはず**
   → 直す前は NLL 1.034 vs 2.374（不一致＝バグ）、直したあと **差 0.000003**（一致）

> **推測で直さず、等価になるはずの条件を作って突き合わせる。**
> 1回目の誤った実装のままなら「sink は逆効果」という**間違った結論**を出していた。

### 結果（626トークン・teacher forcing・fp32 のみ）

| 絶対位置 | 窓なし（上限） | naive | sink 1 | sink 4 | sink 8 |
|---|---:|---:|---:|---:|---:|
| 128〜256 | **0.648** | 0.668 | 0.668 | 0.668 | 0.668 |
| 256〜272 | **0.549** | 3.840 | 3.840 | 3.816 | 3.832 |
| 272〜320 | **0.558** | **4.674** | 4.674 | 5.288 | 5.337 |
| 320〜400 | **0.511** | **4.050** | 4.050 | 4.115 | 4.586 |
| 400〜500 | **0.597** | **4.778** | 4.778 | 5.666 | 5.889 |
| 500〜626 | **0.971** | **4.422** | 4.422 | 7.133 | 7.455 |

（数値は teacher-forced NLL。小さいほど良い）

| | naive との NLL 最大差 |
|---|---:|
| sink 1 | **0.000699**（ほぼ何も変わらない） |
| sink 4 | 16.15（**悪化**） |
| sink 8 | 15.76（**悪化**） |

**sink 1 は実質無効果、sink 4 / 8 は明確に悪化する。**

### 判断

> **Qwen2.5-0.5B にこの構成で attention sink を入れる価値は無い。**
> 実機へ再回転処理（24層×2×256×64 = 786k 要素への毎ステップ演算）を
> 持ち込む理由が立たない。**naive sliding window のままにする。**

sink 1 がほぼ無効果だったことから、**このモデルは先頭トークンに強い sink を持たない**
可能性がある。StreamingLLM は BOS を sink に使う例が多いが、
Qwen2.5 は既定で BOS を付けない。

### ★この結論の弱点

**プロンプト1本・系列1本（626トークン）でしか測っていない。** n=1 である。
[StudyMemo 8.1](../DoC/StudyMemo/08_比較を成立させる.md) の作法からすれば、
複数の系列で確かめるまでは「効かない」と断定しきれない。
ただし sink 4/8 の悪化幅（NLL +0.9〜+2.7）は大きいので、方向が逆転する見込みは薄い。

## 7. 残る事実

窓が埋まったあとの劣化そのものは**消えていない**。

```
窓なし  NLL 0.5〜1.0
窓256   NLL 4.0〜4.8   ← sink を入れても変わらない
```

これは「古い文脈を捨てれば予測は変わる」という当たり前のことでもある。
**固定サイズのキャッシュで長時間動かすときの文脈管理**の問題であって、
Snapdragon へのポーティングの問題ではない（fp32 だけで再現する）。

| 次に考えられる手 | |
|---|---|
| 窓をさらに広げる | KV 512 / 1024。速度と引き換え。KV 256 で +22% だった |
| 要約して詰め直す | 窓が埋まる前に要約を生成し、キャッシュを作り直す |
| 何もしない | デモ用途なら 256 トークンで足りる |

|---|---|---:|---:|
| 計算機の歴史 | 272〜320 | **4.674** | 5.288 |

## 9. ★固定 prefix 保持は効く。ただし**サイズを中身に合わせる**

### 最初の実験は成立していなかった

system prompt（役割・ルール3つ）を置いたチャット形式で測ったが、**無効だった**。

```
窓なし fp32 の生成に含まれる回数
  '[OK]'    : 0
  'Captain' : 0
  'weather' : 0   ← 「触れるな」と書いたのに関係なく出る
```

**モデルが system prompt を完全に無視していた。**
守るべき情報が最初から無いので、prefix を固定しても直近トークンを捨てるだけになり、
当然すべての帯で悪化した（固定なし 4.976 に対し 先頭32固定 6.953）。

> **「先頭に重要な情報がある」という前提を、先に生成物で確かめる。**
> 確かめずに測って「prefix 保持は効かない」と結論しかけた。

### 先頭の情報が後半に必ず効く形で測り直した

```
[先頭 17トークン] Remember this fact carefully: the secret access code is 8317.
[中間 673トークン] 無関係な文（窓 256 を 455 トークン超えさせる）
[末尾 16トークン] Question: what is the secret access code? Answer: ... is
                  → 答え「8317」を何位に置くか
```

| 方式 | 答え「8317」の順位 | NLL |
|---|---:|---:|
| 窓なし fp32（上限） | **1** | **0.016** |
| 固定なし（recent のみ） | 3 | 2.143 |
| **先頭16固定** | **1** | **0.126** |
| 先頭32固定 | 2 | 1.523 |
| 先頭64固定 | 2 | 3.303 |

**先頭16固定で、窓なしとほぼ同じところまで戻る**（順位 3→1、NLL 2.143→0.126）。

**ただし 32 / 64 に広げると悪化する。** 事実は17トークンなので、
16 を超えた分は**中間の無関係な文を固定して、直近トークンを捨てている**ことになる。

### まとめ

| | 効くか | なぜ |
|---|---|---|
| attention sink（1〜8・内容に無関係） | **効かない** | このモデルは先頭に強い sink を持たない |
| **固定 prefix（守るべき内容の長さぴったり）** | **効く** | その情報が後半の予測に必要なとき |
| 固定 prefix（内容より長い） | **害になる** | 無関係な部分を固定して直近を捨てる |

> **「先頭を残す」かどうかではなく、「残すものに価値があるか」で決まる。**
> 実装するなら **prefix の長さを内容に合わせて指定できる**必要がある
> （system prompt のトークン数をアプリが数えて渡す）。

### 実装コスト（実機に入れる場合）

再回転（`R(-1)` を 24層×2×256×64 = 786k 要素へ毎ステップ）が要る。
sink では価値が無かったので見送ったが、**prefix 保持なら価値がある**。
現在 35.8 ms/token に対してどれだけ増えるかは未測定。

### 補足: 固定 prefix に再回転は要るのか（未確定）

StreamingLLM の sink は「注意の逃げ場を近くに置き続ける」ために cache内位置と再回転を使う。
だが**意味のある固定 prefix は目的が違う**。窓なしモデルでも prefix は位置0付近、
現在トークンは位置700付近で注意しているので、**絶対位置のまま置く方が自然**かもしれない。
そうなら**再回転（毎ステップ 786k 要素）が丸ごと不要**になる。

同じ 8317 テストで両方測った。

| 方式 | 答えの順位 | NLL |
|---|---:|---:|
| 窓なし fp32（上限） | **1** | **0.016** |
| 固定なし（recent のみ） | 3 | 2.143 |
| 先頭16固定・絶対位置（**再回転なし**） | 2 | 1.684 |
| 先頭16固定・cache内位置（再回転） | **1** | **0.126** |
| 先頭32固定・絶対位置（**再回転なし**） | **1** | **0.219** |
| 先頭32固定・cache内位置（再回転） | 2 | 1.523 |

**この1本では優劣が付かない。**
16 では再回転あり、32 では再回転なしが良く、**一貫した順序が無い**。
テストケースが1本なので、この差はばらつきの範囲と見るべきである。

> 言えるのは「**絶対位置のままでも上限近くまで戻せる場合がある**」ところまで。
> **再回転が必須とは限らない。** 実装コストが大きく変わるので、
> Qwen3 で複数ケースを使って決めること。

## 10. 文脈長スケーリング（KV 64 / 256 / 512）

**同一セッション・同一手順で3点測った**（速度は発熱で動くので、比較は必ず同じセッション内で行う）。

| KV | OrtRun | tok/s | fp32↔実機 相対L2 | fp32↔実機 top-1 | **★ホスト↔実機** | context binary | KVメモリ |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 64 | 28.73 ms | **34.8** | 17.65% | 70.8% | **16.48%** | 772,065,064 B | 1.5 MB |
| 256 | 35.46 ms | **28.2** | 21.24% | 66.7% | **17.00%** | 772,101,928 B | 6.0 MB |
| 512 | 44.02 ms | **22.7** | 21.11% | 70.8% | **16.95%** | 772,351,784 B | 12.0 MB |

3点とも **全ノード HTP / strict=true / VTCM spill 0 / DLC 検査 2,107本 整合 / md5 3点一致**。

### ★移植の質は文脈長に依存しない

```
ホスト↔実機   KV64 16.48%   KV256 17.00%   KV512 16.95%
```

**KV を8倍にしても HTP 側の誤差は動かない。** 増えるのは速度コストだけである。

### 速度は「固定費 + キャッシュ長に比例」で説明できる

| KV | 実測 | 26.9 + 0.0335×L |
|---:|---:|---:|
| 64 | 28.73 ms | 29.0 ms |
| 256 | 35.46 ms | 35.5 ms |
| 512 | 44.02 ms | 44.0 ms |

```
固定費 26.9 ms    … 重みとの行列積（キャッシュ長に無関係）
可変費 0.0335 ms/スロット … attention（キャッシュ長に比例）
```

3点が 0.1ms 以内で乗る。この式で外挿すると **KV1024 ≈ 61 ms ≈ 16.3 tok/s**。

### 判断

> **Snapdragon 888 / HTP v68 でも KV 512 は現実的。**
> 22.7 tok/s は「読める速さ」を保っている。RAM 8GB の 2021年の端末で、
> 文脈 512 トークンのローカル生成が成立する。
>
> ただし **KV 256 が扱いやすい点**ではある（28.2 tok/s、メモリ 6MB）。
> 512 にする価値は「何トークン覚えたいか」で決めればよく、
> **精度の劣化を心配する必要は無い**（ホスト↔実機は変わらない）。

（`fp32↔実機` の相対L2 と top-1 は**評価セットが KV ごとに別**なので直接比較しない。
同条件で比べられるのは `ホスト↔実機` だけである）
