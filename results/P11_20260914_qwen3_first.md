# P11. Qwen3-0.6B を v68 へ — 最初の1本

- 日付: 2026-09-14
- 端末: Xperia 5 III SOG05 / SM8350 / HTP v68
- 対象: Qwen3-0.6B の decode 2層 / KVキャッシュ 256（パイプライン再利用の確認）

---

## 1. アーキテクチャの差分

| | Qwen2.5-0.5B | **Qwen3-0.6B** |
|---|---:|---:|
| 層数 | 24 | **28** |
| hidden | 896 | 1024 |
| attention heads | 14 | 16 |
| **KV heads** | 2 | **8** |
| **head_dim** | 64 | **128** |
| FFN | 4864 | 3072 |
| vocab | 151936 | 151936 |
| attention bias | あり | **なし** |
| **RMSNorm の数** | **49** | **113** |
| パラメータ | 494M | 596M |

RMSNorm の内訳（Qwen3）: `input_layernorm` 28 + `post_attention_layernorm` 28 +
**`q_norm` 28 + `k_norm` 28** + `norm` 1 = 113。
**projection の直後にヘッドごとの RMSNorm** が入るのが Qwen2.5 との違い。

### KVキャッシュのサイズが 9.3倍になる

| 長さ | Qwen2.5-0.5B | **Qwen3-0.6B** |
|---:|---:|---:|
| 256 | 6.0 MB | **56.0 MB** |
| 512 | 12.0 MB | **112.0 MB** |

グラフ I/O は float32 なので**毎ステップ往復する**。
Qwen3 の L=512 では 1ステップ **224 MB** の転送になる。**ここは要注意。**

---

## 2. パイプラインの改修（2箇所）

### export の配線

| | |
|---|---|
| `head_dim` | **config から取る**。`hidden/heads` だと 1024/16 = 64 になるが実際は **128**。割り算だと q_proj の出力（2048）と合わず形が崩れる |
| `q_norm` / `k_norm` | projection の直後・transpose の前に適用（最後の次元に対する正規化なので transpose 前後どちらでも同じ）。Qwen2.5 には無いので `hasattr` で分岐 |

**検算**: 自前の配線を HF と突き合わせ、**最大絶対差 2.837e-05 / top-1 全一致**。

### ★C-13 の対象漏れ

C-13 のパターンを `input_layernorm` / `post_attention_layernorm` / `norm` と
**列挙で書いていたので、`q_norm` / `k_norm` を取りこぼした**。

```
修正前: 2層で 5本しか拾えない（正しくは 9本 = 2層×4 + 最終）
修正後: `norm.weight` を含むものを全部拾う → 9本 / 28層で 113本
```

> **列挙は、モデルが変わると壊れる。** 「その性質を持つもの」で拾う。
> RMSNorm が HTP 誤差の主因だったので、**半分を取りこぼしたまま進んでいたら
> Qwen3 でも同じ問題を踏んでいた**。

## 3. 実機で動いた

**Qwen3-0.6B の decode 2層が Snapdragon 888 の NPU で全ノード動作。**

| | |
|---|---|
| backend | `QNN HTP - EPContext - all nodes` |
| `strict_no_cpu_fallback` | **true** |
| DLC 検査（型とエンコーディング） | **215本 整合** |
| md5 3点照合 | 一致 |
| C-13 | 9本中9本を自動修正 |
| per-channel | 14本（axis=1） |

### ★VTCM が溢れた（Qwen2.5 では 0 だった）

```
spill_bytes = 659,456
fill_bytes  = 659,456
```

`head_dim` 128 / KV heads 8 でテンソルが大きくなり、**VTCM 4MB に収まらなくなった**。
Qwen2.5 では 24層でも常に 0 だったので、**これは Qwen3 固有**。
2層でこれなので、**28層でどうなるかは要確認**。

## 4. 精度 — Qwen2.5 より良い

| 2層 decode / KV256 / 24件 | 相対L2 | cos | KL | 順位 | top-1 |
|---|---:|---:|---:|---:|---:|
| fp32 ↔ ホストQDQ | 2.84% | 0.99964 | 0.0123 | 1.25 | 87.5% |
| fp32 ↔ 実機HTP | **2.95%** | 0.99965 | 0.0131 | **1.17** | **95.8%** |
| **★ホストQDQ ↔ 実機HTP** | **1.37%** | **0.99993** | **0.0020** | **1.08** | 91.7% |

OrtRun 7.86 ms。

### Qwen2.5 との比較（どちらも2層・C-13 適用後）

| | Qwen2.5-0.5B | **Qwen3-0.6B** |
|---|---:|---:|
| fp32 ↔ ホストQDQ | 11.86% | **2.84%** |
| **ホスト ↔ 実機** | 2.43% | **1.37%** |
| fp32↔実機 top-1 | 83.3% | **95.8%** |

**量子化誤差そのものが 4分の1以下。** `fp32 ↔ ホストQDQ` が 11.86% → 2.84%。

理由はまだ確かめていないが、**`q_norm` / `k_norm` が Q と K のレンジを揃えている**
影響が考えられる。Qwen2.5 では attention スコアのレンジが 1627 に達し、
それが C-8 の回避策（8bit 強制）と相まって誤差の主因のひとつだった。

> **移植のしやすさはモデルの設計で変わる。** 同じパイプライン・同じ端末で、
> 量子化誤差が 4分の1になった。
