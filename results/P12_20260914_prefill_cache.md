# P12. 会話をまたいで KVキャッシュを持ち回す

- 日付: 2026-09-14
- 端末: Xperia 5 III SOG05 / SM8350 / HTP v68
- 対象: `EdgeSLM_AndroidDemo` の `generate_kv`（Qwen2.5-0.5B / KV512）

---

## 1. 何が問題だったか

対話のたびに**全履歴を1トークンずつ入れ直して**いたので、充填時間が履歴の長さに比例して伸びた。

| 往復 | 入力 | 充填 |
|---:|---:|---:|
| 1 | 37 トークン | 924 ms |
| 2 | 59 トークン | 2167 ms |
| 3 | 84 トークン | 3490 ms |
| 4 | 98 トークン | 5550 ms |

`履歴の長さ × 約40ms`。10往復では11秒待つことになる。
**前ターンのキャッシュはそのまま使えるのだから、新しいぶんだけ入れればよい。**

---

## 2. 直したあと

| 往復 | 履歴 | 再利用 | 充填 | 時間 |
|---:|---:|---:|---:|---:|
| 1 | 37 t | 0 t | 37 t | 952 ms |
| 2 | 59 t | **45 t** | 14 t | **778 ms** |
| 3 | 84 t | **66 t** | 18 t | **1045 ms** |
| 4 | 100 t | **89 t** | 11 t | **645 ms** |
| 5 | 132 t | **118 t** | 14 t | **816 ms** |

**充填時間が履歴の長さに依存しなくなった。**

## 3. 設計

### 状態は Session が持つ

```cpp
struct KvCarry {
    std::string model;                         // 張り替えを検出する
    std::vector<std::string> cache_names;
    std::vector<std::vector<uint8_t>> caches;  // past_* の中身
    int64_t n_valid = 0;                       // マスクで開けてよいスロット数
    int64_t pos = 0;                           // 次に使う RoPE の絶対位置
    std::vector<int64_t> tokens;               // **実際にキャッシュへ入った**トークン列
    bool valid = false;
};
```

最初 `static std::map<const Session*, KvCarry>` にしたが、**解放済みアドレスが再利用され、
別セッションの状態を拾った**。KVキャッシュはそのセッションのものなので寿命も合わせる。
`reopen`（モデル張り替え）でも捨てる。

### トークン列を保持して前方一致を確認する

```cpp
size_t reusable(const std::vector<int64_t>& ids) const {
    if (!valid || tokens.empty() || tokens.size() > ids.size()) return 0;
    for (size_t i = 0; i < tokens.size(); ++i)
        if (tokens[i] != ids[i]) return 0;      // 途中で違えば作り直す
    return tokens.size();
}
```

**これが無いと、履歴を編集されたり別の会話を始められたときに、
黙って壊れた文脈で続けてしまう。** 実際、テストで応答を推測して履歴を組んだとき、
前方一致せず安全側に倒れた——**チェックが正しく働いた**。

### 呼び出し側は差分だけ渡す

全履歴を渡す形にすると、**呼び出し側がモデルの実際の応答を正確に持っていないと
前方一致しない**（整形したり空白を落とすと一致しなくなる）。
実際のチャットで足すのは「直前の応答を閉じる特殊トークンと、次の発話を包むテンプレート」
だけで、**応答の中身に依存しない**。実際の履歴はネイティブ側が持つ。

| ジョブの項目 | 意味 |
|---|---|
| `reuse_cache` | 前ターンのキャッシュを使う |
| `reset_cache` | 会話を最初からやり直す |
| `prompt_is_delta` | `prompt_ids` が差分。**履歴を前置させる** |
| `turns` | 複数ターンを1ジョブで回す（差分の配列） |
| 結果 `reused_tokens` / `prefill_tokens` | 何トークン飛ばせたか |

### 失敗したときは保存しない

途中で落ちたキャッシュを引き継ぐと、次のターンが静かに壊れる。

## 4. ★踏んだバグ6件と、見つけ方

**目視や推測では1つも見つからなかった。すべて「等価になるはずの条件」を作って突き合わせた。**

| # | バグ | どう気付いたか |
|---|---|---|
| 1 | ポインタをキーにした `static map` → **解放済みアドレスの再利用**で他セッションの状態を拾う | 4往復目だけ再利用が効くという不自然な挙動 |
| 2 | `start_step = skip - 1` → **再利用した最後のトークンを二重投入** | fp32 と応答が食い違う |
| 3 | `carry.tokens` に**キャッシュに入っていない**最後の生成トークンを含めていた | 「差分＋再利用」と「毎回フル入力」が一致しない |
| 4 | 「EOS なら `<\|im_end\|>` を省く」→ **3の修正と前提が矛盾** | UI がジョブ経由と食い違う |
| 5 | **差分対応が `turns` ブランチにしか無く、UI が通る経路に無かった** | ログに `reused=0` |
| 6 | `renderOutput` / `pollProgress` の最後の1回が確定表示を上書き | 画面に `<\|im_end\|>` が出る / 統計が1行 |

### ★2 と 3 の中身（間違えやすい）

生成ループは「**トークンを選ぶ → 次の周回で食わせる**」形なので:

```
キャッシュにあるのは  prompt + newly[0 .. n-2]
newly[n-1]（最後に選んだ1つ）は **食わせずに終わる**
```

- 2 は「再利用したぶんの最後」をもう一度食わせていた（**二重**）
- 3 は「食わせていないもの」を入っていることにしていた（**欠落**）

**どちらも文脈が1トークンずれる。** 症状は同じ「会話が始まったばかりのような定型文」。

### ★4 の教訓: 修正どうしが噛み合わない

3 で「最後の生成トークンはキャッシュに無い」と直したのに、
4 では「EOS なら既にキャッシュにある」という**成り立たない前提**で省いていた。
**片方を直したら、それに依存している箇所を洗い直す。**

### ★5 の教訓: 検算した経路と本番の経路が違った

ジョブ経由（`turns`）で等価性を確認したのに、**UI は別の経路を通っていた**。
「同じ経路を測る」まで含めて検算である。

## 5. 等価性の検算（これが決め手）

「差分＋キャッシュ再利用」と「毎回フル入力・再利用なし」に
**完全に同じトークン列**を食べさせ、**生成が一致するか**を見る。

```
A: 差分＋再利用        B: 毎回フル入力
[1] 充填  923ms        充填  924ms     一致
[2] 充填  770ms        充填 1993ms     一致   ← 2.6倍速い
[3] 充填 1025ms        充填 3239ms     一致   ← 3.2倍速い
```

**生成トークン列がビット単位で同じで、充填時間だけが短い。**

> この検算を作るのに**2回失敗した**。
>   - 1回目: `turns` モードの `reuse=False` は**文脈ゼロ**になるので対照にならない
>   - 2回目: A と B で**食べている系列が違った**（B だけ `<\|im_end\|>` が二重）
>
> **「同じ入力を与えているか」を先に確かめる。**

UI 側も同じ数字になることをログで確認した。

```
UI : promptLen=37 reused= 0 filled=37     ジョブ: 再利用  0t 充填 37t
     promptLen=58 reused=44 filled=14            再利用 44t 充填 14t
     promptLen=81 reused=63 filled=18            再利用 63t 充填 18t
```

## 6. UI

KV 画面に**対話モード**のチェックボックスを追加した。
**既存の「続きを書かせる」動作はそのまま残している。**

| | 対話モード OFF（従来） | 対話モード ON |
|---|---|---|
| 送るトークン | 入力文そのまま | **差分だけ** |
| `reuse_cache` | 付けない | true |
| 生成上限 | 32 | **96**（32 だと文が途中で切れる） |
| 表示 | プロンプト＋生成 | 会話ログ |
| 統計 | 充填 ◯ms | 充填 ◯ms（◯トークン・**再利用 ◯**） |

日本語プリセット（エアコン / 音楽 / 確認 / 英語）も追加した。
端末の IME を使わずに日本語を試せる。

> **統計は会話ログの上に置く。** 下だと会話が伸びたとき画面外へ押し出される。

## 7. ★会話の品質は移植ではなくモデルの問題

「質問と答えが合っていない」ので切り分けた。

| | 質問 | **fp32（移植の影響ゼロ）** | 実機 |
|---|---|---|---|
| 1 | エアコンを22度にして | 22度に設定します。 | 22度に設定します。 ✅ |
| 2 | 音楽をかけて | **お手伝いできません。** | おやすみなさい。 |
| 3 | さっき何度にしたっけ？ | **申し訳ありませんが、私はリアルタイムで情報を提供する能力はありません…** | お疲れ様です。何かお手伝いできることが… |

**fp32 でも答えになっていない。**
「音楽をかけて」に「お手伝いできません」、
「さっき何度にしたっけ？」には**自分が直前に「22度に設定します」と書いたのに参照せず**
定型の拒否文を返す。**移植を完璧にしても直らない。**

### プロンプトの組み立ては正しい

アプリの差分方式が HF の `apply_chat_template` と一致するか検算した。

```
アプリ 58 トークン / HF 58 トークン   ★一致: True
```

**組み立ての問題ではない。**

### 移植の影響も乗っている（副次的）

1往復目は fp32 と完全一致するが、2・3往復目は違う文になる。
実機の fp32 との top-1 一致は **75.0%**（24層 decode / KV512）なので、
**4トークンに1回は違う選択**をし、貪欲デコードでは1回分岐すると以降が別の文になる。

> **移植誤差は「悪い答えを別の悪い答えに変える」だけで、良い答えを壊してはいない**
> ——というのが今回の材料から言えること。

```
質問と答えが合わない
  ├─ モデルの能力（主因） … fp32 でも合わない。0.5B の限界
  └─ 移植の誤差（副次）  … 同じく合わない答えの、別の変種になる
```
