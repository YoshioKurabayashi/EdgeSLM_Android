# P12b Qwen3-0.6B 28層 実機対話 — 4段の切り分けで「どこで壊れるか」を決める

2026-09-15 / Xperia 5 III (SM8350 / HTP v68) / QAIRT 2.48.0.260626 / ORT 1.30.0

## 結論

**Qwen3-0.6B は HTP で壊れる。モデルでも export でも量子化でもない。**

| 段 | 3ターン目「さっき何度にしたっけ？」 | 判定 |
|---|---|---|
| ① 公式 HF fp32 | さっきは22度に設定しました。 | ○ 文脈参照 |
| ② Export fp32 (ONNX/CPU) | さっきは22度にしてました。 | ○ 文脈参照 |
| ③ Host QDQ (A16W8/CPU) | さっきも22度にしました。 | ○ 文脈参照 |
| ④ **HTP (実機/NPU)** | **E Y E Y E Y …** | **× 崩壊** |

1ターン目から既に壊れている。実機は空 think ブロックを渡しても**思考文を垂れ流す**:

```
あなた: エアコンを22度にして
端末  : Okay, the user wants to set the thermostat to 22 degrees.
        Let me check the current temperature. If it's already 22, they might
        just need to adjust. But wait, the user wrote "22度" which is Japanese
        for "22 degrees". ...
```

同じ41トークンを食べた Host QDQ は「エアコンを22度に調節しました。」を返す。
**最初の1トークン目から分岐している。**

## 入力が同じであることの証明

「個数が合っている」は根拠にならないので、**端末が実際に食べた ID 列を記録**した。

```
端末  : 151644,8948,198,…,151645,198,151644,77091,198,151667,271,151668,271  (41)
公式  : （apply_chat_template + enable_thinking=False）                        (41)
完全一致: True
```

- RoPE テーブル（head_dim 128 / theta 1e6 / concat 形式）は端末配布物と
  ホスト計算値が**最大差 0.000**
- context binary は runner 側と demo 側で **md5 一致**
- `<think>`(151667) / `</think>`(151668) は端末の `specials.tsv` に**無かった**ので追加した。
  Qwen3 の語彙は Qwen2.5 の**厳密な上位集合**（151665個が ID まで一致、追加4個）で、
  `vocab.txt` / `merges.txt` は **md5 一致**。増えたのは specials.tsv の4行だけ

## 測り方の誤りを2つ直した（どちらも対照実験で発覚）

### 1. mask の向きが逆だった

`export_qwen_decode.py:146` のキャッシュは**左シフト式**:

```python
pk = torch.cat((past_k, k), dim=2)[:, :, 1:, :]   # 新しいトークンは末尾に入る
```

有効トークンは**後ろ**に詰まる。実験台は前側を開けていた。
**fp32 エクスポートを同じ実験台に通したら同じように壊れた**ので、
量子化ではなく実験台のバグだと分かった。この対照が無ければ
「Qwen3 は量子化で壊れる」と誤報していた。

### 2. Qwen3 の chat template は append-only ではない

`enable_thinking=False` は assistant 開始直後に `<think>\n\n</think>\n\n` を入れるが、
**そのターンが履歴になるとテンプレートはこのブロックを落とす**。
つまり2ターン目以降の公式レンダリングは、
**既にキャッシュへ入れた列の接頭辞にならない**（共通37 / 既投入52 で検出）。

食べたトークンは取り消せないので、**毎ターン think ブロックを足す**方針にした。
落とすと2ターン目から `<think>` を垂れ流す。

→ 実装は `KvDemoActivity.assistantPrefix()`。`kv_modes.json` の
  `assistant_prefix` で与え、**ネイティブには渡さない**。

## System prompt 追従能力（公式 HF・A/B/C の梯子）

以前「Qwen3 も system prompt を守れない」と報告したのは**誤り**だった。
C（3制約同時）だけを、日本語で、greedy で測っていた。三重に条件が悪い。

| | A: system role 認識 | B: 単一指示 | C: 3制約同時 |
|---|---|---|---|
| Qwen2.5-0.5B 英 | × | ○ 5/5 | × 0/5 |
| Qwen2.5-0.5B 日 | × | × 1/5 | × 0/5 |
| **Qwen3-0.6B 英** | **○ 5/5** | **○ 5/5** | **○ 5/5** |
| **Qwen3-0.6B 日** | **○ 5/5** | **○ 5/5** | × 0/5 |

- A = 「必ず BANANA と答えろ」→ Qwen3 は `BANANA` / `バナナ` を返す
- 日本語 C の失敗は3ルール中2つは守り「艦長」だけ落とす。
  **system role 不認識ではなく、日本語で3制約を同時維持する容量不足**
- **能力評価に greedy を使ってはいけない**（Qwen3 公式が明示）。
  数値一致の検証には greedy、能力評価には T=0.7/top_p=0.8/top_k=20

# 追記 2026-09-15 — 1トークン目の解析で原因を絞った

## 「HTP 誤差を下げる以外に道がない」は誤りだった

壊れた chat prompt の**最初の1トークンだけ**を4段で比べたら、
**1ステップの計算は正常**で、**キャッシュに溜まる誤差**が原因だと分かった。

### 1. 最初の1トークンの top-10

ホスト3段は**全部 `エ` で一致**。しかも接戦ではない。

|---|---|---:|---:|---:|
| HF fp32 | `エ` 18.844 (93.75%) | 4.201 | 1 | 0.0000 |
| Export fp32 | `エ` 18.844 | 4.201 | 1 | **0.0000** |
| Host QDQ | `エ` 18.611 (95.81%) | 5.863 | 1 | 0.0281 |
| **実機 HTP** | **`Okay` 14.963** | 0.138 | **3** | — |

Export fp32 は HF と **KL=0.0000**（完全一致）。

### 2. 実機 top-10 がホストでは何位か（逆方向）

### 3. 決定的な切り分け — ホストのキャッシュを実機に食わせる

41ステップ積んだキャッシュの誤差か、1ステップの計算かを分けるため、
**ホスト QDQ が40トークン分積んだキャッシュ**（59MB）を実機へ push し、

**1ステップの計算は正常。** 誤差はキャッシュ側にある。

### 4. どこで壊れるか — 新しく書くスロット

| テンソル | 全256スロット | **最新スロット** | **旧255スロット** |
|---|---:|---:|---:|
| present_k_13 | 2.68% | **16.12%** | **0.00%** |
| present_v_13 | 3.37% | **25.71%** | **0.00%** |

**旧スロットは 0.00%。** 再量子化で劣化しているのではない。
`past_k` は `Concat` に入るので毎ステップ量子化を通るが、**そこは無害**だった。
壊れているのは**毎ステップ新しく書かれる K/V** で、

## 次に見るところ（絞り込み済み）

**KV を書き出す経路**に限定できた。Qwen3 で Qwen2.5 から変わったのは:

| | Qwen2.5 | Qwen3 |
|---|---|---|
| KV heads × head_dim | 2 × 64 | **8 × 128** |
| K/Q の正規化 | 無し | **q_norm / k_norm（ヘッド毎 RMSNorm）** |

順に当たる:
1. **k_norm の出力**（層3で跳ねる境界と合うか）
2. **K の RoPE 後**
3. **V の射影出力**（V は k_norm も RoPE も通らないのに 38〜50%。ここが一番奇妙）
4. per-tensor 量子化の scale が層ごとにどう決まっているか（V の \|V\| RMS が
   層0 の 0.125 から層26 の 6.620 まで **53倍**動いている）

**V が K より悪い**のは重要な手がかり。V は k_norm も RoPE も通らない単なる射影なので、
Attention 特有の仕組みではなく**量子化の粒度/範囲**の問題である可能性が高い。

# 追記3 2026-09-15 — 根本原因：残差ストリームが実効3ビットだった

## まず私の測定の誤りを訂正する

追記2 の「残差 hidden は 0.04〜0.15% しかずれていない」は**間違い**。
**uint16 のコード値**どうしで相対L2 を取っていた。コードは zero_point（1496）を
含む大きな数なので、±5段の食い違いが 0.09% に見えていた。**分母の取り違え**である
（8章 8.5 に書いた罠そのもの）。

**逆量子化してから測ると 31.53%。**

| 測り方 | add_53 の host↔実機 |
|---|---:|
| uint16 のコード値で（誤） | 0.093% |
| **逆量子化した実数で（正）** | **31.53%** |

## 鎖がつながった

| | 相対L2 |
|---|---:|
| add_53（逆量子化後） host ↔ 実機 | **31.53%** |
| その add_53 を**ホストの** V 経路に入れた present_v_6 | **49.96%** |
| 実機14層が出した present_v_6 | 49.97% |
| 上の2つの差 | **0.18%** |

**増幅などではなく、入口で既に31%ずれていた。** V 経路は最初から無罪で、
ホスト側で実機の hidden を食わせるだけで実機の出力を**0.18%で再現できる**。

## VTCM spill 仮説は否定された

| モデル | ノード | spill_bytes | add_53 | present_k_6 | present_v_6 |
|---|---:|---:|---:|---:|---:|
| 本番 28層 | 9185 | 16,539,648 | — | 17.11% | 49.97% |
| **部分 14層** | 4575 | **0** | 31.53% | **17.107%** | **49.971%** |

**spill が 0 でも本番と同じ誤差が出る。** VTCM は関係ない。

## 根本原因

```
層6に入る残差 hidden (add_53) の量子化
  量子化の範囲   :  -169.537 〜 7257.326   （幅 7426.9）
  1段の大きさ    :    0.113327
  実際の値の範囲 :    -4.131 〜   10.516   （幅 14.6）
  RMS            :    0.4981
  |値| の分位    : p50 0.189 / p99 1.354 / p99.9 4.109

  ★使っている符号語        : 129 / 65536 = 0.20%
  ★典型値(RMS)を表す段数   : 4.4 段  →  実効 3.1 bit 相当
  ★外れ値が無ければ scale は 1/353 で済む
```

**A16 と名乗っているが、残差ストリームの実効分解能は約3ビットしかない。**
較正で得たレンジ（最大 7257）が、この時点の実際の活性（±10.5）より **353倍**広い。
1段が 0.113 もあるので、host と HTP が数段食い違うだけで 31% の誤差になる。

量子化雑音の下限だけでも `step/√12 = 0.0327` ＝ RMS の **6.6%**。
実測の 31.5% はその約4.8倍なので、丸めだけでなく実計算の差も乗っているが、
**どちらにせよ 353倍広いレンジが誤差を実用上の大きさまで持ち上げている。**

## Qwen2.5 との比較（残差 Add の量子化・全本数）

| | Qwen2.5 24層 (290本) | **Qwen3 28層 (366本)** |
|---|---:|---:|
| 1段の大きさ 中央値 | 0.0005 | 0.0007 |
| **1段の大きさ 最大** | **0.0311** | **0.1136（3.7倍）** |
| レンジ上限 中央値 | 13.0 | 19.5 |
| **レンジ上限 最大** | **1625.2** | **7275.2（4.5倍）** |

Qwen2.5 も同じ病気を持っているが、**Qwen3 は外れ値が4.5倍大きい**。
新スロット KV の誤差が Qwen2.5 の約2倍（K 4.83→10.06%、V 12.82→22.83%）
だったことと整合する。

## まだ確かめていないこと

1. **7257 は本物の活性か、較正の事故か。** LLM の残差ストリームには
   特定チャンネル・特定位置（多くは先頭トークン）で桁違いに大きな値が出る
   現象が知られている。本物なら単純なクリップは危険
2. **レンジを絞れば host↔実機 の差が縮むか。** 縮まなければ実計算側の差である

## 次の一手

較正データ上で `add_53` の分布を調べ、**どのチャンネル・どの位置**が
7257 を作っているかを特定する。それが少数チャンネルに閉じているなら、
per-tensor のレンジを浪費しているのはその数本だけということになり、
打ち手（分位点クリップ / 外れチャンネルの分離）が具体化できる。
