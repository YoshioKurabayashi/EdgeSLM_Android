# P12c — Qwen3 の残差 activation 最大値7257を公式FP32で追跡

2026-09-15 / Qwen3-0.6B / 28層 / decode・KV256

## 結論

**最大値7257は、較正処理が作った異常値ではなく、公式モデルでも発生する値だった。**

`add_53`（層6へ入る残差。層・位置・チャンネルはすべて0始まり）の
最大値は、較正sample 0、position 0、channel 35。
token IDは131888、デコードした文字列は **「日本の」**。
較正文全体は「日本の首都は」。

| 同じ入力・位置・チャンネル | 値 |
|---|---:|
| 公式HF FP32 | 7258.100586 |
| export直後のFP32 ONNX | 7258.099609 |
| 前処理後・較正に使うFP32 ONNX | 7257.350098 |
| 既存QDQの表現可能な上限 | 約7257.326 |

最後の2値は同じものではない。QDQ上限は既存scale・zero pointから復元した
量子化格子の上端であり、今回再計算したFP32最大値と完全一致する必要はない。
今回の差は約0.024、約0.22量子化step。

**「モデルが本来出す巨大値」と「較正レンジが通常の値に対して粗い」ことは確認できた。**
ただし、レンジを変更してHost↔HTPの誤差や対話崩壊が改善する因果実験は未実施。
したがって、これだけで精度問題の修正完了とはしない。

## 1. 前回から再開した調査

[P12b](P12b_20260915_qwen3_device_chat.md)追記3とチャット「量子化でAttention劣化」の
未完項目を実施した。

1. 最大値のsample・token位置・channelを特定。
2. 同じ入力列を公式HF FP32で再実行。
3. 較正全30入力の外れ値頻度・channel集中度を集計。
4. 保存済み実機出力と、同一入力のHost再実行から整数コード差を集計。

モデル、量子化パラメータ、Androidアプリは変更していない。
新しいNPU推論は実行しておらず、実機側は前回の保存出力を使用した。

## 2. 最大値は5文すべての先頭・同じchannelに現れた

較正は5文×6ステップ＝30入力。1000超、5000超はどちらも5要素で、
**すべてposition 0・channel 35**だった。

| sample | 先頭tokenの文字列 | 較正用FP32 | 公式HF FP32 |
|---:|---|---:|---:|
| 0 | 日本の | 7257.3501 | 7258.1006 |
| 6 | The | 6541.7383 | 6542.3267 |
| 12 | 1 | 6544.0894 | 6544.4863 |
| 18 | 人工 | 6957.9478 | 6958.9116 |
| 24 | def | 5750.1035 | 5750.2871 |

5000超は **5 / 30,720要素 = 0.01628%**。
この数値は今回の較正集合の比率であり、実運用全体の発生率ではない。
特殊トークンだけに起きた現象でもない。

| 位置の集合 | 最小 | 最大 | RMS |
|---|---:|---:|---:|
| 各文の先頭・5入力 | −169.5126 | 7257.3501 | 208.7309 |
| 2番目以降・25入力 | −7.5159 | 17.2624 | 0.6843 |

先頭を除くと値域が極端に狭くなる。ただし、**先頭も実際に推論されるので、
較正から先頭を除けば解決するとはいえない**。

## 3. 比較方法と対照

### ONNX側

- export直後と前処理後のモデルから、`add_53`の祖先ノードをそのまま保存。
- 元の重み・演算・入力を維持し、不要な後段を除いた観測用モデルを使用。
- 既存の`calib_q3d28.npz`に保存された全入力を使用。
- `p2b_ops.py`で実際に量子化へ渡すのが`prepped`であることも確認。

### 公式HF側

- ローカルに保存されていた公式snapshotを使用。追加ダウンロードなし。
- snapshot: `c1899de289a04d12100db370d81485cdf75e47ca`
- FP32、CPU、eager attention、`use_cache=False`。
- 保存されたtoken IDとmaskから各文の入力列を再構築。
- 各prefixを公式forwardに渡し、`hidden_states[6]`の最終位置を観測。
- 較正時に生成されたtokenについても、再生成せず保存された同じIDを使用。

### 比較結果

相対L2の分母は公式HFの実数値。巨大値で分母が膨らむ問題を避けるため、
先頭と後続を分け、さらに各sample単位の最大誤差も確認した。

| 比較 | 先頭5入力 | 後続25入力 | 各sample誤差の最大 |
|---|---:|---:|---:|
| 公式HF → export ONNX | 0.00004184% | 0.00011420% | 0.00018293% |
| 公式HF → 較正用ONNX | 0.0096124% | 0.0354649% | 0.0623147% |

今回の30入力では、巨大値の存在をexportや前処理の破綻で説明する必要はない。
全モデル・全入力の等価性を証明したものではなく、対象テンソルの照合結果である。

## 4. Host↔HTPの整数コード差を直接確認

端末の`jobs/hid.json`、対応する16入力ファイル、`hid`の各層出力を取得し、
既存の`work/q3_hid/hid_qdq.onnx`をHostで再実行した。

- 入力token ID: **271**、maskの有効token数: **41**。
- 較正30入力とは別の、前回の対話経路の観測入力。
- 既存`eval_q3d28.npz`には全入力が完全一致するsampleはなかった。
- 入力ファイルのSHA-256とHostモデルのSHA-256をJSONに記録。
- 保存済み`hid`と`l14`の`add_53`出力は**1024要素すべて完全一致**。

`delta = q_HTP - q_Host`。uint16のまま減算せず、int32へ変換して計算。

| add_53の差 | 要素数 | 比率 |
|---|---:|---:|
| 完全一致 | 298 | 29.10% |
| ±1段 | 460 | 44.92% |
| ±2段 | 196 | 19.14% |
| ±3段 | 59 | 5.76% |
| ±4段 | 8 | 0.78% |
| ±5段 | 3 | 0.29% |
| ±5段超 | 0 | 0.00% |

**±1段以内74.02%、±2段以内93.16%、全要素±5段以内。**

```
scale                 = 0.1133266613
zero point            = 1496
コード差のRMS          = 1.389834747 段
逆量子化後の誤差RMS    = 1.389834747 × 0.1133266613
                      = 0.157505332
Hostの信号RMS          = 0.499559048
相対L2                = 0.157505332 / 0.499559048
                      = 31.5289%
```

整数空間では数段の差でも、実数空間では信号に対して大きな誤差になることを、
今回の保存サンプルについて直接確認できた。
これは誤差の表現と大きさを説明するもので、整数差の最初の発生演算を特定したものではない。

### 層境界の訂正値

| テンソル | 層への入力 | scale | 逆量子化後のHost↔HTP相対L2 |
|---|---:|---:|---:|
| add_8 | 1 | 0.00014507 | 2.09% |
| add_17 | 2 | 0.00030173 | 3.14% |

| add_35 | 4 | 0.11331985 | 28.50% |

**層3への入口でscaleと実数誤差がともに跳ねる**。
次の原因追跡では層2の出力から層3の入口が具体的な観測候補になる。

## 5. 過去の表現を訂正

- **「129個の符号語を使用」**: 今回のHost出力は、最小から最大までの差が129段。
  実際に現れた異なるコードは**30種類**。幅と種類数を区別する。
- **「レンジが353倍」**: 今回の逆量子化後Host出力の幅は14.6191、
  QDQの全幅は7426.8627なので、この定義では**508.02倍**。
  別の入力・比較範囲を混ぜて倍率を断定しない。
- **「A16が実効3bit」**: 正式なbit数ではない。典型振幅付近の分解能を説明する
  比喩に限定し、格納dtypeやコード種類数と同一視しない。
- **「原因確定」**: 巨大値の由来は確認できた。
  それを扱う量子化方式の変更で対話崩壊が改善するかは未確認。

## 6. 次の実験

次は巨大値を消す前に、**先頭tokenのchannel 35を保持したまま、後続の
通常値を細かく表現する方法**を検証する段階。

実験の合否は次の順で判定する。

1. FP32対照で、追加した変形が元モデルの値を保つか。
2. 先頭と後続を分け、Host量子化誤差・飽和した値の数を測る。
3. 実機で同一入力比較を行い、`add_26`・`add_53`と新規KVの誤差を見る。
4. 同一token列を与える複数ステップ比較と、元の対話例を再評価する。

channel分離、スケーリング、先頭と後続を分ける方式のどれがHTPで成立するかは、
まだ検証していない。単純クリップや先頭を除く較正を改善済みとして採用しない。

## 7. 成果物と再実行

- 診断コード: `app/pipeline/trace_qwen3_activation.py`
- データ: `results/P12c_20260915_activation_outliers/`
  - `graph_info.json`: 観測点・量子化パラメータ

プロジェクトのルートで実行する例。観測用ONNXには対象部分の重みを含めるため、
`scan`の再実行時は一時的なディスク容量が必要。

```powershell
$py = '.\.venv\Scripts\python.exe'
$out = 'results/P12c_20260915_activation_outliers_rerun'
& $py -B -u app/pipeline/trace_qwen3_activation.py --phase inspect --out $out
& $py -B -u app/pipeline/trace_qwen3_activation.py --phase scan --out $out
& $py -B -u app/pipeline/trace_qwen3_activation.py --phase device --out $out
& $py -B -u app/pipeline/trace_qwen3_activation.py --phase histogram --out $out
& $py -B -u app/pipeline/trace_qwen3_activation.py --phase summarize --out $out
```

`inspect`と`scan`はローカルだけで実行可能。`device`と`histogram`は端末上に
前回のジョブ・入力・出力が残っていることが前提。`summarize`は保存結果の集計。
今回の作業で量子化モデルを再生成・配布してはいない。
