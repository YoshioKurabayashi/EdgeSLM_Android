# P12e — 先頭・後続の量子化範囲分離を実モデルで検証

2026-09-15 / EdgeSLM_Android / Qwen3-0.6B / 28層・KV256 / ONNX Runtime CPU

## 結論

**今回の範囲分離モデルは、そのまま実機へ適用できる品質には達しなかった。**

- 全体の活性値を再較正する方法は、共通範囲でも先頭・後続の分離でも大きく悪化した。
- 先頭の巨大値に影響される168組だけを分離すると、固定した対話トークン列での誤差は改善した。
  日本語の後続予測一致率は76.4%→81.1%、層6入口の平均相対誤差は29.7%→23.4%。
- しかし自由生成では、**「音楽をかけて」にエアコンの説明を繰り返した**。
  先頭だけ既存モデルに戻した追加比較でも、同じ指示無視が発生した。
- よって、**数値上の改善を対話品質の改善と判断しない**。HTP変換・実機推論・Androidアプリ変更には進めていない。

これは[P12d](P12d_20260915_dialogue_activation_ranges.md)の「観測したFP32残差の巨大値は先頭だけ」という結果を否定しない。
一方、その分布に合わせた範囲変更だけで、生成の品質も改善することは今回確認できなかった。

## 1. 比較条件

既存の `work/ops/qwen3_dec28c256/qwen3_dec28c256_final_qdq.onnx` を複製し、
活性値のQuantizeLinear/DequantizeLinearに使うscale・zero pointだけを変更した。
単一テンソルの丸めシミュレーションではなく、実際の28層QDQモデルを実行した。

| 条件名 | 変更対象 | 先頭 | 後続 |
|---|---|---|---|
| baseline | 変更なし | 既存 | 既存 |
| shared | 活性値2,226組 | 先頭と後続をまとめた範囲 | 同じ範囲 |
| split | 活性値2,226組 | 先頭の範囲 | 後続の範囲 |
| focused_shared | 巨大値に影響される168組 | まとめた範囲 | 同じ範囲 |
| focused_split | 同じ168組 | focused_sharedと完全に同じモデル | 後続の範囲 |
| hybrid（自由生成のみ） | 同じ168組 | baseline | focused_splitの後続モデル |

168組は、**較正データでの共通範囲のscale÷後続範囲のscaleが32以上**となる組を選んだ。
この閾値を評価データに対して探索していない。ただし、全体変更の失敗を受けて追加した探索的な比較であり、
この168組が最適な変更対象と検証されたわけではない。残差だけでなく、RMSNormの補助テンソル等も含む。

### 固定した条件

- 重みの値・量子化形式、計算ノード9,185個、演算の接続。
- KV入力56組、KV出力側56組、cos/sin/maskの3組、対応付けできなかったlogits出力の1組。
  これら116組の量子化設定は既存のまま。
- 入出力の型・形状、KV256の左シフト、マスク値−60、RoPEテーブル。
- CPUExecutionProvider、ORT推論スレッド4本。各条件は自身が計算したKVを次ステップへ渡す。

各条件の変更対象外のinitializerをバイト列のSHA-256で照合し、不意の変更は0。
計算ノードのSHA-256も共通だった。観測のため、層3入口`add_26`・層6入口`add_53`の
量子化前と逆量子化後を追加出力している。層番号・内部のtoken位置は0始まり。

## 2. 較正と評価

### 較正

既存較正の短文5本に、評価用とは別の日本語・英語チャット3本を加えた。
入力とFP32による生成を合わせて**8本・297token**。先頭8tokenと後続289tokenを分けて測定した。
チャット開始tokenは3本とも同じIDなので、8種類の独立した開始tokenではない。

観測min/maxに0を含め、両端を1.5倍に拡張して量子化範囲を固定した。
較正用チャットは、窓を開ける、休憩地点までの距離、雨の日の持ち物。評価用の温度・音楽の対話は含めていない。

| 観測点 | 既存のstep | 新しい後続用step | 後続用の表現範囲 |
|---|---:|---:|---|
| add_26（層3入口） | 0.113327853 | 0.000459275 | −9.99475 ～ 20.10385 |
| add_53（層6入口） | 0.113326661 | 0.000591449 | −12.87171 ～ 25.88892 |

先頭用の表現上限は両観測点で約12,208～12,210になり、チャット開始時の約8,140を含む。
**この2か所で範囲外の値をなくせても、モデル全体の品質を保証できない**ことが今回の結果。

### 評価

1. P12dで保存した日本語107token、英語109tokenを、全条件に同じ順で入力。
2. 各条件は自身のKVを使い、誤差の蓄積も含めてFP32と比較。
3. 各対話の位置0・1・40・最終位置では、同じFP32のKVを与える1ステップ比較も実施。
4. 元の日本語3ターンを、各モデルが選んだtokenで自由生成。greedy、各回答最大32token。
   FP32・既存モデルは全回答が上限より前に終了し、P12b/P12dの回答文を再現した。

基準は既存の前処理後FP32モデル。P12dの公式モデル由来の残差記録との差は最大0.224%。
観測出力を追加したbaselineと元のQDQを同一入力で照合した8地点では、logitsと全KV出力が完全一致した。

## 3. 同じトークン列を与えた結果

先頭を除いた日本語106token・英語108token。
相対誤差は各tokenで `||量子化モデル−FP32|| / ||FP32||` を計算し、その平均を示す。
zero pointを含む整数コード値を分母には使っていない。

| 条件 | 日本語 予測一致率 | 英語 予測一致率 | 日本語 add_53誤差 | 英語 add_53誤差 |
|---|---:|---:|---:|---:|
| baseline | 81/106 = 76.4% | 91/108 = 84.3% | 29.67% | 27.40% |
| shared | 0/106 = 0.0% | 8/108 = 7.4% | 2033.16% | 7465.30% |
| split | 3/106 = 2.8% | 2/108 = 1.9% | 107.82% | 106.65% |
| focused_shared | 72/106 = 67.9% | 87/108 = 80.6% | 38.12% | 35.17% |
| focused_split | 86/106 = 81.1% | 92/108 = 85.2% | 23.44% | 20.95% |

`focused_split`は、logitsと新規KVスロットの誤差でもbaselineより小さかった。
新規KVは各層の最後の1スロットだけを比較し、空のキャッシュで誤差を薄めていない。
全指標・1ステップ比較は[数値記録](P12e_20260915_temporal_qdq/numeric_evidence.md)とJSONに保存した。

### 一致率の上昇が回答改善を示さなかった理由

日本語の**回答を予測する29地点**に絞ると、baselineもfocused_splitも一致数は**26/29**だった。
全体の一致数81→86の増加は入力文を処理する箇所で生じている。
また、固定トークン列の比較では、モデルが異なる語を選んでも次には所定の語を入力する。
自由生成では、その異なる語とKVを引き継いで進むため、応答全体が変わり得る。

全層splitの2token目では、add_53は丸める前からFP32に対して61.38%ずれていた。
この点では範囲外の値は0であり、add_53そのものの範囲を広げるだけでは、この前段の誤差を直せない。
これをもって、どの前段演算が原因かまで特定したわけではない。

## 4. 自由生成での採否

入力は「エアコンを22度にして」→「音楽をかけて」→「さっき何度にしたっけ？」。

| 条件 | 実際の結果 |
|---|---|
| FP32 | 「エアコンを22度に設定できます。」「音楽をかけてます。」「さっきは22度にしてました。」 |
| baseline | 「エアコンを22度に調節しました。」「音楽をかけてます。」「さっきも22度にしました。」 |
| shared / split | 改行・引用符・`In`等の反復。3回答とも32token上限に達した。 |
| focused_shared | 音楽への応答が不自然になり、温度の参照にも答えられなかった。 |
| focused_split | 音楽の指示に、直前と同じ「エアコンを22度にすると、室内の気臭さが少なくなりますよ。」を返した。温度参照は22度と回答。 |
| hybrid | 先頭だけbaselineに戻しても、音楽の指示に直前と同じエアコンの説明を返した。 |

全出力・token ID・終了理由は数値記録と `*free_generation.json` に保存した。
**先頭側を既存モデルに戻すだけでは、今回の応答悪化は解消しなかった。**
入力箇所の平均一致率や残差誤差を採用条件にせず、指示に応じた回答が保たれることを条件にする。

## 5. 6層実機診断の準備までで止めた理由

同じ候補から、P12cで使用した6層診断モデルの27組を変更したモデルも準備した。
P12cの保存入力16本のSHA-256を照合し、既存Host出力も保存済みの整数コードと完全一致した。
この**同一入力のHost対FP32**では、add_53の誤差は27.84%→10.53%だった。

しかし自由生成の指示追従が悪化したため、**HTP向け変換とスマホでの推論は実行していない**。
P12cの「Host対HTP 31.53%」が改善したという結果ではない。
診断スクリプト `temporal_htp_probe.py` は今回 `prepare` のみ実行済み。
`convert`・`device`の処理は未実行・未検証。

## 6. 現在の問題と次の切り分け

現在は、**量子化の平均誤差を減らしても、自由生成で指示に応じた回答が保たれない**ことが問題。
先頭と後続の分布を分ける発想には数値的な効果が見られたが、変更すべき演算の範囲をまだ絞れていない。

次の検証では、168組を一括で変更せず、残差Add、巨大値を出す線形層、RMSNormの補助テンソルを分ける。
各比較で、最初に生成が分岐する地点のlogitsとKVを確認する。
採用条件は、固定入力での誤差改善に加えて、元の3ターンと別の対話での指示追従を維持すること。
今回の2つの対話だけに設定を合わせても、一般的な改善とは判断しない。

今回の評価は長い文脈やKV入替後の品質、実機の速度・メモリ、2モデル切替の実装コストを検証していない。
既存モデル・Androidアプリを置き換えていない。
