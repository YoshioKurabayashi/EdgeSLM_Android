# P12n — 56本すべてに後続範囲を適用すると、Host だけで完全に崩壊した（先頭トークン位置0が原因）

2026-09-16 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

**P12m で層2単体では改善した調整（`mul_41`/`linear_20` を後続トークン用範囲に）を、28層全体の
同型2本×28層＝56テンソルへそのまま広げ、全位置（先頭トークン込み）に同じモデルを使うと、
Host だけで完全に崩壊した。** 1位保持 85.7%→0.0%、自由生成は日本語どころか単語にもならない
トークン列（`'reonraise ireentiesorcaatti...'`）。28層本番ビルド（136分）に進む前に、
Hostで壊れることを確認できたので、その手前で止めた。

## 1. 方法

- P12m の層2部分モデルと同じ後続範囲（P12e で較正済み、margin 1.5 でフィット）を、
  `layer2_probe.py`/P12j が特定した (SiLU(gate)×up 出力, down_proj 出力) の組を28層分
  グラフ上で機械的に特定し、該当する scale/zero point だけを一括で差し替えた
  （`mul_13/linear_6` が層0、`mul_41/linear_20` が層2、…、`mul_391/linear_195` が層27）
- 新規較正はしていない。P12e の `build_audit.json` の `later` フェーズの値をそのまま流用
- 変更したのは56テンソル分の scale/zero point の initializer だけ。他の重み・グラフ構造は
  SOURCE（`qwen3_dec28c256_final_qdq.onnx`）と完全一致（ノードのSHA-256照合、意図しない
  initializer変更が無いことを照合済み）
- 評価は P12i/P12k/P12l と同じ枠組み（`block_revert_ab.py` の `eval_points`/`score`、
  `fp32_prefix_eval.py` の `free_generation`）: 対話2本（日本語107・英語109トークン）の回答位置
  margin、点B（音楽をかけて直後）、点A（1ターン目の分岐点）、System Prompt「BANANA」/「バナナ」、
  ＋元の日本語3ターンの自由生成（greedy、各回答最大32トークン）
- **先頭トークン（位置0）を含む全位置に同じモデル（56本だけ変更・他は既存）を使う。**
  先頭/後続の2モデル切り替えはしていない

## 3. 読み方

- P12m（層2単体）では改善したのに、28層に広げると崩壊した理由は**先頭トークンの扱い**にある。
  後続範囲（例: mul_41 は −14.92〜9.65）は先頭トークンの巨大値（同 −3086〜3794）を大きく外れており、
  **層2だけなら1層分のクリップで済むが、28層すべてで先頭トークンの情報がクリップされると、
  各層の出力が次の層の入力として使われるため誤差が層を追うごとに複利的に拡大する**
- これは P12j の元々の指摘（「端末は位置0を計算しない（FP32事前計算 or 先頭/後続の2範囲）」という
  設計方針）が、まさにこの理由で必要だったことを裏付ける。P12m の層2narrow実機実験がうまくいったのは、
  **layer2_probe.py の入力 `add_17` がP12jのstep41（もともと後続位置のキャッシュ）で、
  かつ変更が1層分に限られていたから**であり、「56本を先頭トークンにも適用して大丈夫」ことを
  意味しない

## 4. 次

**56本すべてを後続範囲にする単一モデルの筋は畳む。** 次に確かめる価値があるのは、
P12jが元々示していた道筋どおり：

1. **先頭トークン（位置0）だけ既存範囲（baseline）のまま、位置1以降だけ56本を後続範囲にする**
   2モデル切り替え（P12eの「split」と同型だが、対象は56本だけ）
2. またはP12kで検証した「先頭トークンのKVをFP32事前計算して端末に持たせる」方式と組み合わせる

いずれも Host で対話評価点・自由生成が崩れないことを先に確認してから実機へ、という手順は変えない。
