# P12o — 位置0だけbaselineに戻すと崩壊は消えたが、「音楽をかけて」の指示追従は戻らなかった

2026-09-16 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

**P12n の全面崩壊（1位保持0%・KL16.8・自由生成が文字列として破綻）は、位置0だけ既存範囲
（baseline/wide）に戻すことでほぼ消えた。** 1位保持 80.4%、KL 0.304、自由生成も日本語の文として成立する。
→「後続範囲そのものがダメ」ではなく「**位置0に後続範囲を適用したこと**が崩壊の主因」という
P12nの読み筋を裏付けた。

**ただし baseline と同等ではない。** 対話評価点の中で唯一「音楽をかけて」直後（点B）だけ margin が
プラスからマイナスに転じ（+3.35→−0.43）、自由生成でも同じ箇所（turn1）が実際に指示を無視して
壊れた（"Okay, the user wants to play a music..." と英語で自問自答を始め、"音楽をかけてます" を
返さなかった）。System Prompt「BANANA」も margin が 0 まで落ちた（1位を失う境界線）。
**これは P12e の `shared`/`split`/`hybrid` が繰り返し失敗した、まさにその箇所と同じパターン。**
位置0の保護だけでは、この特定の失敗モードを消しきれなかった。

## 1. 方法

- P12n で作った2つのモデルをそのまま使い、新規ビルドはしていない
  - `baseline`（`qwen3_dec28c256_final_qdq.onnx`、既存範囲）
  - `mlp2later`（56本を後続範囲に差し替えたモデル、P12n）
- `fp32_prefix_eval.Pipeline(None, baseline, mlp2later, "none")`: 位置0は`baseline`、位置1以降は
  `mlp2later` を使う2モデル切り替え（FP32事前計算・KV range再較正は混ぜていない。変数は1つだけ）
- baseline・mlp2later 単体の数値は P12n の記録をそのまま再掲（再計算していない。決定論的な評価な
  ので同一の値になるはず）。今回新規に計算したのは `split（wide0/narrow1+）` のみ
- 評価は P12n までと同じ枠組み（`block_revert_ab.eval_points`/`score`、`fp32_prefix_eval.free_generation`）

## 3. 読み方

- **P12nで見えた完全崩壊は、位置0のクリップが主因だったことが強く裏付けられた。** 位置0を保護
  するだけで、1位保持は0%→80.4%、KLは16.8→0.30まで戻った
- **しかし崩壊が消えても、baseline と同水準の品質には戻っていない。** 特に「音楽をかけて」への
  応答だけが再現性を持って壊れる。これは P12e（`shared`/`focused_split`/`hybrid` すべてで同じ
  箇所が壊れた）と一致するパターンで、**位置0以外にも、この特定の対話文脈で narrow range が
  悪さをする要因が残っている**ことを示唆する
- 日本語の対話（chat_original）のほうが英語（chat_english）より margin保持が低い（28.7% vs 56.1%）。
  System Prompt では「バナナ」（日本語）が「BANANA」（英語）より margin を保っている（+3.49 vs
  +0.00）ので、単純に「日本語が弱い」とは言えない。壊れているのは特定の対話文脈・特定の後続語
  （「音楽」）に集中している

## 4. 次

**wide(pos0)+narrow(pos1+) の2モデル切り替えだけでは合格条件を満たさない。** ユーザーが事前に
決めた3条件のうち、第一条件（自由生成がbaseline相当）と第二条件（点Bのmargin維持）を満たしていない。

次に切り分けるべきは、なぜ「音楽をかけて」の応答だけがnarrow rangeで崩れるかという点:

1. 点Bは1ターン目の回答を履歴に含む評価点（P12iで定義）。1ターン目の応答トークン自体が
   split では baseline と異なる可能性があり、そのKVのズレが2ターン目に伝播している疑いがある
   → 1ターン目の応答トークンID自体をbaselineと比較する
2. 位置0だけでなく、位置0の直後（位置1〜数トークン）にも先頭由来の情報が残っている可能性
   （RoPE・attentionを通じて）。保護する範囲を「位置0のみ」から「先頭の数トークン」に広げて
   再評価する価値がある
3. KV range自体の狭さ（P12lで見つかった別問題）を混ぜていない今回の結果が悪いままなら、
   それは今回の変数（pos0/pos1+切り替え）だけでは説明できない要因が別にあることになる

これらをHostで先に確認し、それでも崩れが残るなら「wide/narrowの2モデル切り替え」という
アーキテクチャの筋自体を見直す（FP32事前計算prefix・outlierチャンネル別処理など）。
