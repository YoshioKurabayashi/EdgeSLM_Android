# P12u — D0'：KV入力range修正を加えても、旧D0と同じ失敗が再現した

2026-09-16 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

**P12kの旧D0（位置0だけFP32事前計算＋baseline QDQ）の悪化は、同時に見つかっていたKV入力range
の狭さ（clip）が交絡していたのではないかという仮説を検証したが、否定された。** KV入力range
（16bitの224グループ、P12lで有効性を確認済み）を修正した「D0'」でも、自由生成turn1（「音楽を
かけて」）は旧D0とほぼ一字一句同じ「エアコンの音楽をかけています。」という失敗文になった。

## 1. 方法

- 新規モデルビルドは不要。既存の較正済み成果物2つをメモリ上で組み合わせた:
  - `D:/AI/artifacts/EdgeSLM_Android/P12e_20260915_temporal_qdq/baseline.onnx`（既存範囲のQDQ）
  - `results/P12l_20260916_kv_range_recal/widen_plan.json` の16bitサブセット（224グループ、
    uint8の28グループはC-8制約のため除外。P12lで baseline_kvwide16 として有効性を確認済み）
  - `kv_range_recal.py` の `apply()` で baseline.onnx に16bitサブセットだけを適用（オンメモリ、
    ディスク書き込みなし）
- Pipeline: 位置0はFP32（全28層のK/Vを事前生成）、位置1以降は上記のKV-wide16版baseline
  （narrowな範囲は一切入れていない）
- 評価枠組みはP12k/P12lと同一（`block_revert_ab.eval_points`/`score`、
  `fp32_prefix_eval.free_generation`）

## 3. 読み方

- 集計指標（1位保持・KL・バナナ）はKV修正によって明確に改善した（バナナは+3.79→+6.09で
  baselineを上回るまでになった）。**しかし自由生成の核心の失敗（turn1）は全く変わらなかった。**
  これはKV入力のclipが今回のturn1失敗の主因ではないことを示す
- **旧D0の悪化はKV clippingの交絡だった、という仮説は否定された。** 「位置0だけFP32で計算し、
  そこから先をbaseline QDQで続ける」という構成そのものに、turn1のような特定の応答を壊す何かが
  残っている
- 考えられる説明: 位置0のFP32計算値は、baseline QDQモデルが**量子化誤差込みで学習的に
  "期待している"位置0の値**とわずかに異なる（FP32は完全に正確だが、baseline QDQは量子化された
  近似値を前提に後続の計算が組まれている）。この差が、後続の量子化計算全体の前提とわずかに
  ズレることで、特定の判断（「音楽をかけて」への応答）を狂わせている可能性がある

## 4. 次

事前の合意どおり、**range調整・FP32事前計算どちらの方向でも「音楽をかけて」の失敗を解消できなかった
ため、次はoutlier channel特化処理へ進む**:

1. 層2 `linear_20` だけ高精度/別量子化できないか
2. channel35だけを分離できないか（`linear_20` output の channel 0-34, 36-1023 は narrow
   A16で高分解能、channel35だけwide/高精度でmassive activationを保持）
3. その後にSmoothQuant型の等価変換が成立する場所を探す（ただしdown_proj出力側のchannel35は
   直後に残差加算とRMSNormがあるため、古典的SmoothQuantの単純適用は数学的に自明ではない。
   QAIRT/QNN v68での実装可否も別途確認が必要）

range調整（4x）は保険として保持するが、主ルートにはしない。
