# P12w — add_26の4状態比較：linear_20は主犯ではなく、KVキャッシュの累積差が疑わしい

2026-09-16 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

P12vのoracle失敗（「linear_20の量子化誤差を除けば良くなる」という単純な仮説の反証）を受けて、
「baselineでは複数箇所の量子化誤差が相互に打ち消し合っており、linear_20だけを高精度化すると
その誤差キャンセルのバランスが崩れる」という仮説を検証するため、点B（「音楽をかけて」の判定位置）
と同じ入力条件で add_26（層2出力＝層3入力）をFP32・baseline・4x・oracleの4状態で比較した。

2つの結果が出た:

1. **linear_20の量子化を完全に除去しても、add_26自体はFP32にほとんど近づかない**
   （L2相対誤差 baseline 31.06%→oracle 29.83%、1ポイントのみの改善）。4xとoracleはほぼ
   完全に一致（29.83%、コサイン0.9545）。→ **add_26のFP32からの乖離の大部分はlinear_20より
   上流に由来する**
2. **（予想外・最重要）この1位置のadd_26を差し替えるだけでは、どの条件も判定を壊さない。**
   層3-27の文脈（KVキャッシュ）をFP32の正しい軌跡に固定し、そこへbaseline/4x/oracleの
   add_26を注入すると、3条件すべてでmarginは正のまま（+4.69〜+4.70、FP32自身の+4.617より
   むしろ高い）。P12vのoracle自由生成で見た失敗（点Bのmargin −1.02）は、**この1点のadd_26
   単体の問題ではない**ことを示す

→ P12vのoracle失敗は、「誤差の向き」（P12hの知見）の話ですらなく、**それまでの約79トークンに
わたって各モデルが自分自身の量子化誤差で作り上げてきたKVキャッシュの累積差**に起因している
可能性が高い。次の調査は層2内部ではなく、KVキャッシュの蓄積過程に向ける必要がある。

## 1. 方法

### 状態の準備

- 点B評価点（`chunks[0] + f0 + chunks[1]`、80トークン、判定位置79）を、4つのモデルで
  teacher forcingしながら流した:
  - FP32（`qwen3_dec28c256_prepped.onnx`、量子化なし）
  - baseline（既存QDQ、`qwen3_dec28c256_final_qdq.onnx`）
  - 4x（linear_20だけP12rの4x range、mul_41はbaseline。今回新規に28層フルモデルとしてビルド）
  - oracle（P12vのlinear_20 QDQ除去モデル）
- 各モデルの判定位置79における `add_26`（量子化前のfloat32、層2出口の生の残差和）を採取した

### 比較①: 幾何的な近さ

4状態の add_26 を、FP32のadd_26を基準にL2相対誤差・コサイン類似度・最大絶対誤差で比較した。

### 比較②: decision方向への射影（FP32継続への状態注入）

`qwen3_dec28c256_prepped.onnx`（FP32）から、`add_26`を入力・`logits`を出力とする
「層3-27+lm_head」だけの継続モデルを切り出した（`onnx.utils.extract_model`。重みが2GB超で
protobuf上限に当たるため、外部データ参照を保持したまま`Extractor`クラスを直接使用）。

FP32軌跡（判定位置79の直前までの、FP32モデル自身のcache・cos/sin/attn_mask）を**固定**し、
そこへ4状態それぞれのadd_26を注入して継続モデルに通し、得られたlogitsからmargin
（FP32の1位トークンのlogit − 他の最大logit）を計算した。層3-27の文脈をFP32の「正解」に
固定することで、**add_26の値そのものの効果だけ**を切り出している。

## 2. 結果

| 条件 | L2相対誤差(FP32比) | コサイン類似度 | 最大絶対誤差 | margin(FP32継続へ注入) | Δmargin(FP32比) |
|---|---:|---:|---:|---:|---:|
| FP32 | 0.00% | 1.00000 | 0.00 | +4.617 | 0.000 |
| baseline | 31.06% | 0.95062 | 0.39 | +4.703 | +0.086 |
| 4x | 29.83% | 0.95449 | 0.42 | +4.690 | +0.073 |
| **oracle** | **29.83%** | **0.95449** | 0.42 | +4.690 | +0.073 |

## 3. 読み方

- **4xとoracleのadd_26は幾何的にほぼ同一**（L2誤差・コサインとも小数点以下まで一致）。
  linear_20の量子化幅を変えても（4x）、量子化を完全に除去しても（oracle）、add_26自体は
  ほとんど動かない。**add_26のFP32からの乖離（約30%）の大部分は、linear_20以外の場所
  （up_proj/gate_proj/SiLU/mul_41、あるいは層2のattention側）から来ている**
- **この位置のadd_26を単体で差し替えても、どの条件も判定を壊さない。** これは、P12vで実際に
  観測された自由生成の失敗（oracle条件で「音楽をかけて」に応答できない）が、**この1トークン位置の
  局所的な計算誤差では説明できない**ことを意味する
- 唯一の説明変数として残るのは、**判定位置に至るまでの約79トークン分のKVキャッシュが、各モデル
  自身の量子化誤差を引きずって蓄積された結果、layer3-27のattentionが参照する過去の文脈が
  FP32と実質的に異なっている**という可能性。今回の実験はKVキャッシュをFP32の「正解」に固定して
  add_26だけを動かしたため、まさにこの累積差の影響を除外してしまっていた（＝崩れなかった）
- P12hで確立していた「誤差の大きさより向きが重要」という知見のさらに先: **単一位置での「向き」
  だけでも足りず、複数ポジションにまたがるKVキャッシュの蓄積という時間軸方向の要因を見る必要が
  ある**

## 4. 次

ユーザーの元の計画（②add_26 state swap実験、③Layer2内の逆向き探索）は、この結果を踏まえて
見直しが必要:

1. **KVキャッシュの累積差を直接調べる**: point Bの79トークンを通じて、各モデル（baseline/4x/
   oracle）が実際に自分で作ったKVキャッシュ（特に層2以降）が、FP32のKVキャッシュからどれだけ
   ずれているかを追跡する。ずれが判定位置に近い層・近いトークン位置で急激に大きくなるなら、
   その箇所が真の分岐点
2. **KVキャッシュのswap実験**: 「各モデル自身が作ったKVキャッシュ」と「FP32のKVキャッシュ」を
   入れ替えて判定位置のmarginを見ることで、KVキャッシュの寄与とadd_26の寄与を分離できる
   （本実験がadd_26単体の寄与がほぼゼロだったことを示したので、次はKV側を疑うのが筋）
3. add_26単体のswap実験（当初の②）は、本実験で「効果がほぼない」ことが分かったため、
   優先度を下げてよい
