# P12x — KVキャッシュの累積差をposition×layer×K/Vで追跡：誤差は早期に発生、VがKより大きい、局所異常あり

2026-09-16 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

P12wで「点Bの判定位置のadd_26を単体で差し替えても判定は壊れない」ことが分かったのを受け、
autoregressive特有の「1stepの誤差が約79stepにわたって伝播・蓄積する」という仮説を検証するため、
baseline / 4x / oracle を、FP32と同じ点Bの80トークンで**各モデル自身のKVキャッシュ**を使って
teacher forcingし、position×layer×K/VでFP32比のL2相対誤差を追跡した。

1. **誤差は79ステップかけて徐々に成長するのではなく、位置1-2の時点で既に大きい**
   （baseline位置1でL27のV誤差93.9%）。「蓄積」というより「早期に大きくずれて、その後
   高止まり・変動する」という形
2. **VはKより一貫して誤差が大きい**（P12kの「層12-14のVが52-69%ずれる」を裏付け、
   今回さらに層20-27付近でも同程度以上）
3. **baseline/4x/oracleの3条件は全体としては似た誤差パターンだが、局所的に大きく異なる箇所が
   ある**。特に位置45・層14のVで oracle だけ突出して悪化（baseline/4x ~5% に対し oracle 71.7%）

**3条件のKV誤差の全体的なマグニチュードはほぼ同水準なのに、生成品質には大きな差がある
（baseline成功、oracle失敗）。** これはP12hの「誤差の大きさより向きが重要」が、KV軌跡全体に
対しても成り立つことを示唆する。位置45付近・層14付近のoracle特異的な悪化は、次の絞り込みの
有力な手がかり。

## 1. 方法（および実装上の落とし穴）

- 点Bの80トークンを、baseline（既存範囲）・4x（linear_20だけP12rの4x range、**位置0は
  baseline固定**）・oracle（linear_20のQDQ除去）・FP32の4モデルで、**各モデル自身の
  KVキャッシュ**を使ってteacher forcingした（P12wとは違い、他モデルの文脈に固定しない）
- 各position・各layer（0,2,6,8,12,14,16,20,24,27を抜粋）で、present_k/v の新規スロット
  （最後のトークン分）をFP32比のL2相対誤差で比較した
- **落とし穴（記録として残す）**: 最初の採取で、4xモデルに位置0の保護（P12r/P12sで検証した
  「位置0はbaseline、位置1以降だけ4x」という構成）を入れ忘れ、位置0にも4x rangeをそのまま
  適用してしまった。これによりlinear_20の位置0巨大値（±8143程度）がP12rの4x range
  （±15.67〜31.37程度）で激しくクリップされ、V誤差が最大4285%という壊滅的な数値になった。
  位置0保護を入れて再採取し、正しい結果を得た

## 2. 結果（抜粋: layer 8, 14, 20, 27 の V誤差、FP32比%）

| position | baseline L8 | baseline L14 | baseline L20 | baseline L27 |
|---:|---:|---:|---:|---:|
| 1 | 51.2 | 51.3 | 55.2 | 93.9 |
| 20 | 37.1 | 53.0 | 44.5 | 72.5 |
| 45 | 16.6 | **5.1** | 25.7 | 40.7 |
| 79 | 57.6 | 60.6 | 39.9 | 33.8 |

| position | 4x L8 | 4x L14 | 4x L20 | 4x L27 |
|---:|---:|---:|---:|---:|
| 1 | 47.6 | 50.7 | 49.3 | 79.6 |
| 20 | 41.7 | 69.3 | 47.5 | 71.8 |
| 45 | 21.1 | **5.1** | 21.8 | 23.0 |
| 79 | 52.8 | 67.2 | 50.5 | 60.3 |

| position | oracle L8 | oracle L14 | oracle L20 | oracle L27 |
|---:|---:|---:|---:|---:|
| 1 | 50.0 | 53.5 | 51.2 | 87.3 |
| 20 | 46.8 | 63.6 | 45.2 | 75.2 |
| 45 | 69.5 | **71.7** | 24.3 | 21.0 |
| 79 | 59.3 | 66.1 | 56.4 | 72.1 |

**位置45のL14で、baseline/4xは5.1%とほぼ完全一致なのに、oracleだけ71.7%まで跳ね上がる。**
同じ位置のL8でもoracle 69.5%（baseline/4x 16.6%/21.1%）と明確に悪化している。

## 3. 読み方

- **時間方向の「蓄積」という単純なモデルは支持されなかった。** 誤差は最初の数トークンで
  既に大きく、その後は増加し続けるわけではなく、position・layerに応じて上下に変動する
  （例: baseline L27 Vは位置1で93.9%、位置45で40.7%、位置79で33.8%と、むしろ後半で
  下がる場面もある）
- **V > K は一貫している。** これは既存の知見（P12k: past_v_14の飽和）と整合し、今回は
  特定の層に限らず層20-27でも同程度に大きいことが新たに分かった
- **3条件間の差が最も際立つのは位置45・層14付近。** oracleだけがここで突出して悪化しており、
  baseline/4xはほぼ変わらない。これは「linear_20をどう扱うか」の違いが、**この特定の
  position・layerでKV軌跡に選択的な影響を与えている**ことを示す、初めての具体的な手がかり

## 4. 次

ユーザーの計画どおり:

1. **K-only / V-only swap実験**（判定位置でKとVどちらの寄与が大きいかを特定）
2. **prefix長を変えたKV swap実験**（0-10, 0-20, 0-40, 0-60, 0-79でbaseline KVとoracle KVを
   境界に切り替え、どのposition付近から有害な状態が蓄積し始めるかを特定）
3. 今回見つかった**位置45・層14付近の局所異常**を軸に、layer block単位でのswapを絞り込む
