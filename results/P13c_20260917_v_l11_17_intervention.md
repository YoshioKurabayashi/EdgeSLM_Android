# P13c — L11-17のVだけへの最小介入：range拡張・精度向上どちらもHost自由生成を維持

2026-09-17 / Qwen3-0.6B 28層 KV256 / Host CPU

## 結論

P13bでV側の対策対象がL11-17に絞られたことを受け、**標準のbaseline量子化モデル**（linear_20は
一切変更しない）のまま、L11-17のV量子化パラメータだけを2通りの方向で変更し、Host自由生成への
影響を確認した。**条件A（range拡張）・条件B（8bit→16bit精度向上）のどちらも、K・他layer・MLPを
一切触らずに、Host自由生成を壊さず（むしろ一部指標は改善して）成功した。**

## 1. 方法

V cacheの量子化は2段構成であることを確認した:
- **write側**（present_v_L、cache格納）: uint16、layer毎のscale
- **read側**（repeat_interleave_2X、GQA複製後のact-actMatMul右辺）: uint8（C-8制約）、layer毎のscale

L11-17（7層）について、以下2条件を作成:
- **条件A（range拡張）**: write側・read側とも、P12l較正済みの観測range × margin1.2へ広げる
  （narrowにはしない。既存のclipを解消する方向）
- **条件B（precision向上）**: read側（8bit, C-8制約）だけをuint16に格上げし、同じ観測range・
  marginでfitし直す（bit数そのものを上げる。実機のC-8制約に反する可能性があるためHost限定）

比較はP12r等と同じ枠組み（`block_revert_ab.eval_points`/`score`、`fp32_prefix_eval.free_generation`）。

## 3. 読み方

- **どちらの介入も、Host自由生成を壊さなかった。** これはこのセッションで検証した他の変更
  （linear_20のnarrow化、oracle化等）が軒並みturn1を壊してきたのとは対照的
- **条件Bの方が集計指標で優勢**: 1位保持89.3%（条件A: 87.5%、baseline: 85.7%）、点A +0.35
  （baselineは−0.91だったのが正に転じた）、BANANA +1.50（条件Aの+0.48より強くbaselineに近い）
- **条件Aの方がバナナ（日本語System Prompt）で最良**（+6.06、baseline +4.45を大きく上回る）。
  条件Aはバナナで最良の代わりにBANANA（英語）・点Aでは条件Bに劣る、というトレードオフがある
- どちらも「読みで分かっていたL11-17のV問題」に対する**局所的・低コストな対策**として機能しており、
  K・他layer・MLPを一切変更しなくても効果が出ている

## 4. 次

Host側の合格は確認できた。次の焦点は「**この変更が本来の目的であるHost↔HTP差の縮小にも
効くか**」。ただしL11-17は元々のadd_26測定点（層2出口）とは別の層帯であるため、この介入の
効果を測るには新たな実機測定点（例えばL17付近の残差、あるいはadd_53のような層6入口相当の
測定点）を設計する必要がある。全28層の本番実機ビルド（136分）は依然として高コストなので、
まず部分モデルでの測定方法を検討してから実施するかどうかを判断する。
