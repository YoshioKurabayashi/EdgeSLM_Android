# P13d — L11-17 の V 介入を実機で検証：条件B は v68 で成立せず、条件A は HTP 差を改善しない

2026-09-17 / Qwen3-0.6B 28層 KV256 / 実機 Xperia 5 III（SM8350 / HTP v68）/ 入力は点B の位置41

## 結論

1. **条件B（V read 側 8bit→16bit）は v68 では構成自体が成立しない。** C-8（活性×活性の MatMul は16bit不可）で
   `node_matmul_23` がグラフ検証に落ち、context binary を作れない。精度の良し悪し以前の問題。
   → **この端末では打ち切り。v73 以降での再検討候補として記録に残す。**
2. **条件A（V の range 拡張）は Host↔HTP 差を改善しなかった。** read / write / 層17出口のいずれも
   baseline と同等か、わずかに悪化（L17 write 1.74%→2.09%、L18 入口 8.23%→8.92%）。
3. **そもそも L11-17 の V は、Host↔HTP の観点では既にほとんどずれていなかった**
   （read 1.14〜3.04%、write 0.07〜1.74%、コード一致率 99.6〜99.9%、clip 率 0%）。
   → **P13a/P13b が見つけた「L11-17 の V」は Host の量子化が FP32 からずれる問題であって、
   HTP が Host からずれる問題ではない。** 両者は別の軸だった。
4. 残る Host↔HTP 差は**層境界の残差**に出ている（L18 入口で 8.23%、コード一致率 22.8%）。
   この tap の scale は 0.113 で、P12j で特定した `add_26` と同じ粗い格子。**±1〜2段の差が
   そのまま数%〜十数%の実数誤差になる**という同じ構造。

## 1. 経緯（前セッションからの引き継ぎ）

ディスパッチ側で baseline / 条件A / 条件B の3件をビルド中にセッションが終了し、次の状態で止まっていた:

| モデル | 状態 |
|---|---|
| baseline | S6 の途中で強制終了 |
| 条件A | `could not create op: q::QNN_Convert`（Graph Finalize failure） |
| 条件B | `has incorrect Value 68, expected >= 73`（Graph Compose failure） |

**baseline を S6 から再開したところ、条件A と同じエラーが出た。** つまり条件A の失敗は介入内容ではなく
**部分モデルの作り方**が原因だった（`DequantizeLinear` 後の float を観測タップにしたため、v68 が作れない
fp16→fp32 の Convert が要求された。P12j の `mul_85` と同じ C-1 の罠）。

read 側のタップを **uint8 の量子化コード**（`repeat_interleave_2X_QuantizeLinear_Output`）に変更したところ、
baseline・条件A とも**ビルドが通った**（各 106.4 MiB、S5+S6 で約12分）。観測したいのは read 側の8bitコード
そのものなので、目的にも適う。

## 2. 実機結果（Host↔HTP、strict=true・全ノード NPU、OrtRun 13.2〜13.6ms）

| タップ | dtype | baseline 一致率 / ±1 / max差 / 相対L2 | 条件A 一致率 / ±1 / max差 / 相対L2 |
|---|---|---|---|
| L11 read | uint8 | 99.9% / 100.0% / 1 / **1.14%** | 99.9% / 100.0% / 1 / 1.17% |
| L14 read | uint8 | 99.8% / 100.0% / 2 / **3.04%** | 99.9% / 100.0% / 1 / 3.10% |
| L17 read | uint8 | 99.6% / 99.8% / 7 / **1.80%** | 99.7% / 99.9% / 8 / 2.17% |
| L11 write | uint16 | 99.6% / 99.7% / 14 / **0.07%** | 98.7% / 99.7% / 14 / 0.08% |
| L14 write | uint16 | 99.6% / 99.6% / 317 / **1.72%** | 99.2% / 99.6% / 324 / 1.72% |
| L17 write | uint16 | 99.6% / 99.6% / 1694 / **1.74%** | 96.9% / 99.6% / 1930 / 2.09% |
| **L18 入口 hidden** | uint16 | **22.8% / 59.1% / 12 / 8.23%** | 19.3% / 56.3% / 7 / **8.92%** |

- **clip 率は全タップで 0%**（この入力1点では、条件A が狙った「飽和の解消」は効く余地がなかった）
- 条件A の scale 拡張: read 側 1.21e-01→1.78e-01（L17）、write 側 4.70e-04→6.91e-04（L17）

## 3. 事前に決めた Go 判定への当てはめ

| 判定条件 | 結果 |
|---|---|
| L11-17 V の Host↔HTP 誤差が明確に改善 | **×**（同等〜わずかに悪化） |
| 他の出力を大きく悪化させない | △（L17 write・L18 入口がわずかに悪化） |

→ **28層本体へ持っていく根拠は無い。条件A は No-Go。**

ただし条件A は P13c で **Host の品質を改善**していた（1位保持 85.7→87.5%、バナナ +4.45→+6.06、
自由生成3ターンとも正常）。**Host 品質の改善策としては生きているが、HTP 差の縮小には効かない**、
という分離した結論になる。

## 4. 読み方（2つの軸が別物だったこと）

これまで「V の有害状態」と呼んでいたものは、実験によって指しているものが違っていた。

| 軸 | 測っているもの | L11-17 の V は |
|---|---|---|
| P13a/P13b（swap） | oracle/baseline の KV を入れ替えた時の**判定 margin** = Host 内での FP32 からのずれ | **主要因**（L11-17 だけで +2.349） |
| P13d（実機） | 同じ入力での **Host↔HTP のずれ** | **ほぼ無関係**（0.07〜3.04%、一致率 99.6%以上） |

HTP 側のずれは、**層境界の残差**（L18 入口 8.23%、scale 0.113）に集中している。これは P12j で
`add_26`（22.09%、scale 0.113）に見たものと同じ構造で、**粗い格子の上で ±1〜2段の差が大きな実数誤差になる**。
