# P15 — 別セッションからの引き継ぎ・Qwen3 調査のクローズ・デモの整備

2026-09-17 / EdgeSLM_Android ＋ EdgeSLM_AndroidDemo / 実機 Xperia 5 III（SM8350 / HTP v68）

このセッションで行った作業の記録。技術的な結論そのものは [P13d](P13d_20260917_v_l11_17_device_probe.md) と
[P14](P14_20260917_qwen3_closing.md) にあり、ここでは**何を引き継ぎ、何を直し、何を残したか**を整理する。

## 1. 引き継ぎ

別セッション（「P12l後続: 層2部分モデル実機テスト」）が P12m〜P13d を進めていたが、セッション終了とともに停止していた。
引き継ぎ時点の状態:

| モデル | 状態 |
|---|---|
| baseline | S6（context 生成）の途中で強制終了 |
| 条件A（V range 拡張） | `could not create op: q::QNN_Convert`（Graph Finalize failure） |
| 条件B（V read 8bit→16bit） | `has incorrect Value 68, expected >= 73`（Graph Compose failure） |

**確認したこと**: qairt のプロセスは無く、5分間ファイル更新も無い＝完全停止。端末は接続されたまま、
別セッション「EdgeSLMアプリ再インストール」が同時に動いていた（端末の取り合いに注意が必要だった）。

### 1.1 失敗の切り分け

baseline を S6 から再開したところ**条件A と同じエラー**が出た。→ 条件A の失敗は**介入内容ではなく
部分モデルの作り方**が原因。`DequantizeLinear` 後の float を観測タップにしていたため、v68 が作れない
fp16→fp32 の Convert が要求されていた（P12j の `mul_85` と同じ C-1 の罠）。

**read 側のタップを uint8 の量子化コード**（`repeat_interleave_2X_QuantizeLinear_Output`）に変更 →
baseline・条件A とも**ビルド成功**（各 106.4 MiB、S5+S6 で約12分）。

一方、条件B の失敗は本物で、**C-8（活性×活性の MatMul は16bit不可）**そのもの。`node_matmul_23` が
`QnnBackend_validateOpConfig` に落ちる。**v68 では構成自体が成立しない**（精度の問題ではない）。

### 1.2 編集の競合

作業中に別セッションが同じファイル（`v_l11_17_device_probe.py`）を編集しており、こちらの修正が
一度巻き戻った。ユーザーに停止してもらってから再開。**同じファイルを2つのセッションから触ると壊れる**。

## 2. 実機検証（P13d）

同じ入力（点B の位置41）で Host↔HTP を比較した。

| タップ | dtype | baseline | 条件A |
|---|---|---:|---:|
| L11/L14/L17 read | uint8 | 1.14 / 3.04 / 1.80% | 1.17 / 3.10 / 2.17% |
| L11/L14/L17 write | uint16 | 0.07 / 1.72 / 1.74% | 0.08 / 1.72 / 2.09% |
| L18 入口 hidden | uint16 | **8.23%** | 8.92% |

- **条件A は改善しない**（同等〜わずかに悪化）→ 28層への適用は No-Go
- **L11-17 の V は Host↔HTP では元々ほぼ一致**（一致率 99.6%以上、clip 率 0%）
  → P13a/P13b が見つけた「V の有害状態」は **Host が FP32 からずれる問題**であって、**HTP のずれではない**。
  2つは別の軸だった

## 4. デモアプリの整備（EdgeSLM_AndroidDemo）

### 4.1 直した不具合: モデル切り替えで会話がリセットされない

`switchMode()` はセッションを開き直す（＝KV キャッシュは失われる）のに `chatStarted` が立ったままで、
**system prompt を含まない「2ターン目の差分」を新しいモデルへ渡していた**。

```
修正前: Qwen2.5 で1ターン → Qwen3 へ切替 → 送信 → promptLen=22（system prompt 無し）
修正後: 同じ操作                              → 送信 → promptLen=41（system prompt ＋ 空 think ブロック）
```

`switchMode()` の先頭で `resetChat()` を呼ぶよう修正し、ビルド・インストール・実機確認まで完了。
Qwen2.5 側にも効く（切り替えのたびに履歴が初期化され、前のモデルの発話が混ざらない）。

### 4.2 実機での動作確認（2026-09-17 23:19〜23:26）

| モード | 結果 |
|---|---|
| **Qwen2.5 KV512** | 「エアコンを22度にして」→「22度に設定します。」**26.6 tok/s**（OrtRun 32.5ms、充填 1409ms / 37トークン） |
| **Qwen3 KV256** | 英語の思考文を生成（内容は崩れたまま）。**10.4 tok/s**（OrtRun 77.9ms、充填 3928ms / 41トークン）。切替 1.7秒 |

どちらも **strict=true（全ノード NPU・CPU フォールバックなし）**。

### 4.3 デモとして見せられること / 見せられないこと

| | 内容 |
|---|---|
| 見せられる | 端末内だけで生成（機内モードで動く）／全ノード NPU 実行／KV キャッシュによる対話／**モデル2種の切り替えと速度差**（26.6 vs 10.4 tok/s）／窓ずらし版との比較 |
| 見せられない | **Qwen3 の対話内容**（英語の思考文になる）。Qwen2.5 も 0.5B 相応で、指示追従や履歴参照は限定的 |
