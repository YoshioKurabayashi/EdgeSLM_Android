# P16 — 「実機がよければよい」を確かめる：4x は**実機に載せられる形が存在しなかった**

2026-09-17〜18 / Qwen3-0.6B 28層 KV256 / Host CPU（ORT）

## 0. この実験の問い

P14 でクローズした後、ユーザーから次の問いがあった。

> Host は別に使わないので実機がよければよいのでは？

もっともな問いで、**空白が1つ残っていた**。P12r/P12s で「Host の自由生成が唯一きれいだった 4x」は、
実機では**層2 の部分モデルでの誤差（21.95%→18.67%）しか測っておらず、28層の end-to-end 実機生成を
一度も見ていなかった**。「Host で良い設定を実機に持っていったら実際どうなるか」は未測定だった。

そこで実機ビルド（約140分）に進む前に、**そもそも実機に載せられる形かどうか**を Host で確かめた。

## 1. 結論

**4x は実機に載せられる形が存在しない。** Host 品質の議論以前の問題だった。

P12r の 4x は、記録上は「Host の自由生成が正常」とだけ書かれていたが、実際には
**位置0 は baseline モデル／位置1以降は 4x モデル**という **2モデル構成**に依存していた。
実機は context binary 1本・セッション1つで、**会話の途中でモデルを切り替えられない**。

1モデルにまとめる（＝位置0 も 4x を通す）と、**層2 の scale ただ1つを変えただけで完全崩壊した。**

| 変種 | 位置0 の扱い | 実機で可能か | 1位保持 | KL | 点B | 自由生成 |
|---|---|---|---:|---:|---:|---|
| baseline | — | ○ | 85.7% | 0.195 | +3.35 | ○ 正常 |
| **A1**（層2 のみ 4x） | **4x（1モデル）** | **○** | **0.0%** | **18.24** | −17.19 | **× 文字化け** |
| **B1**（全28層 4x） | **4x（1モデル）** | **○** | **0.0%** | **16.25** | −29.87 | **× 文字化け** |
| A2（層2 のみ 4x） | baseline（2モデル） | **×** | 83.9% | 0.219 | −0.64 | ○ 正常 |

- **A1 と A2 は同じ scale**。違いは位置0 をどちらのモデルで通すかだけ。それで**正常と完全崩壊に分かれた**
- A2 は P12r の 4x の再現テストにもなっており、自由生成は baseline と同等の品質だった
  （「音楽をかけてます。」「さっきは22度にしてました。」）
- baseline も過去の値を完全に再現（85.7% / +3.35 / 3ターンとも同一）。基準は正しく取れている

## 2. 方法

既存の QDQ（`qwen3_dec28c256_final_qdq.onnx`）から **scale / zero point だけ**を差し替えた。
重みとノードは1バイトも変えていないことを、初期化子と全ノードの SHA-256 で検証している。

| 変種 | 変更したテンソル | margin |
|---|---|---|
| A1 | `linear_20`（層2 の down_proj 出力）1本 | 6.0（後続トークン観測レンジ×6.0＝P12r の 4x） |
| B1 | `linear_{7L+6}`（全28層の down_proj 出力）28本 | 同上 |

評価は P12t で確立した順序（①自由生成 → ②回答開始 token の margin → ③集計指標は診断用）。
評価点・基準は P12i 以降と同一（日英の回答位置52、点B、点A、BANANA/バナナ）。

### ビルド時に分かったこと

| 変種 | scale の変化 |
|---|---|
| A1（層2） | **158倍細かく**なる（表現範囲 −15.7〜+31.4） |
| B1（全28層） | 中央値で **7.6倍粗く**なる（＝ほとんどの層では「広げる」変更） |

**層2 以外の down_proj は、元々のレンジが狭い。** 後続レンジ×6.0 を当てると逆に粗くなる。
巨大活性の発生源である層2 だけが特異である、という P12j の結論の傍証になっている。

## 3. なぜ位置0 だけで壊れるのか

位置0 の層2 MLP 出力には **8142** の巨大活性が出る（P12k。トークンによらず位置0・channel 35）。
4x の表現範囲は **−15.7〜+31.4** なので、位置0 は**確実に飽和する**。

```
位置0 で飽和した値が残差に乗る
        ↓
その誤った hidden が層3 以降へ伝播し、KV にも書かれる
        ↓
以降のすべてのトークンがその汚染された文脈の上で動く
        ↓
1位保持 0.0%、日本語ですらないトークン列
```

**「1トークンだけの問題」ではない。** 位置0 は KV の先頭スロットとして最後まで参照され続ける。

## 4. この問いへの回答

「実機がよければよい」は正しい目標だが、今回の候補には次の順で壁があった。

```
① 実機に載せられる形か     ← 4x はここで落ちた（2モデル構成に依存）
② 量子化設計として妥当か   ← Host 品質で測る部分
③ 実行環境の差が小さいか   ← Host↔HTP で測る部分
```

**①を確かめずに②③を議論していた。** 実機ビルド140分を使う前にここで止められたのは、
「Host で先に確かめる」手順が働いた結果である。

なお、実機で位置0 を守る唯一の方法は「位置0 の KV を事前計算して端末に持たせる」だが、
これは P12k で検証済みで、自由生成は改善せず最小 margin は悪化した。

## 5. クローズ判断への影響

**変わらない。** むしろ、P14 で「実機の end-to-end を測らずに閉じた」という空白が、
**測る価値がなかったのではなく、載せる形が作れなかった**という形で埋まった。

## 6. 教訓（StudyMemo 11章へ反映）

**記録には「何が良かったか」だけでなく「それが何に依存していたか」を書く。**
P12r の 4x は「Host の自由生成が唯一きれい」と記録されていたが、
**位置0 を別モデルで守っているという前提**が結論と同じ強さでは書かれていなかった。
そのため後から「良い設定」として再利用しようとしたときに、実機で成立しないことが見えなかった。
