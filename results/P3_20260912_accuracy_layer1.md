# P3: 本物の Qwen2.5-0.5B デコーダ層1枚の精度

| 項目 | 内容 |
|---|---|
| 実施日 | 2026-09-12 |
| 対象 | **Qwen2.5-0.5B-Instruct のデコーダ層0**（本物の重み / hidden 896 / 14ヘッド / KV 2 / FFN 4864 / seq 16） |
| 較正 | **実テキストから作った hidden_states 14件**（埋め込み表を通した本物の入力） |
| 評価 | **較正とは別の文**から作った 11件 |
| 測定 | ホスト CPU 上で QDQ を実行（Q/DQ が実際に量子化するので量子化損失がそのまま出る） |
| 判定 | **動く。ただし精度は足りていない。原因は特定できた** |

---

## 1. まず動いた

本物のデコーダ層1枚が **実機 SOG05 の NPU で `pass_strict` / median 0.958 ms**。
C-9（マスク定数）・C-10（Expand→Concat）の書き換えが実モデルで効いている。

```
S2: 63ノード → 66ノード（Expand 2個が Concat へ）
S4: 232ノード（QDQ）
S6: context binary 14.46 MiB
端末: QNN HTP - EPContext - all nodes / median 0.958ms
```

参考: 縮小版の `block_real`（hidden 128）は 0.390 ms。**hidden が 7倍で 2.5倍**。

---

## 2. 精度: 足りていない

fp32 を正解とした相対 L2 誤差（低いほどよい）。

| 方式 | 相対L2誤差 | cos類似度 | v68 で動くか |
|---|---:|---:|---|
| **A16W8 素** | **5.50%** | **0.9985** | **動かない（C-8）** |
| A16W8 + attention のみ A8（C-8回避） | **30.39%** | 0.9521 | 動く |
| A16W8 混合（**乱数**較正） | 38.88% | 0.9301 | 動く |
| A16W8 混合 + softmax 安定化 | 41.65% | 0.9154 | 動く |
| A8W8（全部 8bit） | 52.39% | 0.9367 | 動く |

**C-8 の回避策そのものが、誤差を 5.5% から 30.4% へ——5.5倍に増やしている。**

これは「量子化が難しい」のではない。**v68 で動かすために払っている代償**である。

---

## 3. 原因の特定

### 3.1 テンソル単体の誤差を見ても分からない

A8 に落とした5つのテンソルについて、8bit 量子化の誤差を個別に測った。

| テンソル | レンジ | 8bit 誤差 | 16bit 誤差 |
|---|---|---:|---:|
| transpose_4 (V) | [-130.4, +121.5] | 0.84% | 0.003% |
| **mul_8（attentionスコア）** | **[-26.7, +1600.4]** | **0.49%** | 0.002% |
| val_110 (softmax出力) | [0, 1] | 0.44% | 0.002% |
| _unsafe_view_1 | [-0.195, +0.290] | 1.99% | 0.008% |
| matmul_2 (context) | [-0.192, +0.290] | 2.60% | 0.010% |

**どれも 0.4〜2.6% しかない。30% を説明できない。**

### 3.2 softmax の先を見て初めて分かる

スコアテンソルだけを取り出し、量子化してから softmax を通した。

| | 1段階の幅 | **スコアの L2 誤差** | **softmax 後の L2 誤差** | argmax 一致 |
|---|---:|---:|---:|---:|
| **8bit** | 6.38 | **0.49%** | **62.82%** | **29.2%** |
| 16bit | 0.025 | 0.0019% | 0.41% | 99.0% |

**スコアの誤差は 0.49% なのに、softmax を通すと 62.8%。**
どこを見ているかで 128倍も違う。

理由: スコアは `[-26.7, +1600.4]`（幅 1627）に広がっており、
8bit だと 1段階が **6.38** になる。softmax の入力で 6.38 の差は確率で約 590倍
（e^6.38）。一方 L2 ノルムは大きい値に支配されるので、誤差が小さく見える。

**→ 量子化の良し悪しは「その先で何に使われるか」まで見ないと判定を誤る。**

### 3.3 なぜレンジが広いのか

ヘッドごとに見ると、**1つのヘッドだけが桁違い**だった。

```
head 1: [ 268.66, 1600.39]  幅 1331.73   ← これ
head 6: [ 443.70,  521.83]  幅   78.13
head 9: [  17.69,   71.52]  幅   53.83
（他の12ヘッドは幅 54〜272）
```

行（トークン）ごとの幅は**中央値 7.37**。つまり
**本当に必要な分解能は 7 程度なのに、1627 のレンジに合わせた目盛りを使わされている。**

---

## 4. 試した対策と結果

### 4.1 スケールを MatMul の前へ移す → 効果なし

`Mul(MatMul(q,k), 1/8)` → `MatMul(Mul(q,1/8), k)`。数学的に厳密に等価
（fp32 で最大絶対差 0 を確認）。QK^T の生値レンジ 12,515 が 1,600 になる。

**結果: 30.3819% → 30.3904%（変わらず）。**

読み違えていた。量子化されるのは**スケール後**の値であって、移動しても
スケール後のレンジは変わらない。最大絶対誤差だけ 2.83 → 2.43 に改善した。

### 4.2 softmax の前で行最大を引く → **悪化した**

`softmax(x) = softmax(x - rowmax(x))` は厳密に等価（fp32 で差 0 を確認）。
numpy 上の単独試算では劇的に効く:

| | 1段階 | softmax後L2誤差 | argmax一致 |
|---|---:|---:|---:|
| そのまま 8bit | 6.38 | 62.8% | 29.2% |
| **行最大を引いて 8bit** | **0.26** | **3.2%** | **90.5%** |

**ところがパイプラインに入れると 30.4% → 41.6% に悪化した。**

理由: **スコアは MatMul の出力時点ですでに 8bit 化されている**。
その後に行最大を引いても手遅れで、追加した ReduceMax/Sub の量子化誤差だけが乗る。

**対策を打つ位置が間違っていた。** 実装は記録として残し、既定は無効にした。

### 4.3 MatMul の出力だけ 16bit に残す → 量子化器が拒否

C-8 が禁じているのが「16bit × 16bit の MatMul」なら、入力だけ 8bit にして
出力は 16bit に残せるのではないか、と考えた。**context 生成は通った**が、
ORT の量子化器が拒否する:

```
ValueError: Desired producer quant_type for matmul_1 doesn't match existing type.
```

**MatMul の出力型は入力型と一致させる**という制約が量子化器側にある。
指定しなければ自動で 8bit に揃えられ、明示すればエラーになる。

→ **v68 では attention スコアを 8bit 以外にする道が塞がっている。**

### 4.4 ヘッドごとに MatMul を分割したら？（試算）

スコアテンソルをヘッド軸で分けて別々のスケールで量子化した場合を numpy で試算した。

| 量子化の粒度 | softmax後L2誤差 | argmax一致 |
|---|---:|---:|
| テンソル全体 8bit（**現状**） | 62.82% | 29.2% |
| **ヘッドごと 8bit（分割すれば可能）** | **17.94%** | **79.6%** |
| ヘッド×行ごと 8bit（理想・実現手段なし） | 0.80% | 99.2% |
| テンソル全体 16bit（**v68 では不可**） | 0.41% | 99.0% |

**ヘッド分割で 3.5倍改善するが、16bit には遠く及ばない。**
本当に効くのは行（トークン）ごとの量子化だが、QNN の活性化はテンソル単位なので
**構造的に到達できない**。

---

## 5. 較正データの効果

| 較正 | 相対L2誤差 |
|---|---:|
| **実テキストから作った hidden_states** | **30.39%** |
| 乱数 ±1.0（P2b まで使っていたもの） | 38.88% |

実データ較正で **8.5ポイント改善**。理由は値域が桁違いだったこと:

```
本物の hidden_states : ±0.09（std 0.0156）
P2b までの乱数較正   : ±1.0        ← 約11倍広い
```

A16（65,536段階）なら 11倍広くても耐えるが、**A8（256段階）では
実データが ±6段階にしか収まらず壊滅する**。

---

## 6. これが意味すること

### 6.1 v68 における LLM 精度の壁

```
C-8（v68 は 16bit×16bit の MatMul 不可）
  → attention スコアは 8bit にせざるを得ない
    → スコアのレンジ 1627 に対し必要な分解能は 7
      → softmax が壊れる（argmax 一致 29%）
        → 層あたりの相対誤差 5.5% → 30.4%
```

**これは実装の巧拙ではなく、v68 のアーキテクチャ制約から来ている。**
v73 以降なら 16bit の act×act MatMul が使えるので、この鎖は最初の環で切れる。

### 6.2 未決事項#6（端末追加調達）への材料

要件定義書の未決事項#6「8 Gen 2以降の端末を追加調達するか」は
**P3 完了時点まで判断を遅らせる**としていた。その材料が出た。

| | SD888 (v68) | 8 Gen 2以降 (v73+) |
|---|---|---|
| act×act MatMul 16bit | **不可** | 可 |
| attention スコアの量子化 | 8bit 強制 | 16bit 可 |
| 層あたり相対誤差（実測/推定） | **30.4%** | 5.5% 相当 |

### 6.3 ただし、まだ結論ではない

**この 30% が最終的な出力にどう効くかは、まだ測っていない。**

- 層1枚の L2 誤差は**最終的なトークン選択の良し悪しとは別物**である
- 24層で誤差がどう積み上がる（あるいは打ち消し合う）かは未測定
- 本当に見るべきは **logits の一致率・perplexity・生成文の質**

「層の L2 が 30% だから使い物にならない」と結論するのは、
**3.2節で自分が指摘した誤り（見る場所を間違える）と同じ**である。
次は端から端まで測る。

```

```

ヘッド分割のような対策に工数を使うべきではない。
