# P3: 実機での精度（runner v0.3 / infer task）

| 項目 | 内容 |
|---|---|
| 実施日 | 2026-09-13 |
| 端末 | Sony Xperia 5 III SOG05（SM8350 / HTP v68） |
| runner | **v0.3**（`infer` task = 実データを読んで出力をファイルに書く） |
| 対象 | Qwen2.5-0.5B の 埋め込み + 先頭2層 + lm_head（440MB EPContext） |
| 評価 | 較正と別の文 **11系列 × 16トークン = 176 位置** |
| 判定 | **ホストのシミュレーションは楽観的だった。ただし方式の順位は保たれた** |

---

## 1. 結論

**ホスト上の QDQ シミュレーションと実機には、無視できない差がある。**

| 方式 | ホスト top-1 | **実機 top-1** | ホスト相対L2 | **実機相対L2** |
|---|---:|---:|---:|---:|
| A16W8 素（**v68 で動かない**） | 85.2% | — | 6.79% | — |
| **`u16×u8` + 左右入替** | **80.7%** | **63.1%** | 9.85% | **22.11%** |
| 両側 A8（当初の回避策） | 50.0% | **46.6%** | 32.59% | **38.27%** |

層1枚でも同じ傾向だった:

| | ホスト | 実機 |
|---|---:|---:|
| 層1枚の相対L2（`u16×u8`+入替） | 9.33% | **16.11%** |

**やってよかった。** ホストの数字だけで「上限 85.2% に対し 80.7%、ほぼ到達」と
報告していたら、実態（63.1%）と 17.6ポイントずれたまま話を進めていた。

---

## 2. 順位は保たれた

これが重要である。**実機でも左右入替の方が良い**（63.1% vs 46.6%、+16.5ポイント）。
ホスト上で選んだ方式は、実機でも正しい選択だった。

ただし**改善幅は縮む**:

| | 改善幅 |
|---|---:|
| ホスト | 50.0% → 80.7%（**+30.7ポイント**） |
| 実機 | 46.6% → 63.1%（**+16.5ポイント**） |

### 劣化の仕方が方式によって違う

| 方式 | ホスト→実機の低下 |
|---|---:|
| 両側 A8（当初） | 50.0 → 46.6（**-3.4ポイント**） |
| `u16×u8` + 入替 | 80.7 → 63.1（**-17.6ポイント**） |

**量子化誤差を小さくした方が、実機での低下が大きい。**
これは **HTP 側に、量子化とは別の誤差要因がある**ことを示している
（積和の中間精度・丸め・タイリング等）。量子化誤差が大きいうちはそれに埋もれ、
小さくすると相対的に顔を出す。

→ **ホスト上で量子化をさらに詰めても、実機では頭打ちになる。**
どこまで詰める価値があるかは、実機で測らないと判断できない。

---

## 3. 測れなかったこと

**A16W8 素（ホストで 85.2%）は v68 では動かないので、実機の値が無い。**
したがって「実機における v68 と v73 の差」は**この測定からは出せない**。

ホストの 85.2% と実機の 63.1% を直接比べるのは誤り（片方はシミュレーション）。
v73 機での実測がなければ、精度面での世代差は定量化できない。

---

## 4. 実装: runner v0.3

| 追加 | 内容 |
|---|---|
| **`infer` task** | `batches[]` で入力ファイルを指定し、推論結果を `out/<job>_<id>_<name>.bin` に書く |
| **`Session::run(..., outputs)`** | 出力テンソルの中身を取り出す。v0.2 までは破棄していた |
| `Session::resolve_path()` | `inputs/x.bin` を端末の実パスへ解決 |
| **入力サイズの検証** | バイト数が期待と違えば**止める**。足りないまま推論すると結果が静かに壊れる |

ホスト側は `app/pipeline/device_accuracy.py`:
npz → 生バイト列 → push → `infer` → pull → fp32 参照と比較、を一息で行う。

### 途中で踏んだもの

**① `subprocess.run(["bash", ...])` が黙って何もしなかった。**
Python（Windows exe）から `bash` が解決できず、**エラーも出さないまま**
「結果が見つからない」とだけ表示された。最初の2回は、私が手で実行した
ジョブの結果を拾っていただけだった。→ adb を直接叩く形に変更。

**② 完了判定を標準出力の文言で行っていた。**
`"done at" not in stdout` で失敗と判定していたが、**端末側は成功していた**。
→ 成果物（結果 JSON の `job_id`）で判定するよう変更。

**③ top-1 一致の判定条件が雑だった。**
`shape[-1] > 100` を logits とみなしていたため、層出力 `[1,16,896]` の
hidden 次元に対する argmax を「top-1 一致 95.3%」として出してしまった。**無意味な数字**。
→ 語彙サイズ級（`>= 10000`）でのみ計算するよう修正。

3件とも**「成功したように見えて実は違う」**類である。このプロジェクトで
繰り返し踏んでいる型で、今回は自分のスクリプトでやった。

---

## 5. サンプル数について

最初 4サンプルで測ったときは top-1 **54.7%** だったが、11サンプルでは **63.1%**。
**8.4ポイントの差**があった。

→ **4サンプルでは足りない。** 176トークン位置（11系列）でも十分とは言えず、
判断に使う数字はもっと増やすべきである（較正データも 14系列と少ない）。

```
                              （例: 量子化をほぼ無損失にした小モデルで実機誤差だけを測る）

```

**優先は「実機の誤差要因の切り分け」**。2章の観察（量子化を詰めるほど実機での
低下が大きい）が正しいなら、**量子化の作り込みには上限がある**ことになり、
どこで手を止めるかの判断に直結する。
