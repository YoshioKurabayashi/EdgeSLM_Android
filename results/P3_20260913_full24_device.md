# P3: フル 24層の Qwen2.5-0.5B が Snapdragon 888 の NPU で動いた

| 項目 | 内容 |
|---|---|
| 実施日 | 2026-09-13 |
| 端末 | Sony Xperia 5 III SOG05（SM8350 / HTP **v68**） |
| モデル | **Qwen2.5-0.5B-Instruct 全24層 + 埋め込み(151,936語彙) + lm_head** |
| 量子化 | A16W8 + RMSNorm 正規化(C-11) + `u16×u8`(C-8) + 左右入替 |
| サイズ | context binary **736.55 MiB** |
| 判定 | **動いた。全ノード HTP、CPU フォールバックなし** |

## 1. 結果

```
backend : QNN HTP - EPContext - all nodes
strict  : True                      ← 全ノードが HTP
io      : input_ids [1,16] int64  ->  logits [1,16,151936] float32
OrtRun  : median 37.22 ms / min 36.29 / max 37.68 (n=5)
warmup  : 64.2 → 36.6 ms
power   : default(unsigned_pd)
```

**prefill 16トークンが 37ms。** 1トークンあたり 2.3ms 相当。

### 実機での精度

| | ホスト top-1 | **実機 top-1** | 実機 相対L2 | cos |
|---|---:|---:|---:|---:|
| **24層** | 80.7% | **73.3%** | 46.0% | 0.893 |
| 2層（参考） | 80.7% | 63.1% | 22.1% | 0.975 |

**24層の方が 2層より実機 top-1 が良い**（73.3% > 63.1%）。
層2〜23 は層0/1 より量子化に強いという観察（`P3_20260913_mixed_matmul.md` 4章）と整合する。

## 2. ここへ至るまでに越えた壁

| # | 壁 | 解決 |
|---|---|---|
| 1 | **ORT が 2GB 超モデルを量子化できない** | **opset 21 で export**（16bit 量子化の opset 自動変換が fp32 2.52GB をシリアライズしていた） |

## 3. C-12: 大きなモデルは EPContext にバイナリを埋め込まない

### 症状

772MB の EPContext ONNX をロードすると、**6秒後にプロセスが SIGKILL される**。
ログは `model=...` で途切れ、`lowmemorykiller` は「Not killing」と言っていた。

メモリを追跡すると明快だった:

```
RSS 102MB → 220 → 443 → 693 → 1,025 → 1,468MB → SIGKILL
MemAvailable 3.86GB → 2.52GB → (kill後) 3.89GB
```

**アプリの RSS が 1.47GB に達して殺されていた。**

### 原因

`embed_mode=1`（既定）だと **context binary が ONNX の中に入る**ため、
ロード時に**二重に持つ**ことになる:

```
ONNX ファイル 772MB（binary 736MB を内包）
        +
QNN が createFromBinary へ渡すコピー 736MB
        ≈ 1.5GB
```

実測の 1.47GB とほぼ一致する。

### 対処

**`embed_mode=0`** にして context binary を**別ファイル**として参照する。
`ep_cache_context` にファイル名を入れ、ONNX と同じディレクトリに置く。

```
変更前: qwen24_epctx.onnx     772 MB  → RSS 1.47GB → SIGKILL
変更後: qwen24ext_epctx.onnx  442 B   + qwen24_ctx.SM8350.bin 772MB → **動作**
```

**ONNX が 442バイトになった。** 二重持ちが消える。

`app/pipeline/wrap_epctx.py` の `embed=False`。

### いつ必要か

420MB の context（2層モデル）は `embed_mode=1` のまま動いていた。
**境界は実測していないが、736MB では確実に必要。**
大きいモデルでは最初から `embed_mode=0` にしておくのが安全である。

## 4. 当初目標への到達度

目標:「**C++ で作成した推論サービスを搭載して軽量 LLM を搭載し、
スマホのローカル完結で SLM を動作させる**」

| 要素 | 状態 |
|---|---|
| C++ 推論サービスを搭載 | ✅ |
| ローカル完結（通信なし） | ✅ |
| **軽量 LLM（Qwen2.5-0.5B）をフルで搭載** | ✅ **24層すべてが NPU で動作** |
| SLM を動作させる（推論） | ✅ **prefill 16トークン 37ms / 実機 top-1 73.3%** |
| **文章生成**（decode + KVキャッシュ） | ❌ **未着手** |
| 端末側トークナイザ | ❌ 未着手 |

**「モデルが端末の NPU で動く」ところまでは到達した。**
残るのは**生成ループ**（decode + KVキャッシュ）と**トークナイザの端末移植**である。

## 5. 累積した v68 の制約（C-1〜C-12）

| # | 内容 | 発見 |
|---|---|---|
| C-1 | float セグメントを残さない | P1 |
| C-2 | `soc_id` を刻まない | P1 |
| C-3 | backend_extensions の config を渡さない | P1 |
| C-4 | `--preserve_io_datatype` は完全QDQのみ | P1 |
| C-5 | `BatchNormalization` を残さない | P1 |
| C-6 | `useLegacyPackaging = true` | v0.1 |
| C-7 | `<uses-native-library>` を宣言 | v0.1 |
| **C-8** | MatMul は `u16×u8` のみ（非対称） | P2b / P3 |
| **C-9** | 因果マスクの `-3.4e38` を有限値へ | P2b |
| **C-10** | `Expand` を `Concat` へ書き換え | P2b |
| **C-11** | **RMSNorm をトークン最大値で正規化** | **P3** |
| **C-12** | **大きなモデルは `embed_mode=0`** | **P3** |

**C-8 / C-11 / C-12 の3つは、いずれも「公式文書に書かれていない」うえに
症状が真因を示さない。** それぞれ oracle 実験・分布の実測・メモリ追跡で突き止めた。

top-1 73.3% が文章としてどう見えるかは、L2 や KL を眺めるより読んだ方が早い。
