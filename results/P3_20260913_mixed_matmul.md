# P3 続: C-8 は思っていたより狭い制約だった（u16 × u8 は通る）

| 項目 | 内容 |
|---|---|
| 実施日 | 2026-09-13 |
| きっかけ | 「QNN の MatMul 対応は uint16×uint16 だけが不可で、uint16×uint8 は可では」という外部指摘 |
| 結果 | **指摘は正しかった。ただし対応は非対称だった** |
| 効果 | **end-to-end top-1 50.0% → 80.7%**（到達不可能な上限 85.2%）／実機 17.42ms → **14.29ms** |
| 補足 | 「v68 は精度の壁」という前回の結論を**取り下げた**（7章） |

---

## 1. 結論: C-8 を書き直す

**旧**（P2b で立てた理解）:
> v68 は「活性化 × 活性化」の MatMul を 16bit で受け付けない。
> → 両側を A8 に落とすしかない。

**新**（実測で確定）:

| 組合せ | v68 | 実測 |
|---|:--:|---|
| `uint16 × uint16` | **不可** | `has incorrect Value 68, expected >= 73` |
| **`uint16 × uint8`** | **可** | context 生成も実機実行も成功 |
| **`uint8 × uint16`** | **不可** | `has incorrect Value 68, expected >= 73` |
| `uint8 × uint8` | 可 | 従来の回避策 |

**左辺（第1入力）が uint16 で、右辺（第2入力）が uint8 なら通る。逆は通らない。**

外部指摘が引用していた対応表は `u8×u16` も `u16×u8` も可としていたが、
**実機では非対称**だった。**表を鵜呑みにせず実機で確かめた甲斐があった。**

### なぜこれが効くのか

attention は `MatMul(Q, K^T)` の**出力がスコア**になる。従来は両側 A8 だったので
スコアも 8bit に落ち、レンジ 1627 に対し 1段階 6.38 で softmax が壊れていた
（`P3_20260912_accuracy_layer1.md`）。

`u16 × u8` なら **出力を 16bit に保てる**。実際:

```
従来（両側A8）  : mul_8（スコア） 8bit  step 6.38
u16xu8         : mul_8（スコア） 16bit step 0.0248   ← 257倍の分解能
```

---

## 2. ORT では表現できない（ツールとハードウェアは別）

`get_qnn_qdq_config` に片側だけ `QUInt8` を指定しても、**u16×u8 にはならない**。

| 設定 | 結果 |
|---|---|
| 既定（`add_qtype_converts=True`） | **もう片方にも変換ノードを挿して u8 へ落とす**（`add_1_prescaled_convert_...` が出現） |
| `add_qtype_converts=False` | **指定そのものが無視され**、全部 u16 に戻る（＝C-8 違反） |
| 出力だけ u16 に固定 | `ValueError: Desired producer quant_type ... doesn't match existing type` |

**ORT の量子化器は MatMul の入力型を必ず揃える。**

ここで「v68 では無理」と結論していたら**ツールの制約をハードウェアの制約と取り違えて**いた。
そこで QDQ モデルを直接書き換える `app/pipeline/force_mixed_matmul.py` を作り、
**素の A16W8 QDQ の片側入力だけ Q/DQ を uint8 に作り替えて**検証した
（値域は保ったままスケールだけ再計算するので、表している範囲は変わらない）。

### 実装で踏んだ罠

QDQ モデルでは**重みも DequantizeLinear 経由**で入ってくるので、
「入力名が initializer か」では活性化×活性化の MatMul を判定できない。
最初これで判定し、**重み側の MatMul まで書き換えてしまった**。
DQ/Q を辿って大元が initializer かを見るよう直した。

## 3. 精度

### 層1枚（Qwen2.5-0.5B layer 0、fp32 比の相対 L2）

| 方式 | 相対L2誤差 | cos類似度 | v68 で動くか |
|---|---:|---:|---|
| A16W8 素 | **5.50%** | 0.9985 | **不可** |
| `u8×u16`（Q,P を 8bit） | **9.28%** | 0.9957 | **不可**（非対称のため） |
| **`u16×u8`（K,V を 8bit）** | **19.23%** | 0.9804 | **可** |
| 従来（両側 A8） | 30.39% | 0.9521 | 可 |

**皮肉なことに、精度が良い `u8×u16` の側は v68 が受け付けない。**
使えるのは `u16×u8` で、8bit になるのは **K と V**。
K のレンジが ±130 と広く（1段階 0.99）、ここが残った損失の主因である。

### end-to-end（埋め込み + 2層 + lm_head、較正と別の文 176トークン位置）

| 方式 | top-1一致 | top5重なり | KL | **fp32のtop1が何位か** |
|---|---:|---:|---:|---:|
| A16W8 素（v68 不可） | **85.2%** | 88.8% | 0.024 | 1.20位 |
| **`u16×u8`（v68 可）** | **66.5%** | 72.8% | 0.220 | **1.95位** |
| 従来（両側 A8） | 50.0% | 59.0% | 0.556 | 20.64位 |

**fp32 が1位に選ぶトークンの順位が 20.6位 → 1.95位。** KL も 2.5分の1。

### 実機

```
qwen_layer1 u16xu8    pass_strict  median 0.923 ms
qwen_layer1 従来      pass_strict  median 1.178 ms
```

**精度が上がったうえに速い。** 8bit テンソルが減って 16bit が増えたにもかかわらず
速くなった理由は未調査（変換ノードが減ったためと推測）。

## 4. もう一つの発見: 壊れているのは layer 0 だけ

HuggingFace の PyTorch fp32 に spy を仕込んで**層ごとの attention スコア**を測った。

| 層 | スコア幅 | 8bit の1段階 | softmax後L2誤差 | argmax一致 |
|---|---:|---:|---:|---:|
| **0** | **1676.9** | **6.58** | **50.9%** | **35.8%** |
| 1 | 429.3 | 1.68 | 26.6% | 63.5% |
| 2 | 205.6 | 0.81 | 12.4% | 83.2% |
| 3 | 132.2 | 0.52 | 4.8% | **96.7%** |
| 23 | 101.0 | 0.40 | 5.7% | 90.9% |
| **層2〜23 平均** | — | — | **6.7%** | **95.7%** |

**異常なのは layer 0（と layer 1）だけで、残り22層は 8bit でも argmax 一致 95.7%。**

→ **私の end-to-end 測定（先頭2層）は、24層のうち最悪の2層だけを使っていた。**
「24層ではもっと開く」と書いたのは**逆**で、層2以降は大幅に良い。

### ついでに export の正しさも確認できた

同じ spy で、自作 ONNX が出していた値と突き合わせた:

```
自作 ONNX  : QK^T 生値 [-183.277, 12514.777]  scaled [-22.910, 1564.347]
HF PyTorch : QK^T 生値 [-183.28,  12514.78 ]  scaled [-22.91,  1564.35 ]
```

**完全に一致。** +1600 は私の実装バグではなく Qwen2.5-0.5B layer 0 の実際の値である。
（reshape / GQA repeat / transpose / RoPE のいずれにも問題はなかった。）

| | SD888 (v68) | 8 Gen 2以降 (v73+) |
|---|---|---|
| MatMul | `u16×u8` のみ | `u16×u16` 可 |
| **2層 top-1 一致** | **66.5%**（旧評価 50.0%） | 85.2% 相当 |
| **fp32 top1 の順位** | **1.95位**（旧評価 20.64位） | 1.20位 |
| weight sharing | 不可 | 可 |
| 容量（420MB context） | 実測で OK | OK |

**v68 の不利は、前回の評価より小さい。** しかも 66.5% は**最悪の2層だけ**での数字で、
24層全体ではもっと良いはずである（層2〜23 は 8bit でも argmax 一致 95.7%）。

**前回「v68 は精度の壁」と書いたのは、私が回避策を1つしか試していなかったからである。**

> **【この節は 6〜7章で更に更新された】** 左右入替を加えると top-1 は **80.7%**、
> fp32top1 の順位は **1.34位**になる。最終的な評価は7章を見ること。

## 6. 左右を入れ替えて、ほぼ上限に届いた

残った損失の主因は **8bit 側が K（レンジ ±130、1段階 0.99）** であることだった。
v68 は非対称で「8bit にできるのは常に右辺」なので、**右辺に来るテンソルを
選べればよい**。

`A × B = (B^T × A^T)^T` は厳密に等価なので、QK^T を

```
変更前: MatMul(Q, K^T)                    → 右辺 = K   （±130、1段階 0.99）
変更後: Transpose(MatMul(K, Q^T))         → 右辺 = Q^T （[-10,6]、1段階 0.064）
```

と書き換えれば、**8bit 側の分解能が 15倍**になる。
（`app/pipeline/preprocess.py` の `swap_actact_matmul_operands()`。
fp32 での最大絶対差 0 を確認済み。PV の MatMul は右辺 V のレンジが元々狭いので触らない。）

### 効果

**層1枚**（相対 L2 誤差）:

| 方式 | 誤差 | v68 |
|---|---:|---|
| A16W8 素 | **5.50%** | 不可 |
| **`u16×u8` + 左右入替** | **9.33%** | **可** |
| `u8×u16`（理論上の best） | 9.28% | 不可（非対称） |
| `u16×u8`（入替なし） | 19.23% | 可 |
| 両側 A8（当初） | 30.39% | 可 |

**入れ替えることで、v68 が受け付けない `u8×u16` とほぼ同じ精度に到達した。**

**end-to-end**（埋め込み + 2層 + lm_head、176トークン位置）:

| 方式 | top-1一致 | top5重なり | KL | fp32top1の順位 | v68 |
|---|---:|---:|---:|---:|---|
| A16W8 素 | **85.2%** | 88.8% | 0.024 | 1.20位 | 不可 |
| **`u16×u8` + 左右入替** | **80.7%** | 83.4% | **0.050** | **1.34位** | **可** |
| `u16×u8`（入替なし） | 66.5% | 72.8% | 0.220 | 1.95位 | 可 |
| 両側 A8（当初） | 50.0% | 59.0% | 0.556 | 20.64位 | 可 |

**到達不可能な上限 85.2% に対し 80.7%。差は 4.5ポイントまで縮んだ**（当初は 35.2ポイント）。
しかもこれは **24層中で最悪の2層**での数字である。

### 実機

```
440MB EPContext（埋め込み + 2層 + lm_head、左右入替 + u16xu8）
backend : QNN HTP - EPContext - all nodes
strict  : True
OrtRun  : median 14.29 ms（当初の 17.42ms より速い）
warmup  : 24.0 → 14.8 → 14.5 ms
```

**Transpose を3つ足したのに速くなった。** 8bit テンソルが減り 16bit が増えた
にもかかわらず速いのは、型変換ノードが減ったためと推測されるが未確認。

## 7. 結論の修正

**「v68 は精度の壁」という前回の結論は取り下げる。**

| | 当初の理解 | 現在 |
|---|---|---|
| C-8 | 活性化×活性化は 16bit 不可 | **`u16×u8` は可**（非対称） |
| 対策 | 両側を A8 に落とすしかない | **左右を入れ替えて右辺に狭いレンジのテンソルを置く** |
| end-to-end top-1 | 50.0% | **80.7%**（上限 85.2%） |
| 実機速度 | 17.42ms | **14.29ms** |

**前回の悲観的な結論は、回避策を1つしか試していなかったことによる。**
外部からの「`u16×u8` は可では」という指摘が転換点になった。

### 未決事項#6（端末追加調達）

| | SD888 (v68) | 8 Gen 2以降 (v73+) |
|---|---|---|
| 2層 top-1 一致 | **80.7%** | 85.2% |
| fp32 top1 の順位 | 1.34位 | 1.20位 |
| weight sharing | 不可 | 可 |
| 容量（420MB context） | 実測で OK | OK |

**精度差は 4.5ポイントまで縮んだ。** 追加調達の主な動機は精度ではなく
**weight sharing（prefill/decode の重み共有）**に移った。
