# P4: 端末の NPU で文章を生成した

| 項目 | 内容 |
|---|---|
| 実施日 | 2026-09-13 |
| 端末 | Sony Xperia 5 III SOG05（SM8350 / HTP **v68**） |
| モデル | **Qwen2.5-0.5B-Instruct 全24層**（A16W8 + C-8/C-9/C-10/C-11 適用、772MB） |
| 判定 | **生成できた。well-formed なプロンプトでは fp32 と完全一致** |

---

## 1. 結果

```
プロンプト : The capital city of Japan is Tokyo. The capital city of France is
端末(NPU)  : " Paris. The capital city of"
fp32(PC)   : " Paris. The capital city of"
トークン一致: 6/6          ← **完全一致**
所要       : 28.8 秒（6トークン。窓16）
```

**端末の NPU だけで「Paris」と正しく答え、fp32 の出力とトークン単位で一致した。**

### 他のプロンプト

```
プロンプト : 日本の首都は東京です。フランスの首都は   （11トークン）
端末(NPU)  : "、東京の南"
fp32(PC)   : "？ - お笑"
トークン一致: 0/5
```

```
プロンプト : 日本の首都は   （3トークン）
端末(NPU)  : "、その名の「日本語言"
fp32(PC)   : "、2018年10"
トークン一致: 1/8
```

**fp32 側も壊れている**点が重要である。これは量子化のせいではなく、**窓のパディング**が原因である（後述）。

---

## 2. 方式: KV キャッシュを使わない「窓ずらし」

本来の decode は `seq=1 + 固定長KVキャッシュ` だが、**v68 でそれが作れなかった**（3章）。
そこで**既に実機で動いている 24層 prefill モデル（seq=16）**で生成した:

```
プロンプト（16トークンの窓）→ NPU → 最後の有効位置の logits → argmax → 次トークン
窓を1つずらして繰り返す
```

毎トークンでモデル全体を再計算するので遅い（NPU 上の推論 37ms + 呼び出し overhead で約5秒/トークン）。
**「動く」ことの確認が目的**であり、速度は KV キャッシュが通ってから改善する。

### パディングが品質を落としている

プロンプトが 16トークン未満のとき、窓の左側を pad トークンで埋めている。
ところが**この prefill モデルは因果マスクを定数として焼き込んでおり、
パディング用のマスク入力を持たない**。したがって **pad トークンも attention の対象になる**。

| プロンプト長 | pad 数 | 端末 | fp32 |
|---:|---:|---|---|
| **14** | **2** | ` Paris. ...` | ` Paris. ...`（**一致**） |
| 11 | 5 | `、東京の南` | `？ - お笑` |
| 3 | 13 | `、その名の「日本語言` | `、2018年10` |

**pad が少ないほど両方とも素直な出力になる。** fp32 も同じように崩れるので、
これは量子化の問題ではない。

**正しい対処は attention マスクを入力にすること**（decode モデルでは既にそうしている）。
prefill モデルを作り直せば解決するが、今回は「生成が動く」ことの確認を優先した。

---

## 3. decode（seq=1 + KVキャッシュ）は v68 で作れなかった

本筋の decode グラフも作った。**配線は正しい**が、**context 生成で落ちる**。

### 作ったもの

```
入力 52本: input_ids[1,1] / cos[1,1,1,64] / sin[1,1,1,64] / attn_mask[1,1,1,128]
          + past_k_{0..23}, past_v_{0..23}  各 [1,2,128,64]
出力 49本: logits[1,1,151936] + present_k/v ×24
1618 ノード / 17 op 種
```

固定長キャッシュは **左シフト + マスク**方式にした（`Slice` と `Concat` だけで済み、
形状が静的に保てる）:

```
present_k = Concat( past_k[:, :, 1:, :], new_k )     # [1,2,128,64] のまま
```

**配線が HF と一致することを確認済み**（6ステップで最大絶対差 **3.3e-05** / top-1 全一致）。
cos/sin は**ホストが計算して渡す**形にした（`Cos`/`Sin` を端末で使わないため）。

### 落ちる場所

```
<E> "rms_norm_node___959230" generated: could not create op
graph_prepare.cc:1822::ERROR:Op 0x11 preparation failed with err:-1
```

> **【2026-09-13 追記・この診断は誤りだった】**
> 真因は `rms_norm` の融合ではなく **KVキャッシュの float 入力が `Slice` に入って
> 量子化されないこと（C-1 違反48箇所）**。順序を `cat(past,k)[:,:,1:,:]` に変えたら
> **2層 decode が実機で動いた**（全ノード HTP / 11.90 ms）。
> ここに並んだ `could not create op` は**float セグメントの下流症状**だった。
> → [`P6_20260913_decode.md`](P6_20260913_decode.md)

**QNN が RMSNorm のパターンを1つの融合 op（`rms_norm`）にまとめ、
それが seq=1（shape `[1,1,896]`）で作れない。**

C-11（RMSNorm 正規化）を適用すると融合が部分的に崩れ、こちらは
私が挿した `Mul`（`node_pow_N_xs_n`）が作れないと言われる。

### 単体では seq=1 でも通る

最小モデル（`[1,1,896]` の RMSNorm + MatMul）は **C-11 ありで受理された**。
つまり「seq=1 の RMSNorm が一律でダメ」ではなく、
**decode モデルの文脈（融合の掛かり方）に依存している**。原因は未確定である。

### 途中で直した別の穴

C-11 の実装に**全ゼロ入力で `1/max|x| = inf` になる**穴があった。
較正の合成パターンに全ゼロが含まれており、qairt-converter が

```
"quantization max"=inf which exceeds the size of type: float
```

で落ちた。**max に下限 1e-6 を足して修正**（実データの max は1000オーダーなので影響なし）。

## 4. 当初目標への到達度

目標:「**C++ で作成した推論サービスを搭載して軽量 LLM を搭載し、
スマホのローカル完結で SLM を動作させる**」

| 要素 | 状態 |
|---|---|
| C++ 推論サービスを搭載 | ✅ |
| 軽量 LLM（Qwen2.5-0.5B）をフルで搭載 | ✅ 全24層が NPU 上 |
| **文章を生成する** | ✅ **端末だけで生成。well-formed なプロンプトでは fp32 と完全一致** |
| 通信なしで動く | ✅ |
| **トークナイザが端末内にある** | ❌ **まだ PC 側**。厳密な「ローカル完結」は未達 |
| KVキャッシュによる効率的な decode | ❌ v68 で context 生成に失敗（3章） |

**「スマホ上で SLM を動かして文章を生成させた」ところまでは到達した。**
ただし**トークナイザがホスト側に残っている**ので、
「ローカル完結」を名乗るにはもう一歩ある（CPU で動くので難易度は低い）。

## 5. 精度の見え方が変わった

これまで L2 誤差や top-1 一致率で議論してきたが、**実際の出力を読むと印象が変わる**。

| 指標 | 値 |
|---|---|
| 実機 top-1 一致（評価データ 176位置） | **73.3%** |
| 実機の生成トークン一致（well-formed プロンプト） | **6/6 = 100%** |

**73.3% という数字から想像するより、実際の生成は素直だった。**
曖昧さの少ないプロンプト（「フランスの首都は」）では、
量子化後も同じトークンを選ぶ。

一方、パディングで文脈が壊れている場合は fp32 も含めて崩れる。
**つまり今のボトルネックは量子化より「窓とマスクの扱い」である。**

→ **「読んだ方が早い」という判断は正しかった。** 数字だけ見て
量子化を詰めに行っていたら、**実際には効かない方向に工数を使っていた**。

## 6. 次

```
⬜ attention マスクを入力にした prefill モデル   パディング問題の解決。品質が素直に上がるはず
⬜ トークナイザの端末移植                       「ローカル完結」を満たすため（CPU で可）
✅ decode（seq=1 + KVキャッシュ）  2層で実機動作。真因は C-1（上の追記を参照）
⬜ 窓を広げる（seq 16 → 64 等）                 文脈長の制約を緩める
⬜ QNN-HTP 追加分の原因特定                      部分モデルで QK/Softmax/P×V を測る
```

**優先は「attention マスクを入力にする」**。パディングが現状の最大の品質要因で、
しかも decode モデルで既に実装済みの形（マスク入力）をそのまま持ち込めばよい。
