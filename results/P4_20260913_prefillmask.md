## 1. 結論

| 問い | 答え |
|---|---|

## 4. マスク入力版 vs マスク無し版（本題）

判定基準は **パディング無しの fp32 が出す1位トークン**。
まず「パディング＋正しいマスク」が「パディング無し」と一致することを fp32 で確認した:

```
8/8 一致（' Paris' / ' Paris' / ' a' / ' ' / ' __' / '\n' / ' east' / ' language'）
```

**マスクの与え方は正しい。** その上で実機の2モデルを比べる:

| 有効長 | 正解(fp32) | マスク入力版 | マスク無し版 | プロンプト |
|---:|---|---|---|---|
| 6 | `' Paris'` | `' Paris'` ○ | `' Paris'` ○ | The capital city of France is |
| 13 | `' Paris'` | `' Paris'` ○ | `' Paris'` ○ | The capital city of Japan is Tokyo. The capital of France is |
| 3 | `' a'` | `' a'` ○ | `' a'` ○ | Tokyo is |
| 3 | `' '` | `' '` ○ | `' '` ○ | Water boils at |
| 8 | `' __'` | `' the'` × | `' the'` × | The largest planet in our solar system is |
| 4 | `'\n'` | `' four'` × | `' one'` × | Two plus two equals |
| 5 | `' east'` | `' east'` ○ | `' east'` ○ | The sun rises in the |
| 4 | `' language'` | `' language'` ○ | `' language'` ○ | Python is a programming |
| | **合計** | **6/8** | **6/8** | |

### 読み方

- **8プロンプト中7つで両者は同じトークンを出した。** 差は1件だけ
- 外れた2件は**パディングのせいではなく量子化誤差**（マスクを正しく与えても外れる）
- 唯一差が出た `Two plus two equals` では、マスク入力版が `' four'`、マスク無し版が `' one'`。
  **fp32 の正解は `'\n'`** なので両方×だが、**意味としてはマスク入力版の方が妥当**

### なぜマスク無し版でも平気だったのか

当初は「パディングの影響そのものが小さい」と解釈した。**これは不正確だった**（下の追記）。

## 4-bis. ★この節の結論は後に精密化した（2026-09-13 追記）

窓拡張（16→64）の検討で**fp32 だけを使って**同じことを測り直したところ、
上の「差がほぼ無い」は**量子化誤差に埋もれていただけ**と分かった。

判定基準はパディング無しの fp32 の答え、10プロンプト、HF を直接使用（ONNX 不要）:

| 窓 | 正しいマスク | 全部見える（マスク無し相当） |
|---|---:|---:|
| **W=16** | **10/10** | **6/10** |
| **W=64** | **10/10** | **3/10** |

**fp32 では W=16 でも 4/10 で答えが変わっていた。**
それなのに上の実機比較（量子化モデル同士）が 6/8 対 6/8 になったのは、

```
パディングによる差   <  量子化誤差
```

だったためである。実際、両モデルが外した2件のうち
`The largest planet …` は **fp32 のマスク無しなら ' Jupiter'**（マスクありは ' __'）
なのに、量子化した2モデルはどちらも ' the' を出していた。
**量子化の方が大きく動かしていた**ので、パディングの差が見えなくなっていた。

### 精密化した結論

| | |
|---|---|
| 上の実機比較（6/8 対 6/8） | **測定としては正しい** |
| 「パディングは品質要因ではない」 | **言い過ぎだった**。正しくは「W=16 の量子化モデルでは量子化誤差に埋もれる」 |
| W=64 では | **埋もれない**（fp32 で 3/10 まで落ちる）。マスク入力版が**必須** |

> **2つの誤差要因を比べるときは、片方を固定して測る。**
> 量子化モデル同士で比べたために「パディングの効果」と「量子化の効果」が
> 混ざり、小さい方が見えなくなっていた。**fp32 で測れば一発で分かった。**

> それでも **「対策の前に効果を測る」という順序自体は正しかった。**
> 測り方（量子化モデル同士で比較した）が粗かったのが問題である。

窓拡張の詳細は [`P5_20260913_window64.md`](P5_20260913_window64.md)。

## 5. ★最初に出た err 1002 の本当の原因

最初の push では**ロードに失敗した**:

```
<E> Failed to load from EpContext model.
    qnn_backend_manager.cc:1518 LoadCachedQnnContextFromBuffer
    Failed to create context from binary. Error code: 1002
```

err 1002 は過去に **`Expand`（C-10）** と **float セグメント（C-1）** で出していたので、
同じ系統を疑って順に潰した。

| 調べたこと | 結果 |
|---|---|
| C-1（グラフ I/O 境界の float 残存） | **問題なし**（入力は全て `QuantizeLinear` へ、出力は `DequantizeLinear` から） |
| `Expand` の残存 | **0個**（op 種別を数えた） |
| 動く 24層版との op 差分 | Add +49 / Q +52 / DQ +98 だけ。新しい op 種別は無い |
| **マスクをグラフ入力にすること自体**（単体 op `attn_mask_input` を新規作成して実機確認） | **`pass_strict`。無罪** |
| context binary の md5（ホスト生成物 vs 自分が配った側 vs 端末） | **ホストの生成物だけ md5 が違った** ← **これ** |

```
生成器の出力  ctx_qwenpm/qwenpm_ctx.SM8350.bin  772,338,648  b0bac94d…
自分が配った側 ctx/qwenpm_ctx.SM8350.bin        772,342,648  7253d994…   ← 4000 bytes 多い
端末                                            772,342,648  7253d994…   （転送は正しい）
```

**バイト32から内容が違っていた。** `/tmp/pm.log` の mtime と内容を見直すと
**context 生成が2回走っており、2回目が 12:01 に同じパスへ書き直していた。**
自分が EPContext で包んだのは 11:58 — **書き換え途中のファイルを読んでいた。**

生成完了後に同じ手順をやり直したら、**一発で `pass_strict`** になった。

### 得た教訓

> **err 1002 は「v68 が対応していない」とは限らない。**
> **バイナリが壊れていても同じエラーになる。**
> まず **成果物の同一性（サイズと md5）** を確かめる。5秒で済み、切り分けの8割が消える。

> **長時間かかる生成物は「終わったこと」を確認してから触る。**
> ログに「OK」と出ていても、**同じパスへ別のプロセスが書いている**ことがある。
> プロセスの不在とファイルの mtime/サイズの安定を見る。

副産物として、**マスクをグラフ入力にするのは v68 で可**（`attn_mask_input` 単体 op で確認）
という知見が得られた。これは制約ではない。
