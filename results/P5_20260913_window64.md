# P5: 窓を 16 → 64 に広げる（2026-09-13）

| | |
|---|---|
| 目的 | 文脈長の制約（16トークン）を緩める |
| 端末 | Sony Xperia 5 III SOG05（SM8350 / HTP **v68**）、unsigned PD |
| モデル | Qwen2.5-0.5B 全24層 prefill・**マスク入力あり**・seq64・**lm_head は最終位置のみ** |
| 方式 | A16W8 + C-9/C-10/C-11 + 左右入替 + `u16×u8` |

---

## 1. 結論

| 問い | 答え |
|---|---|
| 窓64は v68 で動くか | **動く**。772MB / **全ノード HTP**（`strict_no_cpu_fallback: true`） |
| 速くなったか遅くなったか | **ほぼ変わらない**（36.7 → 42.0 ms/トークン）。`lm_head` を最終位置だけにしたため |
| 量子化の精度は落ちたか | **ホストでは落ちていない**（top-1 74.0% → 73.7%、KL と L2 は改善） |
| 実機の精度は | **落ちた**（64.0% → 57.9%）。**実機側の誤差が窓と共に増える** |
| 実際の生成はどうか | **窓の外にある情報を思い出せるようになった**（下記 `8317` の例） |
| パディングマスクは必要か | **必須**。fp32 で W=64 はマスク無しだと 10件中 3件しか正解と一致しない |

> **精度指標は下がったが、できることは増えた。**
> 窓16では**そもそも見えない情報**があり、指標はその失敗を測っていない。

## 3. ★`lm_head` を最終位置だけに掛ける

窓を広げると `logits [1,W,151936]` が効いてくる。

| | logits のバイト数 | `lm_head` の MatMul |
|---|---:|---|
| W=16 | 9.7 MB | 16×896×151936 |
| W=64（素） | **38.9 MB** | 同×4 |
| **W=64 + 最終位置のみ** | **0.6 MB** | **1×896×151936** |

生成で使うのは最終位置の logits だけで、**因果マスクがあるので最終位置の出力は
他の位置に依存しない**。したがって最終段の `norm` と `lm_head` の前で
`h = h[:, -1:, :]` と切っても答えは変わらない。

`export_qwen_decode.py --last-only` として実装した。**HF の最終位置と
最大絶対差 1.287e-05 / top-1 一致**を確認してから先へ進めた。

### これが速度を救った

| | OrtRun median | 1トークン（実時間） |
|---|---:|---:|
| W=16 | 36.7 ms | 39〜43 ms |
| **W=64** | **37.9〜42.0 ms** | **39〜45 ms** |

**窓を4倍にしても約1割増で収まった。** 切らなければ 38.9MB のコピーと
4倍の `lm_head` が毎ステップ乗っていた。

## 4. パディングマスクは窓64では必須（対策の前に測った）

**高価な context 生成の前に、HF だけで**（ONNX も量子化も使わず）測った。
判定基準は**パディング無しの答え**、10プロンプト。

| 窓 | 正しいマスク | 全部見える（マスク無し相当） |
|---|---:|---:|
| W=16 | 10/10 | 6/10 |
| **W=64** | **10/10** | **3/10** |

窓64でプロンプトが6トークンなら **pad が58個**入る。塞がないと答えが壊れる。

この測定は **P4 の結論を精密化した**。P4 では量子化モデル同士で比べて
「6/8 対 6/8 で差が無い」としたが、それは**パディングの差が量子化誤差に
埋もれていた**ためだった（[`P4_20260913_prefillmask.md`](P4_20260913_prefillmask.md) 4-bis節）。

> **2つの誤差要因を比べるときは片方を固定する。** ここでは fp32 で測れば一発だった。

## 5. 精度

### 5.1 ホスト（fp32 vs QDQ、最終位置のみ）

**評価データは同じ生成器**（`make_prefillmask_data.py`）で作って揃えてある。

| | seq=16（50件） | **seq=64（19件）** |
|---|---:|---:|
| top-1 一致 | 74.0% | **73.7%** |
| top5 overlap | 78.8% | 76.8% |
| KL | 0.185 | **0.128** |
| 相対L2 | 26.7% | **18.6%** |
| fp32 の1位が何位か | 2.20 | **1.42** |

**窓を4倍にしても量子化の精度は落ちていない。** KL・L2・順位は改善した。
較正データに**満了窓（パディング無し）を入れた**ことが効いていると見ている
（生成の大半は窓が埋まった状態なので、そこを較正しないと的外れになる）。

### 5.2 実機（fp32 vs 端末、最終位置のみ）

| | seq=16（50件） | **seq=64（19件）** |
|---|---:|---:|
| top-1 一致 | **64.0%** | **57.9%** |
| 相対L2 | 39.4% | **50.1%** |
| cos 類似度 | 0.9117 | 0.8614 |
| OrtRun | 36.7 ms | 42.0 ms |

### 5.3 ★実機側の誤差が窓と共に増えている

分母をすべて `‖fp32‖` に揃えてあるので、二乗和で分解できる（L2 は加算しない）。

| | 量子化のみ | 合計（実機） | **差分（QNN-HTP 追加分）** |
|---|---:|---:|---:|
| seq=16 | 26.7% | 39.4% | $\sqrt{39.4^2-26.7^2} =$ **29.0%** |
| **seq=64** | **18.6%** | **50.1%** | $\sqrt{50.1^2-18.6^2} =$ **46.5%** |

**量子化誤差は下がったのに、実機の誤差は上がった。** つまり増えたのは
**ホストでは再現しない側**である。

窓が広がって変わったこと（仮説。未検証）:

- Attention スコアの行長が 16 → 64。**per-tensor 量子化のレンジが広がる**
- `Softmax` の入力要素数が 4倍
- `P×V` の積和が 16項 → 64項。**固定小数点アキュムレータの丸めが積み上がる**

> これは未解決課題「**QNN-HTP 追加分の原因特定**」と同じ筋である。
> 今回**窓を変えると系統的に増える**と分かったので、切り分けの手がかりが増えた。
> 次は QNN CPU backend（QNN の reference 実装）と比べて
> 「QNN semantics の差」と「HTP 固有」を分ける。

## 6. ★実際の生成（ここが本題）

### 6.1 窓の中に収まるプロンプト（対照）

```
The capital city of Japan is Tokyo. The capital city of France is
  W=16 : ' Paris. The capital city of the United'
  W=64 : ' Paris. The capital city of the United'    ← 同一
```

**実機 W=64 は fp32 と 8/8 一致**（QDQ も同じ列）。窓を広げて壊れていない。

### 6.2 長く生成させたとき

```
24トークン生成:
  W=16 : ' Paris. The capital city of the United States is Washington, D. C.
           The capital of the United States is the'          ← 同じ話に戻って繰り返す
  W=64 : ' Paris. The capital city of the United States is New York.
           The capital city of the United Kingdom is London. The'   ← 話を進められる
```

内容の正しさ（New York は首都ではない）は 0.5B の限界だが、
**窓16で起きていた「直前の話に戻る」繰り返しが消えた**。
自分が数トークン前に書いた内容が窓から落ちなくなったためである。

### 6.3 ★窓の外にある情報（これが広げた理由）

**事前知識では答えられない情報**をプロンプトに入れて測る。

```
Remember this fact: the access code is 8317. Now here is some unrelated text about
the weather in the mountains during the autumn season, which is cool and rainy most
days. Question: what is the access code? The access code is
                                                    （51トークン）

  W=16（16/51 しか見えない） : ' 123456. If the'      ← **捏造した**
  W=64（51/51 見える）       : ' 8317. The given facts about'   ← **思い出した**
```

ホストも一致する:

| | 出力 |
|---|---|
| fp32（W=64） | `' 8317. The fact about the'` |
| QDQ（W=64） | `' 8317. The unrelated text about'` |
| **実機（W=64）** | **`' 8317. The given facts about'`** |

**3者すべてが `8317` を正しく復元した。** 窓16では原理的に不可能だった動作である。

### 6.4 日本語では外した（原因はモデル側）

```
覚えておいてください。合言葉は「赤い月」です。…（関係ない話）…さて、合言葉は何でしたか。合言葉は
  W=16 実機 : '「は」と「は」です。'      （崩れている）
  W=64 実機 : '「日光」です。日光は光'    （間違い）
```

**切り分けると量子化でも窓でもなかった:**

| | 出力 |
|---|---|
| **fp32（W=64）** | **`'「雨」です。雨は、山の'`** ← **fp32 自身が外している** |
| QDQ（W=64） | `'「赤い月」です。ここからは関'` ← 偶然当たっている |
| 実機（W=64） | `'「日光」です。日光は光'` |

> **fp32 が外しているのだから、これはポーティングの欠陥ではなく
> 0.5B モデルの能力限界である。**
> QDQ が fp32 より良く見えるのは**1サンプルの偶然**で、
> こういう並びを「量子化が効いた」と読んではいけない。

## 7. 実装

### 7.1 ホスト側

| ファイル | 変更 |
|---|---|
| `app/pipeline/export_qwen_decode.py` | **`--last-only`** を追加（最終段 norm + lm_head を最終位置だけに） |
| `app/pipeline/make_prefillmask_data.py`（新規） | マスク入力版の較正／評価データ。**満了窓とパディングありを混ぜる** |
| `app/pipeline/find_swap_matmuls.py`（新規） | 左右入替の対象（QK^T）を**グラフから自動判定**。seq16 の手作業リストと完全一致を確認 |
| `app/pipeline/p2b_ops.py` | 較正 npz のキーを**モデルの入力名で絞る**（`n_valid` のような同梱メタを無視） |
| `app/pipeline/deploy_pm64.py`（新規） | S8 → push → md5 3点照合 → probe を1本に。**生成途中のバイナリを掴む事故**を防ぐ |

`find_swap_matmuls.py` を作った理由: 入替の対象はノード名で指定するが、
**名前は export ごとに変わる**（`qwen_full` は奇数、`qwen_pm` は偶数）。
手で書き写すと **P×V を入れ替えても動いてしまい、精度だけ落ちる**。
「出力が Softmax に届くか」で判定する。

### 7.2 端末側（`EdgeSLM_AndroidDemo`）

| ファイル | 変更 |
|---|---|
| `cpp/runner/job.cpp` | `logits [1,1,V]` を許可。**`dynamic_mask` で毎ステップ attn_mask を構築** |
| `java/.../DemoActivity.kt` | `jobs/demo_override.json` でモデル・窓を**再ビルドなしに**切り替え |

**マスクを固定ファイルで渡せないのが要点。** 生成が進むと有効長が
プロンプト長から W まで増えるので、毎ステップ作り直す必要がある。

```json
{ "dynamic_mask": true, "mask_input": "attn_mask", "mask_neg": -60.0,
  "const_inputs": { "cos": "inputs/cos_w64.bin", "sin": "inputs/sin_w64.bin" } }
```

### 7.3 C++ のマスク生成を先に検証した

端末で動かす前に、**Python に同じ形で書き写して `build_mask` と突き合わせた**:

```
W=16 / W=64 の n_valid 1..W+4（飽和側も含む）で 不一致 0
```

さらに**既知良好な seq=16 マスク入力版**で新しい C++ 経路を先に通した
（コードのバグとモデルの問題を分離するため）:

| 確認 | 結果 |
|---|---|
| 実機で動的マスク生成 | `ok=true` / 36.2 ms/トークン |
| マスクが実際に効いているか | 正しいマスクと全可視マスクで**完全に別の列**（`[279,7772,…]` vs `[271,3862,…]`） |
| 既知挙動との整合 | 短いプロンプトの1トークン目 `' the'` が P4 の実測と一致 |

> **高価な成果物が出る前に、安いモデルで経路を通しておく。**

## 8. 副産物: `lm_head` の重みは per-tensor uint8 になっている

`force_mixed_matmul` のログに `node_linear_168`（= `lm_head`）が出て
一瞬「重み側まで書き換えている」と疑ったが、**必要な処理だった**。

`tie_word_embeddings=True` のため lm_head の重みは埋め込み表と共有されており、
ORT は int8 per-channel ではなく **float 初期化子 → Q → DQ**（uint16 per-tensor）
として扱う。そのままでは `MatMul(u16, u16)` になり **C-8 で v68 に載らない**。
だから 8bit に落とす必要がある。

```
node_linear_168  val_2328（step.lm_head.weight_scale）  step 6e-06 -> 0.00144
```

**ただしこれは精度の改善余地でもある。** per-tensor uint8（255段階）ではなく
**per-channel int8**（151,936 行それぞれに scale）にできれば細かく表せる。
未着手。

## 9. 残る課題

| 課題 | 状況 |
|---|---|
| **QNN-HTP 追加分の原因特定** | **窓を広げると系統的に増える**（29.0% → 46.5%）と分かった。まず QNN CPU backend と比較 |
| `lm_head` 重みを per-channel int8 にする | 上記8節。per-tensor uint8 になっている |
| decode（seq=1 + KVキャッシュ） | **2層で実機動作**（11.90 ms / 全ノード HTP）。真因は `rms_norm` ではなく KVキャッシュ入力の C-1 違反 → [`P6_20260913_decode.md`](P6_20260913_decode.md) |
| 評価データの拡充 | seq64 は19件。seq16 は50件。件数を揃えたい |
| さらに広い窓（128 等） | 同じ手順で作れる。`lm_head` を切ってあるので費用は線形に増えない |
