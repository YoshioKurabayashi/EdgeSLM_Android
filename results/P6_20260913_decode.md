# P6: decode（seq=1 + KVキャッシュ）が実機で動いた — 真因は `rms_norm` 融合ではなかった

| | |
|---|---|
| 実施日 | 2026-09-13 |
| 端末 | Sony Xperia 5 III SOG05（SM8350 / HTP **v68**）、unsigned PD |
| 目的 | 「v68 では decode が作れない」とした過去の判断を検証する |

---

## 1. 結論

| | |
|---|---|
| 過去の記録 | 「QNN が RMSNorm を `rms_norm` に融合し、**seq=1 で作れない**」 |
| **実際の真因** | **KVキャッシュの float グラフ入力が量子化されず C-1 違反**（48箇所） |
| なぜ起きるか | **ORT の QDQ 量子化器は `Slice` に直接入る float のグラフ入力を量子化しない**。`tensor_quant_overrides` で型を指定しても効かない |
| 直し方 | KVキャッシュ更新を **`cat(past,k)[:,:,1:,:]`** の順に変える（`cat(past[:,:,1:,:],k)` と数学的に同一） |
| 結果 | **2層・24層ともに実機で動作**（全ノード HTP）。24層は **OrtRun 29.9 ms**（prefill 窓16 の 36.7ms より速い） |
| ただし | **【訂正】この行の「精度が足りない」は評価セットの偏りによる誤りだった。**48サンプルで測ると実機 top-1 **60.4%**（prefill 窓16 は 64.0%）で**同等**。→ [`P7_20260913_decode_cache_io.md`](P7_20260913_decode_cache_io.md) 4節 |

> **「v68 の制約」だと思っていたものは、ツール（ORT）の制約だった。**
> [`DoC/StudyMemo/06`](../DoC/StudyMemo/06_ログの読み方と原則.md) の原則⑤そのもので、
> **自分で書いた原則に自分が引っかかっていた。**

---

## 2. 何を誤診していたか

記録にはこうあった:

```
decode（seq=1 + 固定長KV 128）は v68 で作れなかった:
  QNN が RMSNorm を融合 op(`rms_norm`) にまとめ、seq=1 で `could not create op`
  最小モデル（[1,1,896] の RMSNorm）は通るので**融合の掛かり方に依存**。原因は未確定
```

### 残っていたログを読み直した

| ログ | 最初に出ている `<E>` |
|---|---|
| `/tmp/d2.log` | `Failed to validate op node_matmul_swapped with error 0xc26` ← **C-8** |
| `/tmp/d2b.log` | `node_mul_9` … `node_matmul_1` … **`QNN_DATATYPE_FLOAT_32_converted_past_k_0_QNN_DATATYPE_FLOAT_16`** |
| `/tmp/d2c.log` | 同上 |
| `/tmp/d2d.log` | 同上 |
| `/tmp/lhs.log` | `has incorrect Value 68, expected >= 73` ← **C-8** |

**`rms_norm` という文字列は1件も無い。** 残っているログの失敗はすべて

- **C-8**（活性化×活性化 MatMul の型）
- **C-1**（`past_k_0` の float32 → float16 変換）

である。しかも `node_mul_9` / `node_add_3` / `node_matmul_1` が
「作れない」と言われているのは、**float セグメントの近傍が fp16 op になった結果**
（v68 の skel は fp16 非対応）と考えるのが自然である。

> **`rms_norm` の「作れない」も、おそらく同じ下流症状だった。**
> C-1 を直したら**`rms_norm` のエラーは一度も出ずに context binary ができた**。
>
> 当時の記録は「最小モデルは通るのに実モデルでは通らない」という観察で止まっており、
> **その間にある C-1 違反を見ていなかった。**

### 教訓

> **`could not create op` は「その op が非対応」とは限らない。**
> **float セグメントがあると近傍の op がまとめて作れなくなる。**
> 先に C-1 を潰してから、残ったエラーを読む。

並んだエラーのうち**どれが原因でどれが結果か**を決めないまま
一番目を引いた名前（`rms_norm`）を真因として記録してしまった。
[`P4_20260913_prefillmask.md`](P4_20260913_prefillmask.md) の
「良性の ERROR 行に騙されない」と同じ型である。

## 3. 真因の特定（最小モデルで1つずつ）

C-1 違反の中身は48件すべて同じ形だった:

```
{'tensor': 'past_k_0', 'producer': '(graph input)',
 'consumer': 'Slice(node_slice_5)',
 'note': 'float のグラフ入力が QuantizeLinear を経ずに計算ノードへ入っている'}
```

`forced_input_quant` は48本すべてを列挙していた（＝強制を依頼していた）のに効いていない。
そこで**消費する op で決まるのでは**という仮説を最小モデルで確かめた。

`x`（float のグラフ入力）が1つの op に直接入るだけのモデルを3種つくり、
`init_overrides` で `QUInt16` を指定する／しないで比べる:

| `x` の消費者 | override なし | override あり |
|---|---|---|
| `MatMul` | **量子化された** | 量子化された |
| `Concat` | **量子化された** | 量子化された |
| **`Slice`** | **★float のまま** | **★float のまま** |

> **`Slice` に直接入る float のグラフ入力は量子化されない。**
> **`tensor_quant_overrides` では強制できない。**

これは P2b の `gqa_repeat`（グラフ入力が `Unsqueeze` に直接入って float が残った）
と**同じ型**である。形状・データ移動の op は量子化対象から外れるらしい。

## 4. 直し方: 連結してから捨てる

KVキャッシュの左シフトは、書き方が2つある。

```
書きたい式     : cat(past[:, :, 1:, :], k)      ← past が Slice に入る
こう書き直した : cat(past, k)[:, :, 1:, :]      ← past が Concat に入る
```

**どちらも結果は同じ**（`[past の2番目以降, k]` で長さ L）。違うのは
**`past_k` / `past_v` というグラフ入力が最初に入る op** だけである。
`Concat` は量子化されるので C-1 違反が消える。

`export_qwen_decode.py` の `QwenDecodeStep.forward` の2行。

### 等価性の確認（必ず数値で）

HF の逐次生成と突き合わせた:

| | 最大絶対差 | top-1 |
|---|---:|---|
| 2層 / KV 32 | **4.292e-05** | 全一致 |
| 24層 / KV 64 | **5.424e-05** | 全一致 |

## 5. 結果

### 5.1 量子化（2層 / KV 32）

```
verdict : ready_for_convert
C-1     : True  計算ノード間・グラフI/O境界ともに float の残存はない
forced_input_quant : ['cos','sin','attn_mask','past_k_0','past_v_0','past_k_1','past_v_1']
```

**48 → 0。** 24層（KV 64）でも `C-1: True`（強制量子化 51本）。

### 5.2 context 生成（2層）

```
S5 qairt-converter              OK  418.06 MiB
S6 qnn-context-binary-generator OK  dec2b_ctx.SM8350.bin  419.64 MiB
ログ中の <E> 行（良性の libcdsprpc.dll を除く）: なし
```

**`rms_norm` のエラーは出なかった。**

### 5.3 実機（2層 / KV 32）

```
backend = QNN HTP - EPContext - all nodes
strict_no_cpu_fallback = true         ← 全ノードが NPU
セッション確立 1.9 s
入力 8 本（input_ids / cos / sin / attn_mask / past_k,v ×2層）
出力 5 本（logits / present_k,v ×2層）
```

精度（評価12サンプル。較正とは別の文）:

| | 値 |
|---|---:|
| logits top-1 一致 | **75.0%** |
| logits 相対L2 | 26.97% |
| logits cos 類似度 | 0.9658 |
| **OrtRun** | **11.90 ms** |

### 5.4 ★KVキャッシュ出力の誤差は層が深いほど大きい

| 出力 | 相対L2 平均 | 最大 |
|---|---:|---:|
| `present_k_0` | 0.03% | 0.20% |
| `present_k_1` | 0.86% | 1.56% |
| `present_v_0` | 2.41% | 4.42% |
| **`present_v_1`** | **10.35%** | **17.77%** |

**これは1ステップぶんの誤差である。** KVキャッシュ出力は**次のステップの入力**
になるので、**ステップを重ねると累積する**。窓ずらし生成には無い種類の問題で、
decode を実用にするならここを測る必要がある（本測定は毎回ホストが作った
新しいキャッシュを与えているので、累積は含まれていない）。

> `v` 側が `k` 側より大きいのは、`v` が softmax 後の確率と直接掛かるためと推測。未検証。

## 6. ★24層 decode の実測

> **【2026-09-13 追記・6.2〜6.5 の数字は訂正した】**
> 本節の精度は **24サンプルの評価セット**で測ったもので、
> **キャッシュが空に近い初期ステップに偏っていた**（step 0 は4件すべて不一致）。
> 48サンプルで測り直すと **ホスト 68.8% / 実機 60.4% / 相対L2 36.0%** で、
> prefill 窓16（64.0%）と**同等**である。
> また「キャッシュ I/O の再量子化が本命」という 6.5 の仮説は
> **単発では寄与ゼロ**と Oracle で確定した（ただし**ループでは最大の要因**だった）。
> → [`P7_20260913_decode_cache_io.md`](P7_20260913_decode_cache_io.md)

24層（KV 64）も**実機で動いた**。context 生成 62分（16:28〜17:30）、
生成ログに `<E>` なし、md5 3点一致。

```
backend = QNN HTP - EPContext - all nodes
strict_no_cpu_fallback = true
入力 52 本 / 出力 49 本
context binary 772,040,480 bytes（md5 6bb4cd86…）/ EPContext ONNX 5,389 bytes
```

### 6.1 速度は prefill より速い

| | OrtRun |
|---|---:|
| prefill 窓16（24層） | 36.7 ms |
| prefill 窓64（24層） | 42.0 ms |
| **decode（24層 / KV 64）** | **29.9 ms** |
| decode（2層 / KV 32） | 11.9 ms |

**2層の 11.9ms から24層で 29.9ms。** 層数12倍に対して2.5倍なので、
**層数に依らない部分（埋め込み表引き + `lm_head` の 1×896×151936）が大きい**
という見立ては当たっていた。

### 6.2 しかし精度が足りない

| | logits top-1 | 相対L2 | KL | fp32 の1位が何位か |
|---|---:|---:|---:|---:|
| prefill 窓16（ホスト） | 74.0% | 26.7% | 0.185 | 2.2位 |
| **decode 24層（ホスト）** | **54.2%** | **42.2%** | **1.29** | **3816位** |
| prefill 窓16（実機） | 64.0% | 39.4% | — | — |
| **decode 24層（実機）** | **33.3%** | **42.3%** | — | — |

`rank_of_fp32_top1_mean = 3816` が効いている。**外すときに大きく外す**ので、
単に「少し精度が低い」のではなく**分布が壊れている**。

### 6.3 ★ボトルネックは量子化側であって HTP ではない

| | 相対L2 |
|---|---:|
| 量子化のみ（fp32 → ホスト QDQ） | **42.2%** |
| 合計（fp32 → 実機） | **42.3%** |
| 差分（QNN-HTP 追加分、二乗和で分解） | **約 2.9%** |

**prefill とは逆の構図である。**

| | 量子化 | QNN-HTP 追加分 |
|---|---:|---:|
| prefill 窓16 | 26.7% | 29.0% |
| prefill 窓64 | 18.6% | 46.5% |
| **decode 24層** | **42.2%** | **2.9%** |

> **decode で効いているのは量子化である。** 実機側はほとんど何も足していない。
> それでも top-1 が 54.2% → 33.3% まで落ちるのは、
> **logits がすでに壊れていて argmax が紙一重**だからである（1位が平均3816位）。

### 6.4 どこで壊れているか

KVキャッシュ出力の誤差（24層ぶん、1ステップ）:

| | 平均 | 最小 | 最大 |
|---|---:|---:|---:|
| `present_k_*` | **11.30%** | 0.03%（層0） | 25.25% |
| `present_v_*` | **20.10%** | 2.43%（層0） | **42.08%**（層22） |

層ごとの `present_v`:

```
層 0   2.43%
層 1   7.66%
層 5  17.57%
層11  14.90%
層17  16.16%
層22  42.08%   ← 最悪
層23  33.27%
```

**深い層ほど悪い**のは prefill の massive activation と同じ形である。

疑っている点（未検証）:

1. **キャッシュがグラフ境界で毎ステップ量子化され直す。**
   `--preserve_io_datatype` のため `present_*` は float32 で出て、次ステップに
   `past_*` として入るとき再量子化される。**24層 × 2（k,v）で1ステップに48回**の
   余分な量子化が入る。prefill には無い経路である
2. **キャッシュの値域が広い**（`past_k_0` は ±130）。64位置ぶんを per-tensor で
   1つの scale にまとめている
3. `v` 側が `k` 側より悪いのは、`v` が softmax 後の確率と直接掛かるためか

### 6.5 次の一手（この順で）

| # | やること | なぜ |
|---|---|---|
| 1 | **キャッシュ I/O を量子化型のまま持ち回す**（`uint16` で入出力する） | 境界の再量子化48回を消せる。**1 が本命** |
| 2 | キャッシュを層ごと／位置ごとに分けて量子化できないか確かめる | 値域 ±130 を1つの scale で持つのを避ける |
| 3 | ループでの累積を測る | 1ステップで 20〜42% なので、重ねると崩れる見込み。**どこまで生成できるか**を数字で出す |

> **「動く」と「使える」は別である。** decode は動いたが、
> **現状の精度では窓ずらし生成（実機 top-1 57.9〜64.0%）の方が良い。**
> 速度は decode が勝つ（29.9ms 対 36.7〜42.0ms）ので、
> **1 を解けば逆転する余地がある。**

## 9. 残る課題

| 課題 | 状況 |
|---|---|
| **キャッシュ I/O を量子化型で持ち回す** | **本命**。境界での再量子化（1ステップ48回）を消す |
| キャッシュ量子化の粒度 | 値域 ±130 を per-tensor 1つの scale で持っている |
| **KVキャッシュ誤差の累積** | 1ステップで `present_v` が平均 20%・最大 42%。ループで測る必要がある |
| decode の生成ループ（C++） | `present_*` を `past_*` に戻す配線が必要。prefill で埋めてから decode に渡す手順も |
| `Slice` 入力の一般的な対処 | 今回は順序変更で避けた。避けられない形が出たら QDQ を直接書き換える必要がある |

**現状の実用的な結論: 生成には窓ずらし（prefill 窓64）を使う。**
decode は速いが精度が足りない。上記1を解いてから再評価する。
