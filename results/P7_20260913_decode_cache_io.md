## 2. Oracle: キャッシュ I/O は単発誤差に効かない

P6 で立てた仮説はこうだった。

> `--preserve_io_datatype` のため `present_*` は float32 で出て、次ステップに
> `past_*` として入るとき再量子化される。24層 × 2 で1ステップに48回。

**確かめる前に実装しなかったのが良かった。** QDQ モデルから該当の
`QuantizeLinear → DequantizeLinear` を外して測る（ホスト、48サンプル）。

| 除外した箇所 | 外した組数 | top-1 | 相対L2 | KL | fp32 の1位が何位か |
|---|---:|---:|---:|---:|---:|
| なし | 0 | 68.8% | 31.19% | 0.680 | 1908.8 |
| **キャッシュ I/O** | 96 | **66.7%** | 31.16% | 0.680 | 1908.8 |
| Concat + Slice | 288 | 68.8% | 31.07% | 0.679 | 1908.8 |
| Softmax | 24 | 70.8% | 31.31% | 0.681 | 1908.8 |
| RMSNorm 内部 | 147 | 64.6% | 31.18% | 0.679 | 1896.4 |
| MatMul 全部 | 217 | 68.8% | 31.74% | 0.706 | 2200.6 |

**どれを外しても動かない。** 相対L2 は 31% 前後で横ばい。

> **prefill とはまったく違う。** prefill では RMSNorm を外すと 6.2% → 74.4% と跳ねた。
> decode の誤差は**特定の op に集中しておらず、全体に薄く広がっている**。

較正を 6ステップ → 16ステップに伸ばしても変わらなかった
（top-1 68.75%、相対L2 30.72%。KL と順位がわずかに改善する程度）。

道具として `app/pipeline/oracle_qdq.py` を作った。
**QDQ モデルの Q/DQ を直接外す**ので再量子化が要らず、多入力モデルでも使える
（既存の `oracle_exclude.py` は量子化をやり直すうえ単一入力前提だった）。

## 3. ループを疑った — 機構は「再量子化」ではなく「クリップ」（**結論は 3-bis で覆る**）

### 3.1 往復そのものは無損失のはず

`dequantize → quantize` は **scale と zero point が同じなら量子化格子の上の恒等写像**
である。だから「float32 で往復するから誤差が乗る」という説明は間違っている。

問題は **ORT が `past_k_0` と `present_k_0` を別のテンソルとして較正する**ことで、
**表せる範囲が食い違う**点にある。

```
past_k_10  入口 [-10.13,  5.478]   出口 [-12.48,  5.990]   はみ出し 15.50%
past_v_5   入口 [-1.955,  1.906]   出口 [-1.955,  2.497]   はみ出し 13.29%
past_k_9   入口 [-8.550,  9.738]   出口 [-9.471, 10.861]   はみ出し 10.05%
```

**48本中42本ではみ出していた**（平均 1.68% / 最大 15.50%）。
はみ出した値は **clip** される。丸め（1段階ぶん）と違って**値そのものを失う**。

往復1回の試算（出口の範囲を一様に散らした10万点）:

| テンソル | 相対L2 | clip された割合 | 最大誤差 / 入口1段階 |
|---|---:|---:|---:|
| `past_k_10` | 7.83% | 15.54% | 9873 |
| `past_v_5` | 9.49% | 13.36% | 10041 |
| `past_k_9` | 3.24% | 10.02% | 4023 |

**単発の推論では往復しないので出ない。ループで初めて出る。**

### 3.2 直し方

入口と出口の **(scale, zero point) を、両方の範囲を含む共通の値に揃える**。
既存の初期化子は他と共有されうるので**上書きせず新しく作って付け替える**。

`app/pipeline/fix_cache_qparams.py`。適用後、**はみ出しは 42/48本 → 0本**。

### 3.3 ホストでループを回して測った（**この節の結論は 3-bis で覆った**）

同じプロンプトから24トークン生成し、fp32 と比べる（キャッシュで進める本物の decode ループ）。

```
fp32        : ' Paris. The capital city of the United States is Washington D. C.
               The capital city of the United Kingdom is London'
```

| | fp32 と一致 | 最初に分岐 | logits 相対L2（step12） | 最終キャッシュ k / v |
|---|---:|---:|---:|---:|
| QDQ そのまま | **9/24** | step 8 | 112.32% | 33.4% / 77.6% |
| **QDQ 統一版** | **19/24** | **step 19** | **22.60%** | **20.0% / 46.9%** |

```
そのまま : ' Paris. The capital city of the United Kingdom is London.
            The capital city of the United States is Washington D. C'   ← step8 で順序が入れ替わる
統一版   : ' Paris. The capital city of the United States is Washington D. C.
            The capital city of India is New Delhi.'                    ← step19 まで一致
```

> **ここで「効いた」と判断したが、それは早すぎた。**
> **1プロンプトしか見ていない。** 追試で覆る（次節）。

## 3-bis. ★追試で覆った — 統一の効果は確認できなかった

3.3 は**1プロンプトの結果**だった。プロンプトを3つに増やして測り直す。

### トークン一致数（fp32 のループ生成と比べる）

| プロンプト | ホスト統一前 | ホスト統一後 | 実機統一前 | 実機統一後 |
|---|---:|---:|---:|---:|
| 0 首都 | 9 | **19** | 11 | 11 |
| 1 惑星 | **18** | **10** | 0 | 0 |
| 2 沸点 | 1 | 1 | 6 | 8 |
| **合計（各72中）** | **28** | **30** | **17** | **19** |

**プロンプト0だけが大きく改善し、プロンプト1は逆に悪化している**（18 → 10）。
合計では +2/72 で、誤差の範囲である。

> **ループのトークン一致数は指標として暴れる。** 一度分岐すると以降は別の文になるので、
> 分岐点が1つ動くだけで一致数が大きく変わる。**1プロンプトで判断してはいけない。**

### 軌道を揃えて、対策が狙った量を直接測る

分岐するせいで比較にならないので、**fp32 と同じトークン列を強制**して回し、
キャッシュのずれと logits を見る（3プロンプトの平均、ホスト）。

| | キャッシュ k | キャッシュ v | logits 相対L2 |
|---|---:|---:|---:|
| 統一前 | 11.00% | 24.98% | 29.93% |
| **統一後** | **10.90%** | **25.10%** | **30.47%** |

**変わらない。** 3.3 で見えた「キャッシュのずれ 77.6% → 46.9%」は、
**2つの実行が別のトークン列を辿っていたことによる見かけの差**だった
（分岐した側のキャッシュが fp32 のキャッシュと違うのは当たり前である）。

### なぜ clip の試算が外れたのか

試算では **出口の範囲を一様に散らした10万点**を使い、clip 率 3〜15% と出した。
**実データで測ると 0.0094%** だった。

| テンソル | 入口の範囲 | 実データの範囲 | **実データの clip 率** |
|---|---|---|---:|
| `past_k_10` | [-10.13, 5.478] | [-10.32, 8.652] | **0.0109%** |
| `past_v_5` | [-1.955, 1.906] | [-2.045, 2.387] | **0.0109%** |
| `past_k_0` | [-130.4, 121.5] | [-130.4, 121.5] | **0.0013%** |

理由は分布である。

```
past_k_10   p50 0.0000   p99 2.58   p99.99 9.74   範囲の端 10.13
past_v_5    p50 0.0000   p99 0.73   p99.99 1.92   範囲の端 1.95
```

**値は0の近くに集中しており、はみ出しが起きる範囲の端はほとんど使われない。**
一様分布で試算したことで、端の重みを実際の**1000倍以上**に見積もっていた。

> **影響の試算に使う入力分布を、実データに合わせる。**
> これは較正で踏んだ誤り（乱数 ±1.0 で較正して誤差が 30.4% → 38.9% に悪化した件）と
> **同じ型**である。**自分の道具の中で二度同じ間違いをした。**

### 結論

| | |
|---|---|
| 範囲の食い違い自体 | **実在する**（48本中42本、最大15.5%） |
| 実データでの clip 率 | **0.0094%** — ほぼ起きていない |
| 統一の効果 | **確認できなかった**（ホスト・実機とも誤差の範囲） |
| では decode ループの発散は何が原因か | **未特定。** 量子化と QNN-HTP の誤差が全体に薄く乗っているため、と考えるのが現状の最良の説明 |

`fix_cache_qparams.py` は残してある（害は無く、範囲の食い違いは確かに消える）が、
**これを使う理由は今のところ無い。**

## 4. ★P6 の数字を訂正する — 評価セットが偏っていた

P6 では「decode 24層は実機 top-1 **33.3%** で精度が足りない」と書いた。
**これは24サンプルの評価セットの偏りによるもので、誤りだった。**

評価を48サンプルに増やすと:

| | 24サンプル | **48サンプル** |
|---|---:|---:|
| ホスト QDQ top-1 | 54.2% | **68.8%** |
| 実機 top-1 | **33.3%** | **60.4%** |
| 実機 相対L2 | 42.3% | **36.0%** |
| OrtRun | 29.9 ms | 28.5 ms |

### なぜそこまで動いたのか（内訳を出した）

ステップ番号ごとに top-1 一致率を見ると理由がはっきりする。

| ステップ | top-1 一致 |
|---|---:|
| **0（キャッシュが空）** | **0.0%** |
| 1〜3 | 75.0% |
| 4〜5 | 50.0% |
| 6〜7 | 75.0% |
| 8 | 100.0% |
| 9〜11 | 75〜100% |
| **前半6ステップ（＝24サンプル版）** | **54.2%** |
| **後半6ステップ** | **83.3%** |

**キャッシュが空の step 0 は4件すべて外している。** キャッシュが埋まるほど一致率が上がる。
24サンプル版は**空に近いキャッシュの区間だけを見ていた**。

実際の生成では prefill でキャッシュを埋めてから decode に入るので、
**step 0 の空キャッシュは通常起きない**。

### 訂正後の位置づけ

| | OrtRun | 実機 top-1 |
|---|---:|---:|
| prefill 窓16（24層） | 36.7 ms | 64.0% |
| prefill 窓64（24層） | 42.0 ms | 57.9% |
| **decode 24層（KV 64）** | **28.5 ms** | **60.4%** |

二乗和で分解すると、decode の **QNN-HTP 追加分は 18.0%**
（prefill 窓16 は 29.0%、窓64 は 46.5%）で**最も小さい**。
seq=1 で積和が短いことと整合する。

> **decode は「速いが精度が足りない」のではなく、「速くて精度は同等」だった。**
> P6 の結論は**評価セットが小さすぎたことによる誤り**である。

## 5. 踏んだ誤りの型

| | |
|---|---|
| **① 仮説を実装前に測った（良かった点）** | Oracle が「キャッシュ I/O は単発に効かない」と即座に示した。実装していたら空振りだった |
| **② しかし仮説は半分当たっていた** | 「単発に効かない」＝「効かない」ではない。**ループでしか出ない誤差がある** |
| **③ 機構の説明が間違っていた** | 「float32 で往復するから」ではなく「**範囲が食い違って clip される**から」。scale が同じなら往復は無損失 |
| **④ 評価セットが小さすぎた** | 24サンプルで 33.3%、48サンプルで 60.4%。**1サンプル = 4.2%** の分解能しかなかった |
| **⑤ 1プロンプトで「効いた」と判断した** | 9/24 → 19/24 は偶然。3プロンプトで 28→30（72中）。**ループの一致数は分岐点1つで大きく動く** |
| **⑥ 影響の試算に非現実的な分布を使った** | 一様分布で clip 率 3〜15% と見積もったが、**実データでは 0.0094%**。較正で踏んだ「乱数±1.0」と同じ型 |
| **⑦ 軌道が違うものを比べた** | 「キャッシュのずれが半減」は、分岐して別の文を書いていたから。**揃えて測ると差は無い** |

> **指標が動かないとき、「効かない」と「その測り方では見えない」を区別する。**
> 単発の top-1 と相対L2 では、ループでの崩れ方が**まったく見えなかった**。

> **ただし「見えなかった差」を探しに行った結果、今度は見えない差を見たと誤認した。**
> 少数サンプル・非現実的な分布・揃っていない軌道——**3つとも今回の中で踏んだ。**
