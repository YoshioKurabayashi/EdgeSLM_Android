# P9. 重みを per-channel にして実機へ（窓64 prefill）

- 日付: 2026-09-14
- 端末: Xperia 5 III SOG05 / SM8350 / HTP v68
- 対象: `qwen_pm64pc`（窓64・マスク入力あり・重み per-channel int8）
- 比較対象: `qwen_pm64`（同じ構成で重み per-tensor）— **消さずに端末へ残してある**

---

## 1. 何をしたか

[P8](P8_20260913_weight_quantization.md) でホスト評価まで終わっていた per-channel 版を、
context 生成 → 実機配備 → 精度測定 → UI へ組み込み、までやった。

**per-tensor 版のファイルは1つも触っていない。** 端末には両方が並んで載っており、
デモ画面のボタンで切り替えられる（4節）。

## 2. 生成物の検査（原則⑦: 設定ではなく生成物）

context 生成（約1時間）に入る**前に**確認した。

```
重みの DQ     390 本（うち 1024要素以上 169 本）
per-channel  168 本 / per-tensor 1 本（1024要素以上のみ）
型の内訳      {'uint16': 222, 'int8': 168}
axis の内訳   {'None': 1, '1': 168}
```

per-tensor 1本は `step.lm_head.weight`（`tie_word_embeddings` のため `Gather` と共有。
per-channel にすると実行時に落ちる。誤差には効かない）。

## 3. 実機の結果

### 3.1 セッション

| | |
|---|---|
| backend | `QNN HTP - EPContext - all nodes` |
| `strict_no_cpu_fallback` | **true**（全ノード NPU） |
| context binary | 772,568,016 bytes |
| md5 3点照合 | 生成器 / 配布側 / 端末 すべて `04bbb528…` 一致 |

### 3.2 精度（19サンプル・最終位置・fp32 との比較）

| | 相対L2 平均 | cos 平均 | **top-1 一致** | OrtRun 平均 |
|---|---:|---:|---:|---:|
| per-tensor（従来） | 50.14% | 0.8614 | **57.9%** | 41.95 ms |
| **per-channel** | **37.09%** | **0.9148** | **68.4%** | **42.23 ms** |

**速度は変わらない**（+0.7%、測定ゆらぎの範囲）。
per-channel int8 は v68 で**ただで効く**。

### 3.3 ★ホストとの差は消えていない

| | ホスト(ORT CPU) | 実機(QNN HTP) | 差（直交分解） |
|---|---:|---:|---:|
| per-tensor | 18.57% | 50.14% | **46.6%** |
| per-channel | 9.99% | 37.09% | **35.7%** |

HTP 追加分は $\sqrt{50.14^2-18.57^2}=46.6\%$、per-channel では $\sqrt{37.09^2-9.99^2}=35.7\%$。

> **HTP 追加分は固定の下駄ではない。** 重みを細かくすると**追加分そのものも小さくなった**
> （46.6% → 35.7%）。HTP 側の誤差の一部は「粗い重みをどう扱うか」に由来している疑いがある。
> 「QNN-HTP 追加分の原因特定」は引き続き残件だが、**重みと独立ではない**ことが分かった。

# P9-2. decode（KVキャッシュ）側の per-channel — 実機では効きが小さい

- 日付: 2026-09-14
- 対象: `qwen_dec24pc`（24層 decode / seq=1 / KV長64 / 重み per-channel int8）
- context 生成 62分（S5 のみで約60分）

## 7. ホストの予想は大きかったが、実機はほとんど動かなかった

**同じ評価セット（`eval_dec24_big.npz` / 48件 / 全位置）で揃えて測った。**

| decode 24層 | 相対L2 | cos | top-1 | KL | fp32 1位の順位 |
|---|---:|---:|---:|---:|---:|
| **ホスト** per-tensor | 31.19% | — | 68.8% | 0.680 | 1908.75 |
| **ホスト** per-channel | **14.06%** | — | **83.3%** | **0.073** | **1.40** |
| **実機** per-tensor | 35.98% | 0.9228 | 60.4% | — | — |
| **実機** per-channel | **34.95%** | **0.9342** | **62.5%** | — | — |

**ホストは 31.19% → 14.06%（半分以下）。実機は 35.98% → 34.95%（ほぼ動かない）。**

top-1 の 60.4% → 62.5% は **48件中 1件**の差である。
[StudyMemo 8.1](../DoC/StudyMemo/08_比較を成立させる.md) の作法どおり
**1サンプル = 2.1%** なので、**この差だけでは改善したと言えない**。
per-tensor 側は日をまたいで測り直しても 35.9824% / 60.4% と**完全に一致**した（決定的な計算である）。

## 8. ★HTP 追加分が食べてしまった

```
fp32 ──[ 量子化誤差 ]──> ホストQDQ ──[ QNN-HTP 追加分 ]──> 実機
```

| | ホスト | 実機 | **HTP 追加分**（二乗差で分解） |
|---|---:|---:|---:|
| **prefill 窓64** per-tensor | 18.57% | 50.14% | 46.6% |
| **prefill 窓64** per-channel | 9.99% | 37.09% | **35.7%**（縮んだ） |
| **decode 24層** per-tensor | 31.19% | 35.98% | 17.9% |
| **decode 24層** per-channel | 14.06% | 34.95% | **32.0%**（増えた） |

**prefill と decode で逆になった。**

- prefill: 重みを細かくすると HTP 追加分も縮んだ（46.6% → 35.7%）
- decode: 量子化誤差は半分以下になったのに、**実機の誤差は 35% に貼り付いたまま**

decode の実機誤差は**重みの粒度をいくら上げても 35% から動かない**。
これは「decode の実機誤差を支配しているのは重みではない別の何か」を意味する。

> **最有力の容疑者は KVキャッシュの float 入出力である。**
> decode は `past_k_0..23` / `past_v_0..23` の **48本が float32 のグラフ I/O** で、
> 毎ステップ HTP の境界で量子化と逆量子化を往復する。prefill にはこれが無い。
> ホストの ORT CPU では float のまま扱われるので**ホストでは絶対に再現しない**。
>
> ただし[P7](P7_20260913_decode_cache_io.md) で「入口と出口のレンジ不一致による clip」は
> **実データの clip 率 0.0094% で否定済み**である。clip ではなく
> **往復そのものの丸め**（1段階ぶんの量子化誤差が毎ステップ全チャンネルに乗る）を疑う。
> **未検証。** 次に調べるならここ。

# P9-3. 実機 decode の誤差はどこで出来るのか

2026-09-14。P9-2 で「KVキャッシュの float I/O が最有力」と書いたが、**取り下げる**。
測ったら犯人は別だった。

## 11. 仮説を1つずつ潰した

| # | 仮説 | 検証 | 結果 |
|---|---|---|---|
| ① | KVキャッシュ I/O の往復丸め | 実データで1往復の誤差を計算 | **桁が足りない**（中央 0.78% / 最大 3.58%。実機は 34.95%） |
| ② | `lm_head` を HTP が誤る | logits 誤差を W の行空間へ射影 | **違う**（lm_head 由来は ホスト 3.24% / 実機 3.06% で**ほぼ同じ**） |
| ③ | QNN lowering か HTP kernel か | 同じ DLC を QNN CPU backend で実行 | **実行不可**（CPU backend は `Gather` も `RmsNorm` も未対応） |
| ④ | **層の中で HTP が誤差を作る** | **同じ入力**を単層モデルに与えてホストと実機を比較 | **★これ**（ホスト 5.55% に対し **実機 16.38%**） |

### ①の測り方

グラフ I/O は **100箇所すべて uint16**（1段階 中央値 2.2e-4）。実データで
`量子化 → 逆量子化` を1回通すと 48本の相対L2 は **中央 0.78% / 最大 3.58%**、
clip 率 中央 0.0048%（P7 の 0.0094% と整合）。

> ただし「48本を直交とみなして √48×0.78%≈5.4% だから否定」は**参考値にとどめる**。
> 48本の誤差が独立とは限らず、softmax が小さな K の差を増幅しうる。
> **「桁が合わないので優先度を大きく下げる」が正確**で、数学的に否定はしていない。

### ②の測り方（追加のビルドが要らない）

`logits = hidden(896) @ W(896, 151936)` なので、**達成可能な logits は 896次元の部分空間**
（W の行空間）にしかない。誤差 e をそこへ射影すると

- `e_∥` … ある hidden のずれで説明できる分 → **誤差は lm_head より前で出来た**
- `e_⊥` … どんな hidden でも説明できない分 → **lm_head 自身が作った**

| | 相対L2 | hidden で説明できる | lm_head が作った |
|---|---:|---:|---:|
| ホスト QDQ | 14.06% | 13.69% | **3.24%** |
| 実機 HTP | 34.85% | **34.72%** | **3.06%** |

**lm_head 由来はホストと実機でほぼ同じ。** 実機の増分（14%→35%）は
**lm_head に入る前の hidden が既にずれている**ことで説明し切れる。
`lm_head` と最終段は白。

> **ここは「prefill と decode 共通の 35% の床があるなら最終段が怪しい」という筋を潰している。**
> 床があるとしても、その原因は最終段ではない。

## 12. ★単層に同じ入力を与えると、HTP だけが誤差を作る

伝播と混ざらないように、**デコーダ層1枚に同じ fp32 入力を与えて**比べた。

| デコーダ層1枚（11サンプル・同一入力） | 相対L2 |
|---|---:|
| ホスト QDQ（＝量子化だけの誤差） | **5.55%** |
| **実機 HTP** | **16.38%**（cos 0.9887） |

二乗差で分ける（この段では入力が同じなので伝播の混入が無い）:

```
HTP が1層で作る誤差 ≈ √(16.38² − 5.55²) = 15.4%
```

**量子化誤差の約3倍を、HTP が層の中で作っている。**

### 24層での見え方と整合するか

| | 層0 | 層23 |
|---|---:|---:|
| ホスト（新スロットのみ） | 0.34% | 8.26% |
| 実機（新スロットのみ） | **0.34%** | **22.63%** |

層0は**完全に一致**する。層0は massive activation で `|K|` が桁違いに大きく、
相対誤差が薄まる層である（[StudyMemo 8.4](../DoC/StudyMemo/08_比較を成立させる.md)）。
深い層ほど開き、層23で 2.7倍。単層の 2.9倍（16.38/5.55）と同じ水準になる。

> ★**`present_k` の全64スロットで測ると過小評価になる。**
> `present_k = cat(past, k)[:,:,1:,:]` なので **64スロットのうち63は past の写し**であり、
> past は入口で1往復するだけ（0.78%）。**新しい1スロットだけで測ると約2.2倍**になる。
> 平均 2.53%→5.61%（ホスト）、5.22%→**12.54%**（実機）。
> P9-2 に載せた層別の表はこの希釈を受けている。

## 13. 現在の整理

```
fp32
 ├─ 量子化誤差（重み per-tensor → per-channel で大きく改善。ホストで確認済み）
 └─ HTP 固有誤差 ≈ 1層あたり 15% 級  ← ★本丸。ここが未解明
      ・I/O 境界ではない（①）
      ・lm_head / 最終段ではない（②）
      ・層の中の演算で作られている（④）
```

decode 固有ではない可能性が高い。**prefill も同じ層を通る。**

> 「実機 logits が 35〜37% に張り付く」ように見えるのは、prefill 19件・最終位置と
> decode 48件・全位置で**評価セットが違う**ので、まだ確定できない。

# P9-4. 犯人は RMSNorm だった（HTP の融合 op）

2026-09-14。**指標を「fp32 との差」から「ホスト QDQ と実機の直接比較」に変えた**うえで、
本物の層を二分探索した結果。

## 16. まず指標を直した

二乗差（quadrature）は直交を仮定するので、**同じ量子化グラフをホストと実機で走らせて
直接引く**方に変えた。24層 decode（per-channel・48件）:

| | fp32↔ホスト | fp32↔実機 | **★ホスト↔実機** |
|---|---:|---:|---:|
| logits | 14.06% | 34.85% | **35.28%** |
| present_k（新スロットのみ） | 5.21% | 11.73% | **11.81%** |
| present_v（新スロットのみ） | 13.17% | 28.29% | **28.50%** |

**ホスト↔実機が fp32↔実機とほぼ同じ大きさ**＝実機の出力は量子化誤差とほとんど無関係に
ずれている。**量子化（14%）より HTP の差（35%）の方が大きい。**

### ★先に1つ撤回

P9-3 で「単層で HTP が 15.4% 作る」と書いたが、**その比較は成立していなかった**。
実機に入っていた `qwen_layer1_swap_epctx.onnx` は `qwen_swap` という別タグで作られており、
私が比べたホスト QDQ（`a16w8_swap`）と**同じグラフである保証が無い**。
実際 `a16w8_swap` は v68 の S6 を通らない（`expected >= 73`）ので**別物**である。
→ 以下は**すべて自分で両方作り直した**ものを使う（scheme は24層と同じ `a16w8_rms_swap`）。

## 17. 本物の層を二分探索した

既存の21個の単体 op モデルは**合成形状（hidden 128 / 4ヘッド）で較正データも無い**ので使えない。
range に起因する問題はランダム入力では出ない。**本物の層を切って本物の activation で較正した**
（`app/pipeline/split_layer.py`）。

デコーダ層1枚・同一入力・11サンプル:

| 部分 | ノード | fp32↔ホスト | fp32↔実機 | **★ホスト↔実機** |
|---|---:|---:|---:|---:|
| FFN 側 全体（norm+MLP+残差） | 14 | 4.10% | 14.76% | **14.37%** |
| └ **RMSNorm だけ** | 7 | **0.18%** | **13.51%** | **★13.53%** |
| └ MLP だけ（MatMul×3 + SiLU） | 6 | 4.08% | 4.09% | **0.21%** |

**MatMul は実機でもほぼ完全に一致する（0.21%）。RMSNorm だけが 13.5% ずれている。**

- 量子化しても RMSNorm はホストでは **0.18%** しか誤差を出さない
- 同じグラフを HTP で走らせると **13.5%** ずれる
- 大きい行列積3本（gate/up/down、896×4864）は **0.21%** ＝ HTP は正確

> **重みの粒度を細かくしても実機が良くならなかった理由がこれである。**
> 実機側のボトルネックは**最初から MatMul ではなかった**。

## 18. なぜそうなるか — converter が C-11 を畳んでしまう

ホスト側の QDQ は、[C-11](../DoC/StudyMemo/03_Transformerの中で何が起きたか.md) の
最大値正規化を入れた **13ノード**である。

```
Abs, ReduceMax, Reciprocal, Mul, Pow, ReduceMean, Add, Sqrt, Reciprocal, Mul, Mul（+ Q/DQ 30本）
```

`qairt-converter` が作った DLC を見ると:

```
RMSNormalization  … 1 個
```

**13ノードの書き換えが、まるごと1個の融合 op に畳まれている。**
HTP は自前の `RMSNormalization` カーネルで計算しており、
**こちらが書いた計算手順は実行されていない。**

C-11 の効果（ホスト top-1 4.5% → 80.7%）が実機に効いたのは
**Q/DQ の量子化レンジが DLC に伝わったから**であって、
**演算手順が伝わったからではなかった。**

> QNN CPU backend が `RmsNorm` を未対応で落ちたのも同じ理由である
> （converter が融合 op を出すので、その op を持たない backend では動かない）。

## 19. 整理し直した構図

```
fp32
 ├─ 量子化誤差         … 重み per-channel で大きく改善（ホストで確認済み）
 └─ HTP との差 ≈ 35%
      ├─ MatMul          0.21%  … ほぼ無害
      └─ ★RMSNorm      13.5%/個 … 1層に2個 × 24層
```

decode 固有でも KVキャッシュ固有でもない。**prefill も同じ RMSNorm を通る。**
深い層ほどホストとの差が開くのも、毎層2個ずつ積み上がるからで説明がつく。

# P9-5. ★真因: 融合 RmsNorm の gamma が符号付き16bitで頭打ちになっていた

2026-09-14。**実機 decode の誤差 35% の主因を特定し、単体で直した。**

## 22. まず前回の「証拠」を撤回する

P9-4 で「converter が RMSNorm を融合している」と書き、根拠に convert.log の
`RMSNormalization` を挙げた。**あれは証拠になっていなかった。**

```
3行目: WARNING - Unable to register converter supported Operation
       [RMSNormalization:Version 23] with your Onnx installation.
```

**起動時に「この op は登録できなかった」と言っているだけ**の行を数えていた。
モデルの中身とは無関係である。

正しい確かめ方は **`qairt-dlc-info` で DLC を開く**こと。開いたら実際に融合されていた。

```
| 6 | rms_norm_node_ | RmsNorm | node_pow_2_xs_..., layer.post_attention_layernorm.weight_..., ..._bias |
```

**結論は合っていたが、根拠が間違っていた。** [原則⑦](../DoC/StudyMemo/06_ログの読み方と原則.md)
（設定値ではなく生成物）を、ログにも適用しそこねた例である。

## 23. 融合 op だけを切り出して測る

C-11 の前処理部（融合されない5 op）と、融合される本体を分けた。

| | DLC の中身 | fp32↔ホスト | fp32↔実機 | **★ホスト↔実機** |
|---|---|---:|---:|---:|
| C-11 前処理（Abs/ReduceMax/Add/Reciprocal/Mul） | 通常 op のまま | 0.0358% | **0.05%** | **0.03%** |
| **RmsNorm 本体** | **`Convert, RmsNorm` の2つだけ** | 0.0274% | **13.54%** | **13.54%** |

**融合 op 単体で 13.54%。** 前処理側は無罪（0.03%）。
量子化そのものは 0.0274% しか誤差を出していない。

## 24. 誤差の正体 — 33列がちょうど頭打ちになっていた

誤差を**列（チャンネル）ごとの倍率**で補正してみたら、**13.54% → 0.03%** になった。
つまり実機の出力は「**一部の列が定数倍されているだけ**」だった。

| ch | gamma | 倍率 | **倍率 × gamma** |
|---:|---:|---:|---:|
| 783 | 1.9922 | 0.5000 | **0.9962** |
| 674 | 1.8125 | 0.5496 | **0.9961** |
| 75 | 1.6953 | 0.5875 | **0.9961** |
| 241 | 1.3906 | 0.7164 | **0.9962** |
| 56 | 1.2422 | 0.8019 | **0.9961** |

**`倍率 × gamma = 0.9961` が全列で一定。** つまり

```
0.9961 = 32767 × 3.03988e-05 = （符号付き int16 の上限）×（gamma の scale）
```

**gamma が 0.9961 で頭打ちになっている。** 896列中 **33列**が該当した。

### なぜそうなるか

ONNX 側の QDQ では gamma は **uint16**（zero_point=0、量子化値 16062〜65535、
scale 3.03988e-05 で [0, 1.9922] を表現）。
ところが DLC では融合 `RmsNorm` の重みとして **`sFxp_16`（符号付き）** で渡されている。

```
layer.post_attention_layernorm.weight_DequantizeLinear_Output
  (data type: sFxp_16; ...)
  encoding : bitwidth 16, min 0.0, max 1.9921875, scale 0.000030398833, offset 0
```

**型は符号付き、エンコーディングは符号なし前提。**
量子化値が 32767 を超える列（gamma > 0.9961）は**黙って切り捨てられる**。
エラーも警告も出ない。

## 25. 直した（3行）

gamma を**符号付き対称**で入れ直す。`|gamma|max / 32767` を新しい scale にすれば
符号付きとして読まれても値が変わらない。

```
32767 を超えていた列 33 本 / q最大 65535
新しい scale 6.07985931e-05   再量子化の誤差 0.0020%
```

`app/pipeline/fix_norm_gamma.py`。**同じ context 生成パイプラインを通しただけ**で:

| RmsNorm 本体（実機） | 相対L2 | cos |
|---|---:|---:|
| 直す前 | **13.17%** | 0.9908 |
| **直したあと** | **0.0342%** | **1.000000** |

**385倍。** 量子化誤差（0.0274%）と同じ水準まで落ちた。

## 26. これが意味すること

```
実機 decode の誤差 35%
  └─ 各層の RMSNorm ×2 × 24層 = 48個が、それぞれ 13.5% ずれていた
```

- **decode 固有でも KVキャッシュ固有でもない。** prefill も同じ RMSNorm を通る
- **重みを per-channel にしても実機が良くならなかった理由がこれ。**
  実機側のボトルネックは MatMul ではなかった（MatMul のホスト↔実機は **0.21%**）
- **C-11（RMSNorm の最大値正規化）は正しかったが、その先で別の問題に当たっていた**

### 新しい制約 C-13

> **v68 / QAIRT 2.48: 融合 `RmsNorm` の gamma は符号付き16bitとして読まれる。**
> ONNX 側で uint16 量子化していると、**量子化値が 32767 を超える要素が黙って頭打ちになる**。
> gamma は `|max|/32767` を scale とする**符号付き対称**で量子化すること。
> 生成物の確認は `qairt-dlc-info` で `data type: sFxp_16` と encoding の max を突き合わせる。

### ケースA（各層で少しずつ積み重なる）は否定された

### ケースB（特定の層で急増）が部分的に当たっていた

「層0と層8は特別に正確」と読み違えていた。

**最終盤で massive activation が消える。** 分布の regime が変わる場所と、
